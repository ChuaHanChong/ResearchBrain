# Model Context Protocol (MCP): Landscape, Security Threats, and Future Research Directions

> [!summary] Summary
> This survey studies the Model Context Protocol, an open standard for discovering and invoking external tools from AI applications. It splits an MCP server's lifecycle into four phases and 16 activities. It builds a threat taxonomy of four attacker types and 16 scenarios, checked with proof-of-concept servers. It also maps the ecosystem, proposes safeguards, and outlines future research.

## Problem

- Tool integration for LLMs is fragmented: developers hand-write interfaces, authentication and execution logic per service, and function-calling mechanisms differ across platforms, forcing redundant implementations.
- Existing agent frameworks choose tools autonomously but only over predefined or hardcoded integrations, which limits interoperability and long-term maintainability across models and applications.
- MCP is adopted quickly, yet academic analysis of its architecture, lifecycle, security and privacy risks, tool discoverability and remote deployment is missing, so no systematic threat model or safeguards exist.

## Method

- ==Lifecycle model== of an MCP server: four phases (creation, deployment, operation, maintenance) decomposed into 16 key activities, alongside a description of the ==host, client and server architecture== and workflow.
- ==Threat taxonomy== covering four attacker types (malicious developers, external attackers, malicious users, security flaws) and 16 threat scenarios, such as ==tool poisoning==, ==installer spoofing==, ==name collision== and ==rug pulls==.
- ==Proof-of-concept MCP servers==, built with the official SDK for each identified risk, validate the attack surfaces. Lifecycle-phase safeguards, an ecosystem landscape survey and a future research agenda complete the study.

## Results

- The threat taxonomy yields **16** concrete scenarios across the **four** attacker types. Each is backed by a proof-of-concept server built for that risk, including tool poisoning through hidden payloads in capability declarations.
- A name-collision demonstration with **two** look-alike servers shows the host picks servers only by name and description, with no provenance check. This exposes a real impersonation and supply-chain gap.
- The landscape survey finds many community server collections, registries and hosting platforms, plus unofficial auto-installers (e.g. mcp-installer, about **1.4k** stars) that add attack surface. Lifecycle-specific safeguards are proposed for each threat.

## Takeaways

> [!tip] Key Insights
> - A universal tool protocol moves trust from per-app hardcoded integrations to an open marketplace. Security therefore has to cover the whole server lifecycle, not just runtime calls.
> - Selecting tools by name and description alone is unsafe. Namespacing, verified publisher provenance and signed installers are needed to stop impersonation, shadowing and supply-chain attacks.
> - Convenience layers such as auto-installers, registries and hosted servers are the weak points. Any agent-tool ecosystem should treat them as security-critical, with integrity checks, version pinning and least-privilege permissions.

## Detailed Report

### 1. How This Work Fits into the Broader Research Landscape

This research is situated at the crucial intersection of Artificial Intelligence (AI) and cybersecurity, specifically addressing the emerging paradigm of tool-augmented Large Language Models (LLMs). The broader research landscape has seen a rapid evolution in how AI models, particularly LLMs, interact with external tools and resources.

Historically, AI applications integrated with external services through fragmented methods such as manual API wiring, platform-specific plugin interfaces (like OpenAI ChatGPT Plugins), or bespoke AI agent frameworks (e.g., LangChain). While these approaches expanded LLM capabilities—enabling real-time data retrieval, computation, and interaction with external systems—they suffered from interoperability challenges, redundant implementations, and significant maintenance burdens. Techniques like Retrieval-Augmented Generation (RAG) enhanced knowledge access but were limited to passive information retrieval, lacking active operational capabilities.

The Model Context Protocol (MCP), launched by Anthropic in late 2024, emerged to address this fragmentation. Inspired by the Language Server Protocol (LSP), MCP introduces a universal, open standard for unified, bi-directional communication and dynamic discovery between AI models and external tools. Its innovations include decoupling tool implementation from usage, supporting dynamic discovery and schema negotiation, enabling bi-directional communication, and integrating access control as a first-class feature. This positions MCP as a foundational architecture poised to transform AI-native applications into an interoperable ecosystem of composable, discoverable network services.

Despite MCP's rapid industry adoption by major players like Anthropic, OpenAI, Google DeepMind, and numerous developer tools and cloud platforms, the authors identify a significant gap in academic research. While existing literature extensively covers LLM-tool integration (e.g., frameworks like AutoTools, EasyTool, and benchmarks like ToolSandbox, UltraTool) and general security risks in LLM-tool interactions (e.g., prompt injection, tool misuse, unsafe execution), there has been a lack of comprehensive, systematic analysis specifically on the MCP ecosystem. Earlier work on MCP security, though growing, tends to focus on isolated vulnerabilities or runtime protections without providing a holistic, lifecycle-wide security model.

This paper directly fills this critical academic void. It provides the **first comprehensive, end-to-end security and privacy analysis of the MCP ecosystem**, systematically mapping its architecture, lifecycle, and current landscape. By analyzing threats across the entire server lifecycle (creation, deployment, operation, and maintenance), the authors distinguish their work from prior studies that often address specific attack vectors or detection methods in isolation. This lifecycle-centric perspective allows for the derivation of more practical mitigation strategies and secure-by-design guidelines, which are crucial for the sustainable and secure evolution of MCP within the broader landscape of tool-augmented AI systems.

### 2. Key Objectives and Motivation

The primary motivation for this research stems from the rapid, yet largely unexamined, emergence and adoption of the Model Context Protocol (MCP) in the AI community. The authors observe that while MCP promises to revolutionize AI-to-tool interactions by standardizing interoperability and addressing the limitations of prior fragmented approaches, its ecosystem is still nascent and lacks comprehensive academic scrutiny, particularly concerning security, tool discoverability, and remote deployment. This gap presents significant untapped opportunities for research and improvement.

Based on this motivation, the paper articulates several key objectives:

- **Provide the first comprehensive analysis of the MCP ecosystem:** This includes detailing its core architecture, components, and communication workflows.
- **Define the full lifecycle of an MCP server:** Systematically map out the stages of an MCP server from its creation to deployment, operation, and maintenance, identifying 16 distinct key activities within these four phases.
- **Construct a systematic threat taxonomy for MCP:** Identify and categorize security and privacy risks from multiple attacker perspectives, specifically focusing on four archetypes (malicious developers, external attackers, malicious users, and general security flaws) and outlining 16 representative threat scenarios.
- **Validate identified security risks through real-world case studies and Proof-of-Concepts (PoCs):** Empirically demonstrate attack surfaces and vulnerability manifestations within MCP implementations.
- **Analyze the current MCP landscape:** Examine industry adoption trends, diverse integration patterns, and supporting tools to highlight both technological strengths and existing limitations impacting broader deployment.
- **Propose actionable security safeguards:** Offer fine-grained recommendations tailored to each lifecycle phase and threat category to guide secure MCP adoption.
- **Outline future research and development directions:** Identify critical challenges and pathways for strengthening MCP's standardization, trust boundaries, and sustainable growth within the evolving AI ecosystem.

In essence, the paper aims to provide a foundational academic understanding of MCP, particularly its security implications, and offer a forward-looking vision to ensure its robust and secure development.

### 3. Methodology and Approach

The authors employ a systematic and multi-faceted methodology to achieve their objectives, combining architectural analysis, threat modeling, empirical validation, and landscape assessment.

1. **Architectural and Workflow Analysis:** The study begins by deconstructing the fundamental architecture of MCP, identifying its core components: MCP host, MCP client, and MCP server. It details their roles, interaction patterns, and the underlying transport layer for communication. This foundational understanding sets the stage for analyzing the operational flow.

2. **Lifecycle Definition:** A key methodological contribution is the formal definition of the MCP server's full lifecycle. This lifecycle, derived from official protocol documentation and systematic analysis of operational workflows, is divided into four sequential phases:
 - **Creation:** Focused on the developer's role (metadata definition, capability declaration, code implementation, slash command definition).
 - **Deployment:** Covers release, installer deployment, environment setup, and tool registration.
 - **Operation:** Involves runtime interactions (intent analysis, external resource access, tool invocation, session management).
 - **Maintenance:** Addresses long-term aspects (version control, configuration changes, access and log audits).
 This granular breakdown into 16 key activities provides a structured framework for identifying vulnerabilities at specific points.

3. **Threat Taxonomy Construction:** Building upon the defined lifecycle, the authors construct a comprehensive threat taxonomy. They categorize security and privacy risks based on four major attacker types:
 - Malicious Developers
 - External Attackers
 - Malicious Users
 - General Security Flaws
 This categorization maps threats to their origins across various lifecycle phases, leading to the identification of 16 distinct threat scenarios. The emphasis on "origins" rather than rigid phase assignment allows for more effective reasoning about mitigation strategies from the source of the vulnerability.

4. **Empirical Validation and Case Studies (Proof-of-Concepts - PoCs):** To validate the identified risks, the researchers developed and analyzed real-world case studies. They constructed specific Proof-of-Concept (PoC) MCP servers for each identified risk type within an isolated environment. A custom MCP host, based on the official MCP SDK, was used to establish controlled connections and demonstrate how these vulnerabilities could be exploited (e.g., namespace typosquatting, tool poisoning, command injection). This empirical validation provides concrete evidence of attack surfaces and vulnerability manifestations.

5. **Landscape Analysis:** The current MCP ecosystem landscape was analyzed through:
 - **Manual inspection:** Reviewing official documentation from early MCP supporters.
 - **Community discussions and repository mining:** Identifying diverse industry adoption, integration patterns, and supporting tools.
 - **Data compilation:** Creating tables summarizing key adopters (companies, products, use cases) and community-driven MCP server collections. This included random sampling and cross-verification of server counts on platforms like MCP.so to assess reliability and quality.

6. **Mitigation Strategy Development:** Based on the lifecycle analysis and validated threats, the paper proposes a set of fine-grained, actionable security safeguards. These recommendations are tailored to specific lifecycle phases and threat categories, offering practical guidance for secure MCP adoption and future development.

7. **Future Research Directions:** Finally, the methodology includes outlining future research and development priorities, aiming to strengthen MCP's standardization, trust boundaries, and sustainable growth.

All collected data and implementation examples related to their PoCs are made publicly available on GitHub, underscoring a commitment to transparency and reproducibility.

### 4. Main Findings and Results

The study yielded several significant findings across the MCP ecosystem landscape, security threat analysis, and proposed mitigations.

#### 4.1. MCP Ecosystem Landscape

- **Rapid but Uneven Industry Adoption:** MCP has seen rapid adoption across diverse sectors. Leading AI companies like Anthropic, OpenAI, and Google DeepMind have integrated MCP for agent capabilities. Developer tools (Replit, Microsoft Copilot Studio, Cursor), IDEs (Zed, JetBrains), cloud platforms (Cloudflare, Tencent Cloud), and even financial service providers (Block, Stripe) are leveraging MCP. However, the ecosystem's maturity is uneven, with resistance from "walled garden" platforms that may only expose low-risk or secondary functions.
- **Thriving Community-Driven Servers:** Despite the absence of an official Anthropic marketplace, numerous independent MCP server collections (e.g., MCP.so, Glama, PulseMCP) have emerged, hosting thousands of servers. While this accelerates adoption, there's significant variability in quality, reliability, and security verification, with many listings being experimental or unmaintained, highlighting a trade-off between openness and quality control.
- **Growing SDKs and Tools:** The ecosystem is supported by official SDKs in multiple languages (TypeScript, Python, Java, Kotlin, C#) and a robust set of community-contributed frameworks and utilities (e.g., EasyMCP, FastMCP, Foxy Contexts) that simplify server development and deployment.
- **Diverse Use Cases:** MCP enhances AI-driven workflows across various domains:
 - **OpenAI:** Improves agent SDKs by enabling standardized, efficient tool integration and expanding ChatGPT's capabilities beyond Q&A to active operations.
 - **Cursor:** Enhances AI-assisted software development by allowing direct access to external APIs and code repositories, streamlining complex tasks within the IDE.
 - **Cloudflare:** Transforms MCP into a scalable, cloud-based solution, offering remote server hosting, managed authentication (OAuth 2.0), persistent state, and multi-tenant infrastructure, lowering deployment barriers.

#### 4.2. Security and Privacy Analysis (Threat Taxonomy and Validation)

The core finding is a comprehensive taxonomy of 16 security and privacy risks categorized under four attacker types, empirically validated through PoC demonstrations:

- **Malicious Developer Threats:** These threats are introduced during the creation phase.
 - **Namespace Typosquatting:** Malicious servers mimic legitimate ones (e.g., `mcp-github` impersonating `github-mcp`), leading to the installation of compromised tools and data exfiltration (Figure 5).
 - **Tool Name Conflict:** Identical or similar tool names cause ambiguity, allowing malicious tools (e.g., a rogue `send_email`) to be invoked instead of legitimate ones.
 - **Preference Manipulation Attack (PMA):** Deceptive phrases in tool descriptions (e.g., "⭐The BEST and MOST RELIABLE addition tool!⭐") bias AI agent selection towards malicious tools, leading to toolflow hijacking (Figure 6).
 - **Tool Poisoning:** Covert malicious logic embedded in tool documentation (e.g., hidden instructions to read SSH keys and exfiltrate data) is followed by the LLM, leading to silent data leakage or system compromise (Figure 7).
 - **Rug Pulls:** Initially benign servers are later surreptitiously updated with malicious code or have functionality withdrawn, compromising established trust (Figure 8).
 - **Cross-Server Shadowing:** A malicious server mimics tools from a legitimate one, intercepting or modifying sensitive information (e.g., redirecting emails) transparently to the user (Figure 9).
 - **Command Injection/Backdoor:** Malicious logic embedded in server code or dependencies allows crafted prompts/parameters to trigger hidden OS commands, enabling data exfiltration or remote code execution (Figure 10).

- **External Attacker Threats:** These target the deployment and operation phases.
 - **Installer Spoofing:** Unofficial auto-installers (e.g., Smithery-CLI, mcp-get) can distribute compromised MCP server packages, leading to malware installation or backdoors.
 - **Indirect Prompt Injection:** Malicious instructions are hidden in external data sources (e.g., GitHub issues) that MCP tools retrieve, causing the model to perform unintended actions like leaking private data (Figure 11).

- **Malicious User Threats:** These arise during the operation phase.
 - **Credential Theft:** Sensitive API keys or credentials are often stored in plaintext in local configuration files (e.g., `~/.cursor/mcp.json`), making them easy targets for exfiltration (Figure 12).
 - **Sandbox Escape:** Poorly configured servers in highly privileged host environments can escape their intended boundaries, leading to indirect influence on agent reasoning or triggering privileged actions.
 - **Tool Chaining Abuse:** Multiple low-risk tools are implicitly combined by the model (e.g., `list_files` + `read_file` + `execute_query` + `write_file`) to perform high-impact operations like data exfiltration, often bypassing traditional access controls (Figure 13).
 - **Unauthorized Access:** Weaknesses in authentication (e.g., exposed `session_id` in SSE transport) or insecure endpoints allow attackers to reuse valid sessions or issue arbitrary commands without re-authentication (Figure 14).

- **Security Flaws:** These are systemic issues impacting maintenance.
 - **Re-deployment of Vulnerable Versions:** Decentralized maintenance and reliance on unofficial auto-installers lead to users inadvertently deploying outdated or unpatched MCP servers.
 - **Post-Update Privilege Persistence:** Outdated or revoked credentials remain valid after server updates due to synchronization issues, allowing attackers to retain elevated privileges.
 - **Configuration Drift:** Unintended changes in system configuration cause deviations from the security baseline, leading to misconfigurations that expose sensitive services, especially in multi-tenant cloud deployments.

#### 4.3. Proposed Safeguards and Recommendations

The paper proposes a lifecycle-based set of recommendations:
- **Creation Phase:** Automate metadata generation and verification, validate capability declarations, separate implementation modules, and enforce input checking.
- **Deployment Phase:** Produce verified and reproducible build packages, and deploy servers within application sandboxes.
- **Operation Phase:** Monitor intent analysis and command execution, maintain sandbox enforcement for dynamic operations, and implement consistent session management with adaptive logging.
- **Maintenance Phase:** Apply structured version control and automated updates, manage configuration changes through validation and review, and conduct continuous auditing and anomaly detection.

### 5. Significance and Potential Impact

This paper makes a highly significant contribution to the evolving landscape of AI-driven systems, particularly in its pioneering and comprehensive analysis of the Model Context Protocol (MCP). Its potential impact spans developers, users, ecosystem maintainers, and the broader AI community.

**Academic Significance:**
The most immediate impact is the **filling of a critical academic gap**. By providing the "first comprehensive analysis of the MCP ecosystem" and "the first end-to-end security and privacy analysis... covering all lifecycle stages," the paper establishes a foundational understanding for future research. It moves beyond isolated studies of LLM-tool interactions to address the systemic security implications of a unifying protocol. The detailed threat taxonomy, complete with empirical validations via PoCs, offers a robust framework for subsequent vulnerability research, benchmark development, and defensive mechanism design in MCP environments.

**Impact on Developers:**
For developers, the paper provides crucial awareness and actionable guidance. It highlights the new attack surfaces inherent in MCP's open and composable design, particularly stemming from metadata definition and code implementation during the *creation and deployment* phases. Developers gain insights into how seemingly benign actions like naming tools or crafting descriptions can be exploited through typosquatting, preference manipulation, or tool poisoning. The recommendations—such as provenance verification, version-controlled releases, static analysis, and secure module design—offer practical steps to build more secure MCP servers, reducing the likelihood of accidental vulnerabilities or intentional malicious injections.

**Impact on Users:**
Users of AI-powered applications that leverage MCP will benefit from increased awareness of runtime threats. The paper elucidates how threats like indirect prompt injection, command injection, and unauthorized access can occur during the *operation* phase, even when interacting with seemingly legitimate tools. This understanding empowers users to demand more robust security features from MCP hosts and client applications, encouraging the prioritization of trusted MCP collections, digital signature verification at installation, and the use of sandboxed environments to confine tool execution.

**Impact on Ecosystem Maintainers:**
The research underscores the significant challenges faced by maintainers of the decentralized MCP ecosystem. The findings on "vulnerable versions," "privilege persistence," and "configuration drift" highlight the need for centralized security oversight, consistent patching, and robust version control mechanisms during the *deployment and maintenance* phases. The paper implicitly advocates for the development of official package management systems, secure registries, automated integrity auditing, and mandatory configuration validation to ensure ecosystem-wide resilience and mitigate the risks associated with fragmented, community-driven development.

**Impact on the Broader AI Community:**
MCP's promise of enhanced interoperability and composability for AI capabilities is enormous. This paper, however, serves as a crucial warning: without proactive security measures, this interoperability can amplify ethical and safety concerns. It encourages the AI community to consider fairness in tool selection, prevent dataset leakage, and maintain accountability in automated decision workflows. The detailed analysis promotes a "security-by-design" mindset, ensuring that as AI agents become more autonomous and interconnected, the underlying protocols and infrastructure are inherently robust and trustworthy.

**Driving Sustainable Growth:**
Ultimately, the paper provides a roadmap for MCP's sustainable growth. By identifying critical challenges (lack of centralized security, authentication gaps, insufficient monitoring, workflow consistency, scalability issues in multi-tenant environments, and risks in smart environments) and offering lifecycle-based recommendations, it guides future research and development. This includes advocating for standardized authentication frameworks, enhanced debugging and monitoring capabilities, robust state validation, tenant isolation models, and secure integration practices for IoT and enterprise systems. Addressing these areas will be paramount for MCP to fulfill its potential as a secure, efficient, and reliable backbone for future AI-native applications.
