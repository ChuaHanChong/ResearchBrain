# Train Together or Merge Later? Unifying VLA Experts via a Shared Action Interface

> [!summary] Summary
> PolicyWeave builds one multi-task VLA by merging independently post-trained LoRA experts instead of co-training. Each expert keeps the base model's action interface frozen: its normalization statistics, action encoder and action decoder. At deployment, the initial visual-language context scores every expert, and a leave-one-layer-out ranking-stability test picks a sparse weighted merge. On 18 RoboCasa365 tasks with GR00T N1.5, it reaches 74.1% versus 60.7% for joint RL.

## Problem

- Co-training one multi-task VLA must balance competing task objectives and often underperforms per-task experts, yet independent experts stay separate policies that need a task ID at deployment.
- Model merging methods from vision and language transfer poorly to VLAs: strong individual experts can yield weak merged policies because task-specific action normalization and encoders break under averaging.
- Static merging applies one parameter set to every task, so unrelated updates interfere. Learned routers need extra training, and picking a single expert fails when tasks share objects.

## Method

- ==Merge-compatible post-training== freezes the VLM, normalization statistics, action encoder and action decoder, and trains only ==rank-8 LoRA== updates in the hidden action-model layers for each task.
- ==Context-response scoring== ranks experts by how strongly each expert's LoRA key-projection update responds to the initial context tokens. The norm is scale-normalized and needs only one base-model forward pass.
- ==Stability-adaptive sparse merging== removes each layer's score in turn to see if the top expert stays first. If not, it score-weights the smallest ==top-k== set covering every leader, fixed per episode.

## Results

- A shared action interface raises the mean success of four static merging methods on 18 RoboCasa365 tasks from **17.0% to 52.8%**. Individual expert success stays comparable at **65.6% versus 64.1%**.
- PolicyWeave reaches **64.7%** after SFT and **74.1%** after RL, versus **58.9%/62.8%** for SSR-Merge and **58.1%/60.7%** for co-training. It retains **9.4 of the 10.6 points** that individual RL adds.
- On LIBERO-10: **75.4%** success, **93.3%** retention versus **79.0%** for MergeVLA, and **93.6%** selection accuracy versus **89.4%** for a trained MLP. On a real Piper arm: **67.5%** versus **48.8%** for co-trained π0.5.

## Takeaways

> [!tip] Key Insights
> - Mergeability is decided at training time. Keep every mapping between representations and physical actions shared, because experts silently compensate for interface drift that weight averaging then breaks.
> - Independent per-task RL followed by merging can beat joint multi-task RL. Expert optimization can then be separated from multi-task deployment, as long as merging preserves each expert's gains.
> - An expert's own adapter response to the context gives a routing signal with no training. Merging more experts is not safer, so set the merge size from ranking uncertainty.

## Detailed Report

### 1. Overview

A robot placing one block on another shows the goal concretely: one policy that can carry out many such skills. A vision-language-action (VLA) model maps images and language to robot actions. Supervised fine-tuning (SFT) adapts it from demonstrations, and reinforcement learning (RL) can improve it through interaction. Training each task independently can give a robot stronger specialists than co-training. Simply averaging those specialist models, however, does not reliably produce a capable multi-task policy.

PolicyWeave makes experts compatible *before* merging and then limits interference *when* merging. During training, it keeps the experts' action mappings shared. At deployment, it uses the initial scene and instruction to choose one expert or a small, weighted group. The authors' motivation is practical: a single policy without a task-ID input is useful at deployment, while separate policies leave the robot needing an external way to choose between them. With GR00T N1.5 on 18 simulated RoboCasa365 tasks, PolicyWeave reaches 74.1% mean success after task-specific SFT and RL, versus 60.7% for a co-trained policy.

### 2. Why compatible action mappings matter

The authors define the action interface as action-normalization statistics plus the action encoder and decoder. Together, these map between physical actions and the model's internal representations.

During task-specific post-training, task-specific normalization and changes to the encoder or decoder alter how actions map into the model and back again. An expert's hidden weights can compensate for those changes. When hidden weights are averaged across experts with different interfaces, that compensation can break, which changes the resulting actions. The authors identify this as one source of merging incompatibility. They do not claim it is the only source.

PolicyWeave's experts start from a common base policy. They keep its interface, with the action encoder and decoder frozen along with the VLM. Task adaptation is limited to LoRA updates, which are low-rank parameter updates, in hidden action-model layers.

The key comparison tests whether the shared interface matters, or whether any gain comes from a better merging rule. The authors applied four static merging methods to expert banks with task-specific interfaces and with shared interfaces. The methods' unweighted mean success rose from 17.0% to 52.8%. These are simulation results. They support the compatibility explanation in these experiments, not a universal causal account.

### 3. Choosing experts from the scene

A shared interface makes experts more compatible, but the merge should still exclude updates unrelated to the current task. To do this, the frozen VLM encodes the initial observation and instruction. A pass through the base model then supplies context inputs at the action model's cross-attention key projections. For each expert, PolicyWeave scores how its learned key-projection updates respond to those inputs, summing the scores across eight layers. This is a relevance signal, not a trained router.

Next, experts are ranked by total score. The method removes each scoring layer's contribution in turn and checks which expert ranks first. If the original leader stays first every time, PolicyWeave selects that expert alone. Otherwise, it selects the shortest prefix of the original ranking that contains every expert that became a leader. The selected updates are weighted by their scores and merged.

This merge stays fixed for the episode. Later observations still condition the policy's actions, but they do not trigger rerouting.

### 4. What the headline result shows

On RoboCasa365, success is the average task success rate, with each task evaluated over 50 episodes. Each SFT expert uses 50 demonstrations, which is 10% of the target-task demonstrations.

PolicyWeave's mean success is 64.7% with SFT experts and 74.1% after task-specific RL. Co-training reaches 58.1% and 60.7% at the same stages. The individual RL continuations total 610 steps, compared with 600 joint RL steps for co-training. This result supports retaining gains from independent RL under this setup. It does not establish lower elapsed time, fewer attempts, or less total computation.

### 5. Closing

Stronger specialists are useful only if their action mappings are compatible and unrelated updates do not overwhelm the current task. In these tests, PolicyWeave addresses the first condition during post-training and the second during deployment, so independently learned skills can form a single policy. The findings support the authors' case for this setup. They do not establish that merging is better for all VLAs or deployment settings.
