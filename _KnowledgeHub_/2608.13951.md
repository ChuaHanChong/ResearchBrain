# HELIX: Model-Harness Co-evolution for Recursive Self-Improvement

> [!summary] Summary
> HELIX treats the agent runtime harness as a first-class co-evolving component alongside the model, organizing recursive self-improvement as build-update-rebuild. It decomposes four open-source coding harnesses into typed ports, atoms, and recipes with pre-execution checks and an evidence plane. A 65-candidate evolution round beats the Pi baseline by 4.0% on a LiveCodeBench repair subset; a 200-slot SWE-bench sibling slice yields 438 verified training records.

## Problem

- Agent-capability scaling is framed as model improvement alone, treating the runtime harness as a neutral wrapper rather than an active co-determinant of reachable behavior.
- Existing trace-driven harness adaptation and joint harness-model optimization make the build-to-update handoff hard to keep source-traceable and auditable across heterogeneous runtime designs.
- Evolving one component while freezing the other severs the feedback loop: harness-generated trajectories never return as verified, provenance-preserving training signal for the next model.

## Method

- ==Build-update-rebuild== formulation: build source-traceable harnesses for a fixed model, update the model from verified sibling trajectories, rebuild the portfolio for the shifted capability profile.
- **HELIX** substrate decomposes OpenCode, Pi Mono, Nanobot, and Hermes Agent into ==typed ports==, ==common and personality atoms==, packs, recipes, product shells, and policies, exposing 96 ports and 1,024 to 4,096 enumerable recipes.
- ==Recipe compiler== emits a deterministic lockfile with conformance, boundary, and source-purity checks; an ==evidence plane== retains traces, workspace diffs, verifier status, and provenance for sibling export.

## Results

- Across **65** candidates on a **100**-task LiveCodeBench repair subset, the best fixed harness solves **52/100** versus Pi's **50/100**, a **4.0%** relative gain.
- The post-hoc portfolio union reaches **79/100**, **58.0%** more coverage, yet only **two of 64** non-baseline candidates beat Pi and **23** solve zero tasks.
- On **55** SWE-bench Verified instances the best selected member resolves **46/55** versus Pi's **44/55**, and a **200**-slot sibling slice exports **438** SFT, critic, filter, and preference records.

## Takeaways

> [!tip] Key Insights
> - Observed agent capability is a function of model, harness, task, budget and verifier, so runtime design deserves the same evolutionary treatment as weights.
> - Blind component recomposition mostly fails, and the framework materializes model-update data without ever training an updated model, so the recursive loop stays unclosed.
> - Passing target tests is not a clean training positive: regressions, patch noise, and structurally clean but semantically wrong patches need separate outcome labels.

## Detailed Report

### 1. How This Work Fits into the Broader Research Landscape

The prevailing approach to enhancing artificial agent capabilities has primarily focused on improving the underlying language model itself. This perspective often treats the model as the sole determinant of an agent's performance. However, a deployed agent operates within a runtime environment, referred to as a "harness," which mediates various aspects of its interaction with the environment. This harness encompasses system instructions, context construction, session state management, tool integration, control flow, permissions, retry policies, and stopping criteria.

Recent research has begun to acknowledge the significant role of these harnesses. Works such as ReAct and Toolformer demonstrated how language models can be integrated with external tools and actions, while SWE-agent explored how agent-computer interfaces directly influence a model's ability to navigate repositories and perform software engineering tasks. These studies collectively indicate that an agent's observed behavior is a product of both the model and its surrounding runtime.

Building on this recognition, a nascent area of research, including Recursive Harness Self-Improvement and HarnessX, has started to explore adaptive harnesses and joint model-harness optimization. These efforts acknowledge a coupling between the model and its runtime. Concurrently, the field of recursive self-improvement (RSI) seeks to develop systems that can autonomously enhance their own capabilities, ranging from bounded behavior refinement to fundamental changes in model policies or research processes, as exemplified by concepts like Gödel Machines and Darwin Gödel Machines. Automated workflow and agent design systems, such as AutoFlow and Automated Design of Agentic Systems (ADAS), also contribute to this landscape by generating and optimizing agentic systems or their operational flows.

HELIX positions itself within this evolving landscape by proposing a systematic and auditable framework for "model-harness co-evolution" as a first-class principle for RSI. It addresses the challenge of making the handoff between harness adaptation and model learning traceable and auditable across heterogeneous runtime designs. Instead of focusing solely on model improvement or ad-hoc harness adjustments, HELIX advocates for a bidirectional, recursive dependency where both components evolve in concert, thereby contributing to the development of more robust and autonomously improving agent systems.

### 2. Key Objectives and Motivation

The central motivation for this work stems from the observation that scaling agent capability has predominantly focused on improving the language model in isolation. The authors argue that this approach overlooks a critical component: the agent's runtime harness. This harness is characterized not as a passive wrapper but as an "active co-determinant of agent behavior," significantly influencing how the model interacts with its environment. For interactive agents, the harness's influence is recursive: it dictates how the model executes tasks in the present and shapes the data trajectories from which the model learns for future improvement.

Treating the model and harness as independent entities, therefore, severs a crucial feedback loop. The primary objective of this research is to close this feedback loop by establishing model-harness co-evolution as a foundational principle for recursive self-improvement (RSI). This principle rejects the assumption that one component evolves while the other remains static. Specifically, the motivations are detailed as follows:

- **Recognition of Bidirectional Dependency:** Harness design directly impacts fixed-model execution and structures the data generated for subsequent model updates. Conversely, an improved model may necessitate or favor a different harness design that better aligns with its new capabilities. Ignoring this bidirectional dependency limits the potential for overall system improvement.
- **Dual Purpose of Harness Building:** Harness construction should serve a dual purpose: not only to enable stronger immediate execution for the current model but also to generate "verified sibling trajectories." These trajectories, which include successes, regressions, near misses, and alternative solutions, provide structured training signals for the next model update.
- **Addressing Auditability and Traceability:** Prior approaches have begun to link harness adaptation with model learning, but making this handoff "source-traceable and auditable across heterogeneous runtime designs" remains a challenge. The paper highlights the need for explicit rather than implicit interventions in harness design.
- **Formalizing RSI through Build–Update–Rebuild:** The authors propose a structured, repeatable paradigm for model-harness co-evolution, articulated as three stages:
 1. **Build:** For a fixed model, construct and evaluate explicit, source-traceable harness candidates on matched tasks.
 2. **Update:** Convert the resulting verified sibling trajectories into learning records to update the model.
 3. **Rebuild:** Re-evolve the harness for the updated model, acknowledging that its shifted capability profile may require or benefit from different runtime designs. This step ensures that the model-harness pair, rather than the model alone, is the unit undergoing recursive improvement, making the entire process recursive.

By addressing these motivations, HELIX aims to provide a concrete, auditable substrate for implementing model-harness co-evolution, thereby enabling a more comprehensive and effective path towards recursive self-improvement in AI agents.

### 3. Methodology and Approach

HELIX proposes a system-level approach to model-harness co-evolution, operationalizing the "build–update–rebuild" paradigm. The methodology is structured around explicit, source-traceable interventions in harness design, followed by a rigorous evaluation and data generation process.

**Harness Representation and Composition:**
HELIX decomposes a monolithic runtime harness into eight distinct, explicit intervention variables: `H_shell`, `H_session/hooks`, `H_config`, `H_prompt`, `H_tools`, `H_turn`, `H_accept`, and `H_policy`. These dimensions cover the model-facing interface and the environment-facing control plane. The system derives behaviors from existing open-source harnesses, including OpenCode, Pi Mono, Nanobot, and Hermes Agent.

To ensure source traceability and bounded modification, HELIX uses six core entities:
- **Ports:** Define stable capability slots within the harness.
- **Atoms:** Provide product-neutral (common atoms) or source-specific (personality atoms) behaviors behind stable ports.
- **Packs:** Convenient groups of atoms.
- **Recipes:** Bind atoms, strategies, policies, and shells into a declared candidate harness.
- **Product Shells:** Expose a candidate harness through an SDK, CLI, TUI, or web interface.
- **Compiler and Lockfile:** The compiler expands declared compositions, resolves dependencies, binds ports, and emits a deterministic lockfile for runtime assembly, ensuring that every evaluated rollout is linked to its intended intervention.

This structured representation enables the enumeration of a finite intervention space. For instance, with five independent source choices (excluding prompt, turn loop, and acceptance which were fixed in some experiments), HELIX can enumerate 4^5 = 1,024 candidates, or 4^6 = 4,096 if acceptance is independently selected. Pre-execution checks, including conformance, boundary, and source-purity checks, validate compositions before live evaluation, flagging invalid or ambiguous designs.

**Model–Harness Interaction at Runtime:**
The assembled runtime facilitates a multi-step interaction loop:
1. Session creation/restoration, hook execution, and user message persistence.
2. Request normalization and prompt/context building under the chosen product personality.
3. Streaming of provider steps, normalization of assistant parts, and collection of proposed tool calls.
4. Tool preflight/permission checks, execution of batches, application of result hooks, and truncation/retry.
5. Evaluation of acceptance evidence and provider finish reason.
6. Continuation or stopping based on acceptance, request boundary, or step limits.
7. Persistence of transcript, session state, runtime trace, and workspace effects for evaluation.
This loop highlights how harness elements like context compaction, tool input normalization, and permission strategy can alter trajectories without changing model weights, underscoring the bidirectional influence.

**Evidence Plane:**
For each run, the system preserves intervention identity by joining the recipe, lockfile, model-task-attempt identity, runtime trace, workspace effects, verifier outcome, and policy evidence into an "evidence envelope." This allows for reconstruction of declared compositions and execution conditions, enabling attribution of gains or regressions to specific component sets. The verifier assigns detailed labels beyond binary success, distinguishing resolved, target-miss, regression, no-action, policy violation, patch-noise, or evaluator gap.

**Experimental Design:**
The evaluation involved a large language model, MiniMax-M2.7-highspeed, used with `deterministic=false`.
- **Main Evolution Matrix (RQ1 & RQ2):** A 65-candidate evolution portfolio, derived from Pi Mono and OpenCode/Hermes/Nanobot components, was evaluated on 100 LiveCodeBench (LCB)-derived repair tasks (26 easy, 24 medium, 50 hard). Each candidate ran once per task (6,500 slots total). Success was defined by trace-strict status (observed normalized bash call executing `test_solution.py` with passing output).
- **Selected-Member LCB Follow-up (RQ1):** Three candidates (Pi and two OpenCode-family members from the 65-candidate set) received ten attempts per task on the same 100 LCB tasks (3,000 slots total) to measure reliability (successful slots) and task coverage.
- **Selected-Member SWE-bench Verified Follow-up (RQ3):** Five candidates (Pi, the top two fixed LCB candidates, and the two OpenCode-family members from the LCB follow-up) were evaluated on 55 instances from SWE-bench. Each received two attempts per instance (550 slots total), with a maximum of 200 agent steps. Task resolution was validated by the official SWE-bench evaluator. This follow-up provided the rich outcome, patch, and sibling trace data for learning data analysis.

### 4. Main Findings and Results

The evaluation addressed three research questions, covering both immediate execution improvements and the generation of learning data for future model updates.

**RQ1: Execution Today—Can Evolution Surpass the Baseline?**
- **Complete Evolution Matrix (LCB):** In the 65-candidate LCB evaluation, Pi solved 50 out of 100 tasks. The best fixed harness candidate solved 52/100 tasks, representing a 4.0% relative improvement over Pi. This candidate utilized Hermes session/hooks combined with other Pi components. Only two of 64 non-baseline candidates surpassed Pi, while 23 solved zero tasks.
- **Selected-Member LCB Follow-up:** In repeated-run LCB evaluation (10 attempts per task), selected OpenCode-family members covered 75/100 tasks, compared to 72/100 for Pi. They also achieved a higher number of successful slots (549 and 546 vs. 529 for Pi), indicating improved reliability.
- **Selected-Member SWE-bench Follow-up:** On the official SWE-bench evaluation (2 attempts per instance), the preference for the best fixed harness shifted. The two candidates leading the one-attempt LCB matrix resolved 44/55 instances, matching Pi. However, the selected OpenCode-family members resolved 46/55 instances, with the strongest recording 86 resolved slots versus 81 for Pi.
- **Finding 1:** Harness evolution successfully identified fixed harnesses that improved execution over the baseline model-harness pair. The specific "best" fixed harness varied depending on the evaluation protocol (LCB vs. SWE-bench), indicating environment-dependent utility.

**RQ2: Execution Breadth from Rapid Harness Evolution**
- **Complete Evolution Matrix (LCB):** While the best fixed candidate solved 52/100 tasks, the *post-hoc oracle coverage* across the entire 65-candidate portfolio reached 79/100 tasks. This represents a 58.0% relative coverage gain over Pi, indicating that a diverse set of harnesses can collectively solve significantly more tasks than any single fixed harness.
- **Selected-Member SWE-bench Follow-up:** The post-hoc union coverage for selected members on SWE-bench was 49/55 instances, exceeding the best fixed member's 46/55 and Pi's 44/55.
- **Finding 2:** Rapid harness evolution exposes substantial complementary task coverage and sibling diversity beyond the performance of any single best fixed harness. This suggests significant headroom for agent performance if an effective routing or selection mechanism could be employed. However, the presence of many poorly performing candidates (23 solved zero LCB tasks) also emphasizes the necessity of selection mechanisms (typed gates, cheap screening) rather than blind composition.

**RQ3: Learning Data for the Next Model Update**
- **From Portfolio Outcomes to Usable Labels:** The selected-member SWE-bench validation provided rich data for generating learning records. Out of 550 evaluated slots, 543 contained non-empty patches. Analysis showed that 411 were officially resolved, but only 205 were both production-only and path-clean, highlighting that raw resolution is insufficient for high-quality training data.
- **Sibling Contrasts Reveal Supervision:** Detailed case studies demonstrated how sibling trajectories yielded valuable supervision:
 - **Sphinx (SWE-bench):** A Pi attempt missed the target, while an OpenCode-config sibling successfully resolved it with a cleaner, smaller patch. This provided a clean positive example and a "resolved-versus-miss" preference contrast.
 - **Pytest (SWE-bench):** A Pi patch passed target tests but introduced regressions, labeled as "gaps-found." An OpenCode-config sibling passed all target and regression tests, labeled "resolved." This provided a high-value "critic negative" example, illustrating why target-only evaluation is insufficient.
 - **Xarray (SWE-bench):** Two clean, single-file patches, differing only in their config atom, showed a subtle semantic divergence. One correctly implemented `keep_attrs` semantics (resolved), while the other did not (gap-found). This provided a configuration-aligned semantic contrast.
 - **LCB Closure and Fragility (LCB):** Traces for `v6-025-abc391-f` showed how a recomposed harness could lead to successful repairs after multiple failed attempts, consistent with a repair-closure mechanism. Conversely, `v6-088-arc191-d` showed regression in recomposed harnesses despite similar trace shapes, indicating fragility and complexity in predicting solution quality.
- **Materializing Training Records:** From a 200-slot slice of the selected-member SWE validation, 438 multi-purpose training records were materialized. These included:
 - 63 Clean SFT examples
 - 56 Cleanup-needed SFT examples
 - 52 Critic negatives
 - 113 Filter samples
 - 154 Preference pairs (e.g., minimal-cleanup vs. larger-cleanup, clean vs. noisy, resolved vs. regression, resolved vs. target misses, resolved vs. no-action).
- **Finding 3:** The process of harness evolution and detailed evaluation generates diverse, verified sibling outcomes that can be converted into structured training records (SFT, critic, filter, preference data) for model updating. This establishes a concrete data handoff for model improvement.

### 5. Significance and Potential Impact

This research presents a framework for model-harness co-evolution that has several significant implications for the development of advanced AI agents, particularly in the context of recursive self-improvement.

**Enabling Auditable Recursive Self-Improvement:** The most prominent contribution is the formulation of system-level recursive improvement as a "build–update–rebuild" cycle, explicitly treating the model-harness pair, Z_t = (M_t, Φ_t), as the unit of improvement. By making harness interventions explicit, source-traceable, and auditable, HELIX allows for the inspection and attribution of changes across rounds. This departs from unconstrained self-rewriting, offering a bounded and measurable path for system evolution. The persistent identity of recipes, coupled with the evidence plane, ensures that the lineage of recursive changes (to the model, harness, or their interaction) can be tracked, which is critical for systematic progress and safety in RSI.

**Optimizing Two Improvement Frontiers:** The findings demonstrate that the model-harness pair operates on two distinct but coupled improvement frontiers:
1. **Performance Frontier:** Selecting a fixed harness that optimizes execution today for the current model. The experiments showed that evolution can identify stronger fixed harnesses, though the "best" one may vary by task and evaluation protocol.
2. **Data Frontier:** Generating a diverse portfolio of verified sibling trajectories that provide rich learning signals for the next model update. The substantial gap between the best fixed candidate and the portfolio's oracle coverage (e.g., 52/100 vs. 79/100 on LCB) highlights the potential for this data yield. This means that even non-winning or "failed" harness candidates can contribute valuable negative examples, semantic near misses, or preference contrasts, enriching the training data.

**Structured Data Generation for Model Updates:** HELIX provides a concrete mechanism for transforming raw interaction trajectories into structured, verified learning records. The detailed categorization of sibling outcomes (clean SFT, critic negatives, filter samples, preference pairs) from a curated slice of runs demonstrates a practical data handoff for various model-update objectives. This allows for more nuanced and effective model training, as models can learn not just from successes, but also from regressions, alternative solutions, and even from the process of failure. This capability is fundamental for closing the learning loop in a recursive system, as the experience gained from execution directly informs the subsequent model refinement.

**Practical Implications for Agent Development:** By decomposing harnesses into interchangeable, source-traceable components (ports, atoms, recipes), HELIX makes harness modification a repeatable, component-level operation rather than a costly engineering endeavor. This bounded modification surface facilitates rapid portfolio construction and rebuilding, essential for the "build" and "rebuild" stages of co-evolution. The system's ability to expose execution headroom (via portfolio coverage) also points towards future potential for learned routing or staged policies that can dynamically select or adapt harnesses based on task features or early trace signals.

In conclusion, HELIX provides an operational framework that integrates harness evolution directly into the recursive self-improvement paradigm. By making model-harness co-evolution explicit, auditable, and data-generating, it offers a path toward developing more capable, robust, and autonomously improving AI agents, where both the model and its operational environment contribute to and learn from their shared evolution.
