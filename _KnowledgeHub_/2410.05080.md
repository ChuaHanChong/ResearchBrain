# ScienceAgentBench: Toward Rigorous Assessment of Language Agents for Data-Driven Scientific Discovery

> [!summary] Summary
> ScienceAgentBench is a benchmark of 102 data-driven discovery tasks extracted from 44 peer-reviewed papers across four scientific disciplines and validated by nine subject experts. Each task requires a self-contained Python program, graded on execution, success criteria, code similarity and cost. The best agent, Claude-3.5-Sonnet with self-debug, solves only 34.3% of tasks, showing agents are far from automating scientific research.

## Problem

- Claims of end-to-end automated scientific discovery, such as The AI Scientist, rest on LLM-reviewer assessment of generated papers rather than rigorous verification of individual workflow tasks.
- High-quality benchmarks built from real scientific workflows are missing; existing code benchmarks use synthetic tasks, GitHub edits, or short snippets, and lack heterogeneous scientific data and expert validation.
- Open-source scientific datasets and code invite LLM training contamination, and agents can take shortcuts such as reading test labels directly, which undermines the validity of agent evaluation.

## Method

- ==Task curation==: 102 tasks adapted from open-source code in 44 publications across Bioinformatics, Computational Chemistry, Geographical Information Science, and Psychology, each unified as a ==self-contained Python program== output, then checked by nine experts and annotators.
- ==Multi-metric evaluation==: ==Valid Execution Rate==, ==Success Rate== from task-specific executable criteria, ==CodeBERTScore== against gold programs, API cost, a GPT-4o figure judge, and expert-refined five-stage rubrics for human partial-credit scoring.
- ==Contamination and shortcut mitigation==: five random test points removed per dataset, and test labels replaced with dummy values after re-splitting model-development datasets, so memorized loaders or label copying fail the success criteria.
- Optional ==expert-provided knowledge== (term explanations, formulas, tool usage) is supplied per task, and three frameworks are compared: direct prompting, OpenHands CodeAct, and a modified ==self-debug==.

## Results

- Claude-3.5-Sonnet with self-debug performs best among standard LLMs, solving **32.4%** of tasks alone and **34.3%** with expert knowledge; OpenAI o1-preview with self-debug reaches **42.2%** at over **ten times** the cost.
- Execution feedback matters: direct prompting gives Claude-3.5-Sonnet **16.7%** success, while self-debug nearly doubles it to **32.4%**. With expert knowledge, valid execution rises from **41.2%** to **86.3%**.
- Self-debug beats OpenHands CodeAct for four of five LLMs; for Claude-3.5-Sonnet it solves **10.8 points** more tasks (**32.4%** vs **21.6%**) at **17 times** lower cost (**$0.057** vs **$0.958**).

## Takeaways

> [!tip] Key Insights
> - Evaluate agents on individual tasks in a scientific workflow before claiming end-to-end automation; today's agents fail on many complex tasks, with successes concentrated in short gold programs.
> - Simpler agent designs can beat complex ones: a large tool action space did not help most LLMs, so cost and performance should both drive agent framework choice.
> - Data loading and processing best separate successful from failed programs, so improving handling of heterogeneous scientific data and discipline-specific tools is the main lever for progress.

## Detailed Report

### 1. How This Work Fits into the Broader Research Landscape

The rapid advancements in large language models (LLMs) have fueled significant interest in developing LLM-based "language agents" capable of automating complex workflows, including the entire process of scientific discovery. Recent works, such as "The AI Scientist" by Lu et al. (2024) and calls for end-to-end data-driven discovery systems by Majumder et al. (2024a), have generated both excitement and skepticism regarding the true capabilities of these agents.

ScienceAgentBench directly intervenes in this landscape by advocating for a more "rigorous assessment" of agents. The authors contend that bold claims of "end-to-end automation" are premature and often unsubstantiated without a thorough evaluation of agents on "individual tasks" within a scientific workflow. This work identifies a critical gap: the lack of high-quality benchmarks specifically designed for objectively assessing language agents on realistic, granular tasks in data-driven scientific discovery.

The paper meticulously positions ScienceAgentBench against existing benchmarks (Table 2 and Appendix B):
- **General Task Automation Benchmarks:** Benchmarks like TaskBench (Shen et al., 2024) focus on synthetic tasks with outputs formatted as JSON API calls, limiting their real-world applicability and flexibility.
- **Code Generation Benchmarks:** SWE-Bench (Jimenez et al., 2024), BioCoder-Py (Tang et al., 2024c), ML-Bench (Tang et al., 2024b), and MLAgentBench (Huang et al., 2024b) focus on code generation but often source their tasks from secondary platforms like GitHub and Kaggle. This raises concerns about "scientific authenticity" and real-world relevance to cutting-edge research. Moreover, many of these benchmarks focus on function-level code completion or minor edits, not the generation of complete, standalone programs.
- **Scientific Task Benchmarks from Publications:** SciCode (Tian et al., 2024), BLADE (Gu et al., 2024), and DiscoveryBench-Real (Majumder et al., 2024b) are more aligned with scientific domains, deriving tasks from publications. However, ScienceAgentBench distinguishes itself further:
 - **DiscoveryBench-Real**, while drawing from publications, requires agents to output abstract natural language steps rather than executable code, which hinders rigorous, automatic evaluation and practical utility.
 - **SciCode** and **BLADE** often focus on function-level code generation, whereas ScienceAgentBench demands the generation of a "standalone program file from scratch."

In summary, ScienceAgentBench fills a crucial void by providing a benchmark that is:
1. **Scientifically Authentic:** Tasks are directly extracted and adapted from *peer-reviewed publications* (44 distinct sources).
2. **Real-World Relevant:** Covers *four diverse scientific disciplines* with *heterogeneous datasets* (images, molecules, maps, time series), reflecting complex real-world data structures.
3. **Rigorous and Comprehensive:** Requires *file-level program generation* and employs *multi-faceted evaluation metrics*.
4. **Robust:** Actively *mitigates data contamination and agent shortcut concerns*, enhancing evaluation validity.

By offering a high-quality, task-focused benchmark, this work aims to pivot the discussion from aspirational end-to-end automation to a more grounded, incremental development of "science co-pilots" that can rigorously assist human scientists with specific, labor-intensive programming tasks.

### 2. Key Objectives and Motivation

The central motivation for ScienceAgentBench arises from the burgeoning interest and concurrent skepticism surrounding the capability of large language models (LLMs) to automate scientific discovery. While many recent efforts claim to achieve end-to-end automation of research workflows (e.g., from idea generation to paper writing), the authors argue that such ambitious claims lack rigorous, granular validation. They contend that for an LLM-based agent to truly automate data-driven discovery, it must first demonstrate proficiency in the "essential tasks" that constitute a scientific workflow, such as data processing, model development, data analysis, and visualization.

Against this backdrop, the **key objectives** of this research are:

1. **Call for Rigorous Assessment:** To shift the focus of evaluation from broad, potentially unverified claims of end-to-end automation to a more meticulous, task-by-task assessment of language agents' capabilities within scientific workflows.
2. **Develop a High-Quality Benchmark:** To introduce **ScienceAgentBench**, a novel benchmark specifically designed for evaluating language agents in data-driven scientific discovery.
3. **Ensure Scientific Authenticity:** To construct the benchmark using tasks directly derived from peer-reviewed scientific publications, ensuring their relevance and grounding in real-world research problems. This also involves extensive validation by subject matter experts to minimize the "generalization gap" to practical scenarios.
4. **Enable Rigorous and Graded Evaluation:** To establish a robust evaluation framework that can objectively measure agent performance. This involves unifying the target output to executable Python programs and employing a comprehensive array of metrics that assess program execution, correctness of results, code quality, and computational cost. The framework also aims to allow for "graded evaluation" by providing rubrics for partial credit.
5. **Mitigate Evaluation Biases:** To implement strategies to combat data contamination (where LLMs might have seen the test data during pre-training) and agent "shortcuts" (where agents might produce seemingly correct but functionally flawed outputs, e.g., by reading ground truth directly).
6. **Provide a Foundational Tool:** To offer ScienceAgentBench as a continuous testbed for rigorously measuring progress in developing language agents that can effectively "augment human scientists' productivity" by serving as "science co-pilots" capable of automating tedious programming efforts.

In essence, the motivation is to bring a much-needed dose of rigor and realism to the evaluation of AI agents in science, moving beyond aspirational visions to measurable, practical utility.

### 3. Methodology and Approach

The construction and evaluation of ScienceAgentBench follow a meticulously designed methodology grounded in three core principles: scientific authenticity, rigorous graded evaluation, and careful multi-stage quality control.

#### 3.1. Problem Formulation

Each task in ScienceAgentBench is formulated as a **code generation problem**. Given a natural language instruction, relevant dataset information, and optional expert-provided knowledge, the agent is required to generate a self-contained Python program file that completes the assigned scientific task. This output format is chosen for its verifiability and direct usability by scientists. Each task instance comprises four key components:
- **Task Instruction:** A concise natural language description of the task goal and output requirements, mimicking real-world scientific requests.
- **Dataset Information:** Includes the dataset's directory structure and a preview of its content, crucial for agents that might lack advanced file system navigation tools.
- **Expert-Provided Knowledge:** Optional input containing explanations for scientific terms, formulas, or programming tool usage, provided by subject matter experts.
- **Annotated Program:** A reference Python solution adapted from open-source code repositories associated with peer-reviewed publications.

#### 3.2. Data Collection

The benchmark curation involved a multi-stage process to ensure quality and authenticity:
- **Task Annotation:** Nine graduate students (annotators) initiated the process, covering four disciplines: Bioinformatics, Computational Chemistry, Geographical Information Science, and Psychology & Cognitive Neuroscience. They identified 44 peer-reviewed publications with permissive licenses that released their code and data. For each task, they followed five steps: (1) Identify a well-documented, self-contained code example; (2) Collect and preprocess datasets; (3) Annotate the reference program; (4) Implement task-specific success criteria and draft fine-grained rubrics (initially with GPT-4o); (5) Write the task instruction and dataset information. This process initially yielded 110 tasks.
- **Data Contamination and Shortcut Mitigation:** To address the common issues of LLMs memorizing code or taking shortcuts, two strategies were implemented:
 1. **Test Set Modification:** For each dataset, five random data points were removed from its test set. This ensures that programs relying on exact, memorized automatic data loaders will fail the success criteria.
 2. **Label Masking for Model Development:** For tasks involving model development, datasets were re-split, and test set labels were replaced with dummy values (e.g., -1 for classification tasks). This prevents agents from simply reporting ground-truth labels.
- **Expert Validation:** Nine subject matter experts (senior Ph.D. students and professors) from the respective disciplines validated the curated tasks. They reviewed the scientific realism of each task, the accuracy and professionalism of the instructions, provided up to three pieces of domain-specific knowledge, and revised the GPT-4o drafted rubrics. This validation led to the revision of 41 task instructions and the removal of 3 tasks.
- **Annotator Verification:** A final round of verification involved annotators checking tasks not originally composed by themselves and executing programs to reproduce results. This refined 29 task annotations and discarded one more, finalizing ScienceAgentBench with **102 high-quality tasks**.

#### 3.3. Evaluation

Recognizing the open-ended nature of scientific tasks, a flexible and comprehensive evaluation pipeline was developed:
- **Environment Setup:** A `conda` environment is dynamically set up for each generated program. It starts with seven basic Python packages, and `pipreqs` and `pip-tools` are used to analyze the program's dependencies and install additional packages, ensuring proper configuration.
- **Program Evaluation Metrics:**
 - **Valid Execution Rate (VER):** Binary metric checking if the program runs without errors and saves output correctly.
 - **Success Rate (SR):** Binary metric assessing if the program's output meets task-specific success criteria (e.g., performance thresholds, prediction accuracy, visualization quality). SR is contingent on VER.
 - **CodeBERTScore (CBS):** Measures the semantic similarity between the generated and annotated programs using contextual embeddings. If SR=1, CBS is set to 1.0.
 - **API Cost:** Calculates the average monetary cost (in USD) to complete one task, emphasizing practical utility.
- **Figure Evaluation:** For tasks producing figures, GPT-4o is used as a judge to compare generated figures against ground truth, with scores averaged from three responses.
- **Rubric-Based Evaluation:** To provide fine-grained insights and partial credits, programs are assessed against human-validated rubrics structured into five stages: Data Loading, Data Processing, Modeling or Visualization, Output Formatting, and Output Saving. Two evaluators manually rate programs based on these rubrics, providing normalized scores.

#### 3.4. Experimental Setup

The study evaluates five state-of-the-art LLMs: three open-weight (Llama-3.1-Instruct-70B, 405B; Mistral-Large-2) and two proprietary (GPT-4o, Claude-3.5-Sonnet). OpenAI o1-preview is also evaluated as a reference. All experiments use 0-shot prompting with standard hyperparameters (temperature=0.2, top_p=0.95), except for OpenAI o1 which uses its default settings.
Three agent frameworks are tested:
- **Direct Prompting:** The LLM generates the program in one pass without environmental interaction.
- **OpenHands CodeAct:** A generalist agent framework (CodeActAgent v1.9) that allows LLMs to interact with Python interpreters, bash shells, and web browsers.
- **Self-Debug:** A framework where LLMs iteratively execute their generated programs, access results, and revise their code based on feedback. The authors re-implemented it with specific modifications for this benchmark.
Each task is repeated with three independent runs, and the best run is selected based on a prioritized order of metrics (SR, VER, CBS, Cost) to ensure robust performance reporting.

### 4. Main Findings and Results

The comprehensive evaluation on ScienceAgentBench yields several critical insights into the current capabilities and limitations of language agents for scientific discovery:

#### 4.1. Overall Performance and Limitations

The most striking finding is that current LLMs and agent frameworks achieve only **low-to-moderate task success rates**. Even the best-performing agent configuration, **Claude-3.5-Sonnet with self-debug and expert-provided knowledge, solved only 34.3% of the tasks**. Without expert knowledge, this dropped to 32.4%. While OpenAI o1-preview showed better performance at 42.2% with self-debug, it came at a significantly higher cost (over 10 times more) and uses more inference-time compute. These results directly challenge the ambitious claims of end-to-end scientific discovery automation made by some recent works.

#### 4.2. Direct Prompting vs. Self-Debug: The Power of Execution Feedback

The study clearly demonstrates the necessity of execution feedback for LLMs to generate robust scientific programs.
- **Direct prompting** alone performed poorly, with Claude-3.5-Sonnet achieving only 16.7% SR independently and 20.6% with knowledge. Failures were often due to correct high-level structures but implementation-level errors (missing steps, incorrect API usage).
- **Self-debug** dramatically improved performance, nearly doubling Claude-3.5-Sonnet’s success rate (16.7% to 32.4% without knowledge). This highlights the crucial role of iterative code execution and revision for complex programming tasks.

#### 4.3. OpenHands CodeAct vs. Self-Debug: Cost-Performance Trade-offs

The comparison between OpenHands CodeAct and self-debug revealed important considerations for agent design:
- **Self-debug generally outperformed OpenHands CodeAct** for four out of five LLMs. GPT-4o was the sole exception, demonstrating better leverage of OpenHands' more complex tools, like the web browser. Other LLMs struggled with specialized bash commands in OpenHands, leading to inefficiency and higher costs.
- Most notably, Claude-3.5-Sonnet using self-debug achieved 10.8% higher SR (32.4% vs. 21.6%) while costing **17 times less** than OpenHands CodeAct (without expert knowledge). This finding strongly resonates with recent research advocating for agent designs that jointly consider costs and capabilities to maximize practical utility, suggesting that a large action space with complex tools is not always beneficial if LLMs cannot effectively utilize them.

#### 4.4. Impact of Expert-Provided Knowledge

Expert-provided knowledge generally led to **consistent improvements in Success Rate (SR) and CodeBERTScore (CBS)** for most agents, indicating that this information helps agents generate more semantically correct and useful programs. However, it paradoxically led to **decreases in Valid Execution Rate (VER)** for most agents.
- This can be attributed to two main reasons: (1) The expert knowledge sometimes introduced less familiar, specialized tools, leading to incorrect API usage or hallucinations. (2) When provided with knowledge, agents attempted more concrete modeling or analysis, which, if flawed, resulted in unexecutable programs, whereas without knowledge, they might have produced simpler but executable (though less meaningful) code.
- Despite the VER decrease, the authors argue that expert knowledge is valuable from a scientist's perspective, as it guides agents toward generating more scientifically relevant programs, even if they require more debugging.

#### 4.5. Analysis of Task Failures

A deeper analysis of the failures revealed specific bottlenecks (Figure 3):
- **Complexity:** Agents struggled significantly with tasks corresponding to longer, more complex gold programs. Over 75% of succeeded tasks were simpler (below the average 58.6 lines of gold programs).
- **Discipline-Specific Challenges:**
 - **Bioinformatics and Computational Chemistry:** High failure rates in data processing and model development due to highly heterogeneous data (cell images, molecules, genes) and the difficulty in configuring complex models (e.g., Convolutional or Graph Neural Networks).
 - **Geographical Information Science and Psychology & Cognitive Neuroscience:** Failures primarily stemmed from the agents' inability to correctly use discipline-specific tools (e.g., Geopandas, Biopsykit), leading to incorrect or hallucinated API calls.

#### 4.6. Human Evaluation Validation

Rubric-based human evaluation (Figure 4) corroborated the automatic metrics, showing that **data loading and data processing** are critical differentiating stages. Successful programs almost universally had high scores in data loading, while failed programs often struggled in these initial stages. This human assessment validates that agents often get stuck at foundational steps, preventing successful completion of downstream tasks like modeling or visualization.

In conclusion, while language agents show promise as code generators, they are far from achieving autonomous scientific discovery. Their current limitations lie in handling complex, heterogeneous scientific data, effectively using domain-specific tools, and producing robust, executable code without extensive iterative debugging.

### 5. Significance and Potential Impact

ScienceAgentBench represents a significant contribution to the field of AI for science and language agent research, with several important implications:

#### 5.1. Setting a New Standard for Assessment

The most immediate impact of ScienceAgentBench is its role in establishing a **new, rigorous standard for evaluating language agents** in data-driven scientific discovery. By moving beyond vague claims of "end-to-end automation" and focusing on the granular, real-world tasks essential to scientific workflows, the benchmark provides a much-needed objective framework. This structured approach to assessment is crucial for understanding the true strengths and limitations of current LLM-based agents, preventing overhyped claims and guiding future research more effectively.

#### 5.2. Highlighting Current Limitations and Guiding Future Research

The comprehensive experimental results unequivocally demonstrate that current language agents, even the most advanced ones, are **not yet capable of fully automating complex scientific tasks or entire research pipelines.** This finding is critical as it challenges prevailing narratives and redirects attention to areas where significant improvements are needed. Specifically, the benchmark highlights key bottlenecks:
- **Robust Data Handling:** Agents struggle with heterogeneous and complex scientific datasets, particularly in data loading and preprocessing.
- **Domain-Specific Tool Usage:** A significant weakness is the inability to effectively integrate and correctly use specialized libraries and tools common in various scientific disciplines.
- **Iterative Refinement and Reasoning:** While "self-debug" shows promise, agents still need better reasoning and self-verification capabilities to produce semantically correct and executable programs consistently.
- **Cost-Effectiveness:** The trade-off between performance and API cost, as seen in the comparison between OpenHands CodeAct and Self-Debug, emphasizes the need for more efficient agent designs.

These identified limitations serve as a clear roadmap for future research in developing more capable and reliable scientific language agents.

#### 5.3. Augmenting Human Scientists' Productivity

Instead of full automation, the paper strongly advocates for language agents to serve as **"science co-pilots."** The authors highlight the practical value: while writing a scientific program from scratch or adapting existing code can take human scientists hours, an agent can generate a meaningful draft within minutes. This potential to significantly **augment human scientists' productivity** by offloading tedious programming tasks, even if imperfectly, is a profound impact. ScienceAgentBench will thus be a necessary testbed for developing agents that can genuinely assist researchers, allowing them to focus on higher-level reasoning and experimentation.

#### 5.4. Ethical Considerations and Responsible AI Development

The paper includes a transparent ethics statement, demonstrating a commitment to responsible AI development in scientific contexts. It explicitly addresses potential safety concerns, particularly in Bioinformatics and Computational Chemistry tasks. The authors clarify that the benchmark's tasks focus on property prediction, feature analysis, and visualization, **not chemical synthesis or generation of dangerous substances**, and agents are not connected to laboratory hardware. By clarifying these boundaries, the paper contributes to the ongoing discussion about the safety of AI in science and emphasizes the need for developers to consider potential risks and implement effective intervention mechanisms for users.

#### 5.5. Extensibility and Community Resource

ScienceAgentBench is designed to be extensible, encouraging future work to expand its coverage to other programming languages, disciplines, and more complex tasks/datasets. Its open availability (including detailed data collection protocols, evaluation scripts, and human-validated rubrics) positions it as a valuable, continually evolving resource for the research community, fostering collaborative progress in the development and assessment of language agents for scientific discovery.
