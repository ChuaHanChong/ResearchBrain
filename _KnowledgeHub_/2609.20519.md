# SoL-Pi: Recursively Scaling Auto-Research Loops for Efficient Agent Harness

> [!summary] Summary
> SoL-Pi is a coding-agent harness built by an RSI-inspired auto-research loop. Research AIs mine execution traces across 535 executable environments, then propose and harden about 150 candidate changes behind fixed capability and efficiency gates, while held-out evaluation stays isolated. Four retained mechanisms cut EdgeBench token traffic by 44.7-49.0% and API cost by about one third, at scores near the Pi baseline.

## Problem

- Most agent-efficiency work lowers per-token cost through faster kernels, quantization or cheaper models, ignoring how the harness itself wastes tokens across long agent trajectories.
- Hand-optimizing a harness is costly: tool use, context, delegation and termination are coupled, so local fixes shift costs downstream and engineers must inspect long traces manually.
- Automated harness search such as Meta-Harness and recursive harness self-improvement tends to overfit its search tasks, yielding only marginal gains once evaluated on genuinely held-out tasks.

## Method

- ==Broad-to-deep auto-research funnel==: 152 directions across six proposal families, ==Oracle Analysis== of trajectories, ==Ralph-Loop== implementation with independent review, map-reduce trace analyzers, and disposable isolated search lineages.
- Frozen two-gate selection over 535 environments (495 GitHub issue-PR repository tasks, 40 verifier-driven tasks): capability within predeclared tolerance plus an efficiency gain, with EdgeBench held out and no feedback.
- Four retained mechanisms: **Action Fusion** merges edit and run into one call; **Online Context Compact** cost-gates compaction at plan steps; **ObservationPack** swaps large outputs for handles; **Evidence-Preserving Reducer** verifies small-model log receipts.

## Results

- On EdgeBench with GPT-5.6 Sol, the full stack uses **1.10B** tokens, **49.0%** fewer than Pi, and costs **$894** versus **$1,339**, scoring **42.0** versus **44.8**; it is **50%** cheaper than Codex.
- Transferred unchanged to Opus 5, it cuts tokens **44.7%** and cost **33.5%** versus Pi at **94.3%** of Pi's score; the best single mechanisms raise scores to **47.2** and **50.5**.
- Terminal-Bench 4: **15** versus **18** tasks solved, but **26.3%** lower cost than Pi; IMO 2026 has the lowest cost per passed problem (**$20.90**); a 20-worker swarm reaches **1,127** cycles at **26.8%** lower cost.

## Takeaways

> [!tip] Key Insights
> - Harness design is an orthogonal, training-free efficiency lever: how actions, observations and context are mediated can roughly halve tokens without changing model weights or serving infrastructure.
> - Strictly isolate held-out evaluation from search and fix acceptance metrics upfront; otherwise automated self-improvement patches validation failures into task-specific tricks that fail to transfer.
> - Judge total task cost, not cache reuse: compaction breaks cached prefixes and raises cache writes yet still cuts spend, though aggressive efficiency stacks can trade away some task score.

## Detailed Report

### 1. Position Within the Broader Research Landscape

SoL-Pi addresses the efficiency of long-running language-model agents. Recent agent systems have progressed from generating isolated code completions to conducting extended sequences of planning, file operations, testing, tool use, and revision. These systems are often controlled by an agent “harness”: the software layer that manages prompts, context, tools, observations, delegation, verification, and termination. As agent trajectories become longer, repeated context and tool interactions can create substantial token and API costs.

Most existing efficiency research operates at other layers of the system. Infrastructure work improves attention kernels, memory management, serving throughput, or caching. Model-level approaches use quantization, compression, routing, or smaller models. SoL-Pi explores a complementary systems-level approach: modifying the harness without retraining the underlying language model.

The work is also situated within research on automated agent design and recursive self-improvement (RSI). Previous systems have searched over prompts, workflow structures, executable harnesses, or modular agent components. Meta-Harness and related work have shown that harness changes can improve agent behavior, while other studies have reported that evolved harnesses may overfit development tasks and fail to transfer to unseen environments. SoL-Pi responds to this generalization concern by separating development search from final evaluation and by using many heterogeneous environments to discover mechanisms intended to transfer across tasks and model backends.

The paper therefore contributes to three intersecting areas: long-horizon agent efficiency, automated harness optimization, and RSI-inspired research automation. Its central claim is that an automated research process can discover reusable efficiency mechanisms rather than merely produce task-specific prompt modifications.

### 2. Objectives and Motivation

The primary objective is to reduce the token traffic and API cost of coding and research agents while maintaining comparable task performance. The authors focus on harness-level inefficiency because long trajectories commonly contain repeated actions and information. Examples include issuing a file-edit command followed by a separate test command, sending the same large tool output repeatedly, retaining context after a subtask is complete, or presenting lengthy logs when only a few pieces of evidence are needed.

The authors identify several difficulties in manually optimizing such systems. Harness components are interdependent: reducing context may remove information needed later, compressing logs may obscure an error, and saving one model call may increase work elsewhere. A locally beneficial change can therefore lower overall performance or shift costs to later stages. Manual optimization also requires inspecting large numbers of execution traces and identifying patterns across different repositories and tasks.

SoL-Pi is motivated by the idea that an AI research agent can perform this inspection and experimentation at scale. Rather than optimizing one benchmark directly, the system searches across diverse executable environments for mechanisms that reduce declared efficiency metrics while preserving capability. The paper emphasizes three design principles. First, breadth and depth are combined: many candidate ideas are explored, while promising ones receive repeated implementation and review. Second, independent validation prevents held-out results from being used to patch candidates after failure. Third, isolated search lineages allow many experiments to run independently without one failed candidate corrupting the others.

A further objective is cross-model transfer. The mechanisms are developed using GPT-5.6 Sol and then evaluated without adaptation on Opus 5. This tests whether the learned harness changes depend narrowly on the behavior of the model used during search.

### 3. Methodology and Approach

#### 3.1. Auto-Research Pipeline

SoL-Pi begins with 152 proposed directions organized into six families: context, progress, tools, delegation, prompts and policies, and improvement and evaluation. An oracle-analysis stage examines execution trajectories from the base Pi harness to identify avoidable work, such as repeated actions, context growth, oversized observations, or insufficient diagnostic signals.

Each proposal enters an isolated, disposable research lineage. The lineage follows an iterative cycle: propose a change, implement it, run a fixed experiment, inspect the results, and retain, revise, or discard the candidate. The implementation process includes an independent review stage. Failed reviews trigger revision before evaluation. Independent analyzers examine trajectories, and a reducer combines their findings into a candidate-level summary.

Capability and efficiency metrics are fixed before experimentation. A candidate must remain within predeclared capability tolerances and improve at least one efficiency metric. Candidates that pass both conditions are selected according to a nondominated, or Pareto-style, criterion. This prevents the optimizing agent from changing the acceptance rule to favor its own proposals.

The search covered 535 executable development environments: 495 repository tasks derived from GitHub issue–pull-request pairs and 40 verifier-driven synthetic tasks. Repository environments use pre-fix repositories with hidden patches and regression tests. The test must fail before the accepted patch and pass afterward. Synthetic environments use executable verifiers and permit multiple valid solution paths. Across the search, the authors report approximately 150 proposed directions, 500 environments, more than 3,000 runs, and over 60,000 agent–environment interactions.

#### 3.2. Retained Mechanisms

Four mechanisms were selected and integrated into SoL-Pi.

**Action Fusion** combines a mutation operation, such as editing a file, with an immediately subsequent command, such as running a test or build. This can reduce three API calls to two. It is not used when the agent must inspect the mutation result before deciding what to do next.

**Online Context Compact** evaluates whether context compaction is worthwhile at plan-step completion. It estimates remaining requests, context growth, and the cost of rewriting the prompt cache. Compaction is applied only when projected input savings exceed the estimated rewrite cost or when the context approaches its limit.

**ObservationPack** handles large tool outputs. Outputs larger than 10 KiB are stored locally and transmitted in full during the first two provider requests. From the third request onward, the harness supplies a stable handle, the original size, and a short excerpt containing complete head and tail lines. The agent can retrieve exact portions using the handle.

**Evidence-Preserving Reducer** compresses build and test logs of at least 4 KiB. A lower-cost model extracts key evidence into a structured receipt. A deterministic verifier checks the receipt’s schema, source hash, status, exact quotations, and size. If verification fails, credentials may be exposed, or no size reduction is achieved, the original log is retained. File reads and search results bypass this reducer.

#### 3.3. Evaluation Design

EdgeBench is reserved for held-out evaluation. Of the 51 publicly available EdgeBench tasks, 11 are used for one-way acceptance of frozen candidates and 40 are reserved for final evaluation. The source, configurations, metrics, tolerances, and acceptance criteria are frozen before evaluation, and held-out outcomes do not return to the search process.

The authors also evaluate on 63 CPU-only Terminal-Bench 4 tasks, six IMO 2026 problems requiring Lean 4 verification, and a two-hour kernel-optimization agent swarm. Comparisons include native Codex and Claude Code harnesses, the Pi baseline, and SoL-Pi. Costs use API prices reported as of August 17, 2026.

### 4. Main Findings and Results

#### 4.1. EdgeBench

On GPT-5.6 Sol, the complete efficiency-oriented SoL-Pi stack records 1.099 billion tokens, compared with 2.154 billion for Pi, representing a 49.0% reduction. Its average score is 42.003, compared with Pi’s 44.833, while API cost falls from $1,339 to $894, a 33.2% reduction. Codex records a lower average score of 34.738 at a cost of $1,787.

On Opus 5, SoL-Pi records 1.310 billion tokens compared with Pi’s 2.370 billion, a 44.7% reduction. Its average score is 42.224 versus 44.756 for Pi, and cost decreases from $1,741 to $1,158, or 33.5%. Relative to the native Claude Code harness, which costs $2,535, the reported cost reduction is 54.3%.

The paper also reports a performance-oriented configuration using the strongest individual mechanism rather than the complete efficiency stack. On GPT-5.6 Sol, ObservationPack raises the average score to 47.208 while reducing token traffic by 6.1% relative to Pi. On Opus 5, Action Fusion produces a score of 50.482. These results indicate that the configuration optimized for minimum cost is not identical to the configuration optimized for maximum benchmark score.

#### 4.2. Other Benchmarks

On Terminal-Bench 4, Codex and Pi each solve 18 of 63 tasks, while SoL-Pi solves 15. However, SoL-Pi reduces total model cost to $211.12, compared with $286.45 for Pi, and reduces cost per solved task from $15.91 to $14.07.

On the six IMO 2026 problems, Pi and SoL-Pi each pass three problems. SoL-Pi costs $62.69 in total, compared with $75.95 for Pi, reducing cost per passed problem from $25.32 to $20.90. These results support cost reductions outside EdgeBench, although SoL-Pi does not improve completion counts in these evaluations.

#### 4.3. Agent Swarm

In the kernel-optimization experiment, a 20-worker SoL-Pi swarm reaches 1,127 cycles at a cost of $60.11. A 20-worker Pi swarm reaches 1,366 cycles at $82.12, while a single Codex agent reaches 1,333 cycles at $39.20. Thus, SoL-Pi improves the swarm’s result and reduces swarm cost by 26.8% relative to the Pi swarm, but it remains more expensive than the single-agent configuration. All final candidates pass correctness checks.

#### 4.4. Mechanism Behavior and Limitations

Each individual mechanism reduces total token traffic under both tested backends. Trigger rates and intensities are generally lower on Opus 5 than on GPT-5.6 Sol, suggesting that the mechanisms’ activation behavior depends partly on the model used during search. Nevertheless, every configuration reduces token efficiency costs on the tasks where it activates. The full stack also shows evidence of complementary behavior, although the authors note that the triggered-subset comparisons do not fully isolate causal interactions.

### 5. Significance and Potential Impact

SoL-Pi demonstrates that agent-harness design can be treated as an automated research problem rather than solely as manual engineering. Its results suggest that substantial cost reductions can be obtained without model retraining, particularly in long-horizon coding and tool-use settings where repeated context and observations accumulate.

The separation between development and held-out evaluation is important for assessing transfer. The cross-backend results provide preliminary evidence that mechanisms developed on one model can remain useful on another. If validated more broadly, this could support reusable harness components for coding agents, autonomous research systems, and multi-agent workflows.

The work also presents efficiency as a possible resource for further improvement: a cheaper harness could allow future research loops to evaluate more environments and candidate mechanisms under a fixed budget. However, the paper does not establish a scaling law for this recursive process. Its evidence is limited to two model backends, selected benchmarks, and a search process centered on one base harness. The authors also acknowledge that mechanisms trigger less frequently on the second backend and that systematic comparisons of search breadth, depth, and cost remain unresolved. Therefore, SoL-Pi is best interpreted as evidence for the feasibility of scalable harness optimization, rather than as a complete demonstration of recursive self-improvement.
