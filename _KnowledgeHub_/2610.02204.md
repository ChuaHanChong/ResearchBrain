# Reconstruct, Practice, Go Real: Guided Self-Improvement for Embodied Agents

> [!summary] Summary
> RPG (Reconstruct, Practice, Go Real) improves a robot's Agent-as-Policy execution system, a shared skill library plus system prompt, without updating model weights. It builds simulation practice tasks from an offline dataset, diagnoses failures by contrasting runtime and privileged-state rollouts with video analysis, and keeps revisions only if they pass cross-task validation. Success on 22 held-out tasks rises from 28.6% to 95.0% over 15 rounds, and the frozen system succeeds in 30/30 physical trials.

## Problem

- Code-as-Policy programs execute efficiently but depend on explicit logic and perception interfaces, so robust checks such as grasp success are hard to specify symbolically.
- Agent-as-Policy keeps the multimodal model in the control loop for flexible visual reasoning, but frequent model calls make low-level decisions slow.
- Building reliable robot capabilities needs heavy human effort for skills and rewards, and prior skill-library learners risk shared revisions that help one task but regress others.

## Method

- Reconstruct: a ==Constructor agent== in **RPG** mines the ABC offline dataset's videos and descriptions to build MuJoCo ==practice tasks== with ==check_success evaluators==, covering partial or analogous manipulations.
- ==Privileged Agent== plus ==Video Analyzer==: a same-model agent given simulator state runs ==paired rollouts==, and the analyzer compares them with runtime traces and source videos to localize the first failure.
- ==Implementor and Merger== with a ==cross-task gate==: candidate skill and system-prompt revisions are accepted only if mean success rises and no task drops more than 20 points, then merged and retested.

## Results

- On **220** held-out episodes across **22** tasks, RPG reaches **95.0%**, beating ASPIRE at **75.5%**, RATs at **41.8%**, and CaP-Agent0 with GPT-6 Astra Pro at **60.0%**.
- Five-round ablations: full RPG scores **78.2%** versus **51.8%** without the Video Analyzer and **50.9%** without the Privileged Agent. A library-only swap raises four-task success from **65.0%** to **92.5%**.
- On the physical YAM robot, frozen RPG succeeds **30/30** across drawer storage, towel folding and bowl handover, while GPT-6 CaP-Agent0 completes only **4/10** drawer and **1/10** handover trials.

## Takeaways

> [!tip] Key Insights
> - Improving the persistent execution system (skills and prompt) can beat swapping in a stronger runtime model: a Flash-class model with refined skills outperformed frontier-model baselines.
> - Privileged-state rollouts are useful as a diagnostic contrast, not just a training signal. Paired with video analysis, they turn observed failures into concrete skill repairs.
> - Shared-skill edits can cause regressions on other tasks, and one prompt change produced a 30.5-point gain in a single round, so validate revisions at task level and attribute gains carefully.

## Detailed Report

### 1. Overview

Placing a bottle into a bin is not finished when the gripper reaches the receptacle. A robot can move its gripper near the bin and still collide with the wall, or release the bottle before it is safely inside. In this case, the system diagnoses the failed attempt. It then revises the reusable pick-and-place procedure to check the route and placement, and tests that change. In five development trials, success rose from 1/5 to 5/5. This is an illustrative development result, not held-out performance. The method is RPG, and it lets robot skills improve through practice without retraining the underlying model.

A five-trial development example, not a held-out result or physical-robot trial. The Runtime Agent calls `pick_and_place_tall_object()` and the bottle collides with the bin wall. The diagnosis identifies insufficient path checking. It proposes checking the full path, releasing only when the bottle is safely inside, and verifying placement. With the revised procedure, success changes from 1/5 to 5/5. A candidate must improve mean task success without any task dropping more than 20 percentage points. The merged system must pass the same validation.

### 2. From a failure to a shared skill

RPG first builds practice tasks. A Constructor uses task descriptions and videos from an offline dataset, here ABC, to identify capabilities and build related simulation tasks. Task definitions and success checkers are fixed before practice, and humans check those evaluators.

During practice, three components examine each attempt:

- **Runtime Agent.** It attempts tasks using only deployment-available observations.
- **Privileged Agent.** It uses the same model and skills in a separate episode from the same initial state, and it can also see simulator state.
- **Video Analyzer.** When available, it compares the two agents' traces with relevant source videos to identify the first observed failure and recommend a correction. It does not edit the system.

The Implementor then adds or revises a shared skill, or revises the system prompt.

Each change must pass a check before it is kept:

1. Candidates are tested on complete Runtime Agent episodes across all 22 tasks.
1. A candidate is eligible only if mean success rises and no task loses more than one success out of five.
1. A Merger combines the eligible changes, and the combined system is tested again.
1. If the combined system fails validation, the previous version is kept.

Model weights, task definitions, and the harness remain fixed during practice.

### 3. What the evaluations establish

The benchmark covers 22 manipulation tasks. Each task has ten held-out initializations, so mean task success equals the pooled 220-episode success rate. Systems were evaluated after practice finished, on seeds excluded from improvement and checkpoint selection.

RPG's task success rose from 63/220 (28.6%) after round 1 to 209/220 (95.0%) after round 15. In the authors' reported evaluation, that exceeded [[2607.00272|ASPIRE]] at 75.5% and CaP-Agent0 with GPT-6 Astra Pro at 60.0%.

The comparison does not match compute:

- RPG and ASPIRE both used Gemini 3.8 Flash with up to 30 turns.
- CaP-Agent0 could use up to 50 turns.
- Practice rounds are not matched computational budgets.

The curve is also not strictly monotonic. Held-out success fell by one at rounds 6 and 14. The largest jump came between rounds 3 and 4, a 30.5-point gain that coincided with a prompt-only change. That change also altered how the observation budget was used, so the gain is not attributed to one instruction.

A controlled comparison tests whether skill-library revisions matter. It held the runtime model, prompt, perception implementation, and episode budgets fixed while the library changed. On four tasks with ten paired initializations each, success rose from 26/40 to 37/40. This shows skill revisions improving complete-task performance in that setup. It does not show that every skill update helps every task.

On a physical robot, the frozen system succeeded in all 30 trials, ten each on drawer placement-and-closure, towel folding, and bowl transfer. All methods received common calibration and hardware adaptation. Autonomous retries were allowed within each trial, but no human assistance or system revision was allowed. The physical towel-folding criterion differs from the simulation criterion and is not intended to match its difficulty. In simulation, standard towel folding reached only 3/10 on the final round.

### 4. Reusable skills, not retraining

Shared skill code and the instructions for using it can be targets for persistent robot improvement while model weights stay fixed. The paper does not establish fewer tokens, fewer attempts, or shorter elapsed time for RPG. Human setup, evaluator checks, the decision to stop practice, and hardware adaptation remain part of the process.
