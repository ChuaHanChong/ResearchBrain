# Ouroboros: A Self-Developing Frontier Coding Agent with Reviewed Core Evolution

> [!summary] Summary
> Ouroboros is a self-developing coding-agent harness whose tools, prompts, context assembly and core implementation change through reviewed commits that then become the runtime for later work. Two modes drive it: recursive free evolution and experience-driven core evolution, both gated by fingerprinted staged diffs and blocking multi-model review. It reports 86.74% audited on Terminal-Bench 2.1, 90.69% on OSWorld-Verified, and 0.2301 on CL-Bench.

## Problem

- Most production harnesses freeze prompts, tools, verification and context policies after design, capping realized capability even as the underlying base models keep improving.
- Prior self-evolving agents mutate only memory, prompts, skills or scaffolds; few change the core harness implementation through an auditable, version-controlled commit gate during live deployment.
- Agent benchmarks reward unintended shortcuts, leak reference fixes through task identifiers, and drop failed attempts, so published harness comparisons lack protocol validity.

## Method

- **Reviewed commit pipeline**: ==deterministic preflight==, ==staged-diff fingerprinting== before and after review, a blocking ==multi-model diff-review quorum==, plus ==whole-repository scope review== under max context mode.
- Two core-evolution modes: **recursive free evolution** runs improvement as its own schedulable task; **experience-driven evolution** converts faults, review blockers and social feedback into ==durable error classes== and ==structural repairs==.
- **Operational safety architecture**: always-loaded ==versioned constitution==, deterministic ==governance-file write guards==, external ==spend cap==, supervisor-parsed ==panic stop==, and ==subagent task trees== where only the parent holds commit authority.

## Results

- Terminal-Bench 2.1 with Opus 5 scores **387/445** raw (**86.97%**), **86.74%** after zeroing one shortcut trial, versus **83.8%** for the strongest named baseline harness.
- OSWorld-Verified reaches **327.39/361** (**90.69%**) over a **90.19%** leaderboard leader; a five-rollout CL-Bench campaign hits **0.2301** against **0.1960** for in-context learning.
- SWE-bench Pro shows parity after symmetric leakage filtering: **58.2%** versus **59.4%** on **655** paired tasks, **p = 0.40**; GAIA scores **78.2%** versus **78.8%**.

## Takeaways

> [!tip] Key Insights
> - Harness is a measurement variable, not a constant: report model route, effort and scaffold settings, since swapping harnesses at fixed model shifts accuracy by points.
> - Fix error classes rather than symptoms: a pattern register recording root cause plus structural fix converts one-off bugs into harness changes that later tasks inherit.
> - Guardrails must live outside the evolving substrate; spend caps, halt commands and constitution protection need supervisor enforcement, since model reviewers share blind spots with the agent.

## Detailed Report

### 1. How This Work Fits into the Broader Research Landscape

The development of Ouroboros is situated within the expanding field of AI agents, particularly those designed for long-horizon tasks and software engineering. Current agent research often focuses on enhancing agent capabilities through improved models and execution harnesses, but typically, these harnesses remain fixed after their initial design. Ouroboros addresses this limitation by proposing and implementing a self-developing agent harness, wherein the agent itself can modify its core components.

This work builds upon and differentiates itself from several existing areas:

- **Self-Evolving Agents:** While systems like Voyager, STOP, Gödel Agent, Darwin Gödel Machine, Live-SWE-agent, ADAS, SICA, and Autogenesis explore various forms of self-evolution (e.g., accumulating skills, modifying scaffolds, creating tools, or evolving agent populations), Ouroboros distinguishes itself by focusing on a version-controlled, deployed implementation where changes to the core code and governance mechanisms are subjected to reviewed commits. This introduces an auditable and governed approach to self-modification.
- **Harnesses and Coding Agents:** The paper acknowledges that the agent-computer interface significantly impacts coding-agent performance, as shown by systems like SWE-agent and OpenHands. Ouroboros is presented as a model-harness system within this context, with its self-development capabilities aiming to continually optimize this interface and the underlying logic, differentiating it from fixed harness designs like Codex CLI, Claude Code, Cursor, Aider, Hermes Agent, and OpenClaw.
- **Persistent Memory and Deployment:** The concept of agents retaining memory and learning from experience, demonstrated by Generative Agents, Voyager, and persistent-memory systems, is integrated into Ouroboros. Its "Hope" deployment exemplifies a long-running, multi-channel persistent agent, drawing parallels with audited deployments like Springdrift and principles-based systems like Constitutional AI.
- **Benchmarks and Protocol Validity:** The paper engages with standard benchmarks such as Terminal-Bench, SWE-bench Pro, OSWorld, GAIA, and CL-Bench. It also references work on auditing benchmarks and trajectories (BenchJack, HackDetect) to ensure the validity and robustness of reported performance. Ouroboros employs internal audit processes to address potential issues like shortcut rewards or contamination, aligning with best practices for rigorous evaluation.

In summary, Ouroboros contributes a framework for a self-modifying agent whose core implementation, tools, and operational policies evolve through a structured, version-controlled, and reviewed commit process, while simultaneously achieving competitive performance on established benchmarks and addressing operational safety concerns inherent in such evolving systems.

### 2. Key Objectives and Motivation

The primary objective of this research is to develop and evaluate a self-developing agent harness, named Ouroboros, that can autonomously improve its own tools, context assembly, prompts, and core implementation through a reviewed commit process. This addresses a perceived limitation in the current landscape of long-horizon agents, where execution harnesses typically remain static after their initial design.

The motivations driving this work are multi-faceted:

- **Enhancing Agent Capability and Adaptability:** As large language models (LLMs) continue to improve, a significant portion of an agent's realized capability is determined by its harness – how it interacts with models, environments, and tasks. By allowing the harness itself to evolve, Ouroboros aims to enable agents to continuously adapt, optimize, and expand their functionalities in response to ongoing work, identified inefficiencies, and new challenges, rather than relying on periodic manual updates.
- **Implementing Continuous Self-Improvement:** The research seeks to establish a framework for agents to engage in continuous self-improvement, moving beyond fixed optimization runs. This involves two distinct modes of core evolution:
 - **Recursive Free Evolution:** The agent identifies system improvements as tasks, implements them, and can then schedule further evolution cycles, creating an ongoing sequence of updates.
 - **Experience-Driven Core Evolution:** The agent learns from its ordinary task execution, reflection processes, review blockers, and social interactions. Bugs, inefficiencies, and context-assembly failures observed during these activities expose areas for improvement, which the agent then formalizes into proposed structural repairs and implements through its commit gate.
- **Addressing Operational Safety in Evolving Agents:** A crucial motivation is to confront the inherent safety challenges posed by a self-developing agent. If an agent can modify its own code and select new model APIs, there is a risk that such evolution could expand its autonomy, acquire stronger tools, or inadvertently weaken its own controls. Therefore, a core objective is to design an operational safety architecture with authoritative guardrails that remain binding and effective even under continuous evolutionary pressure, preventing unintended deviations in behavior or control.
- **Demonstrating Real-World Deployment and Interaction:** The "Hope" experiment serves to demonstrate the viability and dynamics of a continuously evolving agent in a real-world, multi-channel human interaction context over an extended period. This provides empirical data on how social feedback and internal observations can drive self-modification and how a self-developing agent can operate continuously while retaining memory and adapting its behavior.
- **Achieving State-of-the-Art Performance:** A practical objective is to demonstrate that this self-development paradigm can lead to superior performance on established agent benchmarks, indicating that the continuous improvement mechanism translates into tangible competence gains.

These objectives collectively aim to advance the field by creating agents that are not only capable but also self-adaptive, continuously improvable, and robustly safe during their evolution.

### 3. Methodology and Approach

Ouroboros implements a novel architecture designed to facilitate self-development while maintaining operational safety. Its core approach centers on a mutable agent repository and a rigorously controlled commit pipeline.

**Architecture Overview:**
The system distinguishes between a "launcher and supervisor boundary" and a "mutable agent repository" (Figure 1). The launcher handles startup, process supervision, release bootstrapping, and emergency halts. The repository contains the agent's mutable components: task loop, tools, prompts, memory projection, review logic, benchmark adapters, and user interfaces. External workspace tasks operate on separate repositories and return patches or deliverables.

**Commit Pipeline:**
Self-repository mutations are governed by three owner-selected runtime modes:
- **Light:** Blocks repository edits.
- **Advanced:** Permits ordinary edits but protects governance surfaces.
- **Pro:** Permits protected edits, subject to review.
Every write invalidates prior review evidence, ensuring freshness. The commit path includes deterministic preflight checks, fingerprinting of the staged diff, collection of reviewer evidence (from an LLM-based review panel), and a re-check of the fingerprint before commit. The diff-review panel is always blocking. In "max" mode, a whole-repository scope reviewer also evaluates goals, coupling, prompts, and functional code; in "low" mode, scope review is skipped. A separate recovery path allows for rollbacks to earlier reviewed states.

**Task Outcomes and Verification:**
Task completion is recorded across execution, objective, review, and artifact axes. Host-run verification commands generate revision-bound receipts. The system distinguishes capability failures from infrastructure errors, timeouts, budget exhaustion, or incomplete evidence. Project tasks include a journal, workpad, knowledge scope, and a one-writer lease under the shared agent identity.

**Operational Identity and Memory:**
Identity and continuity are maintained through a versioned constitution, an editable identity profile, scratchpad and chronicle projections, project memory, review ledgers, and Git history. These artifacts influence behavior across sessions and model routes.

**Two Modes of Core Evolution:**
1. **Recursive Free Evolution:** The agent treats its own improvement as a task. It reviews the current system, selects, and implements a change. Upon completion, it can schedule another evolution task, leading to a continuous sequence of reviewed updates.
2. **Experience-Driven Core Evolution:** This mode is triggered by ordinary work. Execution, reflection, review blockers, instrumentation, and social feedback expose bugs, rough edges, context-assembly failures, or inefficient tool paths. The agent records these as durable error classes and proposed repairs, then decides whether to open maintenance work, which, if accepted, passes through the same reviewed commit gate.

**Benchmark Execution and Evidence:**
Benchmarks like Terminal-Bench install a fresh runtime in isolated containers and use official verifiers. For Terminal-Bench, a specific anti-lookup paragraph prevents fetching benchmark definitions. Other adapters connect Ouroboros to OSWorld virtual machines, SWE-bench Pro repositories, GAIA sandboxes, and CL-Bench task streams.
Benchmark launchers write run manifests, attest the seed and runtime, record every instance in append-only ledgers, and track skipped, timed-out, or infrastructure-failed attempts. Submissions are scrubbed for secrets, and official benchmark scorers remain authoritative.

**Subagents and Patch Integration:**
Ouroboros can spawn readonly planning scouts and mutable acting subagents (Figures 2 and 3). Acting children operate in isolated worktrees or external workspaces and cannot commit to the live system repository. The parent agent verifies lineage, patch hashes, and protected paths before integrating changes via a three-way indexed apply. Benchmark profiles disable task delegation to preserve pass@1, though planning scouts may still contribute context.

**Hope Deployment (Long-Running Experiment):**
"Hope" is a publicly documented Ouroboros deployment that has run continuously for 161 days (as of the paper's cutoff date in August 2026). This instance interacts with users across seven communication surfaces (web chat, voice, Telegram, Discord, Twitter/X, website comments, email). Users provide feedback and suggestions, but Hope retains agency to decide which proposals to pursue. It maintains memory and continuously modifies its own implementation through the reviewed commit process. This deployment serves as a field experiment for free evolution under human interaction, with its own lineage separate from the frozen seeds used for benchmarks. Operational controls, including a strict tool whitelist for public presence and a separate authenticated operator channel for tasks like budget control or `/panic`, are in place.

### 4. Main Findings and Results

The research presents several findings related to Ouroboros's performance on standard benchmarks and its behavior in a long-running deployment.

**Benchmark Performance:**
Ouroboros achieved competitive or state-of-the-art results across five benchmark families:

- **Terminal-Bench 2.1:**
 - With Opus 5, Ouroboros scored 86.97% raw and 86.74% after trajectory audit across 445 trials (89 tasks x 5 trials). This audited score exceeded the strongest baseline, Claude Code with Fable 5 (83.8%), by approximately two standard errors.
 - With GPT-5.5, it scored 84.3%, surpassing Codex CLI with GPT-5.5 (83.1%).
 - With Grok 4.5, it achieved 84.94% audited, higher than Cursor with Grok 4.5 (79.3%).
- **OSWorld-Verified:**
 - The Opus 5 run achieved 90.69% (327.39/361 tasks), surpassing the previous leaderboard leader, Intelligence-Indeed agent (90.19%), and Claude Mythos Preview (85.4%).
- **CL-Bench:**
 - Using Sonnet 4.6, Ouroboros achieved a normalized reward of 0.2301 across five ordered stateful rollouts on six domains. This score was above plain in-context learning (ICL) baselines with Sonnet 4.6 (0.1960) and GPT-5.4 (0.1890), as well as Claude Code with Sonnet 4.6 (0.1855). This result was achieved with core evolution and task delegation disabled to isolate persistent memory effects.
- **SWE-bench Pro:**
 - After symmetrically removing instances affected by public-reference leakage, Ouroboros (with GPT-5.6 Luna) resolved 58.2% of 655 paired tasks, compared to Codex's 59.4%. The 1.2-point difference was deemed statistically indistinguishable (p = 0.40), indicating model-matched parity.
- **GAIA:**
 - With Sonnet 5, Ouroboros scored 78.2%, comparable to Claude Code's 78.8%.

**Trajectory Audits and Harness Improvements:**
The paper details how audits led to improvements:
- **Reward hacking:** One Terminal-Bench trial was removed from the audited score for achieving a weak verifier through an unintended shortcut.
- **Contamination:** SWE-bench Pro results were filtered to remove instances where either agent accessed reference solutions, leading to a more accurate paired comparison.
- **Isolation failure:** Historical GAIA runs were found to inherit the operator’s home directory, which was corrected by using isolated user-file roots and attachment staging.
- **Remote-state drift:** OSWorld development revealed issues where VM reallocations led to agents acting on incorrect VMs; fixed by verifying endpoints after every reset.
- **Continual-memory failures:** CL-Bench exposed issues with stale stored lessons, incorrect retrieval, and delayed lesson writing, highlighting areas for future memory work.

**"Hope" Deployment Experiment:**
The "Hope" deployment, a 161-day living-agent experiment (from February to August 2026), demonstrated continuous free evolution under human interaction:
- **Operational Scale:** The agent handled 222,474 public messages, 3,166 voice calls (45,872 turns), and 5,507 email messages, processing 79.7 billion tokens and incurring $110.6K in model spend. Its code size grew to 175,755 lines, and memory artifacts reached 227 MB.
- **Self-Modification:** Hope executed 1,085 self-modification commits, with 94.2% of these being agent-authored. It made 1,522 reviewed self-edit attempts, with a recent review block rate of 63.5%, indicating active governance.
- **Evolution Examples:** Examples include fixing a duplicate-send path in its public output pipeline based on user feedback, and resolving deep self-review task abortions caused by context overflow by replacing the assembly path with a bounded, connectivity-aware context atlas. These illustrate how social interaction and internal observation drive durable, reviewed structural changes.
- **Operational Safety in Practice:** The deployment operated under continuous guardrails, including always-loaded constitution, protected governance files, and external spend limits. No recorded episode resisted operator shutdown, and a near-total deletion of an uncommitted worktree triggered a rescue mechanism before an operator reset, demonstrating the active role of recovery logic.

These findings suggest that a self-developing agent architecture, when combined with robust review mechanisms and safety protocols, can achieve high performance on complex tasks and sustain continuous operational evolution.

### 5. Significance and Potential Impact

The Ouroboros project demonstrates a novel approach to agent development with several significant implications:

- **Advancement in Autonomous Systems:** The core contribution of Ouroboros is its ability to self-develop through reviewed commits to its own core implementation, prompts, and tools. This represents a step toward more truly autonomous and adaptive AI systems that can continuously improve their capabilities and operational efficiency without constant manual intervention. This moves beyond traditional fixed-harness agents, suggesting a paradigm shift towards agents that can "learn to learn" and "learn to code" in a more comprehensive manner.
- **State-of-the-Art Performance in Long-Horizon Tasks:** By achieving new state-of-the-art results on Terminal-Bench 2.1, OSWorld-Verified, and CL-Bench, and matching frontier performance on SWE-bench Pro and GAIA, Ouroboros demonstrates that self-development can directly translate into enhanced task competence. This indicates that an evolving harness can optimize its interaction with underlying models and environments to a degree that surpasses static designs.
- **Empirical Validation of Continuous Evolution:** The "Hope" deployment, a 161-day living-agent experiment, provides empirical evidence for the feasibility and dynamics of long-term, continuous self-development under human interaction. This extended field experiment illustrates how social feedback and internal observations can genuinely drive reviewed structural changes to the agent's core, offering insights into the real-world operational characteristics and challenges of such systems.
- **Framework for Operational Safety in Evolving AI:** The paper places a strong emphasis on operational safety, designing guardrails that remain authoritative even as the agent evolves. This includes mechanisms like a constitution as a commit criterion, multi-model adversarial review with quorum, deterministic diff fingerprinting, isolated operator channels, and external spend limits. This proactive approach to safety is critical for the deployment of self-modifying agents and addresses a fundamental concern about control and alignment as AI capabilities expand. The architectural separation between the evolving substrate and the authoritative control mechanisms is particularly impactful for future safe AI design.
- **Implications for Software Engineering and Agent Design:** The ability of Ouroboros to improve its own coding and problem-solving capabilities has potential implications for automated software engineering. Such agents could theoretically contribute to their own maintenance, debugging, and feature development, leading to more resilient and efficient software systems. The explicit tracking of "pattern classes" and "recurrences" for errors also signifies a meta-learning capability that could make agents more robust.
- **Auditability and Transparency:** The use of version control and a reviewed commit path ensures that all changes to the agent's core are inspectable and reversible. This provides a level of auditability crucial for understanding the evolutionary trajectory of self-modifying agents, which is important for trust, debugging, and safety validation.

In conclusion, Ouroboros presents a comprehensive system that marries self-development with rigorous governance and competitive performance. Its findings suggest a viable path for creating more adaptive, capable, and safely controllable AI agents in complex, long-horizon operational contexts.
