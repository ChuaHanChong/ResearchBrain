# EMPIRIC: Experiment-Driven Learning of Residual World Models for Robot Planning

> [!summary] Summary
> EMPIRIC is a coding-agent robot that learns residual world models: Python programs that subclass a rigid-body physics engine to add missing mechanisms such as glue curing, airflow or heating, including hidden recurrent state. Bayesian inference estimates parameters and state from noisy observations, enabling uncertainty-aware planning and informative experiments. It solves all 25 simulated runs across five domains versus at most 16 for baselines, and transfers to a real robot.

## Problem

- Physics engines model rigid-body motion and contact but omit whole mechanisms like glue curing, water heating or wind; real-to-sim reconstruction recovers geometry and articulation, not these mechanisms.
- Hybrid simulators and simulation-based inference mostly fit parameters or corrections within a fixed model family, rather than adding new mechanisms with hidden state from a few noisy experiments.
- Code world models such as WorldCoder learn standalone transition programs that discard reusable engine physics, and rarely keep calibrated uncertainty over parameters and hidden state for planning.

## Method

- **Residual world models**: an agent-written Python program that subclasses the base simulator, adding parameters, recurrent hidden state such as glue cure progress, and new forces, constraints or tracked quantities.
- ==Factored Bayesian belief==: a ==mean-field posterior== over parameters from replaying the buffer, a modular posterior over base state from observations only, and recurrent state recomputed deterministically per parameter draw.
- ==Belief-averaged planning== ranks skill sequences by success rate over joint draws, ==predicate-based mutual information== selects informative experiments, and predicate execution monitoring triggers belief updates or program revision.

## Results

- **EMPIRIC** solves all **25** simulated runs versus **16** for Direct agent, **14** for Direct + scene and **16** for Standalone sim (Fisher's exact **p <= 0.002**), reaching **60%** solve rate with the fewest steps.
- It matches Oracle dynamics at **25/25** successes, using **12-18%** more environment steps in Domino, Bridge and Balloons, **74%** more in Boil, and **8%** fewer in Fan.
- Removing parameter fitting drops success to **20/25** and removing explicit uncertainty to **21/25**; in Balloons the ablations reach only **2/5** and **3/5**, all failures being ceiling bursts.

## Takeaways

> [!tip] Key Insights
> - Extending a physics engine with code, rather than learning dynamics from scratch, lets a few interactions suffice and gives an inductive bias that extrapolates to new configurations.
> - Parameter inference and explicit uncertainty matter most when actions are irreversible; on forgiving tasks, robust conservative strategies can match or beat extra inference in interaction cost.
> - Interaction efficiency shifts cost to computation: median runs need 424 simulator rollouts, 162 language-model turns and 107 minutes, versus 115 turns and 64 minutes for a direct agent.

## Detailed Report

### 1. Overview

A robot planning with a physics engine can rely on its reusable knowledge of motion and contact. The engine cannot be expected to contain every unfamiliar effect the robot will meet, such as wind, glue, heating, or filling. Take a simulated tabletop domino task in which the robot must arrange a cascade that turns rather than simply toppling straight ahead. Knowing how rigid objects move is not the same as knowing the friction in this setup.

EMPIRIC handles this by having a coding agent extend the engine with executable programs for what is missing. The agent infers uncertain parameters and hidden state from noisy observations, then plans or experiments using the combined model. The aim is to avoid learning all of physics from scratch while still representing mechanisms the engine lacks. In the simulated Domino test, the learned model supports a 90-degree turn in the chain.

Domino: the last seconds of a recorded test task.

### 2. A physics engine with a memory

The authors call the combined model a **residual world model**: a base physics simulator plus a Python program for the missing mechanism. Here "residual" means an executable extension, which is not necessarily an additive correction. The base handles existing motion and contact. The program can add forces, constraints, evolving quantities, and recurrent hidden state.

Glue is a concrete example. The code tracks contact or cure progress that the current visible pose does not reveal, and it creates a bond once a learned condition is met. As a result, identical-looking scenes can have different outcomes because they have different histories.

The agent learns this model in a loop:

1. Actions and observations enter a replay buffer.
1. The agent writes or revises its program and outcome predicates.
1. Parameter fitting compares simulator replays with noisy observations. Current object state is also estimated from noisy readings, while the program's hidden state is reconstructed from history under each parameter draw.
1. The agent rehearses candidate skill sequences under joint parameter-and-state draws. It may choose a plan for task success or an informative experiment.
1. After execution, it checks the expected predicates. A mismatch can prompt replanning, more data, a belief update, or program revision.

Learning and planning in a Bridge/glue example. The stages are: act and collect data; write or revise program $P$ and predicates $\Phi$; infer a cure-time parameter belief $q(\theta)$; estimate visible pose while cure progress is hidden; rehearse plans across sampled states and parameters; and monitor predicates after skills. The pictured 13/16 plan-success estimate and code are illustrative. Stages can repeat or occur in a different order.

### 3. What the interaction results show

The method was tested in five simulated domains: Domino (friction and cascades), Bridge (glue and bonds), Balloons (lift and bursts), Boil (filling and heating), and Fan (airflow and drag). Each domain has five seeds per agent. A run counts as solved only if every task in its training-and-test sequence is solved.

**Success rate.** EMPIRIC solved all 25 runs. Each of the two strongest named baselines, Direct agent and Standalone sim., solved 16/25. EMPIRIC's pooled differences from each of the three baselines were significant at two-sided Fisher's exact-test p ≤ 0.002.

**Environment steps.** EMPIRIC used fewer environment steps than Direct agent and Direct + scene in four of five domains, and fewer than Standalone sim. in all five. The exception is Balloons, where Direct + scene also solved all five runs with a slightly lower mean step cost, 829 versus 847. Sandbox simulation is not counted as an environment step.

**Computation.** The step savings come with more computation. Median EMPIRIC runs use 424 simulator rollouts, 162 language-model turns, and 107 minutes, versus 115 turns and 64 minutes for Direct agent.

Results with noisy observations. The upper tier shows runs solved (%) per domain and agent, with EMPIRIC in teal. The lower tier plots the same percentage against each domain's environment-step budget, on separately scaled axes.

**The Balloons ablation.** The sharpest test of the uncertainty account is in Balloons. EMPIRIC solved 5/5 runs there, versus 2/5 without harness fitting and 3/5 without explicit uncertainty. All five ablation failures were ceiling bursts. Balloon releases are irreversible, so an overshoot can burst a balloon before the payload settles.

This ablation has two limits. "No explicit uncertainty" removes noise-scale information, state smoothing, and parameter-uncertainty support together, so it does not isolate one component. The pattern supports the authors' interpretation that inference and explicit uncertainty matter most for irreversible actions, but it does not establish that interpretation as the sole cause. In Boil and Fan, the ablations sometimes use fewer steps.

### 4. Reuse the known physics

In the Domino test, the agent turned the chain by keeping the engine's contact dynamics and adding only what the engine could not explain. Across the five simulated domains, this approach solved every run and generally saved environment steps.

The evidence has clear limits. The domains provide scene geometry and object features. There is one recorded physical-robot run, not a broad real-world benchmark. Belief construction is approximate, and the authors report no held-out calibration test.
