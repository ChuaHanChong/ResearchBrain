# An Empirical Study of Harness Design for Coding Agents

> [!summary] Summary
> A controlled study of coding-agent harness design that fixes a ReAct execution loop and varies planning, action space (predefined tools vs bash-only), and five context-management tiers across four models on SWE-Bench Verified and Terminal-Bench 2.1 (176 settings). Effects are conditional: context management matters under tight windows, staged elision-then-summarization is cheapest, and planning and predefined tools scaffold weak models but mainly cut cost or add overhead for strong ones.

## Problem

- Existing coding-agent evaluations compare complete harnesses as monolithic systems, so performance gaps cannot be attributed to planning, tool design, context management, or their model interaction.
- Cross-harness results show model-specific preferences, e.g., one model best with OpenHands and another with SWE-Agent, but do not explain which component drives the preference or when it transfers.
- Context-management methods are typically proposed as improvements on one model, leaving their dependence on context-window budget and model capability uncharacterized; prior scaffolding ablations used short-horizon tasks without window pressure.

## Method

- Modular ==LangGraph== harness keeps a ==ReAct loop==, safety gates, post-edit ruff/pyflakes diagnostics, and stuck detection fixed while toggling persistent update_plan planning and an eight-tool ==predefined action space== versus ==bash-only==.
- Five ==context-management tiers== built from three composable mechanisms: ==elision== of stale tool outputs (M1), recoverable external storage via recall_event (M2), and LLM running ==summarization== (M3); T4 stages all three.
- Matched 176-setting design on Nemotron-3 30B/120B/550B and Mistral-Medium-3.5: T0-T4 swept over 32k-128k windows, planning and action-space ablations at T4/128k, exact ==McNemar tests==, and ==LLM-judge trajectory-phase annotation==.

## Results

- Managed-versus-unmanaged success gap on SWE-Bench shrinks from **35.7** to **2.7** points as windows grow **32k** to **128k**, tracking T0 overflow falling **78.7%** to **8.7%**; managed tiers never overflow.
- T4 matches T1-T3 accuracy with lowest cost in **7 of 8** model-benchmark panels; recall is never called in **56.3%** of T2/T4 settings, and T2 minus T1 averages **-0.36** points.
- On SWE-Bench, planning lifts Nemotron-3 30B from **13.6%** to **25.2%** but cuts 550B and Mistral cost about **30%**; bash-only lifts 550B **3.6** points while cutting cost **53%**, but drops Mistral **23.2** points.

## Takeaways

> [!tip] Key Insights
> - Harness components are conditional, not universal defaults: one scaffold can be an accuracy crutch for weak models yet overhead or cost saver for strong ones.
> - Context management's value is mostly overflow prevention, not changed agent behavior; cheap rule-based elision before costly summarization wins, and lossless recall machinery goes largely unused by models.
> - Interface should match the model's learned action vocabulary and task shape: capable models compose denser bash commands with fewer re-patches, whereas weak models emit unresolvable tool calls without predefined schemas.

## Detailed Report

### 1. Position Within the Broader Research Landscape

Coding agents use large language models (LLMs) to perform software-engineering tasks such as locating bugs, modifying source files, running tests, and completing command-line workflows. Their performance depends not only on the underlying model but also on the “coding harness”: the software layer that controls the interaction loop, exposes tools, manages the conversation history, and structures the task.

Existing studies commonly compare complete agent systems, such as OpenHands, SWE-Agent, Agentless, or other research and commercial frameworks. These comparisons establish that harness design affects performance, but they often combine several interventions at once. A difference between two systems may result from their planning prompts, tool interfaces, context handling, verification procedures, or interactions among these components. Consequently, it is difficult to determine which mechanisms are responsible for observed gains and whether those mechanisms generalize across models.

This paper addresses that methodological gap through component-level evaluation. It fixes the main execution loop and varies three harness components independently: persistent planning, the action space available to the model, and context-management policies. It also evaluates those components across different model sizes, model families, task types, and context-window budgets. The work therefore connects several research areas: autonomous software engineering, LLM agent architecture, tool-use interfaces, long-horizon reasoning, and context compression.

The study is particularly relevant to recent research on context summarization, external memory, model-specific agent architectures, and trajectory-level analysis. Rather than treating context management or structured tools as universally beneficial, it tests when their value changes with model capability and available resources.

### 2. Objectives and Motivation

The central objective is to estimate the conditional contribution of three coding-harness components while holding the remaining system fixed. The authors ask whether these components are broadly useful or whether their effects depend on the model, task, and context budget.

The motivation has several parts. First, long-horizon coding tasks produce lengthy interaction histories. Tool outputs, file contents, test results, and intermediate reasoning can exceed the model’s context window. When this occurs, an agent may terminate before it edits the relevant code or verifies a solution. Context-management methods could reduce this failure mode, but they may also remove information needed later or introduce additional LLM calls and costs.

Second, persistent planning is often included in coding agents as a way to maintain task structure. However, planning may affect weaker and stronger models differently. A weaker model may need explicit task decomposition to avoid stopping prematurely, while a stronger model may already maintain sufficient structure and use planning mainly to avoid redundant actions.

Third, the design of the action space determines how model intentions become executable operations. A structured interface with tools such as `read_file`, `edit_file`, and `grep_text` can reduce the complexity of individual operations. Conversely, a bash-only interface allows capable models to compose several operations into one shell command. The authors therefore investigate whether structured tools help models with weaker shell control while imposing unnecessary interaction overhead on models that can use bash effectively.

The study also seeks behavioral explanations, not only aggregate success rates and costs. Trajectory analysis examines whether components change how long agents run, where they stop, which workflow phases they reach, and the granularity of their code modifications.

### 3. Methodology and Approach

#### 3.1. Harness Design

The authors implement a lightweight harness using a fixed ReAct-style loop. Each turn consists of model reasoning, an action, and an observation. Workspace access controls, read-before-write checks, permissions, post-edit diagnostics, and stuck detection remain fixed across experiments.

The first variable is planning. In the planning-enabled condition, the model receives instructions to create and maintain an explicit task plan using an `update_plan` tool. The current plan is injected into each model input but is stored outside the ordinary conversation history. In the planning-disabled condition, the instructions, reminders, plan injections, and tool are all removed.

The second variable is the action space. The predefined interface includes file-reading, file-writing, targeted editing, directory listing, glob search, text search, web fetching, and bash execution. The alternative bash-only interface removes the predefined workspace tools, leaving bash for general interaction. This comparison includes not only tool availability but also interface-specific prompts, file-state tracking, read-before-write enforcement, and automatic diagnostics. It therefore measures the effect of the complete interface rather than simply the number of tools.

The third variable is context management. Five tiers are evaluated:

- **T0:** No additional context management; the run ends when the context window is exceeded.
- **T1:** Rule-based elision of bulky, stale tool observations.
- **T2:** Elision plus external storage and a `recall_event` tool for recovering elided observations.
- **T3:** LLM-based summarization without elision.
- **T4:** Elision, recoverable external storage, and summarization applied sequentially.

T4 uses a soft threshold to elide bulky middle-region observations and a hard threshold to summarize older events. The system prompt, task description, and recent turns remain verbatim. Summaries are generated by a separate call to the same model under evaluation.

#### 3.2. Models, Benchmarks, and Experimental Design

The study evaluates three Nemotron-3 models—30B, 120B, and 550B parameters—and Mistral-Medium-3.5-128B as a cross-family comparison. The models are served locally in BF16 precision with temperature zero, top-p 0.95, and a maximum output of 16,384 tokens per turn.

The benchmarks are SWE-Bench Verified, containing 500 repository-level GitHub issues, and Terminal-Bench 2.1, containing 89 end-to-end command-line tasks. The main metrics are task success rate and mean cost per task, calculated from input and output token prices.

Context-management tiers are tested at 32k, 64k, 96k, and 128k token budgets. Planning and action-space ablations are performed at the T4/128k configuration. This produces 22 settings per model–benchmark pair and 176 total settings. Task-paired success outcomes are compared with exact McNemar tests, with Benjamini–Hochberg correction for multiple comparisons.

The authors additionally annotate trajectories using LLM judges, validated against human annotations. SWE-Bench turns are categorized as localization, reproduction, fixing, verification, or other. Terminal-Bench actions are categorized into understanding, code writing, verification, and other operations.

### 4. Main Findings and Results

#### 4.1. Context Management

Context management provides the greatest benefit under tight context budgets. Averaged across models, the managed-versus-unmanaged success-rate gap on SWE-Bench falls from 35.7 percentage points at 32k tokens to 2.7 points at 128k. On Terminal-Bench, the corresponding gap decreases from 9.5 to 2.8 points. The unmanaged T0 condition experiences context-overflow failures on 78.7% of SWE-Bench tasks at 32k and 8.7% at 128k. Managed tiers record no overflow failures.

Trajectory analysis indicates that context management primarily keeps agents running longer. It does not substantially change their workflow or action patterns when the context window is not binding. Under smaller budgets, unmanaged runs often stop during localization before reaching code modification or verification. Management allows more trajectories to reach editing and testing stages.

T4 produces success rates comparable to the other managed tiers while reducing average cost in seven of eight model–benchmark panels. Its staged design uses inexpensive rule-based elision before invoking LLM summarization, lowering peak context and reducing the number of summarization calls. By contrast, recoverable elision in T2 does not provide a reliable accuracy benefit over T1. Across 32 matched comparisons, T2 exceeds T1 in 15, falls below it in 14, and ties in three. Recall use is rare, especially at larger budgets and for stronger models. The authors conclude that external recovery adds complexity that most evaluated models do not exploit.

#### 4.2. Planning

Planning has capability-dependent effects. For Nemotron-3 30B, enabling planning raises SWE-Bench success by 11.6 percentage points and Terminal-Bench success by 4.5 points, but increases cost. Without planning, the model’s median SWE-Bench trajectory falls from 40 to 5 turns, and 68.6% of runs terminate without editing a file. With planning, that figure falls to 27.8%.

For Nemotron-3 120B, planning produces no consistent accuracy improvement. For Nemotron-3 550B and Mistral-Medium-3.5-128B, planning lowers cost while producing only small changes in success. On SWE-Bench, costs fall by approximately 30% and 32%, respectively. The trajectory analysis attributes these savings mainly to fewer redundant post-edit verification steps. Planning therefore shifts from an accuracy scaffold for the weaker model to a stopping and efficiency aid for stronger models.

#### 4.3. Action Space

Structured tools substantially help the weakest model. Relative to bash-only, the predefined interface increases Nemotron-3 30B success by 15.0 percentage points on SWE-Bench and 10.1 points on Terminal-Bench. Bash-only runs frequently produce tool calls that do not match the available interface, causing early termination.

The pattern changes for stronger models. Nemotron-3 550B performs better with bash-only, gaining 3.6 points on SWE-Bench and 5.6 points on Terminal-Bench while reducing cost by 53% and 30%. It also issues fewer calls and performs larger edits, suggesting that bash enables more composite operations.

Mistral shows a task-dependent crossover. Structured tools improve its SWE-Bench success by 23.2 points, but bash-only improves Terminal-Bench success by 6.7 points. Terminal-Bench is more shell-centric, whereas SWE-Bench benefits from structured search, reading, and editing tools. The results indicate that action-space preferences depend on both model capability and task composition.

### 5. Significance and Potential Impact

The paper’s main significance is methodological and practical. It demonstrates that harness components should not be evaluated as universally beneficial defaults. Context management is most important when context capacity is limited, planning can trade cost for persistence or efficient stopping depending on model capability, and structured tools can either scaffold behavior or add interaction overhead.

For system developers, the findings support model- and budget-aware harness configuration. Smaller or bash-weaker models may benefit from explicit plans and structured tools. Stronger shell-capable models may be more efficiently served by a bash-oriented interface. Rule-based elision followed by selective summarization may provide a relatively economical strategy for long trajectories.

The study also identifies important limitations. Planning and action-space ablations are tested only at 128k with T4 context management, so interactions among all components are not fully characterized. The action-space comparison bundles tool availability with prompts, validation, and state tracking. Each task is run once, Terminal-Bench is relatively small, and the model set is limited. Model size is also an imperfect measure of capability because training data and prior tool exposure may influence results. These limitations mean that the reported crossover points require validation on additional models, harnesses, languages, and software-engineering tasks. Nevertheless, the modular framework provides a basis for such future comparisons.
