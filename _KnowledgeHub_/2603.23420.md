# Bilevel Autoresearch: Meta-Autoresearching Itself

> [!summary] Summary
> Bilevel Autoresearch nests two LLM loops: an inner autoresearch loop that proposes, trains and accepts hyperparameter changes, and an outer loop that reads the inner loop's code and trace, then generates and injects new search mechanisms as Python code at runtime. Both loops use the same model. On Karpathy's GPT pretraining benchmark the outer loop yields a 5x larger val_bpb gain than the inner loop alone.

## Problem

- Existing autoresearch systems fix their search procedure by human design: single-track keep/discard loops, multi-batch parallelism and persistent memory were all architected by researchers, not discovered.
- Prior self-improvement work optimizes artifacts such as prompts, pipelines or scientific principles, leaving untouched the mechanism that generates, evaluates and selects future artifacts.
- Classical bilevel optimization and meta-learning tune real-valued parameters or pick from fixed algorithm portfolios, so they cannot produce a genuinely new search program.

## Method

- **Level 1** inner loop: LLM proposes hyperparameter edits to train.py, trains 300 seconds, keeps the change only if val_bpb beats the current best, over 30 iterations.
- **Level 1.5** outer config loop runs every five iterations, freezing parameters proposed three times with no net gain, unfreezing stale ones and injecting a guidance string.
- **Level 2** mechanism research: a four-call ==Explore/Critique/Specify/Generate== dialogue writes a new search mechanism, patches runner.py, and validates it by ==importlib== load with revert on failure.

## Results

- Four-group ablation with three repeats each: full bilevel Group C improved val_bpb by **-0.045 ± 0.030** versus **-0.009 ± 0.002** for the inner loop alone.
- Level 1.5 alone (Group B) reached only **-0.006 ± 0.006**, no better than plain Level 1, so parameter-level adjustment produced no reliable gain within **30** iterations.
- Generated mechanisms (Tabu Search, multi-scale bandit, orthogonal exploration) drove TOTAL_BATCH_SIZE from **2^19** down to **2^17-2^18**, worth **-0.039** to **-0.065**; **five of six** artifacts passed import validation.

## Takeaways

> [!tip] Key Insights
> - Changing a search mechanism beats tuning its parameters: structural edits unlocked directions that parameter freezing and guidance strings could never reach.
> - LLM priors bias search deterministically, here toward larger batches; tabu and diversity mechanisms help mainly by blocking the model's own repeated proposals.
> - Runtime code injection can fail silently: a module-registration bug invalidated an entire run, so validate-and-revert plus explicit activation logging is mandatory.

## Detailed Report

### 1. How this work fits into the broader research landscape

This research is situated within the field of automated machine learning and artificial intelligence, specifically focusing on the concept of "autoresearch" and agentic self-improvement. The work builds upon the foundation of Large Language Model (LLM)-driven scientific iteration, where an LLM proposes changes, executes experiments, and evaluates outcomes in a closed loop, a process exemplified by Karpathy's autoresearch for neural network hyperparameter search.

Prior advancements in autoresearch, such as AutoResearchClaw's multi-batch parallelism and EvoScientist's persistent experience memory, introduced enhancements designed by human researchers. These systems maintained fixed search procedures. This paper distinguishes itself by addressing whether an LLM can autonomously improve its *own* search procedure, rather than simply optimizing a task within a pre-defined search framework.

The work connects to the concept of bilevel optimization, where an upper-level objective optimizes a lower-level problem. However, it departs from classical bilevel optimization by treating the upper-level optimization target (the search mechanism, or runner code) as a discrete program generated by code rather than a real-valued parameter vector.

Furthermore, it relates to the broader trend of LLM-based code generation, seen in systems like AlphaCode and FunSearch, which demonstrated LLMs' capacity to write correct programs or aid scientific discovery. This paper applies similar LLM code generation capabilities to a different target: autonomously creating and injecting *search mechanism code* that modifies the inner loop's operational logic.

In contrast to meta-learning and algorithm configuration, which often rely on gradient-based optimization or fixed portfolios, this work employs LLM code generation to generate or select search mechanisms. The authors frame their approach as "mechanism-level self-improvement," distinguishing it from "artifact-level" self-improvement (e.g., optimizing prompts or skills). While artifacts influence behavior, mechanism-level improvement aims to change the underlying logic by which an agent generates, evaluates, selects, and revises future artifacts or behaviors. This positioning suggests a trajectory toward more fundamental agentic autonomy in optimizing their own operational procedures.

### 2. Key objectives and motivation

The primary objective of this research is to investigate whether an autoresearch loop can be autonomously optimized by applying autoresearch principles to itself. This central idea is operationalized through a bilevel framework, where an outer loop ("meta-autoresearch") is designed to optimize the search process of an inner autoresearch loop.

The motivation for this work stems from the observation that existing autoresearch systems, despite their capacity for self-directed iteration, still rely on search procedures (e.g., proposal generation logic, acceptance criteria, state management) that are designed and fixed by human engineers. The authors pose the question of whether an LLM can autonomously perform this design step: reading the inner loop's code, identifying operational bottlenecks or inefficiencies, and generating new mechanisms (implemented as Python code) that alter how future improvements are searched for.

Specifically, the paper aims to:
1. **Formulate autoresearch as a closed-loop search process** and introduce a bilevel framework where an outer loop optimizes the inner loop's search/update mechanism.
2. **Demonstrate the feasibility of mechanism-level self-improvement**: Show that an LLM can generate and inject new search mechanisms as Python code at runtime to modify the behavior of another agentic loop. This focuses on improving *how* an agent generates, evaluates, selects, and revises changes, rather than merely improving a one-off artifact.
3. **Evaluate the effectiveness of this bilevel approach**: Empirically assess if the outer meta-optimization loop leads to better task performance (e.g., improved hyperparameters for a GPT model) compared to a standard inner autoresearch loop, or one augmented with only parameter-level adjustments.
4. **Analyze the generated mechanisms**: Understand *why* the autonomously discovered mechanisms improve performance, hypothesizing that they might overcome systematic biases or limitations of the LLM's default search strategies.
5. **Explore the potential for recursive bootstrapping**: While not fully demonstrated, the work aims to suggest a path towards recursive self-application, where mechanisms discovered for an inner loop could inform improvements for the meta-level loop itself.

A key aspect of this motivation is the explicit goal of achieving improvements through architectural innovation (the bilevel framework) rather than simply using a more capable LLM for the meta-level. Both loops utilize the same LLM, implying that any observed gains would be attributable to the structural and algorithmic design of the bilevel system.

### 3. Methodology and approach

The authors developed Bilevel Autoresearch, a framework consisting of three nested levels, all powered by the same DeepSeek `deepseek-chat` LLM. The system is evaluated on Karpathy's GPT pretraining benchmark.

#### 3.1. Framework Architecture

- **Level 1: Inner Autoresearch Loop**: This level functions as a standard autoresearch cycle. At each iteration, the LLM:
 1. Receives the current `train.py` configuration (frozen at the best-performing state), a list of editable parameters, frozen parameters, and a strategic guidance string from Level 1.5.
 2. Proposes a set of parameter-value changes with a hypothesis.
 3. Applies the change to a working copy of `train.py` and initiates a 300-second training run.
 4. Evaluates the `val_bpb` (bits per byte) outcome. If the `val_bpb` is lower (better) than the current best, the change is accepted and the configuration updated; otherwise, it is discarded.
 The iteration budget for the inner loop is fixed at 30 per experimental repeat. Initial parameters like `DEPTH=8` and `ASPECT_RATIO=64` are fixed, while others (e.g., `LR`, `WEIGHT_DECAY`, `TOTAL_BATCH_SIZE`) are editable.

- **Level 1.5: Outer Search-Strategy Loop**: This loop operates less frequently, executing every 5 inner iterations. Its role is to adjust parameters of the existing search mechanism. It:
 1. Analyzes the full trace of proposals and their outcomes from the inner loop.
 2. Updates a `SearchConfig` by freezing parameters that have been proposed a minimum number of times (k=3) without net improvement.
 3. Unfreezes parameters if the search has moved to a new region and they haven't been explored since.
 4. Injects a guidance string into the Level 1 prompt, directing the inner loop to prioritize under-explored parameters.
 Level 1.5 influences search diversity but does not alter the fundamental proposal generation logic, acceptance criteria, or structural elements of the inner loop.

- **Level 2: Mechanism Research and Code Injection**: This is the meta-optimization level, executing every 2 outer cycles. It generates and injects new search mechanisms as Python code. This level involves a structured, four-round dialogue with the LLM:
 1. **Explore**: The LLM reads the `runner.py` source code and the accumulated search trace. It surveys mechanisms from related fields (e.g., combinatorial optimization, online learning, design of experiments, Bayesian optimization) and proposes candidate improvements relevant to observed bottlenecks.
 2. **Critique**: The LLM evaluates the proposed mechanisms against the inner loop's observed failure modes (e.g., repetitive proposals, parameter fixation) and selects the most promising one.
 3. **Specify**: The LLM then writes a precise interface specification for the chosen mechanism, detailing class name, constructor arguments, method signatures, and integration points within `runner.py`.
 4. **Generate**: Finally, the LLM writes complete, runnable Python code implementing the specified mechanism, including any necessary modifications to `runner.py` for its invocation.
 The generated code dynamically patches `runner.py`. Before activation, the code is validated through `importlib` dynamic loading. If the import succeeds, the patched `runner.py` replaces the active one; if it fails, the original `runner.py` is restored from a backup, preventing system corruption.

#### 3.2. Experimental Design

To isolate the contribution of each level, four experimental groups were established. All other variables, including the LLM model, GPU hardware (RTX 5090 32 GB across three independent servers), 300-second training budget, 30-iteration search budget, and the baseline `train.py`, were held constant. Each group was run for 3 independent repeats, with the `train.py` restored to its original baseline state between repeats.
- **Group A (Level 1 only)**: Represents pure autoresearch without any outer intervention.
- **Group B (Level 1 + 1.5)**: Includes the inner loop and the outer strategy adjustment.
- **Group C (Level 1 + 1.5 + 2)**: The full bilevel framework, incorporating mechanism research.
- **Group D (Level 1 + 2)**: Includes the inner loop and mechanism research but omits the strategy adjustment of Level 1.5.

The primary metric for evaluation was ∆ = `best - baseline val_bpb`, where a more negative value indicates greater improvement.

### 4. Main findings and results

The experiments demonstrate distinct performance and search behaviors across the four groups, primarily highlighting the impact of mechanism research.

#### 4.1. Primary Ablation Results

The quantitative results, measured as `val_bpb` change (∆ = best − baseline), showed:
- **Group A (Level 1)**: Achieved a mean improvement of −0.009 ± 0.002. Improvements were consistent but relatively small.
- **Group B (Level 1 + 1.5)**: Showed a mean improvement of −0.006 ± 0.006. Its performance was comparable to Group A, with one repeat yielding negligible improvement (−0.000), contributing to higher variance.
- **Group C (Level 1 + 1.5 + 2)**: Achieved a mean improvement of −0.045 ± 0.030. This represents an approximate 5x improvement over Group A in terms of absolute `|∆|`. Two of the three repeats (R1 and R3) demonstrated substantial gains (−0.065 and −0.058), while R2 showed a more modest improvement (−0.011).
- **Group D (Level 1 + 2)**: Exhibited a mean improvement of −0.034 ± 0.031. One repeat (R2) achieved the highest individual improvement across all experiments (−0.063), but R1 showed minimal improvement (−0.001). This group's results were more variable, partly due to issues with mechanism application in some repeats.

#### 4.2. Hypothesis Testing

- **H1 (Group B > Group A)**: Not supported. Group B's mean improvement was marginally worse than Group A's, and the variance was higher. Level 1.5 increased search diversity but did not consistently translate to superior task performance within the given budget.
- **H2 (Group C > Group B)**: Supported. Group C's mean absolute improvement was 7.5x that of Group B, providing evidence that Level 2 mechanism injection contributed significant value beyond Level 1.5.
- **H3 (Level 2 autonomously generates and injects new mechanisms)**: Supported. Across Group C's repeats, Level 2 successfully generated and injected mechanisms from three distinct optimization domains: Tabu Search Manager (combinatorial optimization), Multi-Scale Bandit Proposer (online learning/multi-armed bandits), and Systematic Orthogonal Exploration (design of experiments). All code generation succeeded on the first attempt, and five of six generated artifacts passed import validation.
- **H4 (Group D ≈ Group C without Level 1.5)**: Inconclusive. While Group D produced large improvements in two repeats, the per-repeat reports indicated that mechanism patches were not consistently applied or validated. This confounds a clean comparison, though it suggests Level 1.5 might offer robustness through enriched trace context.

#### 4.3. Level 2 Generated Artifacts and Mechanisms

The active mechanisms generated by Level 2 included:
- **Tabu Search Manager**: Prevents the inner loop from revisiting recently explored parameter regions, aiming to break repetitive search patterns.
- **Multi-Scale Bandit Proposer**: Frames parameter selection as a multi-armed bandit problem, balancing exploration and exploitation across different parameter scales.
- **Systematic Orthogonal Exploration**: Forces the inner loop to explore orthogonal parameter dimensions, aiming to prevent over-focus on single parameters.
One attempted mechanism, a GP Regressor from Bayesian optimization, failed to activate due to a missing `sklearn` dependency, which was correctly handled by the validate-and-revert system.

#### 4.4. Search Behavior Analysis and Key Discovery

Qualitative analysis of search trajectories revealed:
- **Groups A and B**: Exhibited near-deterministic search patterns. Group A repeatedly proposed similar changes, often encountering diminishing returns or consecutive discards. Group B, while having its search redirected by Level 1.5 (e.g., freezing unproductive parameters), remained within the bounds of the existing structural framework and achieved similar improvement sizes. Both groups tended to miss critical high-impact directions.
- **Groups C and D (high-performing repeats)**: The most impactful discovery was a reduction in `TOTAL_BATCH_SIZE` (from 2^19 to 2^17 or 2^18). This change dramatically improved `val_bpb` (up to −0.065) because, on the RTX 5090 with a 300-second budget and SDPA (not Flash Attention 3), smaller batch sizes allowed for significantly more gradient steps within the fixed wall-clock time, leading to better convergence for the 50M-parameter model.
 The Level 2 mechanisms in Group C (Tabu Search and Orthogonal Exploration) appeared instrumental in breaking the LLM's default biases (e.g., an implicit "larger batch is better" assumption) and deterministic search patterns. These mechanisms forced the inner loop to explore previously avoided directions, leading to the discovery of the optimal `TOTAL_BATCH_SIZE` reduction.

### 5. Significance and potential impact

This work presents an empirical demonstration of an LLM-driven outer loop autonomously improving the search behavior of an inner autoresearch loop. This "bilevel autoresearch" framework shows that an LLM can generate and inject new search mechanisms as Python code at runtime, leading to a 5x improvement in `val_bpb` on Karpathy's GPT benchmark compared to the inner loop alone.

The primary significance lies in the concept of **mechanism-level self-improvement**. Unlike prior autoresearch systems that either optimize task-specific artifacts or have human-designed search procedures, this research shows that an agent can modify *how* it proposes, evaluates, selects, and updates future changes. Code serves as a concrete carrier for these modifiable mechanisms, allowing explicit inspection, generation, validation, and injection. This principle extends beyond Python code to other potential carriers such as skills, prompts, workflows, evaluators, scientific principles, world-model assumptions, and memory schemas, all of which can encode logic that shapes future agent behavior.

The autonomous discovery of search strategies, such as Tabu Search, multi-armed bandit exploration, and systematic orthogonal exploration, from distinct optimization domains is a notable outcome. These mechanisms were generated without human specification of their final design and were effective in overcoming systematic biases or repetitive patterns in the LLM's default search, as evidenced by the critical `TOTAL_BATCH_SIZE` discovery.

This initial **bilevel step** suggests a path toward **recursive bootstrapping**, where mechanisms successfully discovered and applied to improve an inner loop could, in principle, be fed back to improve the meta-level loop itself. While the current work demonstrates the first level of this recursion, it frames the longer-term goal of robust, self-improving AI systems capable of optimizing their own learning and discovery processes.

**Potential impacts include:**
- **More efficient and robust automated research systems**: By allowing LLMs to adapt and improve their underlying search strategies, future autoresearch systems could become more effective at discovering optimal configurations and less susceptible to fixed biases.
- **Advancement in agentic self-improvement**: This mechanism-level approach contributes to a deeper understanding of how intelligent agents can fundamentally enhance their own operational logic, moving beyond mere task performance optimization.
- **New avenues for LLM application**: Demonstrates the LLM's capacity not just for generating task-specific code or text, but for self-modifying, strategic programming of its own processes.

**Limitations and Future Work**:
Despite these advancements, the study has several limitations:
- **Small sample size**: With only three repeats per group, statistical rigor is limited, and the high variance in some groups suggests the need for larger-scale experiments.
- **Single benchmark**: The results are specific to a GPT pretraining task on a particular hardware setup, limiting generalizability to other models, tasks, or budgets.
- **Carrier limitation**: The work focused solely on Python code as the mechanism carrier, leaving other potential carriers unevaluated.
- **Recursive limitation**: The paper demonstrates only the first bilevel step, with full recursive self-application remaining a future research challenge.
- **Dynamic load fragility and external dependency exposure**: Runtime code injection introduces reliability risks, though validation and revert mechanisms mitigate some issues.
- **Prompt-induced domain bias**: The Level 2 prompt guided the LLM towards specific optimization domains, potentially limiting the scope of discovered mechanisms.

Future work directions include scaling experiments for statistical power, evaluating on multiple benchmarks, testing alternative mechanism carriers, measuring cross-seed/cross-task transferability, and investigating methods to improve code generation quality and establish robust recursive self-application.
