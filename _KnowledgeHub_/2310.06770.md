# SWE-bench: Can Language Models Resolve Real-World GitHub Issues?

> [!summary] Summary
> SWE-bench is a benchmark of 2,294 real GitHub issue and pull-request pairs from 12 Python repositories. A model must edit a large codebase to resolve each issue, and the repository's own unit tests verify the result. The authors also release a 19,000-instance training set and fine-tuned SWE-Llama models. The best model, Claude 2, resolves only 1.96% of issues.

## Problem

- Existing coding benchmarks like HumanEval use self-contained problems solvable in a few lines, so they miss repository-scale engineering: navigating large codebases and coordinating edits across many functions and files.
- Established language model benchmarks are saturated and no longer reveal the frontier of capabilities, while harder replacements must still be verifiable automatically and stay difficult for current models.
- Open models lacked repository-level training data; off-the-shelf CodeLlama outputs placeholders or unrelated code instead of repository-wide edits, blocking fair comparison against proprietary models.

## Method

- A three-stage ==construction pipeline== scrapes about 90,000 pull requests from 12 repositories, filters by attributes (resolves an issue, adds tests), then by execution, requiring at least one ==fail-to-pass test==.
- Task formulation: the model receives issue text plus a codebase and outputs a ==patch==. Success requires the patch to apply and all fail-to-pass and prior tests to pass, with ==BM25== or ==oracle file retrieval==.
- **SWE-bench-train** holds 19,000 issue-PR pairs from 37 disjoint repositories. It is used to ==LoRA== fine-tune the attention layers of CodeLlama-Python 7b and 13b into **SWE-Llama**; a 300-instance **Lite** subset is also released.

## Results

- With BM25 retrieval, Claude 2 resolves only **1.96%** of instances; GPT-4-turbo gets **1.31%**, ChatGPT-3.5 **0.17%**, both SWE-Llama models **0.70%**, and Claude 3 Opus **3.79%**.
- Oracle retrieval of the files edited by the gold patch lifts Claude 2 to **4.8%**; at **27,000** tokens, BM25 retrieves none of the oracle files in almost half of instances.
- Longer context hurts: Claude 2 falls from **1.96%** at **13k** tokens to **1.22%** at **50k**, and resolve rate drops as total input length grows.

## Takeaways

> [!tip] Key Insights
> - Execution-based verification with existing repository tests turns real artifacts like issues and pull requests into scalable, continually updatable benchmarks, and post-cutoff instances can avoid training-data contamination.
> - Localizing the relevant code, not writing the patch, is the bottleneck: more retrieved context raises recall yet lowers resolve rate because models get distracted by irrelevant code.
> - Realistic tasks expose gaps hidden by saturated benchmarks. Near-zero scores mark a useful frontier, and models solve different subsets of instances, so aggregate rates hide complementary strengths.

## Detailed Report

### 1. How This Work Fits into the Broader Research Landscape

The development of SWE-bench is a direct response to a critical challenge in the field of Large Language Models: the saturation of existing benchmarks. As LMs rapidly advance and are deployed in commercial products, the current evaluation paradigms, often relying on "contrived" or "short input/output" problems, fail to accurately gauge the true frontier of their capabilities. The authors cite previous works (Kiela et al., 2021; Ott et al., 2022; Srivastava et al., 2023) that highlight the need for more challenging and realistic benchmarks.

**Comparison with Code Generation Benchmarks:**
Historically, code generation benchmarks like HumanEval (Chen et al., 2021) have been instrumental in assessing an LM's ability to synthesize code from natural language descriptions. Subsequent benchmarks have expanded HumanEval to different languages (Cassano et al., 2022; Athiwaratkun et al., 2023), variations in edit scope, and new code completion tasks (Muennighoff et al., 2023). However, these benchmarks largely focus on self-contained problems solvable within a few lines of code or limited contexts. SWE-bench significantly departs from this by introducing "repository-scale code editing." This demands capabilities far beyond traditional code generation, including:
- **Long-context reasoning:** Navigating and understanding large codebases (hundreds of thousands of lines across thousands of files).
- **Cross-context coordination:** Making and coordinating changes across multiple functions, classes, and even files simultaneously.
- **Execution environment interaction:** The ability to generate solutions that pass actual unit and system tests within a live repository environment, rather than just matching reference solutions or passing simple test cases.
- **Patch generation:** Requiring models to output structured `diff` format patches, a common software engineering artifact, instead of just new code snippets.

**ML for Software Engineering:**
This work is deeply embedded in the intersection of Machine Learning and Software Engineering. Previous research in ML for SE has explored automating various software development processes, such as commit generation (Jung, 2021), pull request review (Yang et al., 2016), bug localization (Kim et al., 2019), testing (Kang et al., 2023), and program repair (Gupta et al., 2017; Monperrus, 2018; Xia & Zhang, 2022). While LMs have been applied to automated program repair, existing datasets often lack the scale and real-world complexity that SWE-bench provides. SWE-bench distinguishes itself by leveraging real GitHub issues and pull requests, providing an authentic and challenging setting for evaluating LMs as intelligent agents in complex software development workflows.

**Towards Agentic AI Systems:**
The paper also positions SWE-bench as a benchmark that can "serve as a level playing field to compare approaches ranging from retrieval and long-context models to decision-making agents." This aligns with the broader trend in AI research toward developing autonomous agents that can reason, plan, and act in complex, interactive environments (Yao et al., 2022; Zhou et al., 2023). Solving SWE-bench tasks frequently requires models to interact with execution environments and iteratively refine solutions, a key characteristic of agentic behavior.

In essence, SWE-bench pushes the evaluation frontier for LMs in coding by demanding capabilities typically associated with experienced software engineers operating in real-world, large-scale projects, thereby bridging the gap between academic benchmarks and practical software development.

### 2. Key Objectives and Motivation

The primary objective of this research is to **introduce SWE-bench**, a novel and challenging evaluation framework designed to assess the frontier capabilities of Large Language Models in real-world software engineering scenarios.

The motivations behind developing SWE-bench are multifaceted:
- **Addressing Benchmark Saturation:** Existing LM benchmarks have become "saturated," meaning state-of-the-art models often perform near-perfectly, failing to differentiate their true capabilities or expose their limitations. This saturation hinders effective development and understanding of advanced LMs.
- **Reflecting Real-World Complexity:** Traditional coding benchmarks (e.g., HumanEval) typically involve self-contained problems that can be solved with a few lines of code. However, real-world software engineering is far more complex, often requiring developers to:
 - Navigate vast code repositories.
 - Understand intricate interactions between functions and classes across multiple files.
 - Identify and fix subtle errors in convoluted code.
 - Resolve issues that may involve "understanding and coordinating changes across multiple functions, classes, and even files simultaneously."
 - Interact with execution environments to verify solutions.
 - Process "extremely long contexts" to identify relevant code segments.
- **Driving Future LM Development:** By presenting these complex, real-world challenges, SWE-bench aims to "shape their future development and usage." The authors explicitly state that advances on SWE-bench represent steps towards LMs that are "more practical, intelligent, and autonomous." The benchmark is designed to push LMs beyond simple code generation towards more holistic software development capabilities.
- **Sustainability and Continual Update:** The framework is built to be "rich, sustainable, and challenging." Its construction process allows for continuous updates with new task instances, ensuring the benchmark remains relevant and challenging even as LMs improve. This also helps to evaluate LMs on issues created *after* their training data cutoff, reducing the risk of data contamination.

In addition to the core objective of introducing the benchmark, the authors have two key secondary objectives:
- **Facilitating Open Model Development:** To support the broader research community, they release `SWE-bench-train`, a large training dataset of 19,000 non-testing task instances from 37 distinct repositories. This dataset is crucial for fine-tuning open-source models for this challenging domain.
- **Providing Strong Open Baselines:** Utilizing `SWE-bench-train`, they release `SWE-Llama` (7b and 13b parameter variants), fine-tuned versions of CodeLlama, which serve as competitive open-source baselines capable of processing very long contexts.

### 3. Methodology and Approach

The core of this work is the meticulous construction and evaluation framework of SWE-bench.

#### 3.1. Benchmark Construction (SWE-bench)

SWE-bench comprises 2,294 software engineering problems derived from real GitHub issues and their corresponding pull request (PR) solutions across 12 popular Python repositories. The construction process involves a rigorous 3-stage pipeline to ensure high-quality, solvable, and realistic tasks:

- **Stage I: Repository Selection and Data Scraping:**
 - PRs are collected from 12 popular open-source Python repositories (e.g., `django`, `scikit-learn`, `sympy`). Popularity indicates better maintenance, clear guidelines, and good test coverage.
 - Approximately 90,000 PRs are initially scraped.
- **Stage II: Attribute-Based Filtering:**
 - Only `merged` PRs are selected, ensuring the proposed changes were accepted into the codebase.
 - PRs must `resolve a GitHub issue`, indicating they address a specific problem or feature request.
 - PRs must `make changes to the test files`, suggesting that the original developer contributed tests to verify the issue's resolution.
- **Stage III: Execution-Based Filtering:**
 - For each candidate, the PR's test content is applied to the codebase *before* and *after* the PR's main code changes are applied.
 - Only instances with at least one "fail-to-pass" test (i.e., a test that failed before the PR's solution but passed after) are retained. This ensures the problem is non-trivial and truly resolved by the PR.
 - Instances resulting in installation or runtime errors are filtered out to ensure environmental stability.
 - Tasks involving newly created functions/classes in tests (which might be hard for LMs to infer names) are also excluded.

#### 3.2. Task Formulation and Evaluation

- **Input:** A language model is given an issue text description (e.g., bug report, feature request) and a complete snapshot of the relevant codebase.
- **Task:** The model is tasked with editing the codebase to resolve the issue by generating a "patch file" (in `diff` format). This format specifies line-by-line modifications (additions, removals) across multiple files.
- **Evaluation Metrics:** The generated patch is applied to the codebase. The revised codebase is then evaluated by executing the repository's real unit and system tests associated with the task instance. A solution is deemed successful if the patch applies successfully and *all* relevant tests (fail-to-pass and existing pass-to-pass tests) pass. The primary metric is the percentage of resolved tasks.

#### 3.3. Key Features of SWE-bench

- **Real-world:** Utilizes authentic GitHub issues and solutions, requiring complex software engineering skills.
- **Continually Updatable:** The collection process is automated and can be applied to new repositories, allowing for evaluation on fresh data, mitigating data contamination risks for future LMs.
- **Diverse Long Inputs:** Issue descriptions are lengthy (avg. 195 words), and codebases are massive (avg. 438K lines across 3,010 files). Solutions often involve editing multiple files (avg. 1.7 files, 3 functions, 32.8 lines).
- **Robust Evaluation:** Leverages real unit/system tests, including explicit "fail-to-pass" tests (avg. 9.1 per instance) and "pass-to-pass" tests (avg. 51 per instance) to prevent regressions.
- **Cross-context Code Editing:** Unlike prior benchmarks, it doesn't constrain edits to single functions or provide fill-in-the-blanks, demanding broader reasoning.
- **Wide Scope for Solutions:** Allows for diverse approaches, including agent-based systems and tool-augmented LMs.

#### 3.4. SWE-bench Lite

A smaller subset of 300 instances, sampled to be more self-contained, is provided for faster and less costly initial evaluations.

#### 3.5. SWE-Llama: Fine-tuning CodeLlama for SWE-bench

- **Motivation:** Standard CodeLlama models struggled with SWE-bench's long contexts and patch generation instructions.
- **Training Data:** 19,000 issue-PR pairs collected from 37 *disjoint* (from the evaluation set) Python repositories. This training data did *not* require PRs to contribute test changes, allowing for a larger dataset.
- **Training Details:** Supervised fine-tuning of CodeLlama-Python 7b and 13b models using LoRA (Low-Rank Adaptation) for memory efficiency. Models were trained to generate the "gold patch" given instructions, issue text, and relevant code files. Contexts exceeding 30,000 tokens were excluded during training.

#### 3.6. Experimental Setup for Evaluation

- **Context Retrieval:**
 - **Sparse Retrieval (BM25):** A generic BM25 retriever selects relevant files from the codebase to fit within the LM's context window. Experiments were conducted with 13k, 27k, and 50k token limits.
 - **"Oracle" Retrieval:** For analytical purposes, models were also evaluated by providing *only* the files that were edited in the reference solution. This simulates an ideal retrieval scenario.
 - **"Oracle"-collapsed:** An even more constrained setting where only the edited lines (plus a 15-line buffer) from the oracle files were provided, testing the model's ability to fix localized issues.
- **Input Format:** A standardized prompt template including task instructions, issue text, retrieved files (with file paths), and an example patch file format.
- **Models Evaluated:** State-of-the-art proprietary models (ChatGPT-3.5, GPT-4, Claude 2) and the newly fine-tuned open models (SWE-Llama 7b and 13b). These were selected due to their ability to handle long sequence lengths.

### 4. Main Findings and Results

The evaluation results on SWE-bench paint a stark picture: even state-of-the-art Large Language Models currently struggle immensely with real-world software engineering tasks.

- **Extremely Low Resolution Rates:**
 - Using the realistic BM25 retrieval method, the best-performing model, **Claude 2**, was able to resolve only **1.97%** of the issues.
 - The fine-tuned **SWE-Llama** models achieved a **0.70%** resolution rate.
 - **GPT-4-turbo** achieved **1.31%**, and **ChatGPT-3.5** a mere **0.17%**.
 - This highlights that LMs are still very far from autonomously resolving real-world GitHub issues.

- **Impact of Context Retrieval:**
 - When provided with "oracle" context (only the files that were actually modified in the ground truth solution), performance improved but remained low. Claude 2's rate increased to 4.80%, SWE-Llama 13b to 3.97%. This indicates that even with perfect context, the models struggle with reasoning and generating the correct changes.
 - Further restricting context to "oracle"-collapsed (only edited lines +/- 15 lines), performance saw additional gains (e.g., Claude 2 to 5.93%). This suggests that models are highly sensitive to irrelevant context and perform better when the problem space is extremely localized, mimicking traditional code completion.

- **"Lost in the Middle" Phenomenon:**
 - A critical finding is that performance *decreases* as the total input context length increases, even when the BM25 retriever brings more relevant files into the context. This corroborates findings from other studies (Liu et al., 2023b) that LMs struggle to effectively utilize long contexts, often getting "distracted" or losing focus on relevant information. Models are ineffective at localizing problematic code within vast contexts.

- **Difficulty Varies by Repository, but Overlap is Low:**
 - Performance varied across the 12 repositories, but all models showed similar trends in relative difficulty.
 - Interestingly, issues solved by different models often did not extensively overlap (e.g., Claude 2 solved 110 issues, SWE-Llama 13b solved 91, but only 42% of SWE-Llama's solved instances were also solved by Claude 2). This suggests diverse failure modes and that each model might excel at different problem types.

- **Temporal Robustness:**
 - The difficulty of issues did not strongly correlate with their resolution date (before or after 2023). This is a promising sign that models are not simply "cheating" by memorizing recent code changes from their training data but are genuinely attempting to understand and fix problems.

- **Finetuned Model Behavior:**
 - SWE-Llama models performed surprisingly poorly with BM25 retrieval compared to "oracle" retrieval. The authors attribute this to a "context distribution shift": SWE-Llama was fine-tuned on oracle-like contexts where all provided files were expected to be edited. In the BM25 setting, many retrieved files might be irrelevant, confusing the model trained for more targeted editing.

- **Patch vs. Whole File Generation:**
 - Models performed better when asked to generate patch files compared to regenerating entire modified files. This indicates a challenge with maintaining the original, unchanged parts of a large file while making specific edits.

- **Nature of Model-Generated Edits:**
 - Model-generated patches, even when successfully applied, tended to be significantly shorter and simpler than the human-written "gold" patches (e.g., less than half the total lines edited on average). They also rarely edited more than a single file. This suggests models produce more primitive Python code, lack awareness of broader code style or logical constraints, and often fail to make structural improvements or anticipate future issues as human developers might.
 - Qualitative analysis showed models sometimes take a "greedy" approach, directly addressing the immediate error without considering broader code quality or adherence to existing patterns. Issues involving images were also found to be challenging for current LMs.

### 5. Significance and Potential Impact

SWE-bench represents a significant contribution to the field of artificial intelligence and software engineering, with profound implications for the future development and application of Large Language Models.

- **A New Gold Standard for LM Evaluation in Software Engineering:** By moving beyond synthetic, self-contained coding problems, SWE-bench establishes a novel, realistic, and highly challenging benchmark. Its reliance on real-world GitHub issues and pull requests, combined with execution-based evaluation within live codebases, provides an authentic measure of LM capabilities for complex software development tasks. This pushes the boundaries of what is considered "state-of-the-art" for code intelligence.

- **Unveiling Current LM Limitations:** The extremely low success rates of even leading proprietary LMs (less than 2% for Claude 2) on SWE-bench clearly highlight the vast gap between current LM capabilities and the demands of real-world software engineering. This finding is crucial as it points to critical areas where future research and development must focus, including:
 - **Advanced Reasoning and Planning:** LMs need to develop more sophisticated reasoning abilities to understand complex interdependencies across large codebases, infer developer intent from natural language issue descriptions, and devise multi-step solutions.
 - **Robust Long-Context Processing:** Overcoming the "lost in the middle" problem is paramount. Models must become adept at efficiently processing and selectively attending to relevant information within extremely long, noisy code contexts.
 - **Autonomous Agent Capabilities:** The benchmark encourages the development of LMs that can act as more autonomous agents, capable of interacting with execution environments, receiving feedback (e.g., test results), and iteratively refining their solutions.

- **Fostering Open Research and Development:** The release of the SWE-bench benchmark, the large `SWE-bench-train` dataset, and the fine-tuned `SWE-Llama` models provides invaluable resources for the open-source community. This will catalyze accelerated research and development in this domain, allowing researchers to build upon a common, challenging foundation without needing to replicate the extensive data collection and infrastructure.

- **Bridging AI and Software Engineering:** SWE-bench serves as a strong bridge between the AI/ML community and software engineering research. It creates common ground for collaboration, encouraging the development of AI systems that are not only theoretically capable but also practically useful and integrated into software development workflows.

- **Implications for AI Safety and Ethics:** The authors explicitly address the societal impact, positioning SWE-bench as a potential "testbed for designing safe, robust measures towards aligned, verifiable, and safe AI-driven software engineering." As LMs increasingly automate software development, ensuring that AI-generated code aligns with human intent and does not introduce unforeseen vulnerabilities or misinterpret objectives becomes critical. SWE-bench offers a controlled environment to study these complex challenges.

In conclusion, SWE-bench is a landmark contribution that redefines the evaluation landscape for code-aware LMs. By providing a realistic, challenging, and continually updatable benchmark, it sets a clear and ambitious target for the next generation of intelligent and autonomous software engineering agents, driving fundamental advancements at the intersection of AI and software development.
