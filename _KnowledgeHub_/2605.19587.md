# SceneCode: Executable World Programs for Editable Indoor Scenes with Articulated Objects

> [!summary] Summary
> SceneCode turns a natural language prompt into an executable indoor world built from programs instead of static meshes. A room-level planner–designer–critic agent issues per-object requests. Each request is routed to one of five code-generation strategies, which write part-wise Blender programs that are repaired by execution feedback. The programs compile to SDF assets with joints. It beats baselines on prompt fidelity and asset quality.

## Problem

- Most text-to-scene pipelines represent generated content as static meshes, so object structure, parts, and motion are not exposed in the scene representation.
- Articulated objects, when present, inherit part structure and joint semantics from curated asset libraries, so an object missing from the dataset cannot be retrieved or customized on demand.
- Direct single-prompt VLM code generation is unreliable across diverse object families, and image-to-3D assets come as opaque triangle soups with fragmented UVs, non-manifold edges, and no semantic handles for editing.

## Method

- A room-level ==planner–designer–critic== backbone builds a house layout and emits per-object AssetRequests. A ==router== sends each request to one of five VLM code strategies or a fixed thin-covering template.
- Each request becomes a reference-conditioned ==ObjectPlan== of parts, primitives, poses, materials, and movability flags. A plan checker verifies it, then ==part-wise Blender programs== are synthesized and validated in headless Blender with 3 repairs and 2 critic refinements.
- A compilation step infers ==revolute or prismatic joints==, mass, inertia, and collision proxies, then exports SDF. A persistent ==scene-state registry== links each request, program, mesh, and simulation asset for traceable local re-execution and editing.

## Results

- On 30 SceneEval prompts, SceneCode leads on object count (**79.4%**) and attribute score (**74.0%**). It also has the lowest collision rate (**11.3%**) among methods and **100%** navigability, against SceneSmith, HSM, and LayoutVLM.
- Nine raters judged SceneCode more prompt-faithful than SceneSmith, HSM, and LayoutVLM, with gains of **+2.8%**, **+13.2%**, and **+24.6%** on a 5-point scale. The gap widens against the layout-oriented baselines.
- Against SAM 3D Objects on the same requests, SceneCode assets have **22** vs **96** UV islands, **0** vs **0.0164** non-manifold edges, and half the faces (**6,014** vs **12,037**). PBR coverage rises from **0.20** to **0.61**.

## Takeaways

> [!tip] Key Insights
> - Representing objects as executable part-aware programs makes geometry, articulation, materials, and physics attributes explicit, which yields editable, regenerable assets and removes the dependency on a fixed articulated-asset library.
> - Routing requests to category-specific prompts and adding a plan-verification step before code synthesis makes VLM code generation more reliable than one generic prompt across diverse object families.
> - Execution feedback (tracebacks plus rendered-view critique) works as a cheap validity filter, so broken assets do not reach scene assembly. Part-wise construction also yields clean topology and UVs.

## Detailed Report

### 1. How this work fits into the broader research landscape

The field of indoor scene synthesis is a foundational component for various applications, including embodied AI, robotic manipulation, and simulation-based policy evaluation. Current methodologies in this area predominantly represent generated content as static meshes. When articulated objects are included, their part structures and joint kinematics are typically derived from pre-existing, curated asset libraries. This dependency imposes limitations on object-level customizability and hinders the scalable, on-demand generation of novel interactable assets.

Existing systems have advanced scene synthesis from different perspectives:
- **Retrieval-based and LLM-guided systems** populate environments by querying large asset libraries, as seen in works like Holodeck, LayoutVLM, and HSM. While capable of diverse environment population, these systems are constrained by the available assets.
- **Layout-centric methods** focus on improving spatial plausibility through optimization techniques.
- **Agentic systems** such as SceneSmith generate simulation-ready environments with physical properties, often by mixing dataset retrieval with image-to-3D generation.

However, a persistent challenge across most of these pipelines is the representation of generated content as opaque, static meshes. This limits the ability to explicitly define how objects are structured, how they move, and how agents can physically interact with them, which is crucial for embodied AI and robotics. The customization and creation of interactable objects remain largely dependent on the availability of suitable pre-modeled assets.

This research addresses this gap by formulating indoor scene synthesis as programmatic world generation. SceneCode proposes a paradigm shift from generating static visual assets to producing executable code that defines entire indoor scenes and their constituent objects. This approach integrates object geometry, part decomposition, material assignment, physical attributes, and motion mechanisms into a unified, explicit, and editable code form, aiming to enable the on-demand creation of interactable objects without reliance on fixed asset libraries. This aligns with the emerging capabilities of vision-language models (VLMs) to translate natural language specifications into structured programs.

### 2. Key objectives and motivation

The core objective of this research is to develop a framework, named SceneCode, that can compile a natural language prompt into an executable, code-driven indoor world. This framework aims to generate scenes where objects are not merely static visual assets but possess explicit physical structure and defined interaction mechanisms, making them suitable for embodied AI, robotic manipulation, and simulation.

The motivation behind this objective stems from several limitations identified in current indoor scene synthesis pipelines:
1. **Limited Object-Level Controllability**: Existing methods predominantly represent generated 3D content as static meshes. This representation restricts the ability to customize object internal structure, functional parts, or interaction properties, which are often crucial for downstream applications requiring physical interaction.
2. **Dependence on Curated Asset Libraries**: When articulated objects are present in generated scenes, their movable parts and joint semantics are typically inherited from pre-existing, curated datasets (e.g., PartNet-Mobility). This dependency means that the range of interactable objects is constrained to what is available in these libraries. It prevents the generation of novel or customized articulated objects on demand, such as a cabinet with a specific number of drawers or a unique joint configuration.
3. **Lack of Intrinsic Physical and Interaction Metadata**: For an embodied agent, a functional indoor scene requires explicit information about object structure, movement capabilities, and interaction affordances, beyond just visual appearance. Current static mesh representations often lack this intrinsic physical metadata, necessitating post-processing or manual annotation for simulation readiness.
4. **Inefficiency in Scaling Interactable Content**: Manually modeling diverse interactable 3D assets is labor-intensive and costly. The absence of a scalable, automated method for generating such assets limits the creation of varied virtual worlds essential for training and testing AI systems.

SceneCode aims to address these motivations by:
- **Formulating scene synthesis as programmatic world generation**: Translating natural language descriptions into executable Blender Python programs that define object geometry, part structure, materials, physical attributes, and articulation.
- **Enabling on-demand interactable asset generation**: Overcoming the limitations of fixed asset libraries by synthesizing novel articulated objects tailored to prompt specifications.
- **Providing a unified, editable representation**: Coupling visual geometry, semantic structure, materials, articulation, and simulation metadata within the same object-level code, allowing for traceability and local modification.
- **Producing simulation-ready assets**: Automatically compiling generated objects into formats like SDF (Simulation Description Format) that are directly loadable into physics simulators.

### 3. Methodology and approach

SceneCode functions as an agentic text-to-scene pipeline that processes a natural language prompt to generate a renderable indoor scene, complete with scene-state metadata and simulation-ready asset files. The system separates the synthesis into two primary, coupled levels: a room-level agent for overall scene planning and a code-driven asset generator for individual object construction.

#### 3.1. Room-Level Agentic Scene Backbone

The room-level backbone translates the input scene prompt into a structured house layout and an ordered sequence of per-object `AssetRequest`s. Object requests within each room are emitted in four semantic stages: large furniture, wall-mounted objects, ceiling-mounted objects, and manipulable items. This process is driven by a planner–designer–critic loop:
- **Plan**: Identifies the next object placement task.
- **Design**: Invokes tools to create or modify objects based on the task.
- **Critic**: Evaluates the intermediate scene using rendered views, scene-state information, and geometric consistency checks.
Each `AssetRequest` (denoted as `A`) specifies the object category, textual description, target dimensions, style context, placement transform, and support relation. This sequence of requests forms the contract for the subsequent object-level program synthesis.

#### 3.2. Code-Driven Object Generation

This subsection details the conversion of each `AssetRequest` into an executable Blender program that produces a part-decomposed, renderable mesh. The pipeline consists of five steps:

##### 3.2.1. Asset Request and Strategy Routing

To accommodate the diverse geometric and functional priors of indoor objects, SceneCode introduces a router that dispatches each `AssetRequest` to one of six construction strategies. The decision considers the requested object category, textual description, support relation, expected size, and functional affordances. Five strategies are VLM-based, while one (`THINCOVER` for rugs/carpets) uses a fixed code template. The VLM-based strategies are:
- **WALLART**: For thin, print-like wall-mounted objects.
- **STATICFURN**: For large, rigid furniture without functional moving parts.
- **SIMPLEMANIP**: For structurally simple rigid objects with a dominant shape.
- **STRUCTMANIP**: For rigid objects with multiple visible components but no articulation.
- **ARTIC**: For objects with functional movable parts, which will be compiled into a link–joint structure.
Each VLM-based route is paired with a specialized construction prompt that encodes geometry-aware coding constraints (e.g., for symmetry, repeated structures, or curve construction).

##### 3.2.2. Reference-Conditioned ObjectPlan Construction

For most strategies (excluding `THINCOVER`), an `AssetRequest` is first expanded into a structured `ObjectPlan` (`P`) to reduce ambiguity. A reference image is generated, and an object planner consumes the `AssetRequest` and reference image to produce `P`. This plan enumerates semantic parts (`p_i`), their primitive types (`s_i`), local poses (`T_loc_i`), materials (`m_i`), symmetry tags (`π_i`), and a movability flag (`μ_i`). For requests routed to `ARTIC`, parts with `μ_i = 1` are subsequently compiled into a joint schema.

##### 3.2.3. ObjectPlan Verification

The generated `ObjectPlan` undergoes a verification step to address potential issues such as missing functional parts, implausible scales, or inconsistent part placements. This verification (`V`) combines rule-based validation with an LLM-based revision step, focusing on:
- **Part completeness**: Ensuring all functional parts are present and unnecessary ones are removed.
- **Dimension plausibility**: Correcting per-part scales to be consistent with the requested category and target dimensions.
- **Spatial consistency**: Revising local poses for coherent integration within the object-local frame.
- **Movable-part independence**: Ensuring movable parts remain distinct components, a prerequisite for downstream joint compilation.

##### 3.2.4. Part-wise Blender Program Synthesis

Given the verified `ObjectPlan` (`P*`) and the reference image, a part constructor synthesizes a Blender Python program (`π_i`) for each part. Each program generates a primitive-based mesh (`M_i`) with procedural materials in the object-local frame. A composition script then assembles the complete object mesh (`M`) by unioning these part meshes, ensuring that each `M_i` remains a separately named Blender object to preserve semantic decomposability.

##### 3.2.5. Execution-Guided Program Validation

Each synthesized program (`π_i`) is executed in a headless Blender instance and validated through a two-budget loop (K_exec = 3 for repairs, K_ref = 2 for refinements):
1. **Execute**: The program is run to materialize `M_i`.
2. **Repair**: If execution fails, the traceback and problematic code are returned to the synthesizer for up to `K_exec` repair attempts per part.
3. **Refine**: Upon successful execution, a critic agent inspects rendered images of the assembled object to verify that it meets the requested category, structure, and material requirements, triggering up to `K_ref` refinement iterations if necessary.
This loop enhances code reliability and prevents invalid assets from progressing to scene-level assembly.

#### 3.3. Simulation-Ready Asset Compilation

This stage converts the generated visual object into simulator-compatible asset files. SceneCode applies a compilation map (`C`) that bridges visual geometry and physical interaction:
- **Rigid Objects**: For non-articulated objects, `C` produces a single-body SDF (Simulation Description Format) with collision and inertial properties.
- **Articulated Objects**: For articulated objects, `C` additionally returns a joint schema (`J`) inferred by a VLM-assisted articulation compiler over the movable parts (`μ_i=1`) of `P*`. The compiler determines parent links, child links, joint types (revolute or prismatic), joint origins, axes, and motion ranges.
Each link is endowed with approximate physical attributes, including mass (estimated from semantics), inertia tensor (computed from mesh and mass), and a collision proxy (derived from simplified geometric envelopes). The resulting assets are exported as SDF artifacts for physics simulation.

#### 3.4. Scene Assembly and State Serialization

Scene assembly integrates the generated objects into the complete scene. Each generated object is registered as a `SceneObject` in a scene-level registry under a shared identifier (`id`). This identifier links the `AssetRequest`, executable programs, rendered mesh, and simulation artifacts (`J`, SDF). Object placement involves scaling the mesh (`M`) to target dimensions, applying the planned transform, and aligning it with its support relation. The shared identifier ensures traceability and local editability, enabling parameter-level edits and partial re-execution.

### 4. Main findings and results

The SceneCode framework was evaluated across scene-level synthesis, object-level asset quality, human judgment, and downstream robot interaction.

#### 4.1. Room-Level Scene Synthesis

##### 4.1.1. Qualitative Comparison

Qualitative assessments (Figure 3, Appendix I.1) indicate that scenes generated by SceneCode generally exhibit closer adherence to the prompt's described atmosphere, object composition, and spatial layout compared to baseline methods. SceneCode demonstrated the ability to render scenes that match specific object sets and spatial arrangements more faithfully. For example, SceneSmith could produce plausible furniture, but its capacity for customizing articulated objects was limited. HSM generated environments with local coherence in object placements within motif subtrees, but often struggled with explicit cross-subtree relationships stated in prompts (e.g., "the desk faces the bed").

##### 4.1.2. Quantitative Summary

Automatic evaluation utilized SceneEval metrics (Table 1) on 30 room-level prompts.
- **Semantic Fidelity**: SceneCode achieved the highest scores in Object Count (CNT: 79.4%) and Object Attribute (ATR: 74.0%). The ATR advantage (e.g., 0.0182 higher than SceneSmith) is attributed to the executable object programs, which allow direct realization of prompt attributes during object construction, rather than relying on approximations from retrieved meshes.
- **Physical Plausibility**: SceneCode demonstrated strong performance in physical usability metrics: it achieved 100.0% navigability (NAV), a collision rate (COL) of 11.3%, and an out-of-bounds (OOB) rate of 0.4%. The collision rate was approximately half that of the baselines, and OOB was an order of magnitude lower than some competitors. This is linked to the generation of clean, bounding-box-faithful geometry, enabling precise reasoning about collisions and floor containment.
- **Areas for Further Development**: SceneCode did not lead in Object–Object Relationship (OOR: 32.6%), Object–Architecture Relationship (OAR: 61.1%), Support (SUP: 44.3%), Accessibility (ACC: 74.2%), and Opening Clearance (OPC: 12.4%). These results are partly attributed to the pipeline's asset-acceptance behavior, where object programs failing validation are skipped, potentially removing some relation-bearing objects. Additionally, specific design choices regarding support type classification and opening-clearance checks are noted as factors.

##### 4.1.3. User Study

A user study involving nine participants evaluated prompt faithfulness, preference, and realism (Table 6). SceneCode was judged to be more prompt-faithful than all baselines, with paired per-trial differences (SceneCode minus Baseline) of +2.8% against SceneSmith, +13.2% against HSM, and +24.6% against LayoutVLM (on a 5-point Likert scale). This indicates that the programmatic object generation approach yields scenes that align more closely with human interpretations of natural language prompts. On realism, SceneCode rated higher than HSM (+0.27) and LayoutVLM (+1.93) but slightly lower than SceneSmith (−0.34). This realism difference is suggested to be related to SceneSmith's use of photorealistic retrieved meshes for some objects, whereas SceneCode prioritizes attribute-faithful programmatic geometry.

#### 4.2. Object-Level Geometry and UV Quality

SceneCode was compared against the image-to-3D baseline SAM 3D Objects using mesh- and material-level metrics (Table 2).
- **Mesh and UV Usability**: SceneCode demonstrated advantages across metrics relevant to editability and simulation readiness:
 - It produced a higher material slot count (MAT: 1.5738 vs. 1.0000) and PBR channel coverage (PBR: 0.6066 vs. 0.2000), indicating more comprehensive material modeling.
 - It generated topologically clean meshes with zero non-manifold edges (NME: 0.0000 vs. 0.0164).
 - SceneCode achieved lower face counts (FAC: 6013.64 vs. 12036.57) and vertex counts (VTX: 4945.07 vs. 7400.79), resulting in more compact geometric representations.
 - Significantly, SceneCode produced substantially fewer UV islands (UVI: 22.0328 vs. 96.4098), indicating a more coherent and organized UV parameterization (Figure 4a), which is beneficial for texturing and editing.
 These improvements are attributed to the part-wise primitive program approach, where each part maintains its own mesh, materials, and UV layout.

- **Code-Level Editability**: The programmatic representation of objects enables post-generation editing. Specific parameters (e.g., number of leaves, angular/radial subdivisions for a potted plant) within an object's code can be modified and re-executed locally to produce variations without regenerating the entire asset (Figure 4b).

- **On-Demand Articulated Objects**: SceneCode addressed the limitation of fixed asset libraries for articulated objects. It demonstrated the ability to synthesize customized articulated assets directly from the prompt, including specific functional structures (e.g., a multi-drawer cabinet) or materials (e.g., a glass-fronted cabinet), which retrieval-based pipelines cannot typically provide (Figure 4c, Appendix I.3).

#### 4.3. Articulation and Robot Interaction

Demonstrations importing SceneCode-generated articulated objects into the MuJoCo physics simulator confirmed their physical interactivity (Figure 5). Movable components were preserved as independent links with compiled joint metadata (e.g., revolute joints for hinged doors, prismatic joints for sliding drawers). This allows robots to physically interact with and manipulate these objects through contact, demonstrating the suitability of the generated assets for embodied interaction and simulation.

### 5. Significance and potential impact

The SceneCode framework introduces an executable, code-driven approach to indoor scene synthesis, representing objects as part-aware programs rather than opaque meshes. This methodology presents several areas of significance and potential impact:

1. **Advancement in Embodied AI and Robotics**: By generating physically interactable indoor scenes with articulated objects, SceneCode provides a more robust and flexible foundation for training and evaluating embodied AI agents and robotic manipulation systems. The explicit representation of physical structure and interaction mechanisms in the generated environments can lead to more realistic and diverse simulation scenarios, potentially accelerating research in areas such as task planning, navigation, and object manipulation.

2. **Unbounded Generation and Customization of Interactable Assets**: A key contribution is the ability to synthesize new interactable objects on demand, overcoming the limitations imposed by reliance on fixed, curated asset libraries. This capability allows for the creation of novel object designs with specific articulation, dimensions, materials, and functional properties directly from natural language prompts. This expands the diversity and specificity of virtual content, reducing the bottleneck of manual asset creation.

3. **Enhanced Controllability and Editability of 3D Scenes**: Representing objects as executable code provides fine-grained control over their geometry, part decomposition, materials, and physical attributes. This programmatic representation facilitates local editing and regeneration of object properties. Users or subsequent AI agents can modify individual attributes (e.g., dimensions, joint ranges, materials) and re-execute the corresponding code, fostering an editable and traceable world-building process.

4. **Improved Asset Quality and Simulation Readiness**: The methodology yields assets with demonstrably cleaner mesh topology (e.g., zero non-manifold edges), better UV organization, and more complete material modeling (e.g., PBR channel coverage) compared to image-to-3D generation pipelines. These characteristics are crucial for downstream applications requiring high-quality rendering and robust physics simulation. The automatic compilation into simulation-ready formats like SDF further streamlines the integration of generated content into physics engines.

5. **Unified and Traceable Scene Representation**: SceneCode integrates all aspects of scene generation—from natural language prompts to object requests, executable programs, rendered geometry, and simulation artifacts—under a shared identifier in a persistent scene-state registry. This unified approach enhances traceability, simplifies scene assembly, and supports localized edits and regeneration, contributing to a more efficient and manageable virtual environment development workflow.

In summary, SceneCode shifts the paradigm from static 3D asset generation to a dynamic, code-driven approach, providing a foundation for creating intelligent, interactable virtual worlds that are directly usable for advanced AI and robotics research.
