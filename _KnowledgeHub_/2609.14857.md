# ModularRSI: Modular and Generalizable Recursive Harness Self-Improvement

> [!summary] Summary
> ModularRSI is a framework for recursive self-improvement of LLM agent harnesses. It contrasts successful and failed trajectories of the same task, aggregates evidence across tasks, and evolves five functional harness modules (Agent Loop, Tool Use, Observation Management, Context Management, Task Completion Detection) independently before cross-module integration under validation gates. Evolved on tasks sampled from a 2,000-instance benchmark-disjoint pool, it lifts TerminalBench 2.0 accuracy from 47.57 to 52.43.

## Problem

- Existing harness RSI methods evolve on downstream evaluation benchmarks or their subsets, so reusable improvements cannot be distinguished from benchmark-specific adaptation.
- Updates derived from individual one-sided trajectories entangle systematic harness deficiencies with instance-specific reasoning and solution details, yielding task-specific edits that transfer poorly to unseen tasks.
- Even when recurring deficiencies are identified, monolithic whole-harness optimization cannot localize them to a responsible component, entangling unrelated mechanisms and producing changes hard to attribute or validate.

## Method

- **Contrastive Trajectory Sampling and Analysis**: K rollouts per task split into Positive, Contrastive and Negative groups, with a **Trajectory Memory** supplying past successes so all-failed tasks still get paired comparisons.
- Harness modularization into five independently evolvable modules, each edited within restricted scope via vote-ranked **Modification Target Selection** and an **Evolution History**, then unified by a **Cross-Module Integration** epoch.
- **Validation Gates** (==program check==, ==generalization-oriented diff review==, ==execution validation==) roll back bad edits; **Function Merge** plus a **Task-Aware Function Composer** keeps the growing function library compact and task-relevant.

## Results

- In-domain evolution lifts TerminalBench 2.0 accuracy from **47.57** to **52.43** and SWE-Bench-Verified from **73.40** to **76.45**; cross-domain transfer still yields **49.40** and **75.80** respectively.
- Frozen harness transfers across backbones: GLM-5.2 **59.55** to **61.80**, MiniMax-2.5 **41.57** to **44.94**; under matched evolution budget it reaches **67.42** versus AHE **62.54** and Meta-Harness **62.92**.
- Modular evolution beats alternatives: joint all-module evolution drops to **44.19** and non-modular to **46.44**; every single-module variant gains, with Observation Management cutting steps from **34.70** to **22.50**.

## Takeaways

> [!tip] Key Insights
> - Benchmark-disjoint evolution data is the honest test of self-improvement: methods strong on benchmark-derived evolution shrink to roughly one accuracy point under disjoint protocols.
> - Restricting each edit to one functional module beats whole-system rewriting; unconstrained joint optimization actively hurt, so credit-assignment scope matters more than optimization budget.
> - Medium-difficulty evolution tasks carry the most learning signal, since contrast needs both successes and failures, which easy or extremely hard tasks cannot supply.

## Detailed Report

### 1. Position Within the Broader Research Landscape

The paper addresses recursive self-improvement (RSI) for large language model agents that operate over long horizons in terminal and software-engineering environments. In these systems, performance depends not only on the foundation model but also on the agent “harness”: the software layer that controls reasoning loops, tool invocation, terminal observations, context handling, error recovery, and decisions about task completion.

Earlier research has explored several forms of self-improvement. Some methods update model parameters, while others accumulate skills, optimize prompts, compress observations, or modify an agent’s external execution mechanisms. Recent harness-evolution systems directly rewrite or synthesize portions of agent code using execution trajectories and task-level rewards. These approaches establish that agents can improve their operating procedures from experience, but they leave open whether the improvements transfer to new tasks.

The paper identifies three weaknesses in existing harness RSI. First, many methods evolve directly on benchmark instances or data derived from evaluation benchmarks. This creates uncertainty about whether the resulting changes are general execution improvements or benchmark-specific adaptations. Second, a single successful or failed trajectory often mixes harness behavior with task-specific reasoning. A modification based on one trajectory may therefore encode details of a particular problem rather than a reusable mechanism. Third, many systems treat the harness as a monolithic object. When a recurring failure is observed, it is difficult to determine whether the relevant cause lies in context management, tool use, the agent loop, or another component. Broad edits can consequently create interference between unrelated mechanisms.

ModularRSI is positioned as a response to these issues. It combines benchmark-disjoint evolution data, contrastive analysis of successful and failed executions for the same task, and independent evolution of functionally defined harness modules. Its broader contribution is methodological: it proposes a way to evaluate harness self-improvement as transferable system-level learning rather than direct optimization against a test benchmark.

### 2. Objectives and Motivation

The central objective is to develop a harness-evolution framework that produces improvements generalizable across unseen tasks, domains, and foundation models. The authors seek to move beyond the common setting in which an agent modifies its harness using examples drawn from the same benchmark on which it is later evaluated.

A second objective is to improve credit assignment. Task-level rewards provide only a binary indication of success or failure and do not directly specify which execution mechanism caused the outcome. ModularRSI therefore compares trajectories generated for the same task. When one trajectory succeeds and another fails, their behavioral divergence provides more specific evidence about what the harness may need to change. The system also aggregates evidence from multiple tasks so that modifications are supported by recurring patterns rather than isolated failures.

A third objective is to reduce interference during code evolution. The authors divide the harness into five modules: Agent Loop, Tool Use, Observation Management, Context Management, and Task Completion Detection. Each module has a restricted modification scope and is evolved independently. The separately evolved modules are subsequently integrated, allowing the system to address cross-module conflicts in a controlled stage.

The paper also aims to establish a more informative experimental protocol. It constructs 2,000 executable evolution tasks from external sources and keeps them disjoint from TerminalBench 2.0 and SWE-Bench Verified. The evolved harness is frozen before downstream evaluation, which allows the reported results to measure transfer beyond the evolution experience.

### 3. Methodology and Approach

#### 3.1. Harness Decomposition

ModularRSI starts with the Terminus-2 harness from the Harbor framework. Its behavioral mechanisms are reorganized into five modules:

1. **Agent Loop**, which coordinates iterative reasoning, action, observation, retries, state, and stopping decisions.
2. **Observation Management**, which processes terminal and environmental feedback, retaining useful information while filtering or compressing noise.
3. **Tool Use**, which parses model responses, selects and invokes tools, and handles execution results and parsing errors.
4. **Context Management**, which maintains conversation history and performs compression or summarization when necessary.
5. **Task Completion Detection**, which determines whether the agent has produced sufficient evidence to stop or should continue interacting with the environment.

Infrastructure components such as sandbox initialization and model communication are not freely evolved because the authors focus on mechanisms that directly mediate agent-environment interaction.

#### 3.2. Contrastive Trajectory Analysis

For each evolution task, the agent is rolled out multiple times. Each trajectory receives a binary task reward. Tasks are classified as:

- **Positive**, when all current rollouts succeed.
- **Contrastive**, when some rollouts succeed and others fail.
- **Negative**, when all current rollouts fail.

Contrastive tasks are the main source of diagnostic evidence. Successful and failed trajectories for the same task are paired, and the system examines where their behavior diverged. The analysis asks whether a concrete change within the currently targeted module could plausibly have changed the failed outcome. This counterfactual requirement is intended to prevent unsupported blame attribution.

For all-fail tasks, the system searches a trajectory memory for a previously successful execution of the same task. If one exists, it can be compared with a current failure. If no successful trajectory is available, the system performs one-sided diagnosis of observable problems such as repetitive loops, incorrect tool calls, weak recovery, or premature termination. For all-success tasks, the analysis focuses on efficiency problems, including redundant exploration or unnecessary tool invocations.

The resulting diagnoses are stored in structured records containing the target module, trajectory evidence, causal interpretation, proposed modification, and whether the issue is considered fixable within the module’s scope.

#### 3.3. Module-Wise Evolution and Integration

Similar diagnoses targeting the same function are consolidated. Candidate modifications receive support counts based on the number of distinct tasks providing evidence. This prioritizes changes that recur across tasks and reduces the effect of one-off failures.

The system maintains an evolution history for each function. Previous modifications and their intended functionality are shown to the code-modification agent to reduce oscillation, duplication, and accidental removal of useful behavior.

Each accepted modification passes three validation gates:

- **Program checks**, including abstract syntax tree validation, import checks, protocol compliance, and interface audits.
- **Diff review**, in which the modification is screened for task-specific names, files, outputs, constants, or heuristics.
- **Execution validation**, in which the updated harness is run on sampled evolution tasks to detect runtime or protocol failures.

After independent evolution of all five modules, ModularRSI performs cross-module integration. This stage addresses duplicated mechanisms, inconsistent responsibilities, and interaction conflicts without introducing unrelated new capabilities. Function merging reduces redundancy in the evolving library, while task-aware composition selects only functions relevant to the current task.

#### 3.4. Evolution Dataset and Evaluation

The authors curate 2,000 executable tasks, divided evenly between SWE-related and terminal-related tasks. Sources include GitHub, Hugging Face, Kaggle, and Linux documentation. The sources are used to obtain broad domain guidance, but downstream benchmark instances and task-specific information are excluded.

Quality control checks environment completeness, task non-triviality, evaluator validity, reference-solution execution, no-op failure, manual correctness, and semantic similarity to downstream benchmarks. For the reported experiments, 120 tasks from each subset are used for evolution. Evolution runs for three epochs using DeepSeek-V4-Flash-Preview and DeepSeek-V4-Flash-0731.

Evaluation uses TerminalBench 2.0, containing 89 terminal tasks, and SWE-Bench Verified, containing 500 software-engineering tasks. Metrics include trajectory accuracy, Pass@3, Pass³, and average interaction steps.

### 4. Main Findings and Results

#### 4.1. Generalization Across Tasks and Domains

With DeepSeek-V4-Flash-Preview, the baseline accuracy on TerminalBench 2.0 is 47.57%, rising to 52.43% after evolution on TB-related tasks. On SWE-Bench Verified, baseline accuracy is 73.40%, rising to 76.45% after evolution on SWE-related tasks.

Cross-domain transfer is also observed. A harness evolved on TB-related tasks increases SWE-Bench Verified accuracy to 75.80%, while a harness evolved on SWE-related tasks increases TerminalBench 2.0 accuracy to 49.40%. On TerminalBench, Pass³ rises from 30.34% to 35.96% for the in-domain evolved harness, indicating improved consistency across repeated attempts.

#### 4.2. Transfer Across Foundation Models

A harness evolved using DeepSeek-V4-Flash-Preview is evaluated with other models on TerminalBench 2.0. Accuracy improves from 59.55% to 61.80% with GLM-5.2, from 41.57% to 44.94% with MiniMax-2.5, and from 47.57% to 52.43% with DeepSeek-V4-Flash. Pass@3 and Pass³ also improve for all three models. This result suggests that the learned changes concern execution procedures rather than only model-specific response patterns.

#### 4.3. Effect of Modularity

The comparison of evolution strategies supports the modular design. The baseline accuracy is 47.57%. Non-modular evolution produces 46.44%, while joint evolution of all modules produces 44.19%. ModularRSI reaches 52.43%. It also produces the highest Pass³ score, 35.96%, compared with 30.34% for the baseline.

All five single-module variants improve accuracy relative to baseline. Agent Loop evolution gives the largest individual accuracy increase, reaching 50.56%. Tool Use reaches 50.19%, Observation Management 49.81%, Context Management 49.44%, and Task Completion Detection 49.44%. Observation Management substantially reduces average steps, from 34.70 to 22.50. Integration of the five modules yields additional gains, indicating that the modules provide partly complementary improvements.

#### 4.4. Comparison with Other RSI Methods

Under a unified benchmark-disjoint protocol, ModularRSI reaches 67.42% accuracy on TerminalBench 2.0, compared with 61.79% for the baseline, 62.92% for Meta-Harness, and 62.54% for AHE. ModularRSI also records higher Pass@3 and Pass³. The authors note that these competing methods can perform more strongly when evolved directly on benchmark data, but their gains are smaller when benchmark data are excluded from evolution.

#### 4.5. Role of Data Quality and Contrastive Evidence

The proportion of available successful-failed trajectory pairs decreases from 40.67% in the first epoch to 34.17% in the third, which the authors interpret as evidence that recurring deficiencies are being reduced. Case studies show improvements such as requiring explicit acceptance checks before completion and routing multiline file-writing commands correctly.

Difficulty distribution also matters. An evolution set centered on medium-difficulty tasks produces 76.45% accuracy on SWE-Bench Verified, compared with 74.25% for a set dominated by easy and hard tasks. The result supports the claim that moderately difficult tasks provide more useful mixtures of successful and failed trajectories.

### 5. Significance and Potential Impact

The paper’s primary significance lies in framing harness evolution as a problem of transferable mechanism discovery. Its benchmark-disjoint protocol provides a clearer test of generalization than direct benchmark optimization. The modular design also offers a practical way to constrain automated code modification, improve interpretability, and reduce interference between unrelated execution functions.

If validated by larger and independently reproduced studies, the approach could support more reliable improvement of coding and terminal agents without retraining their foundation models. The modular function library may also permit reuse across models and task families.

The conclusions remain subject to limitations acknowledged by the authors. The main experiments use only 240 of the 2,000 curated evolution tasks, and the paper does not provide a dedicated ablation isolating contrastive analysis from the other framework components. Several case studies combine multiple updates, so individual causal effects are not fully separated. Future work should therefore test larger evolution sets, broader foundation-model families, stronger controls for evaluator and model bias, and explicit ablations of trajectory contrast, validation gates, function composition, and integration.
