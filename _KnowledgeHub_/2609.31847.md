# Omni-IO Skills: Harnessing Your Agent Omni-Native

> [!summary] Summary
> Omni-IO Skills is a plug-and-play agent harness that makes existing general-purpose agents omni-native without retraining. Hierarchical Atomic, Expert, and Scenario Skills expand requests into dependency-aware Declare Execution Graphs, run concurrently in waves over replaceable MCP-backed providers, and persist outputs in an Asset Registry for cross-turn reuse. On UniM-90 it lifts input support from about 40% to 100% and relative semantic-quality score by roughly 48-50 points.

## Problem

- Extending Omni foundation models to new modalities ties capability growth to costly model updates, requiring new data, codecs, decoders, and alignment stages while specialist models keep improving outside the backbone.
- Model-coordination Omni agents delegate to modality experts but target question answering and evidence gathering, not production workflows that create multiple dependent artifacts with provenance and revision.
- Existing Agent Skills package procedural knowledge for expert, computer-use, or visual tasks, yet leave unresolved how to coordinate dependencies, intermediate assets, local failures, and cross-turn reuse across modalities.

## Method

- ==Hierarchical Skills==: 19 Atomic, 2 Expert, and 6 Scenario Skills share a declarative contract of applicability conditions, inputs, procedure, outputs, and relations, recursively expanded into executable terminal tasks.
- ==Declare Execution Graph==: terminal tasks become validated acyclic nodes scheduled in ==concurrent Waves== by declared dependencies; a failed node cancels only its descendants while independent branches keep executing.
- Four-layer architecture with an ==MCP Tool Service== and ==Provider-Configuration binding== for swappable backends, plus an append-only, file-locked ==Asset Registry== recording provenance and turn IDs for cross-turn reuse.

## Results

- On UniM-90, input-support rate rises from **40.00%** to **100%** for GPT-5.6 Sol and from **38.89%** to **100%** for Claude Sonnet 5.
- Relative SQCS climbs from **26.99** to **74.94** and from **27.82** to **77.78**; absolute SQCS also improves, **67.49** to **74.94** and **71.53** to **77.78**, despite broader coverage.
- Strict Structure Score reaches **100.00** and **99.78**, Lenient Structure Score **100** for both hosts; relative ICS rises from **34.61** to **93.98** and **32.00** to **83.28**. No component ablations reported.

## Takeaways

> [!tip] Key Insights
> - Omni capability can be composed at the harness layer rather than trained into the model, letting modality coverage evolve with specialist backends instead of model update cycles.
> - Representing multi-asset work as an explicit dependency graph with persistent asset IDs makes revision cheap: later turns rerun only changed nodes while reusing validated assets.
> - Caution: gains come from a 90-instance subset without ablations, so the contribution of hierarchy, wave scheduling, or the registry versus simply adding tools stays unisolated.

## Detailed Report

### 1. Overview

A general-purpose agent may reason and plan well. Making a coordinated package across media still requires access to specialist capabilities, and a way to keep procedures, dependencies, and generated files in sync. Consider a request that uses five product photos to ask for three related deliverables: a poster, a precisely specified promotional video, and a responsive landing page. In the paper's case study, both GPT-5.6 Sol and Claude Sonnet 5 produced the requested outputs and preserved product identity across them. This is a qualitative demonstration. It does not show that every multi-asset job will succeed.

The system behind this is Omni-IO Skills. Its central move is to add a harness around the existing agent, rather than retrain or replace its reasoning core. Reusable Skills describe what to do, a dependency graph coordinates tool calls, and a persistent registry lets successful outputs flow into later steps and future turns.

Two qualitative case studies. Top: a request for an 11-image Korean night-market drawing tutorial based on an instructional video and audio, followed by tutorial images. Bottom: the Owala FreeSip product brief and reference images, followed by a poster, video storyboard/frames, and landing-page image.

### 2. From request to coordinated deliverables

A Skill is a reusable procedure for a capability or workflow. The Skills form a hierarchy:

- **Atomic Skills** perform a focused operation.
- **Expert Skills** manage a professional workflow for one deliverable.
- **Scenario Skills** coordinate several deliverables for an application context.

When a request arrives, the host selects and expands Skills into terminal tasks. Each task becomes a node in a Declare Execution Graph (DEG), in which a declared dependency says a task must wait for another task or asset. Before execution, the graph is checked for unresolved references and cycles. Ready independent nodes then run in concurrent Waves, while dependent nodes wait for their inputs. Each node routes through a standardized tool interface to a configured provider, and upstream assets are injected into downstream work.

Successful outputs are registered for reuse. If a node fails, its pending descendants are cancelled, but independent branches can continue. A later request can refer to a registered historical asset as an already-completed source node. The authors describe these steps as coordination and reuse. The paper does not measure faster completion or fewer calls.

A product-promotion request flows through Skills into a DEG executed in Waves 0–3. The waves analyze product-reference images, then generate poster assets and video/sound effects in parallel, then generate the promotional video and poster, and finally assemble a landing webpage. Successful outputs go to the Asset Registry for reuse.

### 3. What the benchmark shows

UniM-90 is a fixed 90-instance subset of UniM, selected across 30 domains. The evaluation uses two metrics:

- **Input-support rate** is the share of instances for which the agent can fully receive and process all input modalities.
- **Relative SQCS** (Semantic–Quality Coupled Score) jointly evaluates semantic correctness and generation quality, scaled by the input-support rate. It therefore reflects the whole 90-instance set.

Failures to generate required outputs remain in metric computation when inputs can be processed.

For GPT-5.6 Sol, adding Omni-IO Skills raises the input-support rate from 40% to 100% and relative SQCS from 26.99 to 74.94. Its Strict Structure Score (StS), which measures adherence to required output structure, rises from 47.84 to 100.00. Claude Sonnet 5 shows the same direction: its input-support rate also reaches 100%, its relative SQCS rises from 27.82 to 77.78, and its StS reaches 99.78.

Each comparison is within a single host. The baseline retained its built-in capabilities, while the harness configuration added Omni-IO Skills and its MCP services. Other settings, prompts, tools, and execution budgets were held unchanged. The authors caution against treating cross-host score differences as a model ranking.

### 4. Scope of the result

The authors frame Omni-IO as a complementary route to omni capability, not a new all-in-one foundation model. It differs from [Agent-Omni](https://www.alphaxiv.org/abs/2511.02834), which coordinates modality-specialist models for multimodal understanding and returns textual answers. This is a difference in scope and mechanism, not a head-to-head result.

The evidence supports the combined harness as evaluated on the fixed 90-instance subset. The paper reports no component ablation that separates graph scheduling or persistent asset reuse from adding the Skills and tool services. Parallel scheduling and cross-turn reuse remain mechanisms the authors describe, not demonstrated efficiency gains in the benchmark.
