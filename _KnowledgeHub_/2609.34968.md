# RoboFL: Federated Expert Assembly for World Action Models

> [!summary] Summary
> RoboFL is a federated framework for training world-action models from task-siloed robot data. Its MoSAIC protocol installs each client's locally trained LoRA adapter as an expert slot in a server-side mixture-of-experts, where routers are trained on server data; FARD distills understanding-generation routing consensus into action routing, and PCEA condenses expert updates into a global adapter. It beats centralized PEFT InternVLA-A1 by 12.23% on a real Franka arm.

## Problem

- Robot interaction data is scarce, costly, and institutionally siloed by privacy and ownership concerns, yet existing VLA and world-action models assume centralized training on pooled data.
- Naive federated averaging of LoRA adapters across task-disjoint, non-IID clients blends transformations that are valid only within their own task families, diluting local specialization.
- Federated MoE methods like FedVLA train routers on narrow client distributions, so averaging experts and routers dilutes knowledge, destabilizes expert selection, and multiplies client communication cost.

## Method

- **MoSAIC** (==Mixture of Slotted Adapters==): each client trains one LoRA adapter on its task family; the server installs it unaveraged into a fixed expert slot and trains routers on mixed-task data.
- **FARD** (==Foresight-to-Action Routing Distillation==): a ==reliability-weighted Jensen-Shannon loss== distills the geometric-mean routing consensus of the understanding and generation paths into the action path's router.
- **PCEA** (==Path-Consensus Expert Aggregation==): ==Hellinger-barycenter== routing evidence across three paths weights complete expert updates, compressed by ==truncated SVD== into a ==rank-16 global adapter== blended with each client's refined expert.

## Results

- RoboTwin 2.0 (50 tasks, 8 clients): **83.12%** overall, beating FedAvg by **4.20 points**, ForgeVLA at **80.70%**, FedVLA at **79.32%**, and centralized InternVLA-A1 at **81.60%**.
- Real Franka, six tasks: **59.17%** versus centralized InternVLA at **46.94%**, ForgeVLA at **35.56%**, and FedVLA at **33.61%**; per-round client communication drops up to **86.81%** versus MoE-based federated baselines.
- Ablation: FARD plus PCEA raises RoboTwin tasks at 90% or higher success from **19** to **24** and perfect tasks from **4** to **9**; on small RLBench, RoboFL's **41.25%** trails centralized **52.75%**.

## Takeaways

> [!tip] Key Insights
> - Separate local specialization from global routing: install client-trained adapters as experts and learn routing centrally, rather than averaging routers and experts trained on narrow client distributions.
> - Agreement across the understanding, foresight, and action paths of a world-action model is a free supervision signal for both expert routing and weighted parameter aggregation.
> - Expert-assembly gains depend on scale and heterogeneity: with few tasks and clients, routed composition trails centralized training, and results use single seeds without formal privacy guarantees.

## Detailed Report

### 1. Overview

Robot demonstrations are costly to collect and often belong to institutions that cannot or do not want to pool their raw trajectories. The tasks at those institutions also differ, so simply averaging locally trained updates can blur the skills that make each model useful. RoboFL keeps those local adaptations separate and has a shared server learn how to route among them. Clients do not have to train or send a multi-expert model. The authors frame this as a way to combine complementary capabilities without "exposing or erasing their source." On six tested single-arm Franka tasks, they report higher average task success than their centralized PEFT reference.

### 2. Keep the adapters distinct

LoRA is a compact, low-rank adaptation to a pretrained model. A mixture-of-experts (MoE) uses a router to select among specialist branches for different input tokens.

The procedure runs as follows:

1. Each client trains one LoRA on its private task-family data. It sends the adapter parameters, not raw trajectories.
1. In each round, the server installs that client's adapter directly in a fixed expert slot. No averaging occurs at installation. The slot preserves client-to-expert identity. It does not restrict which tokens the server router may send to that expert.
1. The server uses mixed-task server data to refine the experts and routers together.
1. The server retains the routers. Clients do not train, receive, or infer with the server MoE.
1. After server refinement, each client receives a rank-constrained adapter. It is an equal blend of that client's post-server expert and a shared global adapter.

This blend is a static adapter conversion for redistribution. It does not guarantee that the compact adapter behaves exactly like the input-dependent server MoE.

The closest robotic predecessor, [FedVLA](https://www.alphaxiv.org/abs/2508.02190), trains dual-gating MoE models on clients. RoboFL changes where the mixture is assembled: clients train and exchange a single LoRA adapter, and the server refines routers and experts.

### 3. The real-robot comparison

Across the six Franka tasks, RoboFL reports 59.17% mean success and centralized InternVLA-A1 PEFT reports 46.94%. That is a 12.23-percentage-point difference, not a 12.23% relative increase. Each method was evaluated in three rounds of 20 trials per task.

The centralized reference pools the task families instead of using the federated silo arrangement. It therefore has stronger data access and is not an equal-budget federated comparator. In both settings, deployment is one rank-16 adapter per client.

### 4. Where the result stops

RLBench is the main exception. That suite has eight tasks with 50 trials each, and its score is an equally weighted mean across the eight tasks. RoboFL's 41.25% is the best federated result there, but it is below centralized InternVLA-A1's 52.75%. The authors hypothesize that this smaller, lower-data suite offers less complementary evidence for routed composition. The comparison does not establish that explanation as the cause.

The server also does more than aggregate. It trains the shared router on a residual task group: 3 of 50 RoboTwin tasks, 2 of 8 RLBench tasks, and 2 of 6 Franka tasks.

Raw trajectories stay with clients, but this is not a formal privacy guarantee. The authors explicitly do not claim differential privacy or secure aggregation, and they note that parameter updates may still leak information.

### 5. The point

RoboFL avoids two extremes: isolating each institution's policy, or averaging away its specialty. The server composes intact, task-trained adapters and then returns a compact personalized adapter to each client. The results support this design in some tested settings, not in every task regime.
