# KernelBench: Can LLMs Write Efficient GPU Kernels?

> [!summary] Summary
> KernelBench is an open-source benchmark of 250 PyTorch workloads, from single operators to full architectures, that tests whether language models can write correct and fast GPU kernels. It scores them with fast_p, the fraction of kernels that are correct and beat a speedup threshold p. Frontier reasoning models match PyTorch in under 20% of tasks. Execution and profiler feedback raises success considerably.

## Problem

- Writing efficient GPU kernels takes scarce expertise and lags new architectures and hardware; FlashAttention arrived five years after the Transformer and two more years to port to Hopper.
- Existing LM code-generation benchmarks target functional correctness or asymptotic efficiency, not wall-clock hardware performance, and lack the rich compiler, profiler and hardware context that kernel engineering needs.
- Prior HPC code-generation evaluations cover only C++-to-CUDA translation or a few well-known low-level kernels such as GEMMs, not diverse real-world deep learning workloads that lack human-written kernels.

## Method

- Task format: given a PyTorch ==Model class== with fixed input shapes and dtypes, the LM writes an optimized ==ModelNew==, choosing which operations to optimize, in any language or library, such as CUDA, Triton or ThunderKittens.
- 250 tasks in ==three levels==: 100 ==single primitive operations==, 100 ==fusable operator sequences==, and 50 ==full architectures== such as AlexNet and MiniGPT taken from popular GitHub repositories.
- The ==fast_p metric== is the fraction of tasks that are both correct across 5 random inputs and faster than PyTorch by more than a ==threshold p==. fast_0 equals the correctness rate. ==Iterative refinement== feeds in ==compiler and profiler feedback==.

## Results

- One-shot on an L40S GPU, models beat PyTorch Eager in under **20%** of tasks on average; DeepSeek R1 leads with **fast_1** of **12%** on Level 1 and **36%** on Level 2, but only **2%** on Level 3.
- Iterative refinement with execution and profiler feedback raises **fast_1** from **12%**, **36%** and **12%** to **43%**, **72%** and **18%** for the three settings the paper reports.
- Most failures are execution errors and functional incorrectness; models fix execution errors with reasoning or repeated attempts but still struggle with correctness. Adding hardware specs and optimization examples surfaces more fusion, sparsity and tensor-core optimizations.

## Takeaways

> [!tip] Key Insights
> - Correctness, not speed, is the main bottleneck: aggressive optimizations such as tensor-core wmma trade off against error-free code, so benchmarks should report both jointly with a threshold metric.
> - Low-resource languages limit LMs; CUDA is only 0.073% of The Stack, suggesting that data scarcity, not just reasoning ability, caps performance and that fine-tuning or other data strategies are needed.
> - Automatic verification and closed-loop feedback from compilers and profilers reliably raise quality, so agentic iterate-and-measure workflows beat one-shot generation in any domain with cheap programmatic evaluation.

## Detailed Report

### 1. Introduction

The development of efficient GPU kernels is a critical bottleneck in accelerating machine learning workloads. While frameworks like PyTorch provide automated optimization, custom kernels written by experts often deliver superior performance. However, creating these kernels requires specialized expertise in parallel programming, hardware architecture, and optimization techniques.

The paper "KernelBench: Can LLMs Write Efficient GPU Kernels?" investigates whether large language models (LLMs) can automate this challenging task, potentially democratizing high-performance computing by allowing developers without specialized knowledge to generate optimized GPU code.

### 2. The Challenge of Kernel Optimization

GPU kernel development faces several key challenges:

1. **Expertise Barrier**: Writing efficient kernels requires deep knowledge of parallel computing, memory hierarchies, and hardware-specific optimizations.

2. **Hardware Diversity**: The growing variety of AI accelerators (GPUs, TPUs, custom ASICs) makes it difficult to maintain optimized implementations across platforms.

3. **Complex Trade-offs**: Developers must balance computation intensity, memory access patterns, register usage, and other factors to achieve optimal performance.

4. **Verification Complexity**: Ensuring kernels produce correct results across all input patterns requires thorough testing.

Existing approaches to address these challenges include:

- **Kernel Libraries**: Domain-specific libraries like cuDNN and CUTLASS provide optimized implementations but require expertise to use effectively.
- **DSLs and Compilers**: Tools like Triton and torch.compile offer higher-level abstractions but often generate less efficient code than hand-tuned implementations.
- **Automated Tuning**: Systems that search for optimal configurations still require manual development of the kernel template.

The core question becomes: can LLMs leverage their capabilities in code generation to automate the creation of efficient GPU kernels?

### 3. Methodology: The KernelBench Framework

The authors developed KernelBench, an open-source framework for evaluating LLMs' kernel generation capabilities. The framework focuses on three levels of increasing complexity:

1. **Level 1**: Individual operations (matrix multiplication, convolutions, etc.)
2. **Level 2**: Sequences of operations with fusion opportunities
3. **Level 3**: End-to-end ML architectures (AlexNet, MiniGPT)

The evaluation process follows these steps:

1. The LLM receives a PyTorch reference implementation as input
2. It generates optimized code with custom CUDA kernels
3. The framework evaluates:
 - Compilation success
 - Functional correctness (matching reference outputs)
 - Performance relative to PyTorch baselines

The key metric is *fast<sub>p</sub>*, the percentage of generated kernels that are both correct and achieve a speedup greater than threshold *p* over the PyTorch baseline.

The authors evaluated several state-of-the-art LLMs, including GPT-4o, Claude-3.5-Sonnet, DeepSeek-Coder V3, DeepSeek-Coder R1, Llama 3.1 (70B and 405B), and others. Primary experiments were conducted on NVIDIA L40S GPUs with additional cross-hardware evaluations.

### 4. Performance of LLMs for Kernel Generation

In one-shot evaluations (using only a simple prompt with an example), LLMs generally performed poorly:

Key findings include:

1. **Limited Success Rate**: Even the best models (DeepSeek-R1 and OpenAI o1) achieved fast<sub>1</sub> scores below 20% on Level 1 tasks, indicating they could match or exceed PyTorch performance on less than 20% of problems.

2. **Declining Performance with Task Complexity**: Performance further decreased on Levels 2 and 3, with most models achieving fast<sub>1</sub> scores below 10%.

3. **Model Variations**: Reasoning-focused models (like Claude-3.5-Sonnet) generally outperformed code-specific models on this task, suggesting that reasoning capabilities might be more important than specialized coding knowledge for kernel generation.

The plot reveals that while most LLM-generated kernels achieved modest speedups (1-2×), some exceptional cases reached 10× or more over the PyTorch baseline, demonstrating the potential for significant optimization in specific scenarios.

### 5. Error Analysis and Failure Modes

To understand why LLMs struggle with kernel generation, the authors conducted a detailed error analysis:

The analysis revealed several common failure modes:

1. **Compilation Errors**: A significant percentage of generated kernels failed to compile, with NVCC (NVIDIA's CUDA compiler) errors being particularly common. These often resulted from syntactic errors or misunderstandings of CUDA semantics.

2. **Runtime Errors**: Many kernels that compiled successfully crashed during execution due to memory access violations, race conditions, or other parallel programming issues.

3. **Correctness Issues**: Among kernels that executed without crashing, many produced incorrect results, either with shape mismatches (wrong output dimensions) or value mismatches (incorrect calculations).

4. **CUDA Expertise Gap**: LLMs showed limited understanding of CUDA-specific concepts like thread blocks, shared memory, and synchronization primitives, likely due to limited representation of CUDA code in their training data.

This analysis highlights that correctness remains a fundamental challenge for LLM-based kernel generation, which must be addressed before performance optimization becomes the primary focus.

### 6. Improving Performance Through Feedback

The authors explored whether providing feedback to LLMs could improve their kernel generation capabilities, mimicking how human developers use compiler errors and profiling data to refine their code.

The study tested three types of feedback:

1. **Generation History**: Providing only the model's previous attempts
2. **Execution Results**: Adding compilation errors and correctness information
3. **Profiler Data**: Including execution timing and performance metrics

The results showed significant improvements with feedback:

Key findings include:

1. **Substantial Improvements**: The fast<sub>1</sub> score increased from under 30% to over 70% after 10 iterations with full feedback.

2. **Feedback Value**: Execution results and profiler data significantly outperformed using only generation history, demonstrating the importance of concrete performance metrics.

3. **Model Differences**: DeepSeek V3 showed greater improvement with feedback than Llama 3.1 70B, suggesting some models may be better at incorporating performance-related feedback.

This approach also enables sampling multiple solutions and selecting the best-performing one, similar to how developers might try various optimizations and keep the fastest implementation.

### 7. Hardware Awareness and Optimization

One key challenge in kernel optimization is adapting code to specific hardware characteristics. The authors investigated whether providing hardware specifications could improve the hardware awareness of LLM-generated kernels.

When given detailed information about the target GPU (like compute capability, number of SMs, memory bandwidth, etc.), LLMs showed improved ability to:

1. **Select Appropriate Block Sizes**: Choosing thread configurations that map efficiently to the hardware's execution units
2. **Optimize Memory Access**: Aligning memory operations with cache line sizes and memory coalescing requirements
3. **Leverage Hardware Features**: Utilizing GPU-specific features like tensor cores when appropriate

The study also examined cross-hardware performance by testing kernels optimized for one GPU on different hardware:

The results showed that kernels optimized for one hardware platform often performed poorly on others, highlighting the importance of hardware-specific optimization and the potential value of LLMs that can adapt their generated code to different target platforms.

### 8. Case Studies and Success Examples

The paper highlights several case studies where LLMs successfully generated highly optimized kernels:

1. **Operator Fusion**: In one example, an LLM combined multiple operations (convolution, bias addition, and activation) into a single kernel, eliminating intermediate memory accesses and achieving a 10× speedup.

2. **Memory Hierarchy Management**: Some models effectively utilized shared memory for frequently accessed data and employed tiling strategies to maximize cache utilization.

3. **Algorithmic Improvements**: In certain cases, LLMs identified more efficient algorithms or mathematical transformations that reduced computational complexity.

4. **Thread Cooperation**: The best kernels demonstrated sophisticated use of thread cooperation patterns, with appropriate synchronization and work distribution.

These success cases often exhibited characteristics similar to expert-written code, including careful management of parallelism, efficient memory access patterns, and hardware-specific optimizations.

### 9. Implications and Future Directions

The KernelBench study provides several important insights about the current state and future potential of LLM-based kernel generation:

1. **Current Limitations**: Off-the-shelf LLMs struggle with kernel generation, particularly with correctness and CUDA-specific knowledge.

2. **Promising Paths Forward**:
 - Iterative refinement with feedback shows substantial promise
 - Hardware-specific prompting can improve optimization quality
 - Sampling multiple solutions increases the chance of finding high-performance kernels

3. **Research Opportunities**:
 - Improving LLM performance for low-resource programming languages like CUDA
 - Developing better feedback mechanisms for code quality and performance
 - Exploring alternative programming abstractions that are more amenable to LLM generation
 - Extending to other hardware accelerators beyond NVIDIA GPUs

4. **Broader Impact**: Successful automation of kernel generation could:
 - Democratize high-performance computing by reducing expertise requirements
 - Accelerate the development and deployment of AI systems
 - Improve energy efficiency of ML workloads through better optimization
 - Facilitate the use of diverse hardware platforms

The authors emphasize that while current LLMs cannot yet replace human kernel developers, the results demonstrate a promising path forward. With continued improvements in feedback-based generation and hardware awareness, LLMs could become valuable tools for augmenting human developers or enabling non-experts to achieve performance previously accessible only to specialists.

The KernelBench framework provides a valuable benchmark for future research in this area, offering a standardized way to measure progress in LLM-based kernel generation capabilities.
