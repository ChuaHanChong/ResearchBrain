# Agnostics: Learning to Code in Any Programming Language via Reinforcement with a Universal Learning Environment

> [!summary] Summary
> Agnostics introduces a post-training pipeline for large language models (LLMs) that enables code synthesis in any programming language, particularly low-resource ones, by leveraging a universal reinforcement learning environment. The framework reformulates coding problems into a language-agnostic I/O format and utilizes an efficient code execution sandbox, allowing small LLMs to achieve state-of-the-art performance for Lua, Julia, and R, and significantly improving Fortran and OCaml code generation accuracy on the Ag-LCB-X benchmark.

## Problem

- Large language models (LLMs) for code generation show a significant performance disparity between high-resource and low-resource programming languages.
- The scarcity of pre-training data for low-resource languages limits LLM knowledge and effective fine-tuning.
- Post-training LLMs to improve performance on low-resource languages typically demands extensive, language-specific engineering for datasets, test harnesses, and reinforcement learning infrastructure.

## Method

- **Agnostics** reformulates existing coding datasets into a uniform, ==language-agnostic== input/output (I/O) format, eliminating the need for language-specific unit tests or function signatures.
- A universal reinforcement learning (RL) environment is used, judging code correctness solely by its external I/O behavior, which minimizes per-language engineering effort.
- A robust and efficient code execution sandbox, built with containerization, resource limits, and optimizations like RAM disks and cached containers, verifies generated code in any target language.

## Results

- Agnostics-trained Qwen 3 **4B** and **8B** models achieved state-of-the-art performance on Lua, Julia, and R on the Ag-LCB-X benchmark, rivaling or surpassing larger open-weight models (**16B**–**70B** parameters).
- For OCaml and Fortran, the framework significantly improved base model scores from near zero to approximately **7%** and 15-**17%** respectively on Ag-LCB-X, outperforming some frontier models on Fortran.
- Qualitative analysis revealed a shift in error profiles, with Agnostics-trained models exhibiting fewer fundamental syntax and misuse errors, and a higher proportion of algorithmic logic flaws, indicating a better grasp of language fundamentals.

## Takeaways

> [!tip] Key Insights
> - Evaluating code correctness based purely on external I/O behavior enables a language-agnostic verification mechanism, dramatically reducing the engineering overhead for LLM post-training.
> - Reinforcement learning with binary pass/fail rewards leads to more robust model learning compared to partial rewards, which can be exploited.
> - Small open-weight LLMs can achieve competitive or superior performance on low-resource languages when trained with this generalized and efficient post-training pipeline, scaling across different model families and sizes.

## Detailed Report

### 1. How This Work Fits into the Broader Research Landscape

The work presented in this paper addresses a recognized challenge within the field of large language models (LLMs) for code generation: the disparity in performance between high-resource and low-resource programming languages. LLMs have demonstrated proficiency in widely used languages such as Python and JavaScript, largely due to the abundance of pre-training data available for these languages. However, their capabilities are significantly limited for low-resource languages, which, despite their niche status (e.g., Fortran and Julia in computational science, R in data science), remain critical in specific scientific and engineering domains.

Existing efforts to improve LLMs for low-resource languages often face two primary hurdles. First, the scarcity of pre-training data for these languages limits initial model knowledge. Previous research has indicated that strategies like up-sampling low-resource languages during pre-training or fine-tuning on limited pre-training data yield only marginal or negligible improvements. Second, post-training, which is crucial for enhancing LLM performance, typically demands substantial per-language engineering. This includes the creation of specialized datasets for supervised fine-tuning, the development of test harnesses, and the establishment of reinforcement learning (RL) infrastructure, all of which require significant human expertise that is scarce for less common languages.

Approaches like MultiPL-T have attempted to address data scarcity by generating synthetic fine-tuning data and using verification with rejection sampling. However, these methods often require models to achieve a baseline level of competence to generate verifiable code within a reasonable number of attempts, and they necessitate language-specific compilers to translate test cases and function signatures, which can be complex and lead to unidiomatic translations.

This paper introduces Agnostics as an alternative post-training pipeline. It differentiates itself by proposing a language-agnostic approach to verification, where code correctness is judged solely by its external I/O behavior. This contrasts with methods that rely on translating internal function signatures or complex data structures, thereby minimizing the per-language engineering effort. By standardizing the verification process through I/O, Agnostics aims to create a universal RL environment applicable to a wide array of programming languages, particularly those with limited existing resources. The work thus contributes to bridging the performance gap for LLMs in low-resource programming languages by simplifying and generalizing the post-training pipeline.

### 2. Key Objectives and Motivation

The primary objective of this research is to facilitate the post-training of large language models (LLMs) on low-resource programming languages, with the goal of narrowing the performance gap that exists between high-resource and low-resource languages in code synthesis tasks. The authors aim to improve LLM proficiency in languages that are essential to various scientific and engineering sectors but are underserved by current LLM development practices.

The motivation for this work stems from several observations:

- **Existing Performance Disparity:** LLMs demonstrate high proficiency in high-resource languages like Python and JavaScript, but their performance significantly degrades for low-resource languages such as Fortran, Julia, R, Lua, and OCaml. This gap is evident in benchmark results and professional discourse.
- **Data Scarcity for Low-Resource Languages:** A fundamental reason for this disparity is the imbalance in available training data. Public code corpora, such as The Stack V2, contain orders of magnitude more data for popular languages compared to low-resource ones. This data scarcity impacts both pre-training and subsequent fine-tuning.
- **High Post-Training Engineering Overhead:** Beyond pre-training data, the post-training phase—critical for enhancing LLM capabilities—presents a significant bottleneck. Current post-training methodologies typically require extensive, language-specific engineering. This includes developing high-quality, curated datasets for supervised fine-tuning and creating bespoke reinforcement learning (RL) environments capable of executing and verifying model-generated code for each new language. Such per-language customization is resource-intensive and requires specialized human expertise, which is often difficult to secure for low-resource languages.
- **Limitations of Prior Approaches:** Previous attempts, such as generating synthetic data or using rejection sampling (e.g., MultiPL-T), have their own limitations. Synthetic data can be of low quality without robust verification. Rejection sampling can be computationally expensive if models cannot generate valid code within a reasonable number of attempts. Furthermore, approaches that rely on translating test cases and function signatures from a source language (e.g., Python) to a target low-resource language can be arduous, requiring a "little compiler" for each language and potentially leading to unidiomatic code or constraints on data types.

To address these motivations, the authors propose Agnostics, a post-training pipeline designed to eliminate or significantly reduce the per-language engineering burden. The core insight is that for many programming tasks, code correctness can be evaluated solely based on its externally observable input/output (I/O) behavior, rather than requiring deep introspection into its internal structure or function signatures. This allows for a universal verification mechanism that is independent of the programming language being learned. The objectives are specifically to:
1. Develop a method to reformulate existing language-specific coding datasets into a uniform, language-agnostic I/O format.
2. Design a system that can adapt to new programming languages with minimal configuration, primarily by supplying a brief specification for compilation and execution.
3. Implement a robust and efficient reinforcement learning environment that can verify code in any target language based on I/O, assigning rewards accordingly.
4. Demonstrate that this pipeline can significantly improve LLM performance on low-resource languages, making models competitive with or superior to larger models specialized in single languages, while scaling to diverse model families and sizes.

### 3. Methodology and Approach

The Agnostics approach consists of a data preparation stage and a training stage, designed to minimize per-language engineering for post-training LLMs. The core principle is to verify code correctness based on its externally observable I/O behavior.

#### 3.1. Data Preparation

The first step involves transforming existing coding datasets into a language-agnostic format compatible with the universal verifier.
- **Dataset Reformulation:** Many code datasets, such as MBPP, present problems with natural language descriptions, function signatures, and unit tests (e.g., Python assertions). Agnostics reformulates these into a standard I/O format. An LLM is prompted to convert language-specific task descriptions and unit tests into an equivalent representation where the program communicates exclusively via plain-text standard input and standard output. This involves specifying concrete I/O conventions, such as number of decimal places, separators, and value ordering, to ensure unambiguous expected behavior. The authors provide an example of an MBPP problem being transformed into a description with explicit input/output formats and corresponding input/output pairs. For datasets like Open-R1 Codeforces, which already define tasks in an I/O style, only minor adjustments are necessary.
- **Training Datasets:** The primary training dataset used is **Ag-Codeforces-X**, derived from Open-R1 Codeforces problems. These problems are already I/O-based, requiring minimal modification. A smaller dataset, **Ag-MBPP-X**, was created from MBPP using the LLM reformulation process. Both datasets were checked for overlap with evaluation benchmarks.

#### 3.2. Programming Language Preparation

To integrate a new programming language into the Agnostics pipeline, a concise configuration file is created.
- **Configuration File:** This file serves two main purposes:
 1. **Prompt Prefix:** It defines a short text string prepended to each problem prompt during training. This prefix instructs the LLM to generate code in the target language. For languages with low baseline accuracy, a longer prefix detailing common I/O API quirks or other language-specific advice can be beneficial. For OCaml and Fortran, advice was generated by a capable LLM (OpenAI o3) after analyzing faulty snippets.
 2. **Toolchain Commands:** It specifies shell commands necessary to install the language toolchain (e.g., `apt-get install -y r-cran-tidyverse`), define the filename for the generated code (e.g., `snippet.R`), compile the code if necessary (e.g., `gfortran -o snippet.out snippet.f90`), and execute the compiled or interpreted code (e.g., `Rscript snippet.R`, `./snippet.out`).

#### 3.3. Trainer and Code Execution Environment

The core of the Agnostics approach is a reinforcement learning trainer coupled with a robust, language-agnostic code execution sandbox.
- **Trainer (GRPO Algorithm):** Agnostics employs the Group-Relative Policy Optimization (GRPO) algorithm, a variant of policy gradient methods.
 - **Group Sampling:** For each task (prompt `x` and I/O examples `{(in_k, out_k)}`), a group `G` of candidate responses `{y_i}` is sampled from the current behavior policy `π_θ_old`.
 - **Reward Assignment:** Each candidate `y_i` is assigned a binary reward `R_i`. `R_i = 1` if the program extracted from `y_i` successfully passes all I/O examples; otherwise, `R_i = 0`. The authors explicitly decided against partial rewards (e.g., for code that runs but produces wrong output or passes only public tests) because such rewards tended to lead to models exploiting the reward system (e.g., hard-coding public tests or generating empty programs).
 - **Policy Update:** Group rewards are converted into sequence-level advantages, `Â_i = (R_i - mean({R_j})) / std({R_j})`, and the policy `θ` is updated using a GRPO objective function. A KL-divergence regularization term is omitted, consistent with some prior work.
- **Code Execution Sandbox:** This component is designed for robustness and efficiency.
 - **Code Extraction:** Model-generated code is expected to be contained within Markdown blocks, which allows for straightforward extraction without additional training for formatting.
 - **Containerization:** For each language, an OCI container is built and cached. This container includes the language toolchain (installed via `L.install`) and a generic execution harness.
 - **Execution Harness:** The harness runs continuously within the container, processing candidate programs. It:
 1. Writes the candidate program to disk (to `L.filename`).
 2. Compiles it if required (using `L.compile`).
 3. Executes it against each I/O example (using `L.execute`).
 4. Verifies if the actual output matches the expected output.
 - **Robustness Measures:**
 - **Timeouts:** Compilation and individual execution steps are subject to timeouts to prevent pathological behaviors (e.g., infinite loops, unbounded macro expansion).
 - **Resource Limits:** Containers enforce limits on CPU, memory, and filesystem usage, and no elevated privileges are granted.
 - **Output Size Limit:** A fixed-size (5MB) read buffer is maintained for program output. Programs exceeding this limit are immediately terminated to prevent verifier crashes.
 - **Efficiency Measures:**
 - **Container Caching:** A pool of warm containers is maintained to significantly reduce overhead compared to spawning new containers for each verification.
 - **RAM Disk:** A RAM disk is mounted in each container to accelerate compilation times, especially for languages that generate many intermediate files.
 - **Implementation:** The trainer and execution environment are implemented using Ray, facilitating multiprocessing and distributed computing. This allows for parallelization of group generation and loss computation across heterogeneous nodes. Python `asyncio` coroutines are used within the execution environment for container management to minimize inter-process data copying.
- **Hyperparameters:** The AdamW optimizer is used with a learning rate of 5 × 10^−6, a cosine decay schedule with a 0.1-epoch warmup. Batches consist of 4 prompts, each with a group size of 32 candidate responses. A temperature of 0.7 is used during generation, and reasoning is disabled in hybrid models.

### 4. Main Findings and Results

The evaluation of Agnostics involved training and benchmarking models on five low-resource programming languages: Lua, Julia, R, OCaml, and Fortran. Performance was measured using pass@1 accuracy with reasoning disabled, based on 20 samples per prompt at a temperature of 0.2, after training models for one epoch unless otherwise specified.

#### 4.1. Training and Benchmarking Datasets

- **Training Datasets:**
 - **Ag-Codeforces-X:** The primary dataset, derived from competitive programming problems in Open-R1 Codeforces, which already use an I/O format. It contains 5369 training problems.
 - **Ag-MBPP-X:** Created by reformulating MBPP problems into the language-agnostic I/O format using an LLM. Contains 776 problems.
- **Benchmarks:**
 - **MultiPL-E:** An established benchmark derived from HumanEval, translating Python prompts and unit tests to target languages. It requires language-specific prompt and test translators.
 - **Ag-LiveCodeBench-X (Ag-LCB-X):** A new multi-language benchmark introduced in this paper, derived from the 499 I/O-based problems of LiveCodeBench 5.0. It is designed to be more challenging than MultiPL-E for frontier models.

#### 4.2. Quantitative Results

- **State-of-the-Art for Small LLMs on Low-Resource Languages:**
 - Agnostics-trained Qwen 3 4B and 8B models (Qwen3-4B-CF-X and Qwen3-8B-CF-X) achieved performance that rivaled or surpassed larger open-weight models (16B–70B parameters) on Ag-LCB-X for Lua, Julia, and R (Table 1).
 - For OCaml and Fortran, Agnostics significantly improved scores from near zero (base Qwen 3 4B/8B at 0-1%) to approximately 7% and 15-17% respectively, outperforming even some frontier models (Sonnet 4 and Llama 3.3 70B Ins) on Fortran (Table 2).
 - Overall, pass@1 scores on Ag-LCB-X improved by a factor of 1.5–2x over base models, indicating that Agnostics training yielded gains beyond pre-training on publicly available code data.
- **Generalization to MultiPL-E:** The improvements were not limited to I/O-based problems. Agnostics-trained models also demonstrated significant performance gains on the MultiPL-E benchmark, which features problems requiring Python functions operating on standard Python data structures (Table 3). This indicates generalization beyond the I/O format used in training.
- **Scalability to Larger Models:** Agnostics training on Ag-Codeforces-X for Qwen 3 8B models resulted in further gains over their 4B counterparts on both Ag-LCB-X and MultiPL-E, suggesting scalability with model size. However, the method did not improve performance for smaller models (Qwen 3 1.7B and Llama 3.2 3B Instruct), possibly due to task difficulty.
- **Effectiveness with Easier Problems:** Training on the Ag-MBPP-X dataset, which consists of comparatively easier problems, also improved Lua and Julia performance on both benchmarks. Although R performance on Ag-LCB-X saw a small drop, it improved significantly on MultiPL-E (Tables 1 and 3).
- **Works Across Model Families:** Agnostics demonstrated effectiveness across various LLM families, including SmolLM 3 (3B), Phi 4 Mini Instruct (non-specified size but generally small), and DeepSeek Coder 6.7B Instruct. Performance improvements were observed on all tested languages for both MultiPL-E and Ag-LCB-X (Table 4). This also suggested applicability to models with more limited prior post-training (e.g., instruction-tuned only DeepSeek Coder).
- **Outperformance Against Alternative Methods:**
 - **Distillation:** An experiment distilling Fortran solutions from Sonnet 4 Thinking to Qwen 3 4B yielded significantly lower scores on Ag-LCB-Fortran (3% after 2 epochs, 2% after 3 epochs) compared to the Agnostics-trained Qwen3-4B-CF-Fortran (15%) (Table 5). This suggests that distillation from larger, but not highly proficient, models for low-resource languages is less effective.
 - **Rejection Sampling:** The authors estimated rejection sampling to be prohibitively expensive for their target problems and models. Qwen3-4B-CF-Fortran had a 6.64% success rate on training problems, generating 11400 verified programs. The base Qwen 3 4B model achieved only a 0.09% success rate, generating 158 programs, implying orders of magnitude more resources would be needed for comparable results.

#### 4.3. Qualitative Improvements

- **Bug Analysis:** A taxonomy of common bugs was developed (Syntax & Typographical, Input Reading & Parsing, Uninitialized Variables, Data Type & Conversion, Function Misuse & Missing Libraries, Algorithmic Logic Flaws, Output Formatting & Presentation).
- **Shift in Error Types:** Analysis of OCaml programs generated by Qwen 3 4B and Agnostics-trained Qwen3-4B-CF-OCaml revealed a qualitative shift in error profiles (Figure 6). The base model exhibited a higher prevalence of fundamental programming mistakes, such as syntax errors (55% vs. 35%) and misuse of built-in functions (60% vs. 32%). The trained model showed a reduction in these shallow errors, leading to a slight increase in the proportion of algorithmic logic flaws (18% vs. 25%). This suggests that training successfully mitigates surface-level language misunderstandings, allowing deeper logical issues to become more apparent. Similar patterns were observed across the other four programming languages (Figures 15-19 in Appendix D.3).

### 5. Significance and Potential Impact

The Agnostics framework introduces a novel and practical approach to enhancing large language model (LLM) performance on low-resource programming languages, addressing a significant limitation in current code generation capabilities. The work's significance and potential impact can be summarized as follows:

- **Reduced Engineering Overhead for Low-Resource Languages:** A primary contribution is the elimination of per-language engineering for post-training. By shifting verification from language-specific unit tests and function signatures to a universal I/O-based approach, Agnostics significantly reduces the manual effort and specialized expertise required to adapt LLMs to new programming languages. The reported adaptation time of "less than an hour each" for OCaml and Fortran demonstrates a substantial practical advantage over previous methods. This ease of adaptation can democratize access to advanced LLM capabilities for languages previously underserved due to resource constraints.

- **Improved LLM Performance in Critical Domains:** Low-resource languages are foundational in specific scientific, engineering, and data science sectors. Improving LLM proficiency in these languages directly supports practitioners in these fields, enabling them to leverage AI tools more effectively for tasks requiring specialized coding knowledge. The empirical results, showing small open-weight models rivaling or surpassing much larger baselines for these languages, indicate a substantial step towards closing this capability gap.

- **Scalability to Diverse Models and Datasets:** The demonstrated ability of Agnostics to scale to larger models (Qwen 3 8B) and work across various model families (SmolLM 3, Phi 4 Mini Instruct, DeepSeek Coder Instruct) suggests its broad applicability. The methodology's compatibility with larger problem sets, such as OpenCodeReasoning's hundreds of thousands of problems, indicates a potential for creating rich RL datasets for numerous target languages with minimal additional engineering, thus further expanding its impact.

- **Robust and Efficient Reinforcement Learning Environment:** The development of a robust and efficient language-agnostic code execution sandbox, utilizing containerization, resource limits, and performance optimizations (e.g., RAM disks, cached containers), is a technical achievement. This infrastructure provides a reliable foundation for reinforcement learning in diverse programming environments, handling common pathologies of generated code effectively. The decision to use binary rewards (pass/fail) is noted for preventing models from exploiting partial reward structures, leading to more robust learning.

- **Qualitative Understanding of Model Learning:** The qualitative analysis using a bug taxonomy provides insights into *how* LLMs improve through Agnostics training. The shift from fundamental syntax/misuse errors to more complex algorithmic logic flaws indicates that the training effectively instills a better grasp of language fundamentals, allowing deeper reasoning issues to emerge as primary challenges. This contributes to a better understanding of LLM learning dynamics in code generation.

In summary, Agnostics represents a significant advancement in making LLM-based code generation more accessible and effective for the long tail of programming languages. Its design principles, robust implementation, and demonstrated empirical success have the potential to broaden the utility of LLMs in specialized technical domains and reduce the development burden associated with supporting a wider array of programming languages.
