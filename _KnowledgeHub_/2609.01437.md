# HarnessDev: Can LLMs Create and Evolve Their Own Agent Harness?

> [!summary] Summary
> HarnessDev is a benchmark evaluating LLMs as builders of agent harnesses, not task solvers. In Creation, a creator model grows an execution system (loop, tools, context, state, lifecycle, verification) from a zero-scoring weak seed; in Evolution it revises that harness from downstream feedback. Across six creators, four domains and 2,207 instances, generated harnesses match human references on writing and ML experimentation but trail on code and search.

## Problem

- Agent benchmarks such as SWE-bench, GAIA and WebArena fix the harness as experimental configuration and score task outputs, treating execution infrastructure as setup rather than a developed artifact.
- Prior automated agent-design work searches prompts, workflows or agent topologies, leaving untested whether models can both create and continually maintain runnable, persistent harnesses.
- Existing setups do not separate the model developing a harness from the one executing it, leaving cross-executor transfer, regression and token cost unmeasured.

## Method

- ==Weak seed harness==: a runnable compatibility layer with passive primitives but no loop, tool policy, context management, state, verifier or stopping rule, so all credit comes from creator-added control logic.
- ==Two-stage protocol==: ==Creation== supplies a spec plus 1-3 development cases; ==Evolution== revises the frozen initial code harness under a ten-evaluation-pair budget on 100 SWE-Pro plus 89 Terminal-Bench feedback tasks.
- Dual axes with ==Self-Eval== and ==Unified-Eval==: capability on held-out tasks and executor-token efficiency, plus a disjoint 630-instance SWE-Pro held-out split and post-hoc constraint-compliance auditing.

## Results

- Under Self-Eval, Opus 4.8 leads at **67.8** average against the **86.2** human reference; writing edges past it (**84.6** vs **83.7**) and MLE-bench medal **32.9** exceeds **24.0**, while BrowseComp **52.4** trails **92.2**.
- Harnesses co-adapt to their creator: Opus's SWE-Pro drops **69.3** to **33.0** under a fixed Gemini executor, its search harness duplicate-query rate rising from **10.1%** to **88.2%**; MLE token cost varies **nineteen-fold**.
- Evolution gains shrink off the feedback set: **+3.0** to **+13.9** feedback-pair points become **+1.43** to **+4.44** held-out; under fixed Gemini only Opus improves, and the two agree in **53.1%** of **64** switches.

## Takeaways

> [!tip] Key Insights
> - Harness quality and model capability are separable; a harness transfers only when its prompts, tool protocol, budgets and stopping rules are not tuned to one executor.
> - Edit volume and self-test count barely predict harness quality; what matters is reading a concrete failure, making a targeted change, and reverifying it end to end.
> - Declared mechanisms are not active mechanisms: much generated code, especially state and memory, never executes, so audit reachability instead of trusting a noisy feedback score.

## Detailed Report

### 1. How This Work Fits into the Broader Research Landscape

The development of large language model (LLM) agents is an active area of research. Existing agent benchmarks, such as SWE-bench, GAIA, WebArena, and τ-bench, typically evaluate a model's performance on downstream tasks under a pre-selected and fixed execution infrastructure, often referred to as an "agent harness." This approach treats the harness as a static part of the experimental setup rather than an artifact to be developed.

This paper addresses a perceived gap in this landscape by focusing on the LLMs' ability to create and evolve the agent harness itself. The authors highlight that as agents transition from prototypes to deployed tools, their capabilities become increasingly dependent on model-external software that manages execution loops, tool use, context, failure recovery, and result verification. Changes to this harness, even with fixed model weights, can significantly alter task performance. The paper points to the role of "forward-deployed engineers" in industry who bridge the gap between general-purpose models and working, continuously improving systems by building and maintaining this external infrastructure. This work isolates the third layer of this work: the creation and maintenance of the execution system itself.

While some recent work has explored harness representations, automated agent design, and agents that build or improve agent systems (e.g., ADAS, AFlow, MASS, EvoAgentX, VeRO, Meta-Harness, Self-Harness, HarnessFix), the authors argue that the capability of models to both create and continually improve runnable, persistent harnesses remains underexplored. Specifically, the paper differentiates itself from related benchmarks such as the Meta-Agent Challenge (which evaluates iterative agent programming in a sandbox, similar to HarnessDev Creation) and HarnessOpt-Bench and Evo-Bench (which focus on optimizing provided harnesses or improving a shared seed). HarnessDev extends these by connecting from-scratch creation to evolution, separating creator and executor models, measuring execution cost, evaluating transfer across executors, and tracking held-out generalization throughout the evolutionary trajectory.

The paper argues that harness engineering fundamentally differs from ordinary code editing because changes to the harness alter the model's own execution substrate, affecting how it observes, plans, and recovers in all future tasks. Effective harness improvement requires models to diagnose structural bottlenecks and commit reusable capability gains. HarnessDev is positioned to measure these specific abilities.

### 2. Key Objectives and Motivation

The primary objective of this research is to evaluate the capacity of LLMs to create and maintain their own agent harnesses. The authors introduce HarnessDev, a benchmark designed to shift the focus of evaluation from task-specific outputs to the underlying runnable infrastructure developed by LLMs.

The motivation for this work stems from several observations:
- **Increasing Reliance on External Infrastructure:** As LLM agents become more sophisticated and are deployed in real-world applications (e.g., coding assistants, data-analysis copilots, browser workers), their performance is increasingly constrained by the "agent harness"—the model-external software that orchestrates their operation. This harness manages critical functions like execution loops, tool invocation, context management, failure recovery, and output verification.
- **Substantial Impact of Harness:** Empirical evidence suggests that the choice and quality of a harness can significantly influence an agent's task-solving capabilities, even when the underlying LLM weights are identical. For example, the paper notes that GPT-5's performance on Terminal-Bench 2.1 varies substantially depending on whether it operates within Terminus 2 or Codex CLI.
- **Growing Demand for Purpose-Built Harnesses:** As agents specialize across diverse domains, there is a continuous need for domain-specific harnesses. These systems require ongoing development and maintenance. The central practical question is whether LLMs can automate or assist human engineers in this continuous development process.
- **Underexplored LLM Capability:** Current agent evaluations typically treat the harness as a fixed experimental configuration. The models' ability to autonomously develop and improve these harnesses has received comparatively less attention.
- **Distinction of Harness Engineering:** The authors emphasize that modifying an agent's own execution harness is different from editing standalone code. When an LLM modifies its harness, it changes the very environment through which it operates, requiring the model to recognize its own limitations, diagnose systemic issues, and implement targeted, reusable improvements.

To address these motivations, HarnessDev aims to answer two primary research questions:
- **RQ1 (Creation):** Can an LLM build an effective and complete agent harness starting from a weak, minimal seed and a limited set of development cases? This stage evaluates the model's ability to design and implement fundamental execution infrastructure.
- **RQ2 (Evolution):** Can an LLM iteratively improve an existing harness (specifically, its own created harness from RQ1) by leveraging downstream execution feedback, with the goal of enhancing benchmark performance? This stage assesses the model's capacity for continuous development and maintenance.

The benchmark evaluates the created harnesses along two axes: **capability** (task success rate on held-out benchmarks) and **efficiency** (execution-token cost).

### 3. Methodology and Approach

HarnessDev is designed to evaluate LLMs' ability to construct and maintain execution systems, rather than merely their ability to produce task-specific outputs. The methodology involves a structured development environment and a rigorous evaluation protocol across two distinct stages: Creation and Evolution.

#### 3.1. Benchmark Design Principles

- **Unit of Evaluation:** The submitted artifact is a runnable, frozen harness (H) that persists across multiple downstream tasks, not a one-off task output.
- **Model Roles:** A clear separation of roles is maintained: a creator LLM (L_C) develops the harness, a development environment (D) supports this process, an executor LLM (L_E) runs tasks within the frozen harness, and an evaluator (J) scores the task output.
- **Harness Components:** A harness is conceptualized as `H = <E, T, C, S, L, V>`, representing its execution loop, tools, context management, state, lifecycle control, and verification mechanisms. The creator is responsible for implementing these components.

#### 3.2. Development Settings

The benchmark covers two stages:

- **Creation (RQ1):**
 - **Starting Point:** The creator LLM begins with a "weak seed" (H_seed). This seed is a runnable compatibility layer that handles basic input/output and exposes low-level tools, but lacks any agent loop, task decomposition, tool policy, context management, persistent task state, verifier, retry/recovery logic, or stopping rule. An unmodified H_seed scores zero on all downstream benchmarks.
 - **Development Signal:** The creator receives a task-family specification, tool/permission constraints, a short design tutorial, and 1-3 development cases. It can revise the harness based on feedback from these cases.
 - **Output:** A final, runnable harness (H) that is frozen before evaluation.

- **Evolution (RQ2):**
 - **Starting Point:** The creator LLM begins with its own frozen Creation harness (H_0).
 - **Development Signal:** The creator receives execution results from a designated feedback set: 100 SWE-Pro tasks (a subset of the public split used in Creation) and all 89 Terminal-Bench tasks.
 - **Iteration Protocol:** The controller provides a budget of ten "full-evaluation pairs" (one SWE-Pro-100 and one Terminal-Bench-89 evaluation of the same commit). Between charged pairs, the creator can use up to two fixed-subset probes (running the first five tasks of both benchmarks for diagnostic purposes). The creator terminates by declaring a final non-H_0 commit.
 - **Output:** A creator-declared final harness (H_n) from its trajectory.

#### 3.3. Evaluation Protocol

- **Scoring:** Every score is generated by a frozen harness running in a standardized runtime. L_E and J remain fixed within each comparison, isolating harness-induced changes.
- **Separation of Development and Evaluation:** Hidden evaluation tasks are never shown to the creator during development in Creation. In Evolution, only the designated feedback set is visible during development; generalization is measured separately on a disjoint held-out set (630 SWE-Pro instances) after Evolution is complete.
- **Creation Evaluation Modes:**
 - **Self-Eval:** L_E = L_C (the creator LLM also executes tasks within its own harness). This measures the co-design and compatibility between the model and its self-built harness.
 - **Unified-Eval:** All generated harnesses are executed by a single, fixed L_E (Gemini 3.1 Pro in this study). This allows for direct comparison of harness quality independent of the creator's execution capability.
- **Constraint Compliance:** Submitted harnesses are explicitly prohibited from hard-coding instance-specific solutions, using hidden tests, or accessing private scorer internals. Compliance is audited post-run via trajectory logs and source code, with all audit artifacts released. No violations were observed in this study.

#### 3.4. Metrics

For each frozen harness, two key quantities are reported:
- **Downstream Task Performance:** Measured using the native metric of each benchmark (e.g., task success, medal score, rubric score, accuracy).
- **Executor-Model Tokens Consumed:** The total and mean tokens L_E uses when deployed to solve downstream tasks. Tokens used by L_C during development are excluded.

#### 3.5. Domains and Downstream Benchmarks

Creation spans four domains and five benchmarks, totaling 2,207 unique instances:
- **Code:** SWE-bench Pro (731 instances), Terminal-Bench 2.1 (89 instances).
- **Data Analysis:** MLE-bench (75 instances).
- **Writing:** EQ-Bench3 (46 instances).
- **Research:** BrowseComp (1,266 instances).
Evolution focuses on code harnesses using SWE-Pro and Terminal-Bench tasks as feedback.

#### 3.6. Experimental Setup

- **Creator LLMs (L_C):** Opus 4.8, GPT-5.5, Gemini 3.1 Pro, DeepSeek V4 Pro, Qwen 3.7 Max, Seed 2.0 Pro.
- **Development Environments (D):** Claude Code 2.1.177 for most, Codex 0.144.3 for GPT-5.5.
- **Replicas:** For Creation, three independent harnesses were built and evaluated for each creator–benchmark pair, with `avg@3` reported.
- **Human References:** Performance is compared against verified results from mature human-engineered open-source systems, though these are not paired controls under a common executor.

### 4. Main Findings and Results

#### 4.1. Harness Creation (RQ1)

- **Overall Performance and Gap to Human References:**
 - The quality of created harnesses varied significantly across task families. Under Self-Eval, Opus 4.8 achieved the highest overall score (67.8%), but still lagged behind the human-engineered reference (86.2%).
 - Model-built harnesses approached or exceeded human references in certain domains: they matched the reference on short-form writing and exceeded it on machine-learning experimentation.
 - The largest performance gaps relative to human references were observed in search and research (requiring long-horizon information seeking) and in code harnesses (requiring coordination of repository inspection, editing, and verification).
 - For data analysis tasks, 77.8% of failures were attributed to harness defects rather than executor model limitations, indicating that harness quality is a significant bottleneck.

- **Performance Variation and Executor Dependence:**
 - Independent harness creations from the same model could exhibit substantial performance differences. An Opus Code harness, for example, performed well under Self-Eval but poorly under a fixed Gemini executor due to hard-coded execution limits. This indicated that a single generated harness might not be representative.
 - Fixing the executor (Unified-Eval with Gemini 3.1 Pro) significantly altered model rankings. Some creators (e.g., Qwen, DeepSeek) saw performance improvements, suggesting their original executors were a bottleneck. Others (e.g., Opus, GPT-5.5) often performed better with their own executors, highlighting model-harness co-adaptation.
 - Execution cost (executor tokens) varied by up to 19-fold across models for the same task family (e.g., MLE-bench). Higher execution cost did not reliably correlate with higher scores, indicating that both capability and efficiency are crucial for assessing harness quality.

- **Implementation Behavior and Mechanism Evidence:**
 - Creator LLMs employed distinct implementation strategies, ranging from rewriting the entire execution stack (Opus) to adding monolithic agents (GPT-5.5) or extending the weak seed with modular components (DeepSeek, Qwen, Seed).
 - Edit size did not predict performance; Gemini, for instance, added the fewest lines (1,006) but achieved the best Terminal-Bench score (68.8%), suggesting that focused changes and verification were more impactful than code volume.
 - Analysis of generated mechanisms showed gaps in functionality, particularly regarding state and memory management; 11/18 code artifacts defined a State class, but only one exposed a saving interface or implemented checkpointing. Many generated features were unobserved or represented dead code (e.g., 18/108 code component instances, 124/587 writing features).
 - Self-test count had a weak, non-significant correlation with downstream scores (0.13–0.26), whereas revision calls showed a stronger correlation (0.57, p ≤ .0005).

- **Executor Transfer:**
 - Portability of harnesses varied. Some harnesses (e.g., Qwen, DeepSeek) improved under a fixed Gemini executor, indicating that their original executors limited performance. Other harnesses (e.g., Opus's SWE-Pro score dropping from 69.3 to 33.0) declined, showing that their internal rules and prompts were adapted to the original model. For instance, Opus's search harness exhibited a significantly higher duplicate-query rate after changing the executor.

#### 4.2. Harness Evolution (RQ2)

- **Gains and Generalization:**
 - All five creator models operating in a self-runtime setting showed improvements on the *visible feedback set* (100-task SWE-Pro and 89-task Terminal-Bench).
 - However, these gains were smaller and less consistent when evaluated on *held-out tasks* (630 SWE-Pro instances never shown to the creator). Opus 4.8 achieved the largest held-out improvement at +4.44 points.
 - Under the fixed Gemini executor, transfer was weaker; only Opus improved on held-out tasks, while the other three lineages regressed.
 - These findings suggest that current models can make useful local improvements but struggle with reliable, robust evolution that generalizes across unseen tasks or transfers effectively across different runtime executors.

- **Editing and Feedback Use:**
 - The median declared version involved changes to 8 files, adding 476 lines and deleting 38. Edit size did not reliably predict improvement.
 - Most changes focused on execution flow, tools, and lifecycle control (58/64, 37/64, 17/64 switches, respectively), with very few changes to state or verification (4/64, 0/64).
 - Diagnosis of failures remained a weak point. The dedicated trajectory interface was rarely used; creators predominantly relied on custom scripts and small probes, which could be inconsistent with full evaluations. A positive example was Opus diagnosing and fixing premature completion.

- **Stability and Final-Version Selection:**
 - Evolutionary trajectories were often non-monotonic. Out of 64 official version switches, 8 regressed on both benchmarks, 16 showed single-benchmark regression, 3 showed trade-offs, 7 yielded no measurable change, 27 showed gains within the noise band, and only 2 had clear positive evidence.
 - The noise band for score changes (approximately ±4.75 pair-score points) meant that small observed gains could not be reliably attributed to code changes alone.
 - A significant portion of added code remained inactive or unreachable (113/169 new functions/classes were reachable, 31 reachable through dead code, 25 had no caller).
 - Creators typically selected a version close to their best visible feedback score. However, this selection rarely matched the version with the best *held-out* performance (only 2 out of 9 declared versions were held-out optimal). Visible feedback was useful for local search, but repeatedly optimizing a noisy score could lead to overfitting and unreliable final version selection.

### 5. Significance and Potential Impact

This research contributes to the understanding of LLM capabilities in autonomous agent development by introducing HarnessDev, a benchmark that focuses on the creation and evolution of agent harnesses. The findings have several implications for the future of agent design and deployment:

- **Shift in Evaluation Paradigm:** HarnessDev shifts the unit of evaluation from task outputs to runnable infrastructure. This provides a framework for measuring the LLM's role as a "system builder" rather than solely a "task solver." This is significant because the quality of the execution system is a critical, yet often overlooked, component of agent performance in real-world applications.

- **Identification of Key Limitations:** The study reveals that while current LLMs can construct runnable harnesses from a weak seed, there are substantial gaps in performance and robustness compared to mature human-engineered systems, particularly in domains requiring complex reasoning (e.g., search, code). The difficulty of reliable, generalizable evolution is also highlighted, demonstrating that iterative improvements often remain local and may not transfer well to unseen tasks or different execution environments.

- **Understanding Model-Harness Co-Adaptation:** The comparison between Self-Eval and Unified-Eval settings demonstrates that LLM agents and their self-generated harnesses can become co-adapted. This finding suggests that a harness designed for one LLM may not perform optimally, or even function correctly, with a different LLM, underscoring challenges in harness portability and transferability.

- **Emphasis on Efficiency and Structural Quality:** The inclusion of execution-token cost as a metric, alongside task performance, emphasizes that a functional harness must also be efficient. The observation that higher cost does not reliably yield better results is important for practical deployment and resource optimization. The detailed analysis of implementation behavior and mechanism evidence, including the prevalence of dead code and unimplemented features, points to the need for LLMs to generate more effective and utilized code for their harnesses.

- **Guidance for Future Research:** The findings provide specific directions for advancing autonomous agent research. Future work could focus on:
 - Developing LLMs that can generate more robust, modular, and generalizable harness architectures.
 - Improving LLMs' diagnostic capabilities to accurately identify and address root causes of harness failures across diverse tasks.
 - Creating evolution mechanisms that prevent overfitting to feedback sets and ensure gains transfer reliably to held-out tasks and different executors.
 - Exploring methods for LLMs to effectively manage state and memory within harnesses, which was identified as a clear gap.
 - Researching how to foster more stable and monotonic improvements in harness evolution.

- **Practical Implications for Industry:** For the growing number of "forward-deployed engineers" working to integrate LLM capabilities into real-world systems, the research underscores that LLMs are not yet capable of fully automating harness development. While they can assist in building and making local improvements, human oversight and engineering expertise remain critical for ensuring the creation of durable, inspectable, and continuously improvable systems that generalize and adapt to evolving requirements.

In conclusion, HarnessDev provides a robust benchmark and empirical evidence for the current state of LLMs in building and evolving their own agent harnesses. It positions the "harness" as a measurable and critical artifact, reinforcing that intelligence accumulates not only in model weights but also in the explicit, inspectable, and continually improvable execution infrastructure.
