# Raven: The Harness of Harnesses for Composable Agentic Intelligence

> [!summary] Summary
> Raven is an open-source multi-agent ecosystem that treats each executable model-harness pair as a composable unit. A Host Agent breaks goals into a dependency graph of specialist agent calls. Diagnosis-driven harness evolution, persistent memory and Skill Forge reuse experience across tasks. Its theory gives sufficient conditions for composition to widen reliable task coverage. Raven leads multi-agent orchestration benchmarks, improving exact-match plan accuracy by over 10 points.

## Problem

- Hand-built harnesses scale poorly: each added tool or execution condition multiplies the interacting design choices that must be configured and validated for every model and domain.
- Specialized harnesses build in domain-specific assumptions about tools, context and outputs, so one harness generalizes poorly and combining specialists needs compatible handoffs.
- Prior multi-agent frameworks suffer from agents working at cross purposes and from weak task verification, and never establish when composition beats individual agents at an equal resource budget.

## Method

- **Host Agent** with ==graph runtime==: it splits goals into subtasks, matches each to a registered native or third-party agent through execution adapters, then validates and dispatches the ==dependency graph== using an artifact ledger.
- Diagnosis-driven harness evolution: it diagnoses failures from execution traces, proposes edits to prompt, knowledge, runtime or config, archives candidates in a ==Harness Gene Bank==, and admits them through ==gated paired screening==.
- Persistent memory (host archive plus ==EverOS== episodic traces and ==semantic consolidation==) alongside **Skill Forge**, which retrieves and self-evolves reusable procedures from local skills, memory-derived skills and SkillHub.

## Results

- On the new Multi-Agent Orchestration Benchmark, Raven beats Claude Code and Hermes Agent on all four graph metrics, with Exact Match **0.711 vs 0.607** on Qwen3.8-27B and **0.867 vs 0.762** on DeepSeek-V4-Flash.
- Harness evolution on a frozen Qwen3.6-27B raises held-out Pass@1 on all seven benchmarks: AppWorld **41.3 to 56.7**, BrowseComp+ **16.9 to 30.8**, LiveCodeBench **58.1 to 71.8**.
- Raven-Oncall reaches **82.35%** success at **$5.10** per case against the best baseline's **64.71%** at **$13.60**, and Raven-Research gains **3.3 to 7.6 points** on mixed deep-research benchmarks.

## Takeaways

> [!tip] Key Insights
> - Treating the harness, not only the model, as the unit of capability lets a system improve and compose agents without retraining any backbone weights.
> - Predicting dependencies is harder than picking specialists: edge F1 trails node F1 for every system, so orchestration bottlenecks lie in handoff structure, not agent choice.
> - Composition helps only when local capabilities complement each other, handoffs are compatible and planning error is bounded, and coordination cost must be counted against worker gains.

## Detailed Report

### 1. Position Within the Broader Research Landscape

Raven addresses a current direction in artificial intelligence research: the development of long-horizon agents that combine language models with tools, memory, execution environments, verification procedures, and domain-specific control policies. Earlier agent systems commonly focused on a single domain, such as web research or software engineering, or coordinated multiple agents through role prompts and conversational exchanges. Frameworks such as AutoGen, MetaGPT, and Magentic-One demonstrate task decomposition and multi-agent collaboration, but generally assume a relatively stable orchestration framework and a common interaction model.

Raven extends this line of work by treating the complete model–harness pair as the unit of composition. A harness includes the tools, context management, memory, skills, execution loop, recovery logic, and verification mechanisms surrounding a model. This distinction is important because the same foundation model can behave differently when placed in different harnesses. Raven therefore aims to compose heterogeneous agents, including native Raven specialists and independently developed systems such as Claude Code, Codex, Hermes Agent, and OpenClaw.

The work also connects four research areas that are often studied separately. First, it contributes to multi-agent planning through explicit dependency graphs. Second, it builds on research into agent self-evolution by modifying harness policies around a frozen model. Third, it incorporates long-term memory systems that distinguish user information from agent experience. Fourth, it uses procedural skills that can be retrieved, reused, and updated from execution traces. The paper’s theoretical component places these mechanisms within a contract-based framework influenced by Hoare logic and probabilistic assume–guarantee reasoning.

### 2. Key Objectives and Motivation

The paper identifies two central scalability problems. The first is harness complexity. As agents gain more tools, longer context windows, persistent memory, execution controls, and recovery behaviors, the number of interacting design decisions increases. Manually building and maintaining a separate harness for every model and domain becomes difficult.

The second problem is limited composability. A research agent, coding agent, design agent, and operational agent may each be effective in its own environment, but their outputs, interfaces, state, and completion criteria may not be compatible. Informal message passing can lose details, obscure provenance, and make it difficult to verify whether a downstream agent received the appropriate information. Coordination can also consume enough resources to offset the value of specialization.

Raven’s objectives are therefore broader than improving one agent on one benchmark. The system is designed to:

1. Construct specialized harnesses for particular models and domains.
2. Improve those harnesses through diagnosis of execution failures and evaluation of candidate changes.
3. Represent model–harness pairs as reusable execution units.
4. Select and coordinate heterogeneous agents for complex tasks.
5. Transfer artifacts through explicit, traceable dependencies rather than only free-form conversation.
6. Preserve user context, agent experience, and reusable procedures across tasks.
7. Establish conditions under which composition can expand reliable task coverage under a common resource budget.

The motivating example is a complex workflow such as developing and operating a video game. Such a task may require research, programming, visual design, integration testing, deployment, and monitoring. The authors argue that these subtasks are better handled by specialized agents connected through a structured execution plan than by a single general-purpose agent or a fixed sequence of role prompts.

### 3. Methodology and Approach

#### 3.1. Host-Mediated Agent Orchestration

Raven uses a Host Agent that receives the user’s goal, consults an agent registry, and constructs a directed acyclic graph (DAG). Each graph node represents an agent invocation, and each edge represents an artifact handoff. Nodes specify an executor, task summary, prompt template, dependencies, input bindings, optional stateful instance handles, and configuration overrides.

Before execution, the runtime performs format, graph-structure, capability, agent-status, and environment checks. It verifies unique identifiers, resolvable dependencies, acyclicity, file-path restrictions, compatibility between references and backend capabilities, registration status, dispatch limits, and user approval where required. Ready nodes are scheduled when their predecessors have completed and been judged successful.

Returned outputs are independently judged for task completion. If a node fails, the host may continue it with additional instructions, abandon it, or replan the remaining workflow. Prompts, outputs, transcripts, and artifacts are persisted, allowing later nodes to access content directly or through file references. This creates an artifact ledger and preserves provenance across graphs and sessions.

#### 3.2. Formal Theory of Composition

The theoretical model defines an agent as a model combined with a harness and defines capability as the probability of producing a correct result within a shared budget. A composed plan includes the graph, executor assignment, input-binding functions, contracts, schedule, and resource allocations.

Node and handoff contracts specify preconditions, acceptable outputs, state transitions, and faithful artifact transfer. Under compatibility assumptions, the paper proves deterministic composition soundness: if all operations succeed, a compatible plan delivers a correct result within budget.

For stochastic execution, the authors assign each node and handoff a conditional failure probability. A union-bound-style result gives a lower bound on workflow reliability based on planning error and the sum of local execution and transfer errors. The analysis explicitly avoids assuming independent failures. It also accounts for planning, verification, retries, handoffs, and final delivery in the total resource budget.

The paper defines complementary local capabilities as a situation in which every subtask has an eligible agent, but no single agent is eligible for all subtasks under the stated contracts and allocations. Under additional assumptions, composition can solve tasks that no individual agent reliably solves under the same budget. The authors emphasize that these are sufficient conditions, not guarantees that arbitrary multi-agent systems will improve performance.

#### 3.3. Harness Self-Evolution

Raven builds on HarnessBank. A harness around a frozen model is divided into four editable strategy interfaces: Memory, Planning, Capability, and Action. These control context assembly, turn guidance, tool exposure, model response handling, completion checks, and recovery behavior.

An Evolver Agent diagnoses failures from execution traces and proposes patches or recombinations of previously evaluated harness components. Candidate harnesses are stored in a semantic gene bank indexed by edit category and diagnosed failure type. Screening requires three conditions: the candidate must be valid, the proposed intervention must activate during evaluation, and the candidate must show a paired improvement over its parent on a sampled task subset. Survivors are evaluated on the full training set, and the selected harness is frozen before held-out testing.

#### 3.4. Memory and Skill Systems

Raven uses EverOS for episodic traces, semantic consolidation, user profiles, agent cases, and persistent skills. User memory and agent experience are stored on separate tracks. Retrieval combines lexical and dense search, while execution artifacts remain distinct from memory records and graph dependencies.

Skill Forge combines local skills, memory-derived skills, and the SkillHub catalog. SkillHub is based on a curated corpus of 96,401 active skills in the reference snapshot. The curation process removes malformed, duplicated, unsafe, or poorly specified entries. At task time, candidate skills are retrieved, fused across sources, filtered for compatibility and safety, and selected by a language-model gate. Execution cases can later be clustered into task intents and converted into new or revised procedures.

### 4. Main Findings and Results

#### 4.1. Orchestration

The Multi-Agent Orchestration Benchmark contains 140 occupationally framed tasks and evaluates specialist selection and dependency prediction before workers execute. With Qwen3.8-27B, Raven achieved Node F1 of 0.923, compared with 0.776 for the strongest baseline, and Partial Order Accuracy of 0.950 versus 0.780. Exact Match was 0.711 versus 0.607. With DeepSeek-V4-Flash-0731, Raven achieved Node F1 of 0.963, Edge F1 of 0.897, Partial Order Accuracy of 0.918, and Exact Match of 0.867. The strongest baseline Exact Match was 0.762. These results indicate improved graph construction under the tested protocol, although graph agreement does not itself establish end-to-end task correctness.

#### 4.2. Harness Evolution

The reproduced HarnessBank results used a frozen Qwen3.6-27B task model. Held-out Pass@1 increased from 36.1% to 45.4% on Terminal-Bench-2, from 16.9% to 30.8% on BrowseComp+, from 41.3% to 56.7% on AppWorld, and from 47.4% to 52.6% on SWE-bench Verified. Improvements were reported on all seven evaluated benchmarks. However, the paper notes that detailed run manifests for some source experiments are unavailable, and the adaptation procedure can be unstable or transfer only partially to unseen tasks.

#### 4.3. Domain Specialists

Raven-Research exceeded the strongest same-backbone baseline on the pooled DeepResearch Mixed benchmark by 6.6, 3.3, and 7.6 percentage points for the three tested backbones. With DeepSeek-V4-Flash, it reached 76.5% pooled accuracy at an estimated cost of $0.0242 per question. The advantage was associated with search stopping rules, explicit page reading, recovery from stalled investigations, citation tracing, and independent claim review.

Raven-Code was competitive or leading across several repository-level benchmarks. On SWE-bench Pro with Qwen3.8-27B, it resolved 54.4% of tasks compared with 52.4% for Claude Code. On SWE-Refactor with DeepSeek-V4-Flash, its mean score was 16.5 compared with 7.0 for the cited baseline. The harness emphasizes current file contents, repository instructions, syntax checks, tests, and execution manifests.

Raven-Design improved PresentBench scores over Claude Code with both tested backbones, reaching 80.2 with Claude Opus 5 versus 78.3, and 72.9 with GPT-5.6 Luna versus 52.4. It also led the reported internal Dashboard, SVG, and GDPval comparisons, although some of these results used internal graders and incomplete task coverage.

Raven-Oncall reached 1.038 validation bits per byte on the autoresearch task with Claude Opus 5, compared with 1.053 for Claude Code, while using fewer reported tokens and lower cost. On the internal AI4S benchmark, it completed 14 of 17 tasks versus 11 for Claude Code, with lower average runtime, token use, and reported cost.

#### 4.4. Skill Reuse

Adding the curated SkillCorpus improved all twelve harness–backbone–benchmark comparisons. For Raven, gains were 6.5 and 13.4 points on SkillsBench, 1.2 points on GDPval for both tested backbones, and 3.9 and 4.4 points on QwenClawBench. Ablations indicated that both corpus curation and trained retrieval contributed to performance. Gains were larger when the retrieved skills had higher estimated task coverage.

### 5. Significance and Potential Impact

Raven’s main significance is architectural. It proposes that future agent systems may be organized as networks of specialized, executable model–harness units rather than as a single universal agent or a collection of agents sharing only conversational messages. Explicit artifact dependencies, runtime validation, persistent experience, and harness evolution provide mechanisms for managing increasingly complex workflows.

The approach could affect software engineering, research automation, scientific computing, design production, and operational monitoring. It also offers a framework for comparing model improvements with harness improvements, since the same model can be evaluated under different execution policies.

The evidence remains subject to important limitations. Several evaluations are internal, sourced from prior publications, or use different resource limits and grading systems. Some visual and operational comparisons rely on model-based judges or manually assessed outcomes. The theory depends on contract compatibility, calibrated local reliability, and correct correspondence between local experiments and real workflow contexts. The paper also does not yet demonstrate a broad, end-to-end All-Domain Collaboration Network across devices or independent Raven instances. Its future impact will therefore depend on stronger matched-cost evaluations, causal ablations of individual components, robust safety controls for tools and memory, and testing on tasks whose structure is not aligned with the system’s own planning abstractions.
