# RACaP: Agentic Reasoning, Acting, and Coding as Policies for Evolvable Robot Learning

> [!summary] Summary
> RACaP is an agentic Code-as-Policies framework that moves code generation off the execution path into an offline evolution stage, yielding frozen typed Policy APIs, a two-tier ReAct harness and experience memory; at runtime the agent only selects APIs and revises their arguments from visual feedback. It reaches 54.4% in-domain on LIBERO-90, 45.0% zero-shot on LIBERO-PRO, and 46.0% on LIBERO-Long, where CaP baselines reach at most 4.0%.

## Problem

- Runtime code generation sits on the physical execution path: one CaP-X coding iteration costs 6.8 to 23.8 seconds and a multi-turn trial 60.8 to 113.6 seconds.
- Generated programs mix reusable physical mechanisms with task-specific object names, coordinates and grasp heights, so each new task forces writing code from scratch.
- Self-improving CaP methods use ambiguous play objectives: play on LIBERO-90 drops success from 21.1% to 11.1% in-domain and from 17.8% to 8.3% zero-shot.

## Method

- ==Typed Policy APIs== (pickplace, insert, stack, push, articulate, actuate_control) each own one bounded contact mechanism, exposing steerable arguments like grasp type, clearance, yaw and contact mode.
- ==Two-phase agentic evolution==: a capability curriculum builds execution, recovery, breadth and orchestration, then autonomous self-evolution promotes a candidate only when paired native-success gains exceed regressions under identical tasks and seeds.
- ==Two-tier runtime ReAct==: Full ReAct orders goals and routes across six APIs while Transport ReAct runs local transport loops, both fed by task-objective working memory plus frozen long-term experience memory.

## Results

- LIBERO-90 in-domain success is **54.4%** and zero-shot LIBERO-PRO is **45.0%** (81/180), against **13.3%** for CaP-X and **8.3 to 17.8%** for RATS variants, McNemar p = **0.00126**.
- LIBERO-Long reaches **46.0%** versus **2.0 to 4.0%** for code-generation baselines, with median PRO policy time of **380** seconds versus **726 to 954** seconds, **15.9** calls and **$0.24** per episode.
- Rejection-sampled fine-tuning of a compact student raises exact teacher-decision agreement from **83.3%** to **97.6%**, cuts repeated physical calls from **16** to **4**, and gives **0.750** versus **9.895** seconds per call.

## Takeaways

> [!tip] Key Insights
> - Splitting durable physical mechanisms (code) from scene-dependent choices (function calls) buys transfer and runtime speed together; freezing source code need not cost adaptivity.
> - Persistent code reuse only pays off with strict typed interfaces and paired regression gating; unchecked self-play caused interface drift that halved one baseline's success.
> - Small in-domain gains can hide large robustness gains: one extra dev task coincided with +12 points zero-shot, so measure transfer rather than the development set.

## Detailed Report

### 1. Overview

Runtime code generation and repair add delays while a robot is executing. Generated programs can also mix reusable control with coordinates or recovery choices tied to one scene. RACaP changes *when* the robot's code is written. It evolves reusable physical mechanisms before deployment. While the robot works, a visual agent chooses and adjusts typed function calls. In the paper's transfer test on altered tasks, the frozen system succeeded more often than runtime-coding baselines.

(a) Native success rate on all 180 zero-shot LIBERO-PRO episodes: CaP-X 13.3%, RATS-base 17.8%, RATS-90 8.3%, RACaP Phase 1 32.8%, Phase 2 45.0%. (b) A separate one-calibration-trial diagnostic on 60 paired seed-1 episodes per method. This panel is not the 180-episode zero-shot result, and its Phase 2 one-trial comparison is not statistically significant (raw p = 0.146).

### 2. Put code before the task

The building block is a **Policy API**. It is a typed, callable interface that packages a bounded physical operation. It exposes arguments that can change with the scene, such as grasp choice, target interpretation, or contact strategy.

At runtime, the work is divided among several components:

- **Full ReAct** decomposes the instruction into ordered subgoals. ReAct is a repeated loop: observe the scene, choose a tool call, inspect its report and fresh image, then decide what to do next.
- **Transport ReAct** manages a local source-to-destination loop.
- **The APIs** carry out physical operations.
- **Working memory** tracks current task progress.
- **Long-term experience memory** supplies reusable lessons.

After each operation, fresh RGB-D observations, measurements, and tool reports let ReAct verify, retry, change arguments, or stop. Deployment freezes the APIs, harness, and persistent memory. The runtime agent does not generate, compile, or repair Python code.

Evolution happens in two phases before deployment. Phase 1 uses a capability curriculum to establish execution and recovery, broaden the physical APIs, and build orchestration. Phase 2 evolves APIs, the ReAct harness, and memory together. Paired promotion screens candidate changes against a parent.

A workflow schematic, not a measured result. The evolution-time side covers the curriculum, paired champion/candidate rollouts, visual critic and coding agent, compile/test/regression gate, and promotion or archive. The execution-time side runs from instruction through Full ReAct and Transport ReAct calls to frozen APIs, robot execution, and returned images and reports. Evaluator-only native success selects candidates during evolution but does not enter deployment observations.

### 3. What the transfer test shows

The main test is zero-shot LIBERO-PRO. It has 180 episodes: six perturbation suites, with 10 tasks and three seeds per suite. "Zero-shot" means no target-domain rollout updates persistent code, memory, prompts, skills, or parameters. Visual feedback can still guide decisions within an episode. Results are scored as native success, meaning the benchmark's hidden simulator predicate judged the task successful. The agent's own declaration does not count.

Under these conditions, frozen RACaP Phase 2 achieved **45.0% native success (81/180 episodes)**. The strongest runtime-coding CaP baseline, RATS-base, achieved **17.8% (32/180)**.

The paired Phase 2 versus Phase 1 comparison also favored Phase 2. Phase 2 succeeded on 33 episodes Phase 1 missed. Phase 1 succeeded on 11 that Phase 2 missed (exact McNemar p = 0.00126).

These comparisons have limits. They do not form a one-factor ablation proving that typed APIs alone caused the gains. Phase 2 changes APIs, harness, and memory together, and the experiment does not independently switch only the API typing on and off.

### 4. A toolkit that still adapts

The authors frame RACaP as an evolution-to-execution boundary. Source code is frozen at deployment, while the agent can revise tool choice, arguments, recovery, and stopping from public visual observations. The boundary cuts both ways: RACaP can adapt only within its available Policy APIs, and it does not invent new physical skills online. The reported evidence comes from simulator benchmarks. On-robot deployment remains a proposed path, not a demonstrated physical-robot result.
