# TaskAnchor: Grounding Task State in Reactive VLAs for Long-Horizon Manipulation

> [!summary] Summary
> TaskAnchor is a 27M-parameter adapter that resolves task-state aliasing in reactive VLAs by injecting execution context through their native inputs: a milestone-supervised scalar stage coordinate prepended to the instruction, and a history-conditioned residual on current visual tokens computed by context-adaptive test-time-training layers over a compressed memory bank. It raises pi0.5 RMBench success from 0.14 to 0.79 with about 2 ms added latency.

## Problem

- Reactive VLAs condition only on the current observation and instruction, so visually identical states under the same instruction demand conflicting actions, causing failures despite possessing the needed skills.
- History-aware policies retain temporal evidence for intra-stage branching but leave the subtask stage implicit, forcing unreliable inference of stage transitions from raw latent states.
- Hierarchical approaches rely on a separate VLM planner generating subtask instructions, a fractured architecture that discards fine-grained visual detail and incurs high inference latency.

## Method

- ==Context-Adaptive TTT (CA-TTT)==: eight stacked layers rebuild temporary ==fast weights== each step from an offline-learned initialization via one self-supervised ==key-value reconstruction== update over memory, then discard them after readout.
- ==Visual offset head==: history-conditioned query tokens produce a residual added to the current visual tokens, delivering fine-grained historical evidence through the VLA's native visual interface without architecture changes; this is the core of **TaskAnchor**.
- ==Task-state coordinate==: a scalar in [0,1] equal to milestone index over milestone count, regressed with ==MSE==, formatted as a decimal prepended to the instruction, and teacher-forced with ground truth during training.

## Results

- RMBench: task-specific TaskAnchor-pi0.5 reaches **0.79** average success versus **0.14** for pi0.5 and **0.53** for Mem-0; jointly trained multi-task variants reach **0.70** on pi0.5 and **0.66** on X-VLA.
- RoboMemArena: **50.1%** TSR and **64.7%** CSR, beating pi0.5 by **28.6/26.0** points and PrediMem by **11.6/9.5**; on a real robot it scores **25/25** on all three tasks versus X-VLA's **0, 1, and 4**.
- Ablation: coordinate-only scores **0.31** and history-visual-only **0.20** versus **0.70** combined; swapping the coordinate to adjacent values with fixed inputs flips correct drawer closing into wrong opening behavior.

## Takeaways

> [!tip] Key Insights
> - Long-horizon VLA failures may stem from input ambiguity rather than missing capacity; disambiguating the inputs can unlock skills a pretrained policy already has.
> - Stage identity and intra-stage history are distinct ambiguities needing different signals: a coarse progress cue plus fine-grained visual evidence proved complementary rather than redundant.
> - Injecting context through a model's native prompt and token interfaces is a cheap alternative to separate planners, keeping latency nearly unchanged while letting language steer stage selection.

## Detailed Report

### 1. Overview

A robot is asked to lift a red block and return it to its marker three times. After each return, the tabletop looks much the same, but the correct next action differs. The robot must lift the block again if it has completed fewer than three repetitions, and stop after the third. Reactive vision–language–action (VLA) policies choose short action sequences from the current camera view and instruction. For them, that view alone leaves the decision ambiguous.

TaskAnchor gives a pretrained policy two kinds of context from the episode it is executing. One is a compact signal for *where it is in the task*. The other is a visual update that preserves useful evidence from *what happened before*. On the red-block task, TaskAnchor-XVLA completed the full sequence in 25/25 trials, versus 1/25 for X-VLA. This was one of three physical tasks, each evaluated in 25 trials, and it is not evidence of generalization to arbitrary tasks.

Three real-robot tasks. In (b), the red block is lifted and returned three times, with the first, second, and third lift stages identified. The other panels show (a) human-cued matching with a plush toy, chip bag, and bottle, and (c) chip-bag checkout. Colored boxes mark human cues and corresponding targets.

### 2. Two signals for task state

Two nearly identical current views may need different actions because the task stage or an earlier interaction differs. The authors hypothesize that ambiguity in the inputs, rather than a lack of learned manipulation skills, is a key bottleneck.

TaskAnchor addresses this through two paths. First, it keeps a chronological memory of compressed visual features from past observations. At each decision, it reconstructs temporary fast weights from that memory using Context-Adaptive Test-Time Training (CA-TTT). This is a history-adaptation operation, not an online update to persistent model parameters. The resulting context adds a residual offset to the current visual tokens.

Second, a separate head predicts a scalar coordinate for the semantic execution milestone. This scalar represents the stage in the task. It is not a spatial position or an elapsed-time estimate. During training, milestones provide coordinate supervision, and the ground-truth coordinate is used in the prompt. At inference, the predicted coordinate is formatted as text and prepended to the instruction.

The original VLA then receives the modified visual features and the augmented instruction through its existing interfaces. It generates actions through its existing action-generation mechanism.

Panel (a) shows the current and previous observations feeding TaskAnchor. The coordinate enters the text instruction, and the visual offset enters the reactive VLA's visual path. Panel (b) shows current visual features and compressed memory tokens $m_{1}$ through $m_{t-1}$, a stack of CA-TTT layers with an inner update and fast weight, and the coordinate and offset heads. The "0.27" is an illustrative prompt value, not a reported result.

The addition is small. TaskAnchor adds about 26.93 million parameters in the π0.5 implementation. In the reported efficiency test, it adds 2.08 ms per policy invocation on RMBench and 2.16 ms on RoboMemArena, measured after warm-up and excluding simulator stepping and visual I/O.

### 3. Benchmark evidence on RoboMemArena

RoboMemArena contains 26 tasks averaging 1,076 steps. Of its 151 annotated subtasks, 104 require history, such as remembering source–target mappings, hidden objects, repetition counts, or prerequisite order. The benchmark uses two metrics:

- **Task Success Rate (TSR)** is the share of tasks for which every stage-level verification predicate is satisfied.
- **Cumulative Success Rate (CSR)** is the mean fraction of verification stages completed per task.

TaskAnchor-π0.5 reports 50.1% average TSR and 64.7% average CSR. These are averages across the 26 tasks. The strongest reported prior baseline, PrediMem, reports 38.5% and 55.2%. PrediMem is a dual-system design in which a high-level VLM manages memory and selects subtasks for a low-level VLA actor ([[2605.10921|PrediMem / RoboMemArena paper]]). This is a comparison of reported systems, not a matched-backbone experiment that isolates architecture as the cause.

TaskAnchor is not better in every category. On sequence tasks, its TSR and CSR are lower than PrediMem's. It uses 100 demonstrations per task and infers both task-state signals from observation history without inference-time annotations. The authors interpret the results as showing that history-grounded task-state conditioning helps policies track hidden state and execution stage. The measurement is a benchmark comparison, not proof that the proposed mechanism alone explains the gains.

### 4. Context Changes the Choice

TaskAnchor reuses an existing action policy and gives it a more informative input, rather than adding a new action planner. The experiments support the value of that added context, but they do not prove that input ambiguity is the only source of failure. The authors also note three limits. Milestone-supervised coordinates require task-specific semantic stage annotations. Transfer to completely unseen tasks or execution structures was not extensively evaluated. Memory is limited to an individual trajectory.
