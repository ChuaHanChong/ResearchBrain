# SkillRefine: Cross-Source Skill Induction and Execution Validation for LLM Agents in Refinery Planning Software

> [!summary] Summary
> SkillRefine is a framework that teaches LLM agents to operate AspenTech PIMS refinery planning software. Expert CASE records suggest which tables are changed together, documentation checks those suggestions against valid schemas, and the resulting skills are repaired using execution feedback. The skill library is refined once and then frozen. On 100 held-out PIMS-Bench tasks it raises match F1 by 0.139-0.296 over baseline across four LLM backbones.

## Problem

- Industrial software documentation covers table schemas and interfaces by component, but omits the task-level coordination rules needed to turn a business instruction into coupled multi-table edits.
- Expert CASE records show which tables experts modify together, but without schema grounding, business-language indexing, or any explanation of why those modifications must be coordinated.
- Existing skill-refinement methods such as SkillOpt and Trace2Skill rely on scalar validation scores or trajectory consolidation, so they cannot pinpoint which skill content caused a table-, row-, or column-level error.

## Method

- Role-separated ==cross-source skill induction==: co-modification patterns mined from expert CASE records become coordination hypotheses, which are then checked against documentation-derived table schemas, column semantics, value ranges, and COM interface specifications.
- ==COM interface stabilization== wraps 174 COM methods into tested Python functions, so that software-invocation failures are not mistaken for gaps in planning knowledge, and packages skills as a progressively disclosed L0/L1/L2 ==SKILL.md== hierarchy.
- Structured multi-signal refinement combines label-free format and solver-convergence screening, oracle match decomposition over table, row, column, and value, and signal-conditioned ==trajectory attribution== that drives add, modify, remove, or constrain repairs.

## Results

- SkillRefine reaches match F1 of **0.770**, **0.757**, **0.800**, and **0.764** on DeepSeek-V4-Pro, DeepSeek-V4-Flash, Gemma-4-31B, and Qwen-3.6-27B, the best score on every backbone, ahead of SkillOpt and Trace2Skill.
- Giving the agent raw documentation changes F1 by only -0.025 to +**0.039**, while compiled SkillBase skills add **0.074-0.122**, and refinement adds a further **0.052-0.174** on top of SkillBase.
- The gain over baseline grows from **10-15pp** on L1-L2 tasks to **18-28pp** on L3-L5. Removing the compliance or match attribution branch costs **0.011-0.041** and **0.016-0.077** F1, respectively.

## Takeaways

> [!tip] Key Insights
> - Different knowledge sources should play different roles. Sparse expert practice proposes hypotheses, documentation grounds them, and execution filters them. Simply adding more raw documentation to the context helps little.
> - Breaking failures down into structured error dimensions tells the refiner which skill to fix and how. A single scalar score only says whether a fix helped.
> - A skill library refined once with a strong model can be frozen and reused across weaker backbones, and the smallest model gains the most from it.

## Detailed Report

### 1. Overview

An LLM agent using AspenTech PIMS must turn a short refinery-planning request into correctly formatted, feasible edits to specific tables, rows, columns, and values. In the evaluated Gulf Coast example, a request to shut down the FCC unit can require changes beyond the capacity table. This case is specific to that model and scenario. It does not show that the same edits are required elsewhere. The practical bottleneck is translating intent into coupled, schema-sensitive operations, not simply finding a relevant manual page.

The approach gives three evidence sources distinct jobs. Expert records suggest which operations experts make together. Documentation checks and grounds those candidate patterns. Execution then screens and repairs the resulting skills. The authors call this SkillRefine. Raw documentation produces inconsistent gains, while compiling evidence into task-oriented skills improves match F1 consistently.

### 2. Three sources, different jobs

PIMS documentation covers schemas, column meanings, data types, and interface conventions. However, it is organized by component rather than task. CASE records come from PIMS's structured interface for specifying table edits. They reveal which tables experts modify together, but they do not explain the schema or why the edits go together. COM specifications cover the software automation interface used to operate PIMS. They describe executable methods, not refinery logic.

The authors call this the "Documentation–Practice Gap." Static documentation and expert practice are complementary, incomplete sources, and execution contributes information neither necessarily states.

SkillRefine builds its skills in several steps:

- It parses the documentation into structural and interface knowledge.
- It mines CASE records for co-modification patterns.
- It treats those patterns as hypotheses rather than validated rules, because co-occurrence does not establish that one table requires another and CASE coverage is limited.
- It grounds or expands the patterns with documented schemas, column interactions, ranges, and formatting rules.

Execution-based checks then distinguish malformed CASE or solver non-convergence from mismatches against expert operation references. Consulted skills and tool-use trajectories help narrow which candidate skill content to inspect. This trajectory attribution narrows repair candidates. It does not prove which skill caused an error.

SkillRefine pipeline. Phase 1 documentation grounding and Phase 2a extraction from expert CASE records feed candidate patterns. Phase 2b uses deep table semantics and value-range constraints to expand the candidate skills. Phase 3 shows an LLM agent, PIMS COM API, and executable script. Phase 4 loops execution logs and errors through compliance checks (format and convergence), match decomposition, and trajectory attribution. Proposed repairs include add, modify, remove, and constrain.

### 3. What the execution test establishes

PIMS-Bench comprises 140 tasks across two demonstration models and five structural-complexity levels. Its 40 construction/refinement tasks are disjoint from the 100 held-out test tasks. The primary metric, match F1, measures precision and recall over table–row–column–value operation tuples.

The skill library was built and refined once with DeepSeek-V4-Pro. It was then frozen and reused across four backbones. On Qwen-3.6-27B, component match F1 on the held-out tasks rises from 0.590±0.185 with the unrefined SkillBase library to 0.764±0.072 with SkillRefine. These scores are averages across 100 held-out tasks, with five independent runs per task. SkillBase and SkillRefine use the same tools, so this comparison isolates refined versus unrefined skills within that setup.

The ablations test the repair mechanism directly. Each ablation keeps one diagnostic signal but removes its trajectory-based localization branch. The full system performs best for all four backbones. Removing compliance-conditioned localization lowers match F1 by 0.011–0.041. Removing match-conditioned localization lowers it by 0.016–0.077. Both localization branches therefore contribute in this experiment. The result does not show that the attribution identifies the true cause of each error.

Match F1 for SkillBase, "w/o compliance-conditioned branch," "w/o match-conditioned branch," and SkillRefine (Ours), across DS-V4-Pro, DS-V4-Flash, Gemma-4, and Qwen-3.6. The full-model endpoint labels are 0.770, 0.757, 0.800, and 0.764 respectively. Each removed branch loses its trajectory-based localization while retaining its diagnostic signal.

### 4. A reusable library, within PIMS

The held-out results support two claims within two PIMS demonstration models: the method generalizes to held-out tasks, and one frozen skill library can be reused across the four tested backbones. They are not evidence of transfer to unseen refineries, production deployments, or other platforms. The authors also note that a single expert reference may not capture every valid solution.
