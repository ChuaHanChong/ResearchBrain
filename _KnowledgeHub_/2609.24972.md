# RRSI: Regularized Recursive Self-Improvement of Agent Harnesses

> [!summary] Summary
> RRSI regularizes recursive self-improvement of LLM agent harnesses, where an LLM proposer edits prompts, tools, memory and control flow using a finite evolve set. It constrains proposals with an annealed edit budget, history-aware credit and stall-triggered exploration, and constrains selection with a leakage critic, noise-adjusted floor, cost-aware acceptance and pruning. Across eight benchmarks, it gains up to 4.7 points out of distribution using fewer tokens than unregularized evolution.

## Problem

- Automated harness-evolution methods repeatedly propose and select edits on the same finite evolve set, an adaptive reuse that lets evolve-set gains grow without matching gains on unseen tasks.
- Score-only greedy selection admits benchmark-specific logic, stochastic winners favored by evaluation noise, and accumulated complexity, so AHE and TTHE end below the initial harness out of distribution.
- Prior search loops carry no term for generalization or inference cost and bundle many unrelated edits per candidate, making gains hard to attribute and letting harnesses bloat.

## Method

- **Proposal-side regularization**: a cosine-annealed ==L0-style== edit budget shrinks bundled edits per candidate to one, evidence-aware credit logs every edit's outcome, and stall-triggered exploration targets untried harness components.
- **Leakage critic** and noise-adjusted floor: an LLM critic rejects diffs encoding task names or benchmark-specific logic before evaluation, and candidates scoring more than a calibrated noise band below the best score are rejected.
- **Complexity control**: ==Ridge-style== cost-aware acceptance lets policy-token cost rise only within an allowance linear in measured gain, and ==Lasso-style== structural pruning flags components with no recent positive gain for deletion.

## Results

- Despite the smallest evolve-set gain, RRSI lifts agentic-workspace OOD average from **39.7** to **43.6**; Meta-Harness adds **0.9 points**, while AHE and TTHE end below the base harness.
- Gains transfer across domains and backbones: Terminal-Bench 2.1 rises **6.0** with Claude Opus 4.8 and **14.1** with Gemini 3.5 Flash, SWE-bench Verified **1.8-2.2**, Frontier-Eng **4.3** Medal points.
- Ablation: unregularized evolution scores highest on evolve (**92.8**) but only **40.3** OOD at **3.80M** tokens per trial, versus RRSI's **43.6** at **2.42M**; removing either regularizer group hurts transfer.

## Takeaways

> [!tip] Key Insights
> - Iterative harness search on a fixed evolve set is adaptive data analysis; evolve-set gains are a poor proxy, and held-out cross-benchmark evaluation should be mandatory for self-improving agents.
> - Classical regularization ideas (sparse updates, noise-aware selection, complexity penalties, pruning) transfer to discrete program search: constrain the search trajectory rather than the edit space.
> - Calibrating a noise band from repeated base-harness runs before search is a simple guard; without it, stochastic winners and small cumulative regressions become permanent harness state.

## Detailed Report

### 1. Position Within the Broader Research Landscape

#### 1.1. Agent harnesses as a research target

The paper addresses a growing view in agent research that an LLM agent is not defined solely by its underlying model weights. Instead, the agent also depends on a surrounding “harness,” including system prompts, task prompts, control flow, tool interfaces, memory, context management, subagents, and output-processing logic. These components determine how the model observes a task, chooses actions, recovers from errors, and produces a final deliverable.

This perspective has motivated substantial work on harness engineering. Traditionally, harnesses have been designed manually by inspecting failed trajectories and revising prompts, tools, or control logic. More recent methods automate this process by having an LLM propose harness modifications and retain those that improve performance on a target benchmark. The paper characterizes this procedure as a practical, system-level form of recursive self-improvement because an agent system uses feedback from its own behavior to modify the structure governing future behavior.

#### 1.2. The generalization problem

The central problem identified by the authors is adaptive overfitting. In ordinary machine learning, repeated optimization against a finite training set can produce a model that performs well on that set but poorly on unseen data. Harness evolution creates a related risk: the same evolve set is repeatedly evaluated, and later proposals are influenced by all earlier measurements on those tasks. Because the harness search space is broad and includes executable code and natural-language instructions, it can memorize task-specific patterns, exploit evaluation noise, or accumulate unnecessary complexity.

Prior harness-evolution methods generally select candidates according to empirical performance on the evolve set. The paper argues that this objective does not adequately distinguish reusable mechanisms from benchmark-specific changes. Consequently, large gains on the evolve split may fail to transfer to held-out tasks or other benchmarks. RRSI is positioned as a method for controlling this failure through regularization of the search process rather than by restricting which harness components can be edited.

### 2. Objectives and Motivation

The paper has three principal objectives.

First, it seeks to establish overfitting as a significant methodological concern in recursive harness self-improvement. The authors distinguish among three related failure modes: benchmark-specific fitting, noise chasing, and complexity accumulation. Benchmark-specific fitting occurs when a harness encodes task names, values, answer patterns, or other properties of the evolve suite. Noise chasing occurs when stochastic evaluation causes a candidate to appear better by chance and allows it to become part of the persistent harness. Complexity accumulation occurs when additional prompts, control branches, tools, or context operations raise evolve-set performance without producing a corresponding improvement in the agent’s general mechanism.

Second, the paper introduces RRSI, which regularizes both candidate proposal and candidate selection. The goal is not merely to improve the score on the evolve benchmark, but to produce harness changes that remain useful when the harness is transferred to new tasks, verifiers, tool interfaces, and even backbone policies.

Third, the authors evaluate whether regularization can improve computational efficiency. Uncontrolled evolution may increase the number of reasoning steps, context length, tool calls, or policy tokens. RRSI therefore treats inference cost as part of the acceptance decision, requiring additional computation to be justified by measured performance gains.

### 3. Methodology and Approach

#### 3.1. Formal setup

The agent is represented as \(A=(\pi,H)\), where \(\pi\) is a frozen backbone policy and \(H\) is the editable harness. For a task set \(D\), the authors measure both the average reward score \(S(H;D)\) and the average policy-token cost \(C(H;D)\).

At each evolution round, the current harness is executed on an evolve set. An analyst summarizes the resulting trajectories and failures. A proposer then generates candidate harnesses, which are evaluated on the same evolve set. In an unregularized procedure, the candidate with the highest empirical score becomes the next incumbent. RRSI modifies both the proposal distribution and the admissibility criteria used during selection.

#### 3.2. Proposal-side regularization

RRSI applies three constraints to candidate generation.

**Annealed update sparsity.** The number of independent edits that can be bundled into a candidate decreases over time according to a cosine schedule. Early rounds permit broader changes to discover potentially useful mechanisms. Later rounds impose a smaller edit budget, usually approaching one edit, so that performance changes are easier to attribute to particular modifications. The authors describe this as analogous to an \(L_0\)-style constraint, while noting that RRSI does not optimize an actual \(L_0\)-penalized objective.

**Evidence-aware credit assignment.** Every evaluated edit is recorded with its component type, hypothesis, source diff, score change, cost change, and whether its candidate was accepted. This history is passed to later proposal rounds. Previously unsuccessful mechanisms provide negative evidence, while accepted changes retain explicit credit. This is intended to prevent the search from repeatedly testing ideas that have already failed on the evolve set.

**Structured exploration and pruning.** RRSI monitors whether progress has stalled within an empirically estimated noise range. During a stall, some proposal capacity is directed toward previously unexplored component types, such as memory, tools, skills, subagents, or context management. Separately, components with no recent positive contribution are marked as pruning targets. The proposer is encouraged to remove such machinery in subsequent edits.

#### 3.3. Selection-side regularization

Before full evaluation, a critic screens proposed diffs for leakage. Candidates that explicitly encode evolve-task names, entity names, task-specific values, answers, or other benchmark-specific logic are rejected. The screen is intended to target inappropriate specificity rather than exclude generic prompt, tool, or control-flow improvements.

RRSI also estimates an empirical noise tolerance by repeatedly evaluating the unchanged base harness before evolution. A candidate must remain above a noise-adjusted performance floor relative to the best score observed so far. This prevents a sequence of small apparent improvements from gradually replacing the incumbent with a genuinely worse harness.

For candidates whose improvement exceeds the noise tolerance, RRSI imposes a cost-performance rule. The relative increase in policy-token cost must remain below a threshold that increases with the measured score gain. Thus a candidate that consumes more tokens must provide a sufficiently large performance improvement.

For candidates whose score change falls within the noise band, RRSI uses a separate admissibility rule that combines score change, cost reduction, and novelty of previously untested structural components. This prevents a small noisy score increase from being sufficient by itself. In engineering-design tasks, additional safeguards reject candidates that substantially reduce valid-output rates or increase the rate of missing submissions.

#### 3.4. Experimental design

The authors evaluate eight benchmarks across three domains:

- **Coding:** Terminal-Bench 2.1 for evolution and SWE-bench Verified for out-of-distribution evaluation.
- **Agentic workspace:** Harvey LAB as the evolution suite, with an in-distribution held-out split, plus JobBench, GDPval, and APEX-Agents as OOD benchmarks.
- **Engineering design:** EngDesign for evolution and Frontier-Eng for OOD evaluation.

The experiments use frozen backbone policies. Most experiments use Claude Opus 4.8, while a coding robustness study also uses Gemini 3.5 Flash. Four baselines are compared with RRSI: Meta-Harness, Agentic Harness Engineering, Test-Time Harness Evolution, and HarnessX. All methods begin from the same base harness and use the same evolve set and candidate budget. The paper also evaluates policy-token cost, trajectory length, ablations, and transfer to a backbone that was not used during evolution.

### 4. Main Findings and Results

#### 4.1. Transfer beyond the evolve set

RRSI improves every held-out split reported in the main experiments. With Claude Opus 4.8, it raises Terminal-Bench 2.1 from 74.2 to 80.2, a 6.0-point evolve-set gain, while improving SWE-bench Verified from 82.0 to 83.8. On Harvey LAB, the evolve-set score increases from 89.4 to 90.5, and the in-distribution held-out score rises from 86.9 to 89.2.

The transfer results on agentic workspace benchmarks are larger. RRSI improves JobBench from 36.0 to 40.7, GDPval from 48.8 to 52.3, and APEX-Agents from 34.2 to 37.9. These correspond to gains of 4.7, 3.5, and 3.7 points, respectively. On engineering design, EngDesign improves from 50.0 to 54.9 on the evolve suite, while Frontier-Eng increases from 17.7 to 22.0, a 4.3-point gain.

The results are not limited to judge-based evaluation. Harvey LAB, JobBench, GDPval, and APEX-Agents use LLM-based grading in different ways, whereas EngDesign and Frontier-Eng rely on deterministic simulators or testbenches. The observed transfer on both types of evaluation suggests that the method is not dependent solely on optimizing linguistic properties that judges reward.

#### 4.2. Comparison with prior evolution methods

The baselines generally improve their evolve-set scores, but their gains transfer less consistently. On the agentic workspace setting, Meta-Harness reaches 93.0 on the evolve set compared with RRSI’s 90.5, yet its OOD average is 37.3, compared with RRSI’s 43.6. AHE and TTHE perform below the unevolved harness on some OOD benchmarks, while HarnessX remains close to the base system. This supports the paper’s argument that a lower evolve-set score can accompany better generalization when selection is more conservative.

#### 4.3. Ablation and efficiency results

Removing acceptance-side regularization increases the evolve-set score from 90.5 to 91.5 but reduces the OOD average from 43.6 to 41.0 and raises token cost from 2.42 million to 3.59 million tokens per trial. Removing proposal-side regularization produces a smaller evolve-set change but lowers OOD performance to 41.9. Removing both groups yields the highest evolve-set score, 92.8, but an OOD average of only 40.3 and a cost of 3.80 million tokens.

RRSI’s final harness uses approximately 30 percent fewer policy tokens than unregularized evolution in the reported agentic-workspace comparison. It also produces shorter trajectories than the prior evolved harnesses, although the unevolved base remains less expensive. Therefore, RRSI does not eliminate the computational cost of evolution, but it limits the additional inference burden associated with retained changes.

#### 4.4. Backbone robustness

Under Gemini 3.5 Flash, RRSI improves Terminal-Bench 2.1 from 64.6 to 78.7, a 14.1-point gain, and improves SWE-bench Verified from 76.8 to 79.0. A harness evolved with Gemini 3.5 Flash also improves Terminal-Bench performance from 11.2 to 14.6 when run with the unseen Gemini 3.1 Flash Lite policy. This indicates some transfer across backbone models, although the absolute gains are smaller with the weaker model.

### 5. Significance and Potential Impact

The paper’s primary significance is methodological. It argues that recursive improvement of agent systems cannot be evaluated reliably through evolve-set performance alone because the evolution loop repeatedly reuses the same data. RRSI provides a concrete framework for treating generalization, cost, leakage, and noise as parts of the evolution process.

If supported by further studies, this approach could influence how automated harness engineering is conducted. The use of edit histories, conservative acceptance, structural pruning, and cross-benchmark evaluation may help developers identify changes that represent reusable agent mechanisms rather than task-specific adaptations. The lower token consumption also gives the method operational relevance for long-running agents, where context and inference costs are substantial.

The conclusions remain bounded by the study design. RRSI still depends on a finite evolve set, manually chosen regularization hyperparameters, an LLM-based proposer and critic, and benchmark-specific feedback quality. The experiments focus on frozen backbone models and do not address joint evolution of model weights and harnesses. Broader validation is also needed across other agent architectures, tool ecosystems, longer evolution runs, and independent random seeds. Thus, the results support regularized harness evolution as a promising research direction, but they do not establish that the method will generalize uniformly across future agent settings.
