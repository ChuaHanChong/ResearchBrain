# Demo2Code: From Summarizing Demonstrations to Synthesizing Code via Extended Chain-of-Thought

> [!summary] Summary
> Demo2Code generates executable robot task code from language instructions plus demonstrations using an extended chain-of-thought. An LLM first recursively summarizes long demonstrations into a compact latent task specification, then recursively expands generated high-level code by defining undefined helper functions. It reaches the highest unit-test pass rate across tabletop manipulation, the new Robotouille cooking simulator, and real EPIC-Kitchens demonstrations.

## Problem

- Naively concatenating demonstrations for long-horizon tasks exhausts the LLM context window, so prior language-to-code methods cannot practically consume rich demonstration data.
- Generating complex robot code with control flow, physical constraints and custom perception and action libraries in a single step is error-prone.
- Language instructions alone are underspecified: they omit spatial details, hidden world constraints and personal preferences, so instruction-only code generation guesses and fails unit tests.

## Method

- ==Recursive summarization==: each demonstration is condensed independently from states to low-level actions to high-level subtasks, then all summaries are jointly summarized into a ==latent task specification== capturing preferences and loops.
- Specification-to-code stage: the language instruction and specification, formatted as a docstring, prompt the LLM to write high-level code that may call undefined functions.
- ==Recursive expansion==: each undefined function is defined by further LLM calls until only imported robot perception and action library APIs remain, yielding reusable, composable ==hierarchical code==.
- **Robotouille**: a new open-source ==PDDLGym==-based cooking game simulator with procedurally generated long-horizon tasks and preferences, used to benchmark code generation from demonstrations.

## Results

- On Robotouille, Demo2Code reaches **0.79** execution success and **0.59** unit test pass rate, versus **0.64** and **0.29** for Lang2Code and **0.49** and **0.38** for demonstration-only prompting.
- On tabletop manipulation, Demo2Code scores **0.88** overall pass rate against **0.19** for Lang2Code, and **0.99** execution success against **1.00** for Lang2Code, which rarely completes the actual goal.
- Prompted only with short tasks averaging **12.7** states, it generalizes to test tasks averaging **31.3** states, and passes **5 of 7** real EPIC-Kitchens dish-washing demonstrations versus **2** for Lang2Code.

## Takeaways

> [!tip] Key Insights
> - Long inputs and complex outputs often share a compact latent specification; routing through it in small chain-of-thought steps sidesteps context limits and single-shot generation errors.
> - Demonstrations and language are complementary: language gives task context and demonstrations ground details, so removing either hurts, with demonstration-only prompting failing execution success.
> - Recursive top-down code expansion yields reusable, interpretable, verifiable policies that generalize to longer horizons and unseen objects, though horizon-length scaling still leaves failures on some very long tasks.

## Detailed Report

### 1. Overview

A person may say “make a burger” and leave open what goes on the patty. A demonstration carries the order and preferences that the words leave out. Long demonstrations are unwieldy prompts, though, and one-shot code generation for long tasks is error-prone. Demo2Code reads the demonstration along with the instruction and turns it into an intermediate task description. It then builds executable robot code from that description in stages. The authors frame this as connecting long demonstrations and complex code through a shared, latent task specification. A latent specification is a detailed description of how to do the task that the user has not necessarily stated explicitly. In a kitchen simulator, two users both ask for a burger, but their demonstrations show different preferred ingredients. Demo2Code summarizes each demonstration and generates code that reflects that user's preference.

User 1 prefers lettuce on the patty, and User 2 prefers cheese. Each example shows a kitchen-game sequence of states, a natural-language task specification, and generated code. These are simulator examples, not evidence of physical-robot deployment.

### 2. From demonstration to code

Stage one recursively summarizes each demonstration. State changes become low-level actions, and those actions become higher-level subtasks. The system combines the summaries and produces a detailed specification. Along the way, it uses intermediate reasoning to identify preferences, action order, and potential loops.

Stage two first generates high-level code that may call undefined functions. It then recursively defines those functions until it reaches the provided low-level perception and action APIs. Recursion therefore serves two purposes: it summarizes demonstrations, and it expands code. The authors say this decomposition helps keep each step manageable for the LLM and helps avoid overfilling its context.

The user's job changes from writing every detail into the instruction to providing language plus a demonstration. The engineer still has to provide the perception and action APIs that the generated code calls.

Conceptual pipeline. Language (“Make a burger”) and demonstrations are recursively summarized into a task specification. The pipeline then produces high-level code from the language and specification, and recursive expansion defines helper functions.

### 3. Does staging help on longer tasks?

Robotouille is a kitchen task-planning simulator with a game interface. Task horizon is the number of states in the demonstrations. The main metric is unit-test pass rate, where a test passes only if all subgoals are achieved and all constraints are satisfied. Execution success is a separate metric that only checks whether code runs without an error.

All methods used GPT-3.5-turbo-16k at temperature 0. Under these conditions, Demo2Code's overall Robotouille unit-test pass rate was 0.59. The comparison baseline, Lang2Code, is the language-only baseline from [[2209.07753|Code as Policies]], and its rate was 0.29.

The prompt examples averaged 12.7 states, while the test tasks averaged 31.3. The prompt examples covered preparing patties and lettuce, whereas the test tasks include more complex burgers and ingredients. This supports a result within the simulator, not a claim of successful real-robot deployment.

A separate ablation tests whether the staged reasoning matters. It compares direct generation (No-Cot) with 1-Step, 2-Steps, and Full summarization chains. Tasks were grouped as short (around 2 states), medium (5–10), and long (at least 15). The authors report that longer chains generally improved unit-test pass rates. The improvement was more consequential for medium- and long-horizon tasks, while short tasks were easier to process with fewer steps.

Unit-test pass rate for No-Cot, 1-Step, 2-Steps, and Full, separated into short-, medium-, and long-horizon tasks. Chain length has little effect for short tasks, and the longer chain improves results more for medium and long tasks.

More reasoning is not always better. In another ablation, the authors report that an “Only Analyze” prompt outperforms Full on normal and hard Robotouille tasks. The evidence supports staged reasoning as useful, not as a universal rule.

### 4. What the evidence establishes

In the simulator examples, demonstrations communicate choices that “make a burger” alone leaves open. The staged pipeline preserves those details while building code in smaller pieces. Demo2Code still depends on supplied low-level skills and remains subject to LLM errors.
