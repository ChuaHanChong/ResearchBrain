# RegenHarness: A Robot Agent Harness with Evidence-Gated Recursive Self-Improvement

> [!summary] Summary
> RegenHarness is an evidence-gated robot-agent harness that separates a model loop producing context-conditioned proposals from an agent loop that dispatches skills, gathers evidence, verifies postconditions, commits state, and recovers under budgets. Four role-isolated contexts, versioned memory, and an identity- and version-bound commit gate block false completion; a cross-mission self-improvement protocol revises configuration under fixed regression checks. A real quadruped warehouse inspection runs end-to-end under it.

## Problem

- Prior reasoning-acting agents and robot runtimes conflate a controller's return or a planner's claim with verified physical completion, so early false positives corrupt every downstream decision.
- Existing guarded-execution systems verify skills but leave unspecified which component may write trusted task state and which evidence each role may see, permitting correlated self-confirmation.
- Long-horizon reliability is multiplicative across stages, so improving one local policy cannot prevent stalled retries, duplicate physical dispatch, resource conflicts, or irreproducible decisions.

## Method

- ==Evidence-gated agent loop==: versioned skill invocations declare preconditions, typed target effects, evidence policy and recovery limits, and only an identity- and version-bound ==commit gate== advances committed facts on a satisfied verdict.
- **Role-isolated context compiler** builds four bounded views from one versioned memory (planner C1, skill C2, verifier C3, recovery C4), so the verifier never inherits the planner's own completion claim.
- Supervised lifecycle plus ==recursive self-improvement==: capability cards, idempotent dispatch keyed to task, node and state version, resource leases, budgeted recovery ladders, and configuration revision gated by fixed regression checks with versioned rollback.

## Results

- Voice-triggered warehouse inspection ran seven stages in **259.94 s** mission time, **271.22 s** for the full voice turn from an **8.16 s** command, with eight 1280x720 panoramic frames whose checksums all matched.
- Navigation reached endpoints inside the configured **0.40 m** arrival radius: outbound **0.11 m** and return **0.17 m** on a 17.62 m reference route, and **0.25 m** on the 18.83 m circuit.
- The circuit started **0.23 m** from its goal, already within tolerance, yet the robot traveled **6.20 m** away and returned at **99.6%** reference progress with **0.068 m** remaining.

## Takeaways

> [!tip] Key Insights
> - Controller done, node success, and goal success are distinct stopping conditions; authorize state transitions with independent evidence rather than a model's or backend's self-report.
> - Information-access policy matters as much as verification: withholding a planner's own success claim from the verifier removes a cheap route to correlated self-confirmation.
> - Self-improvement stays safe when the updater cannot weaken its own acceptance predicate, commit gate, or lower safety interlocks, and revisions land only at mission boundaries.

## Detailed Report

### 1. Overview

A quadruped begins a closed-route navigation task almost at its goal. It starts 0.23 m from its shared start/goal, already inside the configured 0.40 m arrival radius, yet the task requires it to leave, traverse the route, and return. A location check alone would make it look finished before it had done the task. In the recorded run, its distance from the endpoint reaches 6.20 m before it returns. This illustrates why a robot must check task history and route progress, not just endpoint proximity. The distance is based on recorded localization and the deployed navigation logs; it is not an external ground-truth accuracy measurement. It is one recorded navigation case, not a general performance guarantee.

### 2. A proposal is not progress

The paper's central move is to keep a skill's report separate from trusted task progress. A **harness** is the runtime around robot skills that dispatches them, tracks their execution, and decides which results count as accepted progress. It is not the robot's model or its low-level controller. In RegenHarness, the runtime checks evidence against the skill's declared conditions. Only a matching, authorized verification can update the task record.

The harness breaks the user goal into dependent task stages. The planner chooses an eligible stage and skill. Supervision dispatches and monitors that skill, and verification checks its declared conditions against evidence. A commit gate accepts progress only when the verdict, task/attempt identity, and state version match. A failed, ambiguous, stale, or unsafe result does not become success. It can enter recovery, where retry, switch, or replan actions consume explicit budgets. Once required stages are committed, a separate check tests the original user goal before a final success report.

Information access is controlled as well. The verifier's view contains postconditions and sourced, fresh sensor evidence, without the planner's completion claim. Observed facts are not automatically committed facts.

Schematic of the design. The flow runs from user goal/task specification through planning and supervision, execution evidence and verification, to the commit gate. Versioned memory (“observed ≠ committed”) feeds a context compiler that issues C1–C4 views. Providers feed execution but do not own task-state commitment.

### 3. One inspection mission

A separate warehouse-inspection mission links one spoken request to the execution through mission identifiers, timestamps, and checksums. The request is translated as “Help me go and check the office storage area.” The recorded workflow runs through speech recognition, navigation to the warehouse, panoramic capture, visual analysis, DingTalk image/report delivery, return, and a spoken report. The robot saves eight destination images. The configured Qwen3-VL-Plus model reports that boxes obstruct a passage; this is a model-reported finding. The system records acknowledged delivery of four images plus the report and completed speech playback. The supervisor reports 0.11 m endpoint distance on the outbound leg and 0.17 m on return, against a configured 0.40 m arrival radius. These are logged endpoint distances, not externally verified localization accuracy. This chain shows one integrated physical workflow; it does not quantify reliability across repeated missions.

### 4. What was and was not tested

Verification-gated progression is not new. [[2609.01281|EmbodiedSkills]] checks proposed skills before execution and verifies outcomes afterward. [[2609.21908|CommitFlow]] monitors physical conditions, blocks dependent actions, and re-verifies after correction. RegenHarness's claimed distinction is the surrounding execution contract. The paper specifies controlled harness comparisons and an evaluation protocol for evidence-gated recursive self-improvement, but does not report their outcome data. Verification still depends on evidence quality, and the reference deployment is single-host.

### 5. Progress needs proof

The circuit makes clear why “near the goal” is not the same as “done.” RegenHarness contributes a runtime design that admits task progress from evidence rather than from a proposal or stop signal. Its support comes from two documented deployment cases, not from a controlled benchmark showing a general success-rate improvement.
