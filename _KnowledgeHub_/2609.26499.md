# Generalizing Manipulation Skills with a Local Coding Agent

> [!summary] Summary
> A locally served 27B open-weight vision-language model drives a UR3e arm from a coding-agent harness, writing and debugging its own perception and control code atop a hardware service exposing nine primitives plus safety clamps, seeded by one procedural skill document per task. Across nine children's-toy tasks probing color, size, shape and task variation, it generalized in 30 of 45 trials; resuming a session on a rearranged scene halved duration.

## Problem

- Language-driven robots receive fixed task-level action interfaces whose constants a programmer measures in advance, so every new object demands fresh hand-written code and measurements.
- Early code-writing controllers were open-loop with weak programmer models, unable to debug their own generated programs or recover from execution errors.
- Recent coding-agent manipulation work benchmarks interfaces or models mostly in simulation or via API-served frontier models, never testing generalization on hardware with a local open-weight model.

## Method

- ==Platform layer==: one hardware-owning HTTP service wrapping ==airo-mono== exposes ==nine operations== (look, move_tcp, locate_pixel, color-blob locate_objects, descend_to_contact, gripper) with ==workspace-box clamping==, speed and force caps.
- ==Agent setup==: the ==pi harness== gives a 27B VLM shell, filesystem and per-session workspace, a 68-line prompt biasing ==measure-act-verify loops==, and a 617-line robot manual for invariant constants.
- ==Skills==: six hand-written ==procedural documents==, one grasp plus one placement per game, listing each measured value, how it was obtained, verification steps and authoring pitfalls, flagged valid only for the documented instance.

## Results

- **30 of 45** trials succeeded without intervention over **15.8** robot-hours, **3.18M** output tokens, **2,043** tool calls; durations **3.4** to **67.5** minutes, with **20 of 25** cup trials passing.
- Second passes on resumed sessions cut wall-clock time to **0.48x**, tool calls from **734** to **354** (**0.48x**), and output tokens to **0.34x**, with reasoning share falling from **80%** to **67%**.
- Failures split into perception errors, assumption anchoring (recovered in **10 of 30** successes, unrecovered in **4** runs) and morphology unawareness; **8 of 11** failures ended in protective stops.

## Takeaways

> [!tip] Key Insights
> - Documenting a skill as procedure plus provenance for each measured value, explicitly marked instance-specific, lets an agent re-measure rather than blindly reuse numbers.
> - Safety checks on the tool center point alone are insufficient: an agent without a body schema can rotate or open the gripper into collisions while passing every bound.
> - Re-measuring is not re-questioning: an agent can validate a wrong object label nine ways, so plan quality from the first pass largely determines later speed.

## Detailed Report

### 1. Overview

A robot cannot carry out “stack the smaller cup on the bigger one” from words alone. It must locate the cups, estimate their dimensions, choose a grasp, and determine where to release. In many language-guided systems, people pre-program object-specific measurements and actions. This paper instead lets a locally run vision-language model write and execute code that remeasures objects and adapts a procedural skill. On physical hardware, Qwen3.8-27B, served locally on one workstation, completed 30 of 45 first-pass trials without operator intervention across nine tasks, with five trials per task. This result comes from tests on toy-task variations and is not a general success rate for robotics.

A robot arm above a tabletop shape sorter (left). The base-task scenes are two blue cups, the sorter with a red cylinder, and a teal ring beside a rod (right).

### 2. A recipe the robot can adapt

The local model works in a coding-agent harness, with a fresh workspace for each initial task session. Each game has two hand-written skills: one grasp procedure and one placement procedure. The skills describe a single object instance, including measurements, how they were obtained, checks, and pitfalls. The model uses the procedure as transferable knowledge. It remeasures object-specific values for the live scene and writes perception and control scripts.

A hardware-owning platform provides nine operations through both direct tool calls and a Python SDK. These operations include camera capture, state, motion, gripper, pixel localization, color-blob detection, guarded descent, and motion locking. The platform owns kinematics and safety limits, and every actuation passes those limits. The platform has a generic color-blob detector rather than a trained perception model. The agent supplies thresholds and writes the rest of the perception code.

Architectural overview. The local model and system prompt sit above a workspace containing the two skills, the platform manual, and scripts written during a run. Direct tool calls and SDK calls from scripts reach the same platform, which covers the UR3e, gripper, wrist camera, kinematics, workspace box, speed and force caps, and motion lock.

### 3. What the trials establish

Three children’s-toy games supplied the tasks: cups, a peg-in-hole sorter, and rings. Together they yield nine tasks that vary color, size, shape, or task requirements relative to a skill for one instance. The agent ran each task five times on a UR3e with a parallel gripper and wrist camera. Success counts only trials completed without operator intervention. Eventual completion after help does not count. Under that criterion, 30 of 45 trials succeeded.

One representative task was **Cups: Large blue cups**, a size variation that kept the skill’s blue-cup color. All 5 of 5 trials succeeded without intervention, taking 3.4–6.7 minutes, with a 6.1-minute median.

Across trials, the agent followed a recurring process. It read the relevant skill and manual pages, measured the scene with agent-written perception code, and wrote and ran pick-and-place code. It then verified the result from a camera pose and returned to measurement when something went wrong. The authors credit both the documented procedures and verification for the successes. Neither explanation was isolated in an ablation.

In a second pass, the authors resumed the fastest and slowest successful session for each task. They reset the scene with objects in new positions. Across 17 resumed trials, the ratio of second-pass to first-pass elapsed duration was 0.48. The sessions retained conversation history, measurements, and generated scripts. The experiment did not isolate their individual contributions to the speedup. This is in-session reuse, not evidence of persistent learning.

### 4. Scope

The contribution is that a model can turn a one-object procedure into measured, executable work for new objects. The test covers object- and task-related variation only. It does not cover lighting, materials, clutter, workspace layout, task vocabulary, or robot morphology. The agent also depends on a human-written skill for one instance of each game. It relies as well on a platform that clamps every Cartesian target and supplies hardware access and safety limits.
