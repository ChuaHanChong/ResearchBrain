# InterEvolve: Test-Time Evolution of Reward Programs for Humanoid Loco-Manipulation

> [!summary] Summary
> InterEvolve adapts a frozen humanoid whole-body controller to unseen loco-manipulation tasks at test time without retraining. An LLM agent evolves staged reward programs, CMA-ES tunes their constants, and an object-aware forward-backward behavioral foundation model executes each reward zero-shot as a latent prompt. Evolution raises goal-conditioned task success from 34.6% to 86.5%, retains verified programs in a skill library, and deploys on a real Unitree G1.

## Problem

- LLM reward-design methods realize every candidate reward by training a new policy, which makes iterating over many reward revisions slow and computationally expensive.
- Existing humanoid forward-backward behavioral foundation models observe only the body, so rewards that differ only in an object's goal collapse into the same behavior.
- Common humanoid task interfaces such as motion references, goal states and skill labels struggle to specify nuanced contact-rich multi-stage objectives like tipping a box onto a new face.

## Method

- ==Object-aware FB motor model==: trainable object-conditioned residuals added to BFM-Zero's frozen body actor, forward and backward maps, trained on retargeted OMOMO and GRAB human-object interaction data.
- ==Reward programs==: ordered stages, each with reward code and a completion condition, plus tunable constants; the active stage's reward is projected into a latent prompt at every control step through a fixed state bank.
- ==Two-loop test-time evolution==: an LLM agent revises program structure from per-criterion rollout feedback, ==CMA-ES== tunes constants over 192 parallel scenarios, and verified programs enter a text skill library.

## Results

- Across eight goal-conditioned task families, evolution reaches **86.5%** success versus **34.6%** for the calibrated agent program and **18.0%** for a calibrated human-written reward, at **2.1 GPU-hours** per family.
- Ablations: forcing a single stage drops success to **44.7%** and removing CMA-ES tuning to **51.6%**; for tracking, the evolved reward reaches **72%** success versus ULTRA's **66%** and BFM-Zero's **8%**.
- The full skill library solves **8/10** relocate, **4/10** stack and **5/10** carry-place-kick composite episodes versus 0, 0 and 1 without a library; evolved kick and push programs run on a real G1.

## Takeaways

> [!tip] Key Insights
> - Reward structure, not weight tuning, often limits a fixed controller: calibration alone barely helps, while revising what is rewarded and how stages split unlocks latent competence.
> - Behavioral foundation models make test-time reward search practical because each candidate reward costs only rollouts rather than an RL run, mirroring test-time compute scaling in language models.
> - Skill-library reuse helps only when stored programs cover the contact modes a new task needs, and retrieved programs still need evolution rather than direct replay.

## Detailed Report

### 1. Overview

A humanoid controller has learned to push, lift, and carry boxes. It is then asked to tip one onto a different face, without a demonstration of that action. A new contact-rich task like this is hard to express as a motion reference or a sequence of predefined skills, and repeatedly training a policy for each reward revision is slow.

The authors propose to keep the controller fixed and evolve the task strategy around it. The strategy specifies objectives in stages, revises them from execution feedback, and retains successful programs for later tasks. In their example, a human-written reward fails, while an evolved strategy succeeds by using body movement to turn the box. The system is called InterEvolve.

A controller trained on human-object interactions such as lifting and pushing receives a novel in-place box-rotation request. The human-reward example is marked as unsuccessful. The evolved-reward example is marked successful: the robot walks around the box and uses body movement to rotate it.

### 2. A task strategy the controller can execute

The strategy is written as a **reward program**. This is an ordered set of stages, each with a reward and a condition for advancing. Numerical constants set the weights and thresholds.

Each round follows a fixed sequence:

1. An LLM proposes or revises a program, informed by the task description and scene.
1. The reward for the active stage becomes a prompt for a forward-backward (FB) behavioral foundation model. This model turns a reward into a latent prompt for the same policy.
1. The fixed controller executes the prompt.
1. A fixed verifier scores task outcomes and constraints.

The LLM changes program structure, and CMA-ES, a numerical optimizer, tunes the constants for each proposed structure. Feedback from parallel simulated rollouts tells the LLM which criterion or stage failed. Successful programs and their verifier results can be retained in a text skill library.

The FB model also needs to perceive objects. The existing BFM-Zero model observes only the body, so InterEvolve adds object features and trainable object-conditioned residuals on frozen body branches. These residuals are trained beforehand on human-object interaction data. During task evolution, the controller weights stay fixed.

(a) The task and skill library feed an LLM-written staged reward program with CMA-ES-tuned constants. (b) Reward-scored states in a fixed bank become a latent prompt, executed by a frozen body prior plus object residual without retraining. (c) Parallel rollout verification produces feedback for the next structural revision. The kick-task numbers illustrate criterion-level feedback and are separate from the main benchmark result.

### 3. The fixed-program test

The benchmark has eight simulated task families. Examples include pushing to a mark, carrying at different heights, tipping, and feet-only kicking. A verifier independent of the learned reward checks the required outcomes and constraints. Success rate (SR) is the share of rollouts satisfying every task criterion and physical constraint in the same rollout.

Averaged equally across the eight families, InterEvolve reaches 86.5% SR. The agent's initial program after CMA-ES tuning reaches 34.6%, and a human-written program after tuning reaches 18.0%. Each metric averages three independent evaluation runs. Both fixed-program baselines receive the same numerical calibration. The result therefore supports the authors' interpretation that revising program structure (what to reward and how to stage it) unlocks more behavior than calibrating weights alone. It does not isolate the LLM from the rest of the evolving system.

An ablation removes one component from the full system. Disabling multi-stage programs drops SR from 86.5% to 44.7%. This supports staging as important in this benchmark, not as a universal rule.

The search adds computation. One complete evolution costs 2.1 single-GPU hours and 0.23 million LLM tokens per task family, compared with 0.6 GPU-hours for the calibrated agent baseline. The payoff is fewer task-specific policy-training runs, not demonstrated savings in total compute or elapsed time.

### 4. A task interface that learns

Programs evolved and verified in simulation were run on a Unitree G1 for kicking and pushing. InterEvolve's contribution is an editable, testable task interface for a fixed controller. Search can only elicit skills within the learned motor repertoire and reward-inference bank. Evolution itself is too costly for real-time replanning during physical execution.
