# Terminal-Bench: Benchmarking Agents on Hard, Realistic Tasks in Command Line Interfaces

> [!summary] Summary
> Terminal-Bench 2.0 is a benchmark of 89 hard, realistic command-line tasks. Each task has its own Docker environment, a human-written oracle solution and outcome-based tests, and three human reviewers verified each one. Evaluating 16 frontier models across six agent scaffolds, the paper finds the best system, Codex CLI with GPT-5.2, resolves about 63% of tasks. It also provides failure-mode taxonomies.

## Problem

- Existing agent benchmarks either do not reflect real professional workflows or are too easy to separate frontier models, so headroom to measure long-horizon autonomy is lacking.
- Terminal agents such as Claude Code, Codex CLI and Gemini CLI are widely deployed, yet no rigorous benchmark measures skilled, valuable terminal work like legacy system configuration or paper reimplementation.
- Agent scaffolds are tuned to particular models, so model and agent performance are entangled, and task flaws such as unspecified end states or exploitable shortcuts undermine benchmark validity.

## Method

- Task format: each task bundles an instruction, a ==Docker image==, ==outcome-driven tests== on final container state, a human-written ==oracle solution== and a time limit, run through the **Harbor** harness.
- ==Curation pipeline==: 93 contributors submitted 229 tasks; automated CI and LLM checks, expert review, multi-model runs, ==trajectory audits== and an ==adversarial exploit agent== yielded 89 verified tasks.
- **Terminus 2**, a ==neutral scaffold== with a single ==headless-terminal tool==, isolates model capability. It is paired with a ==failure taxonomy== (Execution, Coherence, Verification) and a ==command-level error taxonomy== using LLM judges.

## Results

- Codex CLI with GPT-5.2 scores highest at **63%**, then Terminus 2 with Claude Opus 4.5 at **58%** and Gemini 3 Pro at **57%**; the best open-weight model, Kimi K2 Thinking, reaches **36%**.
- Model choice matters more than scaffold: Codex CLI gains **52%** moving from GPT-5-Nano to GPT-5.2, and state-of-the-art nearly doubled in **eight months**, from Gemini 2.5 Pro to GPT-5.2, across **32,155** trials.
- Human-hard tasks are empirically hard **93.3%** of the time (overall **r=0.436**). Command error rates range from **9.2%** to **26.7%**, and command-not-found is the top command failure at **24.1%**.

## Takeaways

> [!tip] Key Insights
> - Outcome-based tests on final environment state, with oracle solutions and adversarial exploit audits, let a benchmark accept diverse solution paths while resisting shortcuts; this is a reusable design for agent evaluation.
> - Failure signatures differ by model: frontier models fail mostly on execution errors, open models show balanced failures, so improvement strategies should be model-specific rather than one-size-fits-all.
> - Neither more turns nor more tokens reliably improve success, and human difficulty intuition misses many tasks models find hard, so effort scaling and human difficulty labels are weak proxies for capability.

## Detailed Report

### 1. How This Work Fits into the Broader Research Landscape

The development of autonomous AI agents capable of performing complex, real-world tasks is a rapidly advancing field. As LLMs become more sophisticated, the need for robust benchmarks that accurately measure their capabilities in realistic, challenging environments becomes critical. Terminal-Bench positions itself directly within this evolving landscape, addressing several limitations of existing benchmarks.

Prior work has explored various facets of agent evaluation:
- **Software Engineering Benchmarks**: SWE-Bench, SWE-Bench Multimodal, SWE-Lancer, HumanEval, and DevEval focus on code generation, bug fixing, and software development lifecycle tasks. While relevant, many of these might operate in more abstracted environments or focus on specific aspects like code patches rather than interactive problem-solving.
- **Tool-Use Benchmarks**: τ-Bench and the Berkeley Function Calling Leaderboard assess an agent's ability to utilize external tools effectively. Terminal-Bench integrates tool-use implicitly through command-line interactions but broadens the scope to general terminal environments.
- **Computer Use Benchmarks**: WebArena, Visual Web Arena, AppWorld, and OS World evaluate agents in web or desktop GUI environments. Terminal-Bench distinguishes itself by focusing on the command-line interface, a ubiquitous, powerful, and text-based environment crucial for highly skilled technical work (software engineering, scientific computing, cybersecurity). The terminal's text-based nature makes it particularly suitable for LLM agents.
- **Scientific Discovery Benchmarks**: ReplicationBench, MLGym-Bench, and Auto-Bench evaluate agents' abilities in scientific workflows. Terminal-Bench includes tasks in scientific computing and machine learning, emphasizing hands-on terminal interaction for these domains.

Terminal-Bench carves out a unique niche by emphasizing:
- **Realism**: Tasks are "inspired by problems from real workflows" and conducted in "real terminal shell" within containerized environments. This contrasts with synthetic environments or highly constrained problem settings.
- **Difficulty and Long-Horizon Nature**: The benchmark is "carefully curated hard," requiring "extensive domain knowledge, long chains of interdependent actions, and autonomous problem-solving." This ensures it remains challenging for frontier models, as evidenced by current models scoring less than 65%.
- **Diversity**: With 89 tasks across various categories like Software Engineering, System Administration, Data Science, Security, and Scientific Computing, Terminal-Bench avoids specializing in a single domain, reflecting the versatility of terminal usage in professional settings.
- **Outcome-Driven Evaluation**: The framework verifies task completion by testing the final container state, allowing agents diverse approaches rather than dictating specific command sequences.

In essence, Terminal-Bench aims to provide a gold standard for evaluating agents on the kind of high-skill, economically valuable work that professionals perform daily in command-line environments, pushing the boundaries beyond simpler coding tasks or web interactions.

### 2. Key Objectives and Motivation

The core objectives and motivations behind Terminal-Bench are clearly articulated in the paper, driven by the rapid advancements in AI agent capabilities:

1. **Address Limitations of Existing Benchmarks**: The primary motivation is to fill a critical gap in the existing evaluation landscape. Current benchmarks are often criticized for either not measuring real-world tasks or lacking sufficient difficulty to meaningfully differentiate frontier models. As AI agents evolve to autonomously complete "valuable, long-horizon tasks in diverse domains," benchmarks must evolve accordingly.
2. **Develop a Hard, Realistic Benchmark for Terminal Environments**: The central objective is to create a challenging benchmark specifically tailored to the command-line interface. The terminal is identified as a "ubiquitous, versatile, and powerful interface" used for "highly-skilled and valuable work" such as software engineering, scientific computing, and cybersecurity. The benchmark seeks to measure agents' ability to perform this type of high-skill work.
3. **Provide a Comprehensive Evaluation Framework and Dataset**: Terminal-Bench introduces a standardized framework for building and running tasks. This includes a robust dataset (Terminal-Bench 2.0 with 89 tasks), each featuring a containerized environment, clear instructions, a set of tests for verification, and a human-written reference solution. The framework's design facilitates the creation and integration of diverse tasks.
4. **Drive Future Agent and Model Improvement**: By benchmarking frontier LLMs and agents and conducting a detailed error analysis, the authors aim to "identify areas for model and agent improvement." The goal is not just to measure, but to provide actionable insights that guide researchers and developers in enhancing AI agent capabilities, particularly in areas like execution, coherence, and verification.
5. **Foster Reproducibility and Community Collaboration**: The authors state their intention to "publish the dataset and evaluation harness to assist developers and researchers in future work at tbench.ai." This open-source approach, coupled with rigorous quality control and clear documentation, aims to establish Terminal-Bench as a reliable and widely adopted tool for tracking progress in autonomous agent development.

### 3. Methodology and Approach

The methodology employed in Terminal-Bench is rigorous and multi-faceted, focusing on task design, dataset construction, and robust evaluation.

#### 3.1. Task Formulation

A Terminal-Bench task is defined by:
- **Instruction**: A natural language description of the task.
- **Docker Image**: A containerized environment with relevant packages and files, ensuring reproducibility and isolation.
- **Set of Tests**: Programmatic tests that verify task completion by checking the final container state, rather than prescribing specific agent actions. This makes the framework "outcome-driven."
- **Example Solution**: A manually written human solution script to demonstrate solvability and guide test development.
- **Time Limit**: A constraint on agent execution time.

Tasks are interactive, requiring agents to explore and manipulate the environment by issuing Bash commands or invoking custom tools. The framework utilizes the Harbor task format and harness, which supports popular agents like Claude Code, Codex CLI, OpenHands, and Mini-SWE-Agent, as well as a custom-developed "neutral testbed" agent called Terminus 2.

#### 3.2. Dataset Construction (Terminal-Bench 2.0)

The Terminal-Bench 2.0 dataset comprises 89 challenging tasks, diversified across various domains.
- **Crowd-Sourcing**: Tasks were crowd-sourced through open-source contributions, yielding 229 initial tasks from 93 contributors.
- **Selection and Difficulty Assessment**: The 89 tasks for the final dataset were selected based on author difficulty assessments (categorized as "medium" or "hard" for human experts/juniors) and a stringent quality assessment.
- **Categorization**: Tasks are assigned high-level categories (e.g., Software Engineering, System Administration, Data Science), with Software Engineering being the largest but no single category dominating.

#### 3.3. Verification Process

A comprehensive, multi-round verification process ensures task quality, focusing on:
- **Specificity**: Unit tests must accurately reflect all acceptable end states described in the instructions.
- **Solvability**: Each task has an "oracle solution script" that, when executed, passes all test cases.
- **Integrity**: Agents should not be able to "cheat" (e.g., by exploiting hidden information or future states of a repository).

The verification steps include:
1. **Automated CI & LLM Checks**: Upon submission, automated workflows run the oracle solution, verify its success, and ensure a "dummy" solution fails. LLM-based tools review task specifications for common mistakes (e.g., consistency between instructions and tests, anti-cheating measures, correct schema definitions).
2. **Contributor Checklist**: Authors must manually confirm adherence to quality criteria using a detailed checklist.
3. **Expert Human Review**: Experienced reviewers manually check tasks against quality standards.
4. **Terminus Model Experiments**: Tasks are run with powerful LLMs and Terminus 2. Failures are analyzed to distinguish genuine agent limitations from task flaws.
5. **Adversarial Exploit Audit**: An agent specifically designed to "cheat" is run to detect design flaws that could allow unearned passes.
6. **Final Decision**: Tasks passing all audits are added to Terminal-Bench 2.0. This rigorous process involved "multiple hundreds of person-hours" in review alone.

#### 3.4. Experimental Setup

- **Agents and Models**: Six state-of-the-art agents (Claude Code, Codex CLI, Gemini CLI, OpenHands, Mini-SWE-Agent, Terminus 2) were evaluated across 16 frontier models (closed-source like GPT-5.2, Claude Opus 4.5, Gemini 3 Pro; and open-weight like Qwen 3 Coder 480B, Kimi K2 Thinking).
- **Terminus 2 Scaffold**: To ensure fair comparison and isolate model performance, Terminus 2 was developed as a minimalist agent that uses only a headless terminal and Bash commands, without dedicated tools. It also incorporates a context summarization module for long-horizon tasks.
- **Scale**: A total of 32,155 trials were conducted, with each model/agent combination run at least five times per task.
- **Infrastructure**: Evaluations were run using the Harbor harness with Daytona, allowing parallel execution of containers.

### 4. Main Findings and Results

The evaluation of state-of-the-art AI agents on Terminal-Bench 2.0 yielded several significant findings:

1. **Benchmark Difficulty**: Frontier models and agents achieved a resolution rate of less than 65%, with smaller models scoring as low as 15%. Specifically, GPT-5.2 with Codex CLI achieved the highest average resolution rate at 62.9%, followed by Claude Opus 4.5 with Terminus 2 (57.8%) and Gemini 3 Pro with Terminus 2 (56.9%). This confirms Terminal-Bench 2.0's effectiveness as a challenging benchmark for current AI capabilities.
2. **Proprietary Models Lead**: Proprietary models consistently outperformed open-weight models, occupying the top 13 positions in the rankings. Kimi K2 Thinking with Terminus 2 was the best-performing open-weight model, resolving 35.7% of tasks.
3. **Model vs. Agent Scaffold Importance**: Model selection generally proved more critical than the specific agent scaffold. For instance, Codex CLI's resolution rate increased by 52% when using GPT-5.2 over GPT-5-Nano, and Gemini 2.5 Pro saw a 17% increase with Terminus 2 over OpenHands. This implies that the underlying LLM's reasoning capabilities are paramount.
4. **Performance Over Time**: New model releases showed a clear trend of improved performance. State-of-the-art performance nearly doubled in the eight months between the release of Gemini 2.5 Pro and GPT-5.2, suggesting rapid progress in agentic capabilities.
5. **Cost-Performance Trade-off**: Running the benchmark varied in cost from under a dollar to hundreds of dollars, depending on the model's pricing. Most agents completed tasks within 20 minutes, but some took up to two hours, consuming millions of tokens.
6. **Efficiency Metrics vs. Success**: A negligible correlation was found between the average number of turns (episodes) per trial and success rate (r=-0.028). Similarly, a weak negative correlation (r=-0.170) existed between average output tokens and success rate. This indicates that excessive verbosity or numerous attempts do not necessarily lead to better performance; rather, the quality of reasoning per interaction is more important.
7. **Human-Predicted vs. Empirical Difficulty**: There was a positive correlation (r=0.436) between human-predicted and empirical difficulty. 93.3% of human-rated "hard" tasks were also empirically hard for models. The largest discrepancy occurred when humans rated tasks as "medium," but models found them "hard" (54.5%), often for tasks requiring creative or adversarial reasoning that models lack.
8. **Trajectory-Level Error Analysis**: An LLM-as-judge analysis revealed systematic failure modes. For frontier closed-source models (Claude Opus 4.5, GPT-5.2), **Execution errors** (e.g., disobeying specifications, step repetition, unaware of termination conditions) dominated, occurring more frequently than coherence or verification errors. Open-source models (e.g., Qwen Coder) showed a more balanced error pattern across all categories.
9. **Command-Level Error Analysis**: Focusing on individual command failures, the analysis found that "Command not found" (e.g., executables not installed or not in PATH) was the most frequent failure (24.1% of all failures), followed by general "App failure" when running executables (9.6%). Command error rates ranged from 9.2% (Grok 4) to 26.7% (GPT-OSS-120B).

### 5. Significance and Potential Impact

Terminal-Bench represents a significant advancement in the evaluation of AI agents, with several profound implications and potential impacts:

1. **Advancing Agent Capabilities**: By providing a benchmark of "hard, realistic tasks" that even frontier models struggle with, Terminal-Bench directly challenges researchers to develop more capable and robust AI agents. The detailed error analysis offers a roadmap for improvement, pinpointing specific areas like execution fidelity, context management, and verification strategies.
2. **Bridging Research and Real-World Applications**: The benchmark's emphasis on "economically valuable" tasks (e.g., configuring legacy systems, reimplementing research papers, solving software engineering problems) connects academic research more directly to practical industry needs. Agents proficient on Terminal-Bench could automate highly skilled technical work, leading to increased productivity and efficiency in various domains.
3. **Standardized and Reproducible Evaluation**: The framework's use of containerized environments, programmatic tests, and the Harbor harness promotes standardization and reproducibility in agent evaluation. This is crucial for comparing different models and agents fairly and tracking progress over time, which has been a persistent challenge in the rapidly evolving field of AI.
4. **Robust Quality Control**: The rigorous, multi-stage verification process, incorporating human auditing, automated checks, LLM-backed tools, and adversarial agents, sets a high standard for benchmark quality. This commitment to integrity and solvability enhances confidence in the benchmark's results and its utility for robust scientific inquiry. The assessment via the Agentic Benchmark Checklist (ABC), where Terminal-Bench scored commendably, further validates its rigor.
5. **Open-Source Contribution**: Publishing the dataset and evaluation harness at tbench.ai empowers the broader AI community to contribute, replicate experiments, and build upon the existing work. This open access fosters collaborative research and accelerates the pace of innovation in agent development.
6. **Forecasting Future AI Trends**: The observed trend of rapidly improving model performance on Terminal-Bench highlights the dynamic nature of AI capabilities. The authors anticipate the benchmark might become saturated within the next year, indicating a continuous need for even more challenging tasks and demonstrating the benchmark's role in marking the frontier of AI progress.

**Limitations and Future Directions**: The authors candidly acknowledge limitations, including the theoretical risk of data contamination (mitigated by canary strings but not a private test set), potential non-determinism due to external internet access or resource variability, and the inherent difficulty of comprehensive task verification. These limitations also open avenues for future work, such as developing private test sets, enhancing reproducibility, and continuously curating new, more challenging task sets as AI capabilities advance.

In conclusion, Terminal-Bench provides a much-needed, high-quality benchmark that pushes the boundaries of AI agent evaluation. Its comprehensive design, rigorous validation, and focus on real-world challenges make it an invaluable resource for driving the next generation of autonomous AI systems.
