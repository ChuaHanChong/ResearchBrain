# Constrained Decoding for Secure Code Generation

> [!summary] Summary
> Researchers from the University of Maryland and Google DeepMind introduce CODEGUARD+, a new benchmark and metrics for evaluating Code Large Language Models (LLMs) that concurrently assess both security and functional correctness. They propose constrained decoding, specifically Constrained Beam Sampling, as an inference-time defense strategy, demonstrating its superior effectiveness over prior defense mechanisms and even GPT-4 for generating secure and functionally correct code.

## Problem

- Code LLMs frequently generate code with security vulnerabilities, yet existing evaluation methods primarily focus on security, neglecting functional correctness, leading to a "false sense of security."
- Prior evaluation benchmarks and metrics for secure code generation lack the ability to simultaneously measure both security and functional correctness, making it difficult to assess real-world utility and compare defense techniques.
- Current "defense" techniques like prompt engineering and prefix tuning often require retraining or fine-tuning and have shown limitations, sometimes sacrificing correctness for security improvements.

## Method

- Developed **CODEGUARD+**, a benchmark of 91 prompts covering 34 CWEs with comprehensive ==unit tests== for functional correctness, derived from existing datasets but modified for automated testing.
- Introduced new evaluation metrics, ==`secure-pass@k`== (likelihood of generating both secure and correct code) and ==`secure@k_pass`== (likelihood of correct code being secure), for holistic assessment.
- Proposed and evaluated ==constrained decoding== techniques, ==Constrained Beam Sampling== (autoregressive) and an adapted ==MUCOLA== (non-autoregressive), which enforce security constraints (keywords/templates) during the inference stage.

## Results

- Beam Sampling consistently led to higher `pass@1` and `secure-pass@1` compared to Nucleus Sampling for **six out of seven** open-source models, highlighting its general effectiveness.
- SVEN-SR significantly overestimates security; when re-evaluated with `secure-pass@1`, SVEN showed only a marginal improvement (**3.07%**) over baseline CodeGen, and even performed worse on some specific CWEs it was trained on.
- Constrained Beam Sampling applied to CodeGen achieved **51.25%** `secure-pass@1`, which is **14.95%** higher than SVEN (the prefix-tuned CodeGen model) using unconstrained Beam Sampling, and even surpassed GPT-4's **47.45%** on several open-source models.

## Takeaways

> [!tip] Key Insights
> - The choice of decoding method significantly impacts code quality; Beam Sampling consistently yields higher functional correctness and combined security-correctness than Nucleus Sampling.
> - Prior security metrics like SVEN-SR severely overestimate true security, and state-of-the-art prefix tuning (SVEN) showed only marginal improvements when re-evaluated, often at the cost of functional correctness.
> - Constrained Beam Sampling is a highly effective, training-free defense, outperforming both prefix tuning and unconstrained GPT-4 in generating code that is both secure and functionally correct.

## Detailed Report

### 1. How This Work Fits into the Broader Research Landscape

The rapid adoption of Code Large Language Models (Code LLMs) like GitHub Copilot and Amazon CodeWhisperer has revolutionized developer productivity. However, this increased reliance introduces a significant security risk: Code LLMs are prone to generating code with vulnerabilities. Prior research, such as that by Pearce et al., demonstrated that a substantial portion (e.g., 40% of GitHub Copilot's output) can be insecure. This problem has spurred a critical need for solutions that ensure the *security* of AI-generated code.

Existing research in secure code generation has largely focused on developing "defense" techniques such as prompt engineering, prefix tuning, and instruction tuning. These methods aim to steer LLMs towards generating secure code by modifying the input prompts, adding trainable continuous prefixes, or fine-tuning the model on secure code examples. While these techniques have shown promise in improving security rates, a critical oversight identified by this paper is their sole emphasis on security, often neglecting functional *correctness*. The authors argue that a secure but incorrect piece of code is fundamentally useless to a developer, leading to a "false sense of security" and hindering genuine progress in the field.

Furthermore, the community has lacked a comprehensive and realistic evaluation framework that simultaneously assesses both the security and correctness of LLM-generated code. Previous metrics, such as SVEN Security Rate (SVEN-SR), only measure the percentage of secure programs among compilable outputs, ignoring whether these programs actually function as intended. This methodological gap made it difficult to accurately compare different defense techniques and truly understand their real-world utility.

This paper addresses these two significant gaps. First, it introduces a novel benchmark and evaluation metrics that explicitly combine both security and functional correctness. This new framework provides a more realistic measure of a Code LLM's utility in generating secure and usable code. Second, it explores a new "defense direction"—constrained decoding—which operates at the inference stage without requiring expensive re-training or fine-tuning. This approach directly manipulates the code generation process by enforcing predefined security constraints, offering a complementary or alternative strategy to existing training-based defenses. By doing so, this work aims to move the research landscape beyond isolated metrics and towards holistic solutions for truly secure and correct AI-assisted code generation.

### 2. Key Objectives and Motivation

The primary motivation for this research stems from two critical shortcomings in the current landscape of Code LLM-based code generation:
1. **Prevalence of Vulnerable and Incorrect Code:** Despite their productivity benefits, Code LLMs frequently generate code containing security vulnerabilities. More critically, prior research and evaluation methods have predominantly focused on *only* the security aspect, overlooking functional correctness. The authors argue that secure but incorrect code is impractical for developers, creating a misleading perception of security. This oversight, they contend, leads to a "false sense of security" and impedes genuine progress in developing truly safe and usable Code LLMs.
2. **Inadequate Evaluation Methodologies:** The existing evaluation metrics and benchmarks for secure code generation fail to capture the dual requirement of security and correctness. Benchmarks like HumanEval focus on correctness but lack security relevance, while security-focused datasets lack unit tests for correctness. Previous metrics like SVEN-SR further exacerbate this by only considering the security of compilable code, ignoring its functional validity and often overestimating security performance due to issues like counting trivially secure, incomplete outputs.

Based on these motivations, the paper sets out to achieve the following key objectives:

- **Develop a New Benchmark (CODEGUARD+) and Metrics:** To overcome the limitations of existing evaluation methods, the paper aims to create a new benchmark, CODEGUARD+, that includes prompts designed to trigger security vulnerabilities alongside comprehensive unit tests for functional correctness. Concurrently, it proposes two new metrics, `secure-pass@k` and `secure@k_pass`, to holistically measure a Code LLM's ability to generate code that is both secure and functionally correct.
- **Investigate Decoding Methods for Security:** The paper seeks to understand how different decoding methods (e.g., Nucleus Sampling, Beam Sampling), which transform an LLM's probabilistic output into a concrete code sequence, influence the security and correctness of generated code. This aims to open the "black box" of decoding, revealing new opportunities for defense.
- **Propose and Evaluate Constrained Decoding Techniques:** The central objective is to explore constrained decoding as a novel defense direction. This involves formulating the problem of constrained decoding for secure code generation, specifying practical security constraints (expressed as keywords or template strings), and developing two distinct constrained decoding techniques: Constrained Beam Sampling (autoregressive) and an adapted MUCOLA (non-autoregressive).
- **Demonstrate the Effectiveness of Constrained Decoding:** The research aims to empirically evaluate the proposed constrained decoding techniques across a wide range of state-of-the-art open-source Code LLMs and compare their performance against existing defense mechanisms (like prefix tuning) and proprietary models (like GPT-4), using the newly introduced benchmark and metrics.

In essence, the paper is motivated by the need for more realistic evaluations and more effective, inference-time defense strategies to ensure that Code LLMs generate code that is not only secure but also functionally correct and therefore truly useful to developers.

### 3. Methodology and Approach

The research follows a systematic approach encompassing the development of new evaluation tools and the exploration of novel defense mechanisms.

#### 3.1. New Evaluation Guidelines: CODEGUARD+ Benchmark and Metrics

- **CODEGUARD+ Benchmark:**
 - **Source and Scope:** The benchmark comprises 91 prompts, covering 34 Common Weakness Enumerations (CWEs) across C/C++ and Python. This makes it larger and more comprehensive than previous security-focused datasets.
 - **Prompt Modification:** Prompts were sourced from existing security datasets (Pearce et al., SecurityEval) but critically *modified* to be suitable for automated testing. This involved:
 - Adding specific instructions to prompts to define expected behavior, allowing for testable outputs (e.g., "print out the buffer").
 - Switching to testing-friendly libraries (e.g., `sqlite3` instead of `MySQLdb` for local database setup).
 - Updating deprecated libraries and importing safe alternatives (e.g., `send_from_directory` instead of `send_file`).
 - **Unit Tests:** For each modified prompt, unit tests were developed to assess functional correctness. These tests fall into three categories:
 - Assertions on function calls and arguments for Python programs.
 - Checks on database or file changes for programs interacting with storage.
 - Verification of printed output for programs using `stdout`. Importantly, these unit tests solely check correctness and do not implicitly check security, allowing for a clear separation of concerns in evaluation.
- **New Metrics:**
 - **Critique of SVEN-SR:** The paper highlights two major flaws in SVEN-SR (Security Rate from): (1) it overestimates security by de-duplicating programs and ignoring the likelihood of generating a secure *unique* program, and (2) it completely disregards functional correctness.
 - **Introduction of `pass@k`:** The established `pass@k` metric (expected likelihood of generating any correct code within `k` samples) is adopted as a baseline for correctness.
 - **`secure-pass@k`:** This new metric measures the expected likelihood of generating code that is *both* secure *and* functionally correct within `k` samples. For `k=1`, it represents the likelihood of a single generation satisfying both criteria.
 - **`secure@k_pass`:** This metric measures how likely any one of `k` *correct* generations is also secure. For `k=1`, it indicates the likelihood that an arbitrary correct generation is secure. These metrics ensure a realistic, combined assessment of utility and safety.
 - **Security Evaluation:** For detecting vulnerabilities, an ensemble of two static analyzers, CodeQL and Sonar, is used. A program is considered vulnerable if either tool identifies an issue; it's considered secure only if both deem it safe.

#### 3.2. Constrained Decoding for Secure Code Generation

- **Problem Formulation:** The core idea is to move beyond treating decoding as a black box. The paper explicitly formulates the constrained decoding problem: `y = Gen(P(y|x)), s.t. y |= φ_i, ∀φ_i ∈ Φ`, where `Φ` is a set of security constraints that the generated code `y` must satisfy. This formulation enables a systematic study of how decoding procedures can be enhanced.
- **Security Constraint Specification:**
 - **Basis:** Constraints are derived from common secure coding practices, mapped to specific CWE types.
 - **Types:** Categories include "use safe libraries," "input validation," "separate data from instruction," "array index bound check," "use an allowlist," "check if memory allocation failed," "set permission," "use INT_MAX," "use uint64_t," and "do not use a freed buffer."
 - **Realization:** Constraints are expressed as either simple keywords (e.g., `snprintf`, `uint64_t`, `0644`) or template strings (e.g., `if ({i} >= 0 && {i} < {size})`). This manual but straightforward process is deemed accessible to developers with undergraduate-level security knowledge.
 - **Positive and Negative Constraints:** Constraints are categorized as "positive" (key phrases that *must* appear) or "negative" (key phrases that *must be blocked*).
- **Constrained Decoding Techniques:**
 - **Constrained Beam Sampling (Autoregressive):**
 - **Adaptation:** This technique adapts the standard Beam Search by introducing sampling to enhance diversity (beyond deterministic selection) and enforce constraints during token generation.
 - **Mechanism:** At each decoding step, `B` beams are maintained. Candidate beams are generated by (1) sampling from the next-token distribution while actively *avoiding* tokens leading to negative phrases, and (2) *forcefully extending* beams with tokens that help satisfy positive phrases. Finally, `B` beams are selected, stratified by their progress toward satisfying positive constraints, balancing exploitation (constraint satisfaction) and exploration (sampling).
 - **Adapted MUCOLA (Non-autoregressive):**
 - **Approach:** MUCOLA (Gradient-based Constraint Sampling) is a state-of-the-art non-autoregressive method for constrained *text* generation. It treats decoding as sampling from an energy-based model using Langevin Dynamics, iteratively updating output token embeddings with gradients of an energy function.
 - **Adaptation for Code:** The authors define a novel energy function `E'(e)` for code generation that incorporates both positive and negative key phrase constraints, by penalizing `E'(e)` when negative constraints are violated.
 - **Challenges:** The paper notes specific difficulties in applying MUCOLA to code generation, including the complexity of multi-token constraints, sensitivity to punctuation, and the position-dependent nature of security-critical code phrases, which are less prevalent in natural language text generation.

#### 3.3. Experiment Setup

- **Models:** Eight state-of-the-art Code LLMs are evaluated, ranging from 2.7B to 34B parameters (CodeGen, SVEN, StarCoder2, CodeGemma, Llama3, DeepseekCoder, CodeLlama), plus the proprietary GPT-4. SVEN is included as the state-of-the-art prefix-tuned defense.
- **Generations:** For open-source models, 10 code completions per prompt are generated (10 runs with different seeds). For GPT-4, 25 completions per prompt are generated. Constrained decoding methods aim for 10 constrained outputs, with re-generation up to a maximum (100 for Constrained Beam Sampling, 30 for MUCOLA).
- **Hyperparameters:** Standard settings for Nucleus Sampling (temperature 0.4, top-p 0.95) and Beam Sampling (beam size 25) are used. Specific parameters for MUCOLA are also detailed.

This comprehensive methodology allows for a rigorous and multifaceted evaluation of Code LLM security and the efficacy of the proposed constrained decoding techniques.

### 4. Main Findings and Results

The research yielded several significant findings, challenging existing assumptions and demonstrating the promise of constrained decoding:

- **Decoding Methods Significantly Affect Code Quality (RQ1):**
 - The choice of decoding method profoundly impacts the security and correctness of generated code.
 - For six out of seven open-source models evaluated, **Beam Sampling consistently yielded higher `pass@1` (functional correctness) and `secure-pass@1` (combined security and correctness) compared to Nucleus Sampling**. This suggests that Beam Sampling, by exploring more diverse sequences, is generally more effective for generating functionally correct and secure code, even without explicit constraints.

- **SVEN-SR Severely Overestimates Security; Prefix Tuning (SVEN) is Less Effective Than Previously Believed (RQ2):**
 - The paper's new metrics reveal that **SVEN-SR significantly overestimates the true security level of Code LLMs** because it ignores functional correctness. The `secure-pass@1` values are drastically lower than SVEN-SR, indicating that a large portion of "secure" code generated by SVEN-SR-validated models is functionally incorrect.
 - When re-evaluated with `secure-pass@1`, the state-of-the-art prefix tuning defense (SVEN) shows **only a marginal improvement over the baseline CodeGen model (3.07% with Nucleus Sampling, 2.53% with Beam Sampling)**.
 - A critical finding is that **SVEN achieves its improved security (`secure@1_pass`) by sacrificing functional correctness (`pass@1` decreases by 6.94% for Nucleus Sampling)**. This highlights a crucial trade-off previously masked by inadequate evaluation.
 - **Reversed Conclusions for Specific CWEs:** For 11 prompts within the CWEs that SVEN was specifically trained on, SVEN performed *worse* than CodeGen in `secure-pass@1` despite having higher (or equivalent) SVEN-SR. This demonstrates that the new metrics effectively debug limitations in existing defenses.

- **Constrained Decoding (Constrained Beam Sampling) is Highly Effective and Outperforms Prefix Tuning (RQ3):**
 - **Superior to Prefix Tuning:** Constrained Beam Sampling applied to CodeGen achieved 51.25% `secure-pass@1`, which is **14.95% higher than SVEN (the prefix-tuned CodeGen model) using unconstrained Beam Sampling**. This strongly suggests that constrained decoding is a more effective defense strategy for generating secure and correct code than prefix tuning, without requiring specialized training datasets.
 - **Performance on Untrained CWEs:** Constrained Beam Sampling demonstrates strong generalization capabilities. When evaluated on CWEs *not* in SVEN's training set, SVEN's `secure-pass@1` dropped significantly (from 51.09% to 27.88%). In contrast, models using Constrained Beam Sampling, like StarCoder2-3B, achieved substantially higher `secure-pass@1` (53.4%), nearly double that of SVEN, without any specialized training. This highlights a key advantage: **constrained decoding does not require a specialized training dataset and generalizes well.**
 - **Outperforms GPT-4:** Constrained Beam Sampling on several open-source Code LLMs (even smaller ones like StarCoder2-3B) achieved higher `secure-pass@1` than GPT-4 using unconstrained Nucleus Sampling (e.g., StarCoder2-3B at 59.56% vs. GPT-4 at 47.45%). This is a remarkable result, indicating that strategic decoding can enable smaller, open-source models to outperform much larger, proprietary models in combined security and correctness.
 - **Complements Prefix Tuning:** While Constrained Beam Sampling on vanilla CodeGen was superior, applying it to SVEN still yielded the highest `secure-pass@1` for SVEN (46.26%), suggesting that constrained decoding can still enhance fine-tuned models.

- **Challenges with Non-Autoregressive Decoding (MUCOLA) for Code (RQ4):**
 - Despite MUCOLA's strong performance in constrained *text* generation, its adaptation for secure *code* generation (on StarCoder2-3B) struggled significantly with functional correctness, showing much worse `pass@1` than unconstrained baselines. While it achieved a high `secure@1_pass`, its overall `secure-pass@1` was lower than Constrained Beam Sampling.
 - The authors identified key reasons for MUCOLA's struggles: difficulty with multi-token constraints common in code, sensitivity to subtle punctuation differences, and the position-dependent nature of security-critical code phrases, issues less prevalent in natural language processing.

In summary, the paper successfully introduced a more realistic evaluation framework, exposed limitations in previous SOTA defenses, and demonstrated that constrained decoding, particularly Constrained Beam Sampling, is a highly effective, training-free method for generating functionally correct and secure code, even surpassing the performance of large proprietary models.

### 5. Significance and Potential Impact

This research has profound significance and potential impact across several dimensions of AI safety, software engineering, and the development of large language models:

- **Rethinking Evaluation Standards for Secure Code Generation:** The introduction of CODEGUARD+ and the `secure-pass@k` / `secure@k_pass` metrics is a critical contribution. It shifts the paradigm from evaluating security in isolation to a more realistic, holistic assessment that combines both security and functional correctness. This will enable researchers to measure actual progress more accurately, identify true trade-offs, and debug the limitations of existing and future defense mechanisms more effectively. The demonstrated overestimation by SVEN-SR serves as a stark warning against incomplete evaluation.

- **A New, Potent Defense Direction for AI Safety:** Constrained decoding, particularly the Constrained Beam Sampling technique, emerges as a highly effective and practical defense strategy. Its key advantages—not requiring specialized training datasets, strong generalization to untrained vulnerability types, and significant performance gains over prior state-of-the-art defenses (prefix tuning)—make it a game-changer. This approach offers an inference-time solution that can be applied to any pre-trained Code LLM, providing flexibility and efficiency that fine-tuning or instruction tuning might lack. This opens up a new avenue for improving AI safety in code generation that complements or, in some cases, outperforms existing methods.

- **Empowering Open-Source Models to Outperform Proprietary Giants:** The finding that constrained decoding enables open-source models (like StarCoder2-3B) to achieve higher `secure-pass@1` scores than GPT-4 is extremely impactful. This suggests that sophisticated decoding strategies can effectively bridge the performance gap between smaller, accessible models and massive, proprietary ones, especially in specialized safety-critical tasks. This could democratize access to safer AI-powered coding assistants, reducing reliance on black-box proprietary solutions.

- **Guiding Future Research in Constrained Generation:** The exploration of MUCOLA's struggles in code generation, despite its success in text, highlights unique challenges in applying non-autoregressive constrained decoding to code. This sets a clear research agenda for developing more robust and code-aware constraint-handling mechanisms for gradient-based or other non-autoregressive decoding paradigms. Future work could focus on more expressive constraint languages beyond keywords/templates, incorporating semantic understanding, and improving constraint satisfaction rates without excessive re-generation.

- **Direct Impact on Developer Productivity and Security:** By enabling Code LLMs to generate code that is both secure and correct, this research directly contributes to developer productivity and software system security. Developers can rely more confidently on AI assistants, reducing the time spent on manual vulnerability detection and correction, and ultimately leading to more secure software from the outset.

In essence, this paper does not just propose a new technique; it fundamentally challenges and redefines how we evaluate and achieve secure code generation with LLMs, paving the way for a future where AI-powered coding assistants are both powerful and inherently trustworthy.
