# CodeMidas: Scaling Agentic Coding RL Environments from Code Itself

> [!summary] Summary
> CodeMidas is an agentic pipeline that turns implemented functionality in open-source codebases into executable coding RL environments, using source code as the only task-specific input. Agents remove core implementations, write behavioral task statements, build tests grounded in reference execution, and filter tasks via consistency checks and adversarial rollouts. GRPO training of MiMo-V2.5 on 5,545 tasks from 3,185 codebases improves all five benchmarks, lifting DeepSWE from 10.0% to 21.7%.

## Problem

- Existing coding RL environment pipelines seed tasks from development records such as issues, pull requests, and commits, so task supply is capped by what changes were recorded.
- Alternatives that synthesize bugs around existing tests or specify functionality from documentation inherit those artifacts' coverage, and many cover only a single programming language.
- Execution rewards depend on test oracles, yet generated or repository tests can accept incorrect patches or over-constrain unspecified details, rejecting valid alternative implementations.

## Method

- **Task design and codebase adaptation**: an agent picks functionality with public entry points, removes the core implementation, and co-revises a behavioral task statement and code boundaries, keeping the original as reference solution.
- **Execution-grounded test construction**: agents run the reference code on requirement-mapped inputs to fix expected values, then relax assertions on unspecified wording, ordering, or internals, followed by a two-fail/four-pass fresh-container ==consistency check==.
- **Post-rollout filtering**: adversarial rollouts hunt leaked solutions in caches or compiled artifacts, a reviewing agent flags verifier false positives/negatives on four agent attempts, and only tasks with mixed pass/fail outcomes are kept.

## Results

- GRPO on **5,545** tasks lifts MiMo-V2.5 on all five external benchmarks: DeepSWE **10.0%** to **21.7%**, ProgramBench Almost Solved **4.5** to **21.5**, Terminal-Bench v2.1 **63.7%** to **72.2%**, SWE-bench Pro **50.3%** to **54.4%**.
- Scaling filtered tasks from **1k** to **3k** to **5,545** raises DeepSWE **17.57** to **19.05** to **21.70**; the filtered 3k subset beats an unfiltered 8k pool on all three evaluations (8k DeepSWE **17.11**).
- Behavior shifts during RL: pre-edit exploration calls rise **27.2** to **40.1**, and rollouts with agent-written checks pass **4.2 points** more often (95% CI **1.8-6.6**); exploration also grows on held-out benchmarks.

## Takeaways

> [!tip] Key Insights
> - Implemented functionality itself is an underused RL-task source: deleting working code and grading reimplementation against the original's executed behavior removes dependence on issues, commits, tests, or documentation.
> - Environment quality beats raw quantity: rigorous cleaning and rollout-based filtering let a smaller task pool outperform a larger unfiltered one, though individual filters are not ablated separately.
> - Single-format tasks can transfer broadly: RL on functionality reimplementation improves issue repair, program construction, translation, and terminal work, with exploration and self-verification habits carrying over.

## Detailed Report

### 1. Position in the Broader Research Landscape

CodeMidas addresses the problem of generating training environments for reinforcement learning (RL) applied to coding agents. Recent coding agents operate in repositories, terminals, and development environments rather than generating isolated code snippets. Training such agents with RL requires tasks that have two properties: they must represent a sufficiently diverse range of software work, and they must provide reliable, executable rewards indicating whether an attempted solution is correct.

Existing environment-construction approaches generally begin with development artifacts. For example, SWE-bench and related systems use GitHub issues, pull requests, commits, or human-authored task descriptions. Other approaches construct tasks by modifying existing tests, synthesizing bugs, or extracting requirements from documentation and function-level descriptions. These strategies are useful but constrain task creation to the availability and quality of recorded development activity, test suites, or written specifications.

CodeMidas proposes a different data source: implemented functionality in the source code itself. The central idea is that a completed implementation contains both a candidate task and a reference solution. Its public interfaces and observable behavior can be used to describe what an agent should implement, while execution of the original code can provide expected test outcomes. The surrounding repository supplies a realistic development context, including project structure and dependencies.

The work also contributes to the literature on code verification and RL rewards. It uses direct execution rewards from generated tests rather than a learned reward model or process-level verifier. This makes test quality central to the system. The paper therefore incorporates several checks intended to address the software-testing “oracle problem,” including accidental over-specification, weak tests, false positives, false negatives, and information leakage from residual implementation artifacts.

### 2. Objectives and Motivation

#### 2.1. Primary Objective

The primary objective is to create executable coding RL environments automatically, using source code as the only task-specific input. Each resulting environment should contain:

1. A natural-language task statement.
2. An adapted and containerized codebase in which selected functionality is missing.
3. A hidden executable verifier that evaluates the submitted implementation.

The solver is expected to reconstruct the missing functionality without accessing the verifier or the original implementation during development.

#### 2.2. Motivation

The authors identify task diversity and reward reliability as complementary requirements for coding-agent RL. A narrow collection of issue-repair tasks may not adequately train agents for whole-program construction, code translation, command-line interaction, or work involving different programming languages and domains. Source repositories offer many implemented functions and tools that can be converted into tasks without relying on whether a corresponding issue or commit exists.

A second motivation is to preserve realistic software-engineering context. Rather than presenting an isolated function-generation problem, CodeMidas retains the original repository structure, shared dependencies, build configuration, and runtime environment. This creates tasks that require repository exploration and integration with existing code.

A third motivation is to avoid imposing implementation-specific requirements. The task should specify externally observable behavior while allowing alternative internal algorithms and helper functions. The verifier must therefore test stated behavior rather than simply compare a patch with the original implementation.

### 3. Methodology and Approach

#### 3.1. Task Design and Codebase Adaptation

An agent first inspects repository structure and build metadata to identify functionality with public entry points and observable outcomes. Supported interfaces include command-line programs, pure library functions, and stateful APIs. Observable behavior may consist of process output, return values, exceptions, or state changes across multiple calls.

The agent traces the selected entry point and its shared dependencies to determine the task scope. It then removes the core implementation while preserving the surrounding project context. The remaining repository is modified so that it forms a coherent starting point for development. The original implementation is stored separately as a reference solution.

The task statement describes required inputs, outputs, behavioral constraints, and public interfaces. Internal implementation choices remain open. The authors state that task statements and code boundaries are revised together, since removing too much or too little code can make the environment incoherent.

#### 3.2. Execution-Grounded Test Construction

A second agent translates the behavioral specification into test cases. It selects ordinary inputs, boundary cases, and, for stateful APIs, sequences of calls that test ordering, dependencies, and cleanup behavior.

For behaviors explicitly fixed by the statement, the tests use the original implementation to obtain expected outputs. For unspecified details, tests check only the stated constraints. For example, a test may require a particular exception type without requiring an exact error message. This is intended to reduce accidental restrictions on valid alternative implementations.

The generated assertions are reviewed for overfitting. The review removes checks of incidental ordering, exact wording, private symbols, or internal structure when these are not required by the task statement. If a requirement depends on a private implementation detail and cannot be replaced with an observable behavioral check, the task is rejected. The revised test suite is rerun against the reference implementation before being fixed for grading.

#### 3.3. Environment Preparation and Consistency Checks

Each environment is built from a base container image. Dependencies, build steps, runtime resources, fixtures, and project-specific wrappers are installed according to the repository’s declarations.

The construction process removes artifacts that could reveal the deleted implementation. These include compiled outputs, caches, files left by construction agents, and original tests associated with the target functionality. The verifier is kept outside the solver-visible environment and is injected only during grading.

Execution consistency is checked in six fresh containers. The starting codebase must fail in both of two runs, while the reference solution must pass in all four remaining runs. This procedure checks both the intended fail-to-pass transition and basic runtime stability.

#### 3.4. Post-Rollout Filtering

CodeMidas uses additional model rollouts to assess whether environments are suitable for RL.

First, adversarial agents search the solver-visible environment for leakage, including compiled artifacts, caches, installed copies, or construction residues. Candidate exploits are logged and reviewed. Tasks are rejected when leaked information can bypass the intended implementation work.

Second, coding agents make four attempts per task. A reviewing agent compares submitted code, execution traces, verifier results, task requirements, and the reference implementation. It flags false positives, in which an incorrect solution passes, and false negatives, in which a correct solution fails. Tasks with identified verifier defects are removed.

Third, another model makes multiple attempts on each task. Tasks are retained only if at least one attempt passes and at least one fails. This filter excludes environments that are either trivially solvable or consistently unsolvable under the screening budget, although mixed outcomes do not by themselves prove that a task is well specified.

#### 3.5. Dataset and Training Setup

The final dataset contains 5,545 tasks from 3,185 open-source codebases, covering 23 programming languages and 15 technical domains. Python, TypeScript, Go, C++, and JavaScript are the most frequent languages. Systems software, web technologies, and developer tools together account for 45.6% of tasks.

The median reference patch size is 142 lines, with an interquartile range of 66 to 305 lines. In 65.9% of tasks, the reference patch changes at least two source files.

The authors train MiMo-V2.5 using Group Relative Policy Optimization (GRPO). Training uses binary execution rewards, a batch size of 32, and 32 rollouts per task. Evaluation is conducted on five external benchmarks: SWE-bench Pro, DeepSWE v1.1, ProgramBench, RepoZero C2Rust, and Terminal-Bench v2.1. CodeMidas Val contains 200 held-out tasks, with three attempts per task.

### 4. Main Findings and Results

#### 4.1. External Benchmark Performance

RL training on CodeMidas improves performance on all five external benchmarks:

- SWE-bench Pro increases from 50.3% to 54.4%, a gain of 4.1 percentage points.
- DeepSWE increases from 10.0% to 21.7%, a gain of 11.7 points.
- ProgramBench’s “Almost Solved” score increases from 4.5% to 21.5%, a gain of 17.0 points.
- RepoZero C2Rust increases from 40.5% to 51.8%, a gain of 11.3 points.
- Terminal-Bench v2.1 increases from 63.7% to 72.2%, a gain of 8.5 points.

The benchmarks cover issue repair, whole-program construction, code translation, and terminal-based work. This pattern indicates transfer beyond the exact task format used for training.

On CodeMidas Val, the pass rate rises from 35.0% for the initial policy to 44.7% during training. The improvement is accompanied by longer trajectories, suggesting that the trained agent uses more of the available interaction budget.

#### 4.2. Effects of Task Scale and Quality

The authors compare training on filtered subsets of 1,000, 3,000, and 5,545 tasks with training on approximately 8,000 tasks collected before cleaning and filtering.

Performance increases with the size of the high-quality task pool. On DeepSWE, scores rise from 17.57% with 1,000 tasks to 19.05% with 3,000 and 21.70% with the full dataset. CodeMidas Val scores rise from 41.30% to 43.22% and then 44.73%.

The filtered 5,545-task dataset outperforms the unfiltered 8,000-task sample by 0.59 points on SWE-bench Pro, 4.59 points on DeepSWE, and 4.49 points on CodeMidas Val. Even the filtered 3,000-task subset exceeds the unfiltered 8,000-task setting on all three reported evaluations. These comparisons support the importance of verifier reliability, environment cleaning, and rollout-based filtering in addition to raw task count.

#### 4.3. Behavioral Changes

RL changes how the agent interacts with repositories. On CodeMidas tasks, pre-edit reading and search calls increase from 27.2 to 40.1 on average. The fraction of code fragments drafted in prior reasoning increases from 0.358 to 0.629. The number of distinct post-edit verification commands increases from 2.03 to 2.53.

Rollouts containing agent-written and executed checks have a pass rate 4.2 percentage points higher than rollouts without such checks, with a reported 95% confidence interval of 1.8 to 6.6 points. The association is not evidence by itself that self-verification causes success, but it indicates that verification behavior is correlated with better outcomes.

Similar behavioral changes appear on held-out benchmarks. Exploration increases on SWE-bench Pro, ProgramBench, and Terminal-Bench. Drafting ratios increase on SWE-bench Pro and ProgramBench. Interaction length changes by task type: it increases for issue repair but decreases for whole-program construction, suggesting that more exploration does not necessarily require longer overall trajectories.

### 5. Significance and Potential Impact

CodeMidas provides a method for expanding coding-agent RL data without depending on issue trackers, commit histories, existing tests, or written documentation. Its main contribution is methodological: it treats source repositories as executable specifications from which task statements, reference solutions, test expectations, and development environments can be derived.

The results suggest that filtered, behaviorally grounded environments can improve an agent across multiple software-work categories. The findings also indicate that data quality can matter more than task count alone, since a smaller verified collection outperforms a larger unfiltered one.

Potential limitations remain. The reliability of the approach depends on the quality of agent-generated specifications, tests, and reviews. Execution consistency does not guarantee complete behavioral coverage, and the mixed rollout criterion may exclude difficult but valid tasks. The experiments also center on one base model and one RL configuration, so the extent to which the findings generalize to other models and training methods requires further study. Nevertheless, the paper establishes source-code-derived environment construction as a practical direction for scaling executable training data for coding agents.
