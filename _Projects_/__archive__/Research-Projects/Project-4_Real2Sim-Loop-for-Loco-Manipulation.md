# Real2Sim Self-Improvement Loop for Loco-Manipulation

> [!abstract] Thesis
> Real2sim2real self-improvement outside pure locomotion has the irreducible truth that single-shot synthetic-data generation is the field's current ceiling in loco-manipulation - exactly the stage locomotion itself was at before this vault's [[Project-2_Terrain-Extended-Direct-Dynamic-Retargeting|Project-2]]/[[Project-3_Dynamics-Fold-Back-Loop-for-VideoMimic|Project-3]] - which breaks the field's implicit assumption (GRAIL, current SOTA with running code) that scaling one-shot generation diversity is sufficient once achieved, and I bet that wrapping GRAIL's own weakest measured gap in a gated multi-round fold-back loop pushes its unseen-object pick-up from **80%→≥90%** within 3 rounds.

**Anchor:** [[2606.05160|GRAIL]] (NVIDIA/NVlabs) - code released, dataset partially released (`github.com/NVlabs/GRAIL`; Docker image verified pullable, `nvgrail/grail:latest`, 29.8GB, pushed 2026-07-02; `nvidia/PhysicalAI-Robotics-Locomanipulation-GRAIL` on HuggingFace covers pick-up/terrain/sitting, not the full manipulation dataset - the repo's own TODO list still has "Release GRAIL manipulation dataset" unchecked), built on [[2511.07820|SONIC]]'s released whole-body tracking checkpoints (weights independently confirmed downloadable, not just documented). No fold-back mechanism of any kind, confirmed from two independent sources (see Background).

**Scope note:** an earlier draft of this project covered both loco-manipulation (GRAIL) and mobile-manipulation (BestMan/WANDA) as two tracks in one doc. Mobile-manipulation is deferred out of active scope - see [[#Deferred - mobile-manipulation axis]] for the investigation already done, kept rather than deleted per this vault's standing rule to record dead/deferred candidates, not just live ones.

## Background - what's actually verified, not assumed

GRAIL's core numbers, mechanisms, and no-loop confirmation are verified directly against its full paper text via alphaXiv (`answer_pdf_queries`) and against its actual source code (`data/repositories/GRAIL`, cloned and read this session, the same rigor Project-3 applied to ASAP).

- **GRAIL has no fold-back loop, confirmed from two independent sources.** Its own GitHub README and NVIDIA research page both describe a strictly one-directional pipeline: 3D asset → video-foundation-model-generated interaction video → 4D HOI reconstruction → retarget to Unitree G1 → SONIC-based tracking policy (IsaacLab, PPO, 64×L40 GPUs, 30k iterations) → deploy. Neither source mentions any signal flowing from real deployment back into data generation.
- **GRAIL's own numbers, verified against the full paper text, not the marketing page - but the two headline sim numbers are two different artifacts on two different eval sets, not one pipeline run (a conflation an earlier pass of this doc made and this pass corrected).** Table 1 (HOI-generation quality, 20-object ComAsset shared eval set): GRAIL's generated 4D HOI sequences, replayed through InterMimic on SMPL-X capsule humanoids (no motion retargeting needed), score 88.9% physical-executability tracking success and 0.90% penetration, vs HOIDiff 15.8%, CHOIS 10.5%, DAViD 24.0% (range **10.5–24.0%**). Table 2 (Task-General Loco-Manipulation Tracking, a separate 124-motion/43-object benchmark, using HDMI's and ResMimic's *official implementations*): GRAIL's trained G1 tracking policy scores 81.4% manipulation success vs HDMI 48.5%, ResMimic 49.2%. The 20,000+-sequence generation dataset (not the 124-motion/43-object benchmark specifically) draws on public asset sources (Robocasa, ComAsset, OMOMO, Hunyuan3D). Gate 0 therefore has two separate reproduction targets, not one. Real Unitree G1: **pick-up is a solid N** - Table 3 reports 10 trials per object across 5 seen objects (84% avg: cube 100%, apple 60%, tea box 100%, carrot 70%, wet wipes 90%) and 5 unseen objects (80% avg: spray can 100%, lint roller 50%, peach 90%, flashlight 80%, medicine bottle 80%) - 100 trials total, not the "12 qualitative trials" a first pass at the project's own marketing page suggested (corrected after re-verifying against the paper itself via alphaXiv). **Stair-climbing's trial count is not stated in the main text** - 90% success is reported without an explicit N; this one number stays flagged as thinner evidence than the pick-up numbers.
- **GRAIL's dataset release is partial, not the full generation set - verified from the HuggingFace repo's own file tree, not just its existence.** `nvidia/PhysicalAI-Robotics-Locomanipulation-GRAIL`'s `data/` folder contains 7 categories: `pickup_table`, `pickup_ground`, `curb`, `slope`, `stair_p1`, `stair_p2`, `sitting` - covering 3 of the paper's 4 task families (pick-up, terrain traversal, sitting), not the fourth (whole-body manipulation: carrying/pushing large items). The repo's own README TODO list confirms this directly: "[ ] Release GRAIL manipulation dataset" is unchecked, while "[x] Release task-general tracking policy checkpoints" is checked. Practically: Gate 0's pick-up (84%/80%) and stair-climbing (90%) reproduction targets are covered by released data; the 81.4% manipulation-SR target on the 124-motion/43-object benchmark is not directly reproducible from released artifacts alone and would need pipeline-regenerated data.
- **GRAIL's fold-back hook points are code-verified, not asserted - read directly against `data/repositories/GRAIL`, the same rigor Project-3 applied to ASAP. First pass at this got the injection point wrong; corrected here.** The first draft of this bullet claimed a failed real deployment's own RGBD recording could become a new `video_id` fed straight into `recon_4dhoi.py`'s reconstruction steps unmodified. That's false, and the code that disproves it was already on hand: `_load_motion` (`hoi_optimizer.py:303–374`) hard-`raise`s if `predicted_body_height` is missing and pulls GT shape params from `data/RenderPeople_fitsmpl` keyed on `character_name` (a synthetic-character ID parsed from `video_id`, `__init__`, line 82); `_load_camera_config` (lines 205–239) requires a `first_frame_pose.pickle` and calls `cam_pose_blender_to_opencv` - a Blender-render artifact; step 1 is HMR4D *human* pose estimation (`recon_4dhoi.py:86`) on a synthetic human demonstrator, not a robot; `_detect_contact_labels` (lines 376–456) labels human body parts (`"R_Hand"`/`"L_Hand"`). A real failed-robot recording has none of these - it's a G1 in frame, on the far side of retargeting, not reconstruction input.

  The genuine hook is one stage earlier, and it *is* config-only. `configs/objects/{dataset}.yaml` (e.g. `configs/objects/comasset.yaml`) is a flat per-object dict (`obj_scale`, `obj_rot`, `obj_pos`, `scene`) that `grail/pipelines/gen_3d_assets.py` (Hunyuan3D-2.1 mesh generation from an OpenAI-Image-API reference photo) and `grail/pipelines/gen_2dhoi.py` (Blender physics sim → iterative scale-determination via render+ChatGPT eval → Blender scene render → Kling-AI video generation, `grail.adapters.kling.generate_video`) both read to *synthesize* the human-object-interaction video that steps 1–4 then reconstruct unmodified. **The fold-back round is: add/edit a `configs/objects/*.yaml` entry for the failed object - its scale/pose corrected from what the real deployment's failure revealed - and re-run `gen_3d_assets.py` → `gen_2dhoi.py` → the unmodified `recon_4dhoi.py` step1–4 pipeline on the resulting new synthetic video.** This is genuinely zero code changes across all three existing scripts, but it is honestly a *config-driven resynthesis*, not a direct real-recording ingestion - the real RGBD failure capture is a diagnostic input that informs which object attributes to correct in the YAML, not a pipeline input itself. Translating a real failure into a corrected YAML entry (e.g. measuring the true object scale from the failure footage) is small glue logic this project still has to write, not something GRAIL's released code does for you. Once resynthesized, the same Eq. 4–5 depth-/contact-alignment terms apply as before - `_depth_pointcloud_loss` (`loss_computer.py:274–319`, `bidirectional_chamfer_loss` in `loss_terms.py:25–62`) and `_contact_loss` with `depth_only=True` (`loss_computer.py:80–152`, `contact_depth_loss` in `loss_terms.py:111–171`), weighted in `configs/recon_4dhoi/manip_smplx.yaml:126–133` (`contact_opt` stage: `depth_pointcloud.weight=100.0`, `contact.weight=30000.0`, `max_contact_dist=0.15`) - tightening `max_contact_dist`/raising `contact.weight` for fold-back rounds specifically is a genuinely zero-code lever on top of the resynthesized data.

  Retargeting: `grail/pipelines/retarget.py` (4-stage `_step_retarget`/`_step_process`/`_step_compute_bps`/`_step_verify`, lines 63–236) writes `data/motion_lib/<output_folder>/{robot,objects,object_usd,meta}/` (line 300–301), the exact schema SONIC training reads via `manager_env.commands.motion.motion_lib_cfg.motion_file` (`imports/SONIC/gear_sonic/config/manager_env/commands/terms/motion.yaml:6`; a real example path in `.../config/exp/manager/universal_token/all_modes/sonic_release.yaml:72`). Policy fine-tune - GRAIL/SONIC's own `train_delta_a_closed_loop` analog: `imports/SONIC/gear_sonic/train_agent_trl.py::resume_training()` (lines 73–107) warm-resumes (`config.checkpoint=<released ckpt>`, `config.warm_resume=True`) into a fresh `experiment_dir`, and a Hydra override repoints `motion_lib_cfg.motion_file` at the fold-back round's expanded motion library (the override pattern is already used elsewhere in this exact config tree: `.../config/eval_exp_david_hoi.yaml:43–47`'s `++manager_env.commands.motion.motion_lib_cfg.*` overrides) - warm-start plus new data pointer, not a from-scratch retrain.
- **Proposed-method steps 1 (deploy), 2 (log failures), and 4 (retrain) each have a real code anchor in SONIC's released tree, code-checked this session - not just step 3, which was already verified above.**
  - **Step 2, failure logging, is the strongest finding of this pass - it reverses the naive assumption it would need building from scratch.** `imports/SONIC/gear_sonic/trl/callbacks/im_eval_callback.py::ImEvalCallback` already logs **per-episode, per-object** outcomes, not just an aggregate success rate: `failed_keys`/`failed_idxes` (which motions failed), `all_metrics_dict["terminate_reason"]` (the first termination cause per env, sourced from `env.termination_manager`), and per-motion `obj_pos_error`/`obj_ori_error` (lines 386–409, 897–952), all persisted to disk via `save_metrics_eval()` → `metrics_eval.json`. Object attribution comes for free: motion keys are literal object-bearing strings (e.g. `canned_food_31_jason_rigged_001_indoor2-v4_rand00063_000065`, `motion_lib_base.py:534`), and one of the real termination terms is HOI-specific and per-object-triggerable - `object_pos_deviation` (`envs/manager_env/mdp/terminations.py:502`, Interaction-Early-Termination condition (i): object drifts >0.2m from reference). This is exactly the object-attributed failure signal the fold-back loop needs to know *which* `configs/objects/*.yaml` entry to correct - it already exists at the sim-eval layer. The caveat: this is IsaacLab-sim eval infrastructure, not real-hardware logging - Phase 4's real-G1 leg would still need its own failure classifier (the ROS2 deploy stack has an `error_monitor.hpp`/`file_sink.hpp` pair (`gear_sonic_deploy/src/g1/g1_deploy_onnx_ref/include/`) that could seed one, but object-pose-error attribution on real hardware, not just simulated `object.data.root_pos_w`, is new glue this project would still write).
  - **Step 4, warm-start retraining, is code-confirmed to do exactly what the doc claims - weights + optimizer state, not LR schedule/env-state/counters.** `ppo_trainer.py::load_checkpoint(..., warm_resume=True)` (lines 2183–2257) is explicit in its own docstring and code: `warm_resume` loads `actor_model_state_dict`/`value_state_dict` and `optimizer_state_dict`, and explicitly skips the LR scheduler, `env_state_dict`, and trainer counters "so training starts fresh ... without tripping HF's `DefaultFlowCallback.on_step_end` early-stop" (lines 2192–2196). Expanding the motion library between fold-back rounds is architecturally safe for this warm-start: `motion_lib_base.py` (lines 500–545) loads motions as a flat dict keyed by string, with `_num_unique_motions` simply `len()` of however many keys that round's config resolves - no `grep` hit for any `nn.Embedding` or other per-motion learnable parameter anywhere in `gear_sonic`, so a round-N policy checkpoint loads cleanly against a round-(N+1) motion library of a different size. The codebase already treats "object" as a first-class grouping independent of this project's needs - an `interleave_by_object` flag and `interleave_keys_by_object` helper (same file) exist for object-balanced motion sampling.
  - **Step 1, deployment, is a real, substantial stack, not a stub.** `gear_sonic_deploy/` is a full C++/ROS2 project (`CMakeLists.txt`, `.justfile`, a vendored `unitree_sdk2`) with a real ONNX/TensorRT inference path (`src/g1/g1_deploy_onnx_ref/include/ort_session.hpp`, `src/TRTInference/InferenceEngine.cpp`) and real G1 MJCF scenes (`g1/scene_29dof.xml`, `g1/g1_29dof_with_hand.xml`) - this is a genuine deployment target, not a placeholder that Phase 4 would need to build from nothing.
- **GRAIL reports real wall-clock/compute cost, unlike DDR in Project-2 which reports none.** 4D HOI generation: ~14 min/sequence on 1×A100 (breakdown: video gen ~1min, motion estimation ~2min, object tracking ~1min, optimization ~2min+8min). Policy training: 30,000 PPO iterations on 64×L40 GPUs (~30 hours), 2,000–4,000 motions per pool, amortized to ~0.5–0.9 min/motion; incremental fine-tuning on new motions converges in ~6,000 iterations (~6 hours, one-fifth cost). This removes "wall-clock unknown" as a risk - it's a known, cheap number, not an inference.
- **SONIC (the tracking-policy substrate GRAIL fine-tunes from) has code, checkpoints, and a deployment stack all released - confirmed directly from the repo's own download script and target HuggingFace repo, not just web search.** SONIC's own paper Declarations section states code is at `github.com/NVlabs/GR00T-WholeBodyControl` (confirmed, pushed 2026-08-13). That repo's `download_from_hf.py` pulls real weights from `nvidia/GEAR-SONIC` on HuggingFace (repo existence independently confirmed via the HF API): ONNX deployment weights (`model_encoder.onnx`/`model_decoder.onnx`), a PyTorch training checkpoint (`sonic_release/last.pt`), and named variants including `sonic_v1_1` and `low_latency` - so "SONIC v1.1" is a real, separately versioned, downloadable checkpoint, not a marketing label. This means this project has a code-verified substrate at *both* the data-generation layer (GRAIL) and the policy layer (SONIC) - a stronger reproducibility floor than [[Project-2_Terrain-Extended-Direct-Dynamic-Retargeting|Project-2]] had with MeshMimic.
- **SONIC is not superseded, confirmed by checking GRAIL's own vendored copy against the live upstream, not by inference.** GRAIL's `imports/SONIC` is a plain vendored snapshot (not a git submodule - `git ls-files` shows it as ordinary tracked files with no `.gitmodules` entry), last touched by a GRAIL commit dated 2026-08-11. The live `nvidia/GEAR-SONIC` HuggingFace repo (`lastModified: 2026-07-27`, checked via the HF API's sibling-file list) exposes exactly three checkpoint variants: `sonic_release/`, `sonic_v1_1/`, and `low_latency/` - no fourth or newer variant exists. GRAIL's own `download_from_hf.py` (dated after the HF repo's last update) deliberately targets `sonic_release/last.pt`, not `sonic_v1_1/` or `low_latency/`, despite both already existing at vendor time - a documented choice, not a gap. `NVlabs/GR00T-WholeBodyControl`'s GitHub history (commits as recent as 2026-08-13, two days after GRAIL's vendor snapshot; no tags/releases published) shows active development but nothing suggesting a checkpoint line beyond what's already on HF. There is no newer substrate to swap onto.
- **Four earlier search rounds found no better-evidenced loco-manipulation anchor and no paper that already closes this project's specific loop.** [[2606.30645|VLK]] ("Code coming soon" on its own project page) and [[2606.12995|GenHOI]] (no project page, no code found) were the closest alternatives; neither has code. A fourth round also checked candidates that looked promising by title alone against their full paper text: **ENPIRE** (2606.19980, a genuine real-world closed loop, but bimanual fixed-arm tabletop, no simulator reconstruction at all - wrong domain and wrong mechanism); **POT-VLA** (2607.18016, closes a loop on a real Unitree G1, but explicitly states it "does not assume a simulator, explicit physics engine, or learned dynamics model" - a perception/execution-verification loop, not real2sim2real); **RoboSeek** (2509.17783, calls itself "real2sim2real closed-loop" but on fixed-arm tabletop platforms, and its "closed-loop" is CEM/RL training within one simulation build - single-pass, not multi-round deploy-then-fold-back); **OASIS** (2606.08548, a genuine loco-manipulation paper on a real Unitree G1, but explicitly single-pass by the authors' own admission - "physics-aware trajectory augmentation is a natural next step" - and no code repository found anywhere in the fetched full text). None combine (a) loco-manipulation domain, (b) a real2sim2real reconstruction step, and (c) multi-round correction from deployment failures.
- **A fifth round cast the net on mechanism rather than the phrase "real2sim2real," and added a new axis no prior round applied: structural amenability to fold-back - does the candidate have a config-level or data-level re-entry point analogous to GRAIL's `configs/objects/*.yaml`.** Two `alphaXiv discover_papers` calls (`prioritize: recency` and `prioritize: default`, mechanism keywords: "4D HOI reconstruction," "digital generation pipeline," "whole-body tracking policy data engine," "real2sim2real closed-loop") returned ~15 candidates; all were already in `_KnowledgeHub_` (vault recency bias, per this session's own memory note on that blind spot), so absence-from-KH wasn't a usable filter here - each was read against its own full text instead. Four cleared the first bar (loco-manipulation domain or a genuine multi-round loop) and were checked to the code/mechanism level:
  - **RoboReact** (2608.03387, whole-body manipulation, JD Technology/CUHK-Shenzhen) - the closest *mechanism* analog found: a genuine 15-round loop where real robot calibration rollouts feed a VLM that proposes bounded, structured edits (`keep`/`align`/`offset`/`insert`/`delete`) to a frozen keyframe-skill representation, with a deterministic feasibility projection gating every edit - a config-like re-entry point in spirit. Dies on two independent axes: (1) domain - its four tasks (Hand Over, Pour Water, Open Box, Open Drawer) are stationary-base bimanual arm manipulation with a squat, no locomotion component, so it is not loco-manipulation; (2) code - its project page (`roboreact.github.io`, checked directly) has no code link, no "code coming soon," nothing.
  - **Humanoid-DART** (2606.26855, TUM MIRMI) - genuine loco-manipulation (push/kick/hand-off/pick-and-place on a real Unitree G1) with an iterative curriculum that most resembles GRAIL's own shape (motion generator ↔ tracking policy, alternating retraining). But the loop is **entirely simulation-internal**: goal-conditioned diffusion proposes trajectories, a sim-only physics-based tracker evaluates and relabels them, successes join an "elite archive," both components retrain - real G1 deployment is an end-of-pipeline validation, not a step the archive-growing loop ever reads from. The paper's own text states "we will open-source the codebase upon acceptance" - not yet released, confirmed via web search finding no repository.
  - **SUGAR** (2605.20373, Peking University) - genuine loco-manipulation with a real2sim mechanism close in shape to GRAIL's (here: real human video → automated kinematic-prior extraction → privileged-RL refiner in sim → hierarchical policy → real G1 deployment), and it **does have code** - `github.com/tianshuwu/SUGAR`, confirmed live (115 stars, pushed 2026-06-08). Checked the repo tree directly: it ships `sugar_rl` (refiner + tracker training) and `sugar_il` (command-generator training) with **per-task** config files (`CarryBox.yaml`, `PushBox.yaml`, etc.) - but no video-ingest/reconstruction code at all (the Stage-1 human-video-to-kinematic-prior extraction the paper describes isn't in the released tree). Two independent reasons it's not a better anchor: (1) mechanism - the pipeline is single-pass (video → refine → distill → deploy once); "autonomous failure recovery" in the paper is test-time in-episode behavior, not a training-data fold-back across rounds; (2) code completeness - unlike GRAIL, whose released code covers every pipeline stage end-to-end even though its *dataset* is partial, SUGAR's released *code* itself is missing the real2sim reconstruction stage, and its per-task (not per-object) config granularity gives no analog to GRAIL's per-object `configs/objects/*.yaml` re-entry point.
  - **CLAIMS** (2602.21599, Oxford/HKUST) - a genuine 6-round closed loop (VLM + physics-metric feedback drives a text-to-motion diffusion model, retrains a tracker each round), the closest thing to a fold-back loop with code-adjacent rigor found in this search. But it operates on pure locomotion/motion-synthesis (martial arts, dance, combat, sports, gymnastics) with no object interaction at all, and the loop's feedback is VLM/physics-metric judgment of *synthetic* motions, not a real deployment's actual failure - wrong domain and, on inspection, the same "no real2sim2real" gap as the four earlier-round rejects.
  - Two more were checked and dropped without a deep read: **Zero2Skill** (2607.14047) has a genuine multi-round real-world correction loop with a persistent "Corrective Memory," but it's fixed-arm tabletop manipulation with no simulator/reconstruction step at all - same shape as ENPIRE, already rejected on that basis. **FATE** (2603.01505, Tsinghua/BIGAI, not yet in KH) has an "active repair" loop that reads promising by title, but on full-text inspection it is sim-only LLM curriculum generation for a stationary RidgebackFranka arm - no humanoid, no locomotion, no real deployment; the paper's own Future Work section lists "incorporating real-world failure logs" as unbuilt.
  - **Net result: nothing found beats GRAIL on the conjunction this project needs.** GRAIL remains the only candidate with (a) loco-manipulation domain, (b) a real2sim2real reconstruction step, (c) a multi-round-capable fold-back re-entry point that's already config-level, and (d) a complete, runnable, end-to-end codebase (its dataset gap is real but narrower - three of four task families are released - than every alternative's code gap).
- **The theoretical grounding this project inherits is domain-agnostic, already established in this vault.** [[2605.21458|Fisher-SEP]]'s local/reachability bound (any passive fold-back loop's error splits into a component closed by more rounds and a component provably bounded away from zero) and [[2206.14661|ADR Benchmark]]'s documented SimOpt-under-noise drift apply to *any* passive fold-back loop, not specifically locomotion - both are reused here unmodified, per [[Project-3_Dynamics-Fold-Back-Loop-for-VideoMimic|Project-3]]'s own precedent for reuse rather than re-deriving.

## First-principles framing

- **First principle.** A single-shot data-generation pipeline's quality is a *fixed point in time*, not a converging process - however good its one-shot diversity/scale story is (GRAIL's 20,000+ sequences), it has no mechanism to improve from its own deployment's actual failure modes. This is exactly the assumption [[Project-2_Terrain-Extended-Direct-Dynamic-Retargeting|Project-2]] and [[Project-3_Dynamics-Fold-Back-Loop-for-VideoMimic|Project-3]] already broke for locomotion; nothing about loco-manipulation's underlying data-generation logic makes that argument locomotion-specific.
- **Assumption being challenged.** The field (GRAIL, Jun 2026, current-generation) treats "scale and diversify the one-shot generation" as the lever - more assets, more scenes, more object diversity - and stops there. GRAIL's own weakest reported number (80% unseen-object pick-up vs. 84% seen) is not treated as a target for iterative correction; the paper reports it as a limitation, not a loop input.
- **The bet.** Wrap GRAIL's own weakest measured axis - the seen→unseen generalization gap - in a gated multi-round fold-back loop (deploy → log failure segments → regenerate the failed cases with the observed failure as a new constraint → retrain → redeploy), gated the same way [[Project-2_Terrain-Extended-Direct-Dynamic-Retargeting|Project-2]]/[[Project-3_Dynamics-Fold-Back-Loop-for-VideoMimic|Project-3]] gate theirs. Specific numbers in [[#Falsifiable bets]].

## Proposed method: fold-back loop on GRAIL's pipeline

**Substrate stays unchanged:** GRAIL's reconstruction pipeline and SONIC's tracking-policy checkpoints, both used as released - no reimplementation needed to start.

1. Deploy the current policy (round 0: GRAIL's released checkpoint) on held-out unseen-object pick-up trials on the Unitree G1 (sim2sim first, real if hardware access materializes).
2. Log failure segments - which unseen-object geometries/contact configurations fail.
3. Fold failures back into generation: translate the observed failure into a corrected `configs/objects/*.yaml` entry for that object (scale/pose corrected from what the deployment failure revealed - this translation is the one piece of new glue logic this project writes) and re-run GRAIL's unmodified `gen_3d_assets.py` → `gen_2dhoi.py` → `recon_4dhoi.py` step1–4 pipeline on the resulting resynthesized video, so `depth_pointcloud`/`contact` (`grail/optimization/loss_computer.py`, Eq. 4–5's depth- and contact-alignment terms) are optimized against the corrected object's geometry - the real failure recording informs the YAML correction, it is not itself a pipeline input (Background has the exact call chain and the reasoning that ruled out feeding it in directly).
4. Retrain: fine-tune the SONIC-based tracker on the expanded data and redeploy.
5. Repeat for up to 3 rounds, gated on whether each round's correction actually reduced held-out failure rate - same fidelity-gate discipline as [[Project-2_Terrain-Extended-Direct-Dynamic-Retargeting|Project-2]]/[[Project-3_Dynamics-Fold-Back-Loop-for-VideoMimic|Project-3]], directly testing the same gated-vs-ungated drift question against [[2206.14661|ADR Benchmark]]'s precedent.

## Phase 0 - go/no-go gates (mandatory, before any full pipeline build)

**Gate 0 - bootstrap (low risk for the released subset; directional for the rest).** Reproduce GRAIL's pipeline via its released Docker image and SONIC's released checkpoints. Two separate reproduction targets, not one pipeline run (Background): (a) HOI-generation quality - replay GRAIL-generated 4D HOI sequences through InterMimic on SMPL-X capsule humanoids, targeting Table 1's **88.9%** physical-executability tracking success (20-object ComAsset set); the released pick-up/terrain/sitting data subset covers this. (b) G1 manipulation policy - targeting Table 2's **81.4%** manipulation SR on the separate 124-motion/43-object benchmark; the manipulation-specific dataset needed for a released-artifact reproduction is not yet public (repo's own TODO), so this half is a directional pipeline-regenerated check, not an exact-artifact reproduction. Decision rule: (a) should reproduce within tolerance from released data alone - failure here means the environment, not the mechanism, is broken; stop and resolve before any loop work. (b) failing to move in the right direction after pipeline-regenerated data is the same stop signal, but exact-match is not expected the way (a)'s is.

**Gate A - failure-mode feasibility.** Before building the loop: confirm the pipeline can actually produce failure cases worth folding back - does GRAIL's own 80% unseen-object number correspond to identifiable, reproducible failure geometries, not just noise? A fold-back loop only helps if failures are systematic, not random - this gate checks that precondition directly, informed by [[2605.21458|Fisher-SEP]]'s reachability argument (systematic failures are exactly what passive fold-back *can* close; random noise it cannot).

## Phase 1 - implement and unit-verify

- Build the fold-back wrapper around GRAIL's asset-generation stage (Proposed method step 3), regression-tested against Gate 0's reproduced baseline with zero fold-back data (should reproduce GRAIL's own numbers bit-comparably).

## Phase 2 - single-shot baseline (no loop yet)

- Reproduce GRAIL's own 10-trials-per-object pick-up protocol on a wider object set - **≥20 unseen objects (≥200 trials)**, not Table 3's 5 (n=50), sized so Bet 1's claimed 80%→90% move is actually detectable: a two-proportion test at n=50 per arm gives z≈1.4 for that effect size (underpowered, below the z≈1.96 needed at α=0.05), while n≈200 per arm gives ~80% power to detect it. Table 3's 5 seen + 5 unseen objects is solid-N *per object*, but Bet 1 is a claim about the aggregate seen/unseen gap, which needs object-count, not just per-object trial-count. Using GRAIL's own released checkpoint, unmodified, this is the floor Bet 1 measures against. Separately, run a small pilot to establish an actual N for stair-climbing (unstated in the paper) before trusting the 90% figure as a fold-back baseline.

## Phase 3 - closed fold-back loop, gated vs. ungated

- Run the 3-round fold-back procedure (Proposed method, steps 3–5) both with and without the fidelity gate, reporting failure-rate trajectory per round - directly replicating [[2206.14661|ADR Benchmark]]'s drift-check pattern, same as Project-2/3's Gate C.

## Phase 4 - sim-to-real (conditional, not assumed)

- Real Unitree G1 access not assumed at scoping time - if available, larger-N replication of GRAIL's own protocol.
- If unavailable, report sim-only results (Isaac-Lab-internal held-out sim), with that caveat explicit in every result, same discipline as Project-2/3's Phase 4.

## Falsifiable bets

**Bet 1 is the load-bearing stop-condition.**

1. **Closed-loop win on the generalization gap (load-bearing).** GRAIL's unseen-object pick-up success rate rises from **80%→≥90%** within **3** fold-back rounds, measured on Phase 2's ≥20-object (≥200-trial) replication of Table 3's 10-trials-per-object protocol - sized for ~80% power to detect this specific effect size, not just solid-N per individual object. **If this fails, the thesis is wrong.**
2. **Gated beats ungated (directional, precondition for Bet 1 to mean "the loop matters," not just "more data helps").** The gated 3-round loop should show a non-increasing failure-rate trajectory where the ungated variant shows at least one round of increase - replicating [[2206.14661|ADR Benchmark]]'s pattern, same test as Project-2/3's Gate C.
3. **No regression on GRAIL's already-strong numbers.** Seen-object pick-up (84%) and stair-climbing (90%) should not regress as a side effect of the fold-back wrapper.

---

> [!warning] Risks
> - **Thin evidence on one specific number.** GRAIL's pick-up numbers are solid (100 trials, verified against the paper); its 90% stair-climbing figure has no stated N.
> - **Gate 0 is only fully reproducible from released artifacts for half its target.** The pick-up/stair-climbing numbers (Table 3, 90% stair/84–80% pick-up) are covered by the released HuggingFace data subset; the 81.4% manipulation-SR target (Table 2, 124-motion/43-object benchmark) is not - the repo's own TODO still marks the manipulation dataset unreleased, so that half of Gate 0 is a directional pipeline-regeneration check, not an exact-artifact reproduction.
> - **Fold-back may not have a systematic failure mode to exploit.** Gate A exists precisely because - unlike Project-2/3, where the failure modes (contact infeasibility, dynamics mismatch) are physically well-characterized - loco-manip's "unseen object" failure mode may be too heterogeneous for a handful of fold-back rounds to systematically close, per [[2605.21458|Fisher-SEP]]'s reachability argument generalized to a higher-dimensional failure space than locomotion's.
> - **Hardware risk.** Phase 4 is explicitly conditional - real-result claims must never silently read as achieved without that caveat, same discipline as every project in this vault.
> - **Phase 2's power-adequate object set (≥20 objects) exceeds what GRAIL's released data covers.** The released pick-up subset's own seen/unseen split is 5+5; sourcing ≥15 more unseen objects with usable meshes/scans is new asset-collection work this project would need to scope, not something the released artifacts hand over.
> - **Step 2's failure-attribution mechanism is proven only in sim.** `ImEvalCallback`'s per-object logging (Background) runs inside IsaacLab eval; Phase 4's real-G1 leg needs an analogous real-hardware failure classifier built from `gear_sonic_deploy`'s `error_monitor.hpp`/logging primitives - a real but smaller build-out than the doc previously implied might be needed for the whole step.

## Deferred - mobile-manipulation axis

Investigated in depth this session, then descoped (see Killed, Option B) so this project stays single-mechanism, matching Project-2/3's discipline. Kept here rather than deleted.

- **Anchor candidate:** [[2606.18646|BestMan]] (Chongqing University) - code released (`github.com/AutonoBot-Lab/BestMan`), but the repo is frozen at an older base-platform release (last commit 2025-06-27, a year before this paper's own Automated Scene Generation/THMM/HUM contributions were published; default branch literally named `0.3.0`). Confirmed via the repo's own arxiv badge and self-citation to the earlier short paper (2410.13407), and its README TODO ("Release the baseline models and benchmark modules," unchecked) - not just an inference.
- **Code-level seam, read from the actual repo (`data/repositories/BestMan`, submodules initialized):** `DigitalTwin/__init__.py` is a literal two-line seam. It already vendors **ACDC** (arxiv 2410.07408, a same-task real2sim pipeline) with ready wrappers for 4 of ASG's 5 named foundation models (GPT-4o, Grounded-SAM, Depth-Anything-v2, DINOv2, plus CLIP) - porting ASG is closer to adapting an already-running same-task pipeline than building from scratch; only ACDC's OmniGibson-targeted Step 3 needs reimplementing against `Env/Client.py::load_object()` (PyBullet). Conversely, the THMM/CSE strategy layer is **confirmed absent** - `Motion_Planning/`/`Task_Planning/` hold only classical planners, no Sense-Plan-Act scaffold; the only real hook is a bare joint-waypoint loop in `Robotics_API/Bestman_sim.py::sim_execute_trajectory()`.
- **Mechanism reference:** [[2607.13154|WANDA]] (CMU/LeCAR Lab) - no code ("Code (coming soon)"), but its Corrective State Expansion ablation (54.8%→15.7% without it) is the strongest published evidence that a specific long-horizon-robustness mechanism, not just data volume, matters. Would have been grafted onto BestMan's substrate the same way Project-2 grafts MeshMimic's equations onto VideoMimic.
- **BestMan's own numbers (Table 2/3/5):** ASG reconstruction accuracy 100% category/up to 94% modeling/90% joint (sim); beats URDFormer (90% vs 88%) and ACDC (90% vs 78%) on joint accuracy; THMM OSR 66.2% sim (F-R-R-R) / 52.2% real (F-R-F-R best strategy).
- **If revisited:** the two-track structure, a bootstrap gate with the same ASG-lower-risk/THMM-CSE-higher-risk split this doc's own Gate 0 uses for GRAIL's two reproduction targets, and the falsifiable bet (BestMan+ASG+CSE real OSR 52.2%→≥65% in 3 rounds) are the shape a future Project-5 would take. No new search needed first - four rounds this session (Background) already confirmed BestMan/WANDA are the best-evidenced pair for this axis.
